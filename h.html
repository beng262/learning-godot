Hierarchies of code: classes

A script is a class: extends, class_name, inner classes, _init, inheritance, super – and when to compose instead.

In this chapter

  • what you have been writing since Chapter A: every script is a class, and every node with a script is an object made from it
  • _init, the function that runs when an object is made
  • extends: building one class on another, replacing a function, and calling the original with super
  • three ways to name and reach a class: class_name, inner classes, and static functions that need no object at all
  • the question to ask before you write extends: is it one, or does it have one?

A script is a class

A class is a description of a kind of thing: the variables it keeps and the functions it can run. An object is one thing made from that description. You have written a class in every chapter so far, because in Godot a script file is one.

Think of the script you attach to a coin. It has a variable for its value and a function for being picked up. Put twenty coins in a level and there are twenty objects, also called instances, of that one class. They share the functions. Each has its own copy of the variables, so one coin can be worth 5 while its neighbour is worth 1.

The book's examples are one script each, so to have a second class to play with we write it inside the script, with the keyword class. Everything indented under class Plot: is what a file called plot.gd would hold.

extends Node

class Plot:
	var crop := ""
	var watered := false

	func describe() -> String:
		if crop == "":
			return "bare earth"
		return crop + (" (watered)" if watered else " (dry)")

func _ready() -> void:
	var a := Plot.new()
	var b := Plot.new()
	a.crop = "carrot"
	a.watered = true
	b.crop = "tomato"
	print(a.describe())
	print(b.describe())
	print(Plot.new().describe())

Plot.new() makes an object. The dot reaches into it: a.crop is a's crop, a.describe() runs the function for a. Inside describe() the bare name crop means "the crop of whichever object I was called on", which is why the same three lines give three different answers. Water plot b and run it again.

In Chapter G a plot was a dictionary. A class is the other way to bundle facts together, and it buys you three things: the fields have names the editor can check and complete, they can have types, and the functions that work on them travel with them. A dictionary is still the better choice for anything that has to be saved to a file, which is why the game's state is one. An object is the better choice for anything that does something.

Objects are shared, as arrays are

Assigning an object to a second variable does not copy it. Both names refer to the one object, exactly as two names referred to one array in Chapter G.

extends Node

class Plot:
	var crop := ""

func _ready() -> void:
	var a := Plot.new()
	var b := a              # not a second plot: a second name
	b.crop = "pumpkin"
	print(a.crop)

	var c := Plot.new()     # this is a second plot
	print(c.crop == "")

_init: starting an object off

An object straight out of new() has whatever its variables were declared with. Usually you want to say what it is at the moment you make it, and _init is where that happens.

If a class has a function called _init, Godot runs it as part of new(), and whatever you put in the brackets of new(…) arrives as its arguments. It is often called the constructor.

extends Node

class Crop:
	var title: String
	var grow: float

	func _init(crop_title: String, grow_seconds: float = 20.0) -> void:
		title = crop_title
		grow = grow_seconds

	func label() -> String:
		return "%s, ripe in %s seconds" % [title, grow]

func _ready() -> void:
	var carrot := Crop.new("Carrot", 15.0)
	var mystery := Crop.new("Mystery seed")
	print(carrot.label())
	print(mystery.label())

Parameters of _init follow the rules of any function (Chapter F): the second has a default, so Crop.new("Mystery seed") is allowed. The first does not, so a crop cannot be made without a name. Try it: change the last new to Crop.new() and read the error. That refusal is the point of a constructor. There is no moment at which a half-made crop exists for other code to trip over.

_init and nodes

A script on a node may have an _init too, and it runs when the node object is created, before the node is anywhere in the tree. Two things follow. Most setup for a node belongs in _ready(), when its children exist; Chapter I is about that order. And a node that Godot creates for you from a scene is made with no arguments, so a script you attach in the editor cannot have an _init with required parameters.

In Little Hours

The game builds its nodes in code, with new(), so it is free to give them constructors with arguments.

Who cleans up

A class that does not say what it extends, like Crop above, extends RefCounted. Godot counts the references to each such object and frees it when the last one goes: when the variable holding it goes out of scope, or the array it was in is cleared. You make them and forget them. Nodes are not counted. A node lives until it is freed, by queue_free() or along with its parent, which Chapter C covered.

extends: building on another class

The first line of every script you have written says extends something. It means: start with everything that class has, and add to it. You can do the same with classes of your own.

extends Node

class Animal:
	func sound() -> String:
		return "..."

	func speak() -> String:
		return "It says " + sound()

class Dog extends Animal:
	func sound() -> String:
		return "Woof"

class Puppy extends Dog:
	func sound() -> String:
		return super.sound() + "! " + super.sound() + "!"

func _ready() -> void:
	for creature in [Animal.new(), Dog.new(), Puppy.new()]:
		print(creature.speak())

	var d := Dog.new()
	print(d is Dog, " ", d is Animal, " ", d is Puppy)

Four ideas are in those twenty lines.

  1. Inheriting. Dog never mentions speak(), and has it anyway, from Animal. The class you extend is the parent or base class; the one that extends is the child, or subclass.
  2. Overriding. Dog defines sound() again, and for dogs its version replaces the parent's.
  3. The object decides. speak() was written once, in Animal, and calls sound(). Called on a dog, it reaches the dog's sound(). Which function runs depends on what the object is, not on where the calling code was written. This is what makes a parent class useful: it can lay out the steps and leave one of them to its children.
  4. super. Inside a child, super means "the class I extend". super.sound() runs the parent's version, so Puppy can build on Dog's answer without repeating it.

The last line prints true true false. is asks whether an object is of a class or of any class built on it: every dog is an animal, not every dog is a puppy. Change Puppy's parent to Animal and predict the third line of output before it appears.

_init up the chain

When the parent's _init takes arguments, the child's _init hands them up with super(…), then does its own setting up.

extends Node

class Animal:
	var title: String

	func _init(t: String) -> void:
		title = t

class Cat extends Animal:
	var naps: int

	func _init(t: String, nap_count: int) -> void:
		super(t)
		naps = nap_count

func _ready() -> void:
	var mog := Cat.new("Mog", 3)
	print(mog.title, " has had ", mog.naps, " naps")

Cat does not set title itself. It passes the name to the class that owns that variable and knows what to do with it.

You have been inheriting all along

Godot's own classes are a family tree of exactly this kind. A Sprite2D is a Node2D, which is a CanvasItem, which is a Node, which is an Object:

ClassWhat it adds to its parent
ObjectThe root of everything: signals, connect(), being a thing a script can be attached to.
NodeA name, a parent and children, a place in the tree, _ready() and _process().
CanvasItemBeing drawn in 2D: visible, modulate, _draw().
Node2DA place in the 2D world: position, rotation, scale.
Sprite2DA texture to show there.

So extends Node2D at the top of a script is the same statement as class Dog extends Animal: your class starts with everything a Node2D has, which is why position works without your declaring it. And writing func _ready() is overriding: Node has a _ready() that does nothing, and yours takes its place. It also explains a rule you may have met in the editor. A script can only be attached to a node of the class it extends, or one built on it: a script that extends Node2D fits a Sprite2D, and not a Label.

Names: class_name, inner classes and statics

A class in its own file has no name until you give it one. How you name a class decides who can reach it, and some of what is in a class can be reached without making an object at all.

class_name

Put class_name at the top of a script and the class has a name the whole project knows:

# crop.gd
class_name Crop
extends RefCounted

var title := ""
var grow := 20.0
# any other script in the project
var seed_packet: Crop = Crop.new()

func is_crop(thing) -> bool:
	return thing is Crop

With it you can write Crop.new(), use Crop as a type, and test is Crop from any script, with nothing to load first. If the class extends a node type, it also appears in the Add Child Node window beside Godot's own. Without a class_name a script is still a class; you reach it by loading the file, const CropScript := preload("res://crop.gd"), and calling CropScript.new() (Chapter V has more on preload).

In Little Hours

Nearly every script in the game begins with a class_name: Player, Pet, RoomView, HUD. One place reaches a named class the long way round all the same, and its comment records the practical catch with global names:

Player.gd · lines 12–16

## Preloaded rather than named: the global class list is built by an editor
## scan, so a script added since the last one is not a name the parser knows —
## and a parse error in a file the game preloads does not report as an error, it
## reports as the game never starting.
const DRAWN := preload("res://scripts/DrawnAvatar.gd")

The list of class names is built when the editor scans the project. A preload names the file itself, so it works however the script arrived.

Inner classes

The class Plot: blocks in this chapter are inner classes: classes written inside another script. In a real project they are for a small class that only one file uses, where a separate file would be more ceremony than the class deserves. From inside its script you use the bare name, Plot.new(). From another script you go through the outer class: the game's phone is made with Widgets.Phone.new(), an inner class Phone in the script named Widgets.

An inner class is a class of its own in every respect. In particular it cannot see the variables of the script it sits in; if it needs something from outside, it has to be handed it.

static: belonging to the class, not to an object

An ordinary function runs on an object and can use that object's variables. A static func belongs to the class itself. You call it on the class name, and there need not be any object at all:

extends Node

class Catalog:
	const PRICES := {"carrot": 18, "tomato": 18, "pumpkin": 26}

	static func price_of(key: String) -> int:
		return PRICES.get(key, 0)

	static func dearest() -> String:
		var best := ""
		for key in PRICES:
			if best == "" or PRICES[key] > PRICES[best]:
				best = key
		return best

func _ready() -> void:
	print(Catalog.price_of("pumpkin"))
	print(Catalog.price_of("koi"))
	print(Catalog.dearest())

Nobody wrote Catalog.new(). A class like this is a named shelf for constants and the functions that read them, and you will meet whole files of it in the game. The price of having no object is that a static function has no object's variables to use. Calling an ordinary function the static way is an error for the same reason, seen from the other side:

extends Node

class Crop:
	var title := "Carrot"

	func label() -> String:
		return title

func _ready() -> void:
	print(Crop.label())

Which crop's title? There is no crop, only the class. Make one first, Crop.new().label(), and it runs.

Variables can be static too. A static var is one value kept by the class and shared by every object of it:

extends Node

class Ticket:
	static var issued := 0
	var number: int

	func _init() -> void:
		issued += 1
		number = issued

func _ready() -> void:
	var a := Ticket.new()
	var b := Ticket.new()
	var c := Ticket.new()
	print(a.number, " ", b.number, " ", c.number)
	print(Ticket.issued, " issued")

number is each ticket's own; issued is the one counter they all add to. Use static variables sparingly. A value that anything can change from anywhere is hard to reason about, and Chapter U has more to say on that.

Is it one, or does it have one?

Inheritance is the first tool people reach for once they know it, and it is the right one less often than it looks. The alternative is older and plainer: an object that keeps another object in a variable and asks it to do part of the work.

extends says is a kind of. A Sprite2D is a kind of Node2D; a puppy is a kind of dog. When that sentence is true and will stay true, inheritance is a good fit.

Now take the people in a town. They differ in who steers them: the player's taps, a partner who follows, a neighbour who potters about a shop. They also differ in how they are drawn: as a paper doll in layers, or from a drawing of your own. With inheritance alone you need a class for every pairing, and a class can extend only one parent, so you must decide which difference is "the real one" and copy code for the other. Worse, an object can never change its class. A character who puts on a different look would have to be destroyed and made again.

The other way is to notice that a walker has a look, and give it one:

extends Node

class PaperDoll:
	func show(dir: String) -> String:
		return "paper doll facing " + dir

class Sketch:
	func show(dir: String) -> String:
		return "pencil sketch facing " + dir

class Walker:
	var title: String
	var look            # a PaperDoll or a Sketch: anything with show()

	func _init(t: String, l) -> void:
		title = t
		look = l

	func walk(dir: String) -> String:
		return title + ": " + look.show(dir)

func _ready() -> void:
	var you := Walker.new("You", Sketch.new())
	var partner := Walker.new("Partner", PaperDoll.new())
	print(you.walk("left"))
	print(partner.walk("down"))

	you.look = PaperDoll.new()      # a change of look, and still the same walker
	print(you.walk("left"))

This is composition. Walker extends neither look; it holds one and passes the drawing on to it. Two walkers and two looks give four combinations from three classes, and a fifth look is one new class that nothing else has to hear about.

Notice too that PaperDoll and Sketch have no parent in common. They only both happen to have a show() function, and GDScript looks a function up by name at the moment of the call. Give you.look something without a show(), the number 5 say, and the error arrives at walk(), when the function is asked for and not found.

You already compose every day in Godot: a scene is a node that has child nodes, each doing one job (Chapter A). A sound is not something a player class inherits. It is an AudioStreamPlayer the player has as a child.

Reach forWhen
extends an engine classAlways: every script does. It is how your node gets to be a node.
extends a class of your ownSeveral classes are truly the same kind of thing, share most of their code, and differ in a few functions.
a variable or child node holding another objectThe part could be swapped, shared between unrelated things, or absent.

In Little Hours

The game's 42 scripts are 42 classes and several dozen inner ones. Read their first lines and a pattern shows: nearly all of them extend a class of Godot's, almost none extends another class of the game, and the parts are put together by one object holding another.

An inner class that is a node

Rain and snow are drawn by a class that lives at the bottom of Main.gd. It begins:

	var kind := "Clear"

Classes nobody makes an object of

The townspeople, the rooms, the letters and the phone are data, and each has a script that holds the tables and the questions you can ask of them. NeighborData.gd starts with class_name NeighborData and extends RefCounted, and its functions are all like these two:

NeighborData.gd · lines 816–821

## Their name, or the id itself if there is no such person. Used wherever an id
## has to be shown to the player — the phone, mostly — so that a missing person
## reads as a bug rather than as a blank.
static func name_of(id: String) -> String:
	var p := by_id(id)
	return str(p["name"]) if not p.is_empty() else id

NeighborData.gd · lines 823–827

static func by_id(id: String) -> Dictionary:
	for p in PEOPLE:
		if str((p as Dictionary)["id"]) == id:
			return p
	return {}

Both are static, so the rest of the game writes NeighborData.name_of(id) and never NeighborData.new(). The class is a name for a shelf: PEOPLE, which by_id() walks, is a static var on the same class. RoomData.gd is built the same way, and so is the Catalog you ran above. by_id() returns an empty dictionary for someone who does not exist, and name_of() turns that into the id itself, so that a missing person shows up on the phone as an obvious bug and not as a blank. Neighbours uses these; NeighborData and RoomData are in the tour.

The one family tree

The Arcade TV has two longer games on cartridges, in Carts.gd. They are the same kind of thing: each is a Control that reads fingers on drawn buttons, turns rows of letters into pixel pictures and plays short tunes. So that part is written once, in a parent class, whose setting up is this:

void:" data-nth="1" data-to="Sfx.warm_notes(57, 89)">

That is CartBase, declared as class CartBase extends Control:. The two games are class LampRun extends CartBase: and class TideBell extends CartBase:, and the first of them starts itself like this:

void:" data-nth="2" data-to="restart()">

LampRun's _ready() replaces CartBase's, as an override does. Its first line calls the original with super._ready(), so the shared setting up still happens, and then it does its own. Everywhere else in LampRun, functions such as held() and tapped() are called as if they were its own, because through extends they are. This is inheritance used where it fits: two classes that share most of what they are. Quiet games has the games themselves.

The player has a look

The resident can be drawn two ways: as Avatar, a paper doll in five layers, or as DrawnAvatar, the character you draw at the start. Player is neither. It keeps one of them in a variable:

Player.gd · lines 83–89

## Either kind of character: the LimeZu paper doll, or the one the user drew.
##
## Typed loosely on purpose. The two share the whole of the small interface this
## file uses — apply, moving, face_along, position — and nothing here wants to
## know which it has. Only the resident swaps; the neighbours stay paper dolls
## until there is drawn art for them too.
var _avatar: Node2D

Player.gd · lines 100–109

func _rebuild_avatar() -> void:
	if _avatar != null and is_instance_valid(_avatar):
		remove_child(_avatar)
		_avatar.queue_free()
	if _drawn():
		_avatar = DRAWN.new()
	else:
		_avatar = Avatar.new()
	add_child(_avatar)
	refresh_look()

This is the Walker and its look, with nodes. Player does the walking: the route, the speed, what it bumps into. Whichever avatar it holds does the drawing, as a child node. Avatar and DrawnAvatar do not extend one another, and both simply have the few things Player asks for, which is why the variable is typed as the plain Node2D they both are. When you change the setting, _rebuild_avatar() frees the old look and makes the other kind, and the player who owns it carries on from where they stood. Had Player been written as extends Avatar, that swap would mean destroying the player. The townspeople in Neighbor.gd hold an avatar in the same way.

The walking itself is in Reaching, and the three scripts are in the tour: Player, Avatar, DrawnAvatar.

What to remember

  • A script is a class; a node with that script, or anything made with new(), is an object of it. Objects share the functions and each has its own variables.
  • _init runs inside new() and receives its arguments. Use it so an object cannot exist half-made.
  • extends gives a class everything its parent has. A function with the same name replaces the parent's, super.name() calls the one it replaced, and super(…) in _init passes arguments up.
  • class_name makes a class known to the whole project; an inner class is for a small one that a single file uses; static functions and variables belong to the class and need no object.
  • Objects are shared by reference, as arrays and dictionaries are.
  • Before extends, ask "is it one, or does it have one?". Extend Godot's classes freely and your own rarely; compose the rest by holding an object in a variable or a child node.
