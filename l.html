Laying out the 2D world

Node2D, position and global_position, rotation, scale, draw order, y-sorting and the camera.

In this chapter

  • where a Node2D is: position, global_position, and why a child's numbers are measured from its parent
  • turning and stretching: rotation in radians, rotation_degrees, scale
  • arithmetic with Vector2: length, direction, distance and lerp – and why y points down
  • who is drawn in front: tree order, z_index and y-sorting
  • the camera – limits, zoom, smoothing – and CanvasLayer for the interface that must not move with it

Where a thing is

Everything that lives in a 2D world is a Node2D or something built on one, and a Node2D is, before anything else, a place. Laying out a world is deciding those places – and knowing what each one is measured from.

Sprite2D, Camera2D, CharacterBody2D, Area2D and Marker2D all extend Node2D, so they all have the three properties it adds: position, rotation and scale. Together those are the node's transform, and in the editor they sit at the top of the Inspector under Transform. (Buttons and labels are Control nodes and are placed another way; that is Chapter R.)

A position is a Vector2 (Chapter D): an x and a y, in pixels. The origin, (0, 0), is the top-left corner. x grows to the right, as you would expect. y grows downwards, which you might not: it is how screens have always counted rows, and it is the opposite of the graphs you drew at school.

extends Node

func _ready() -> void:
	var pos := Vector2(100, 100)
	print("start:      ", pos)
	pos += Vector2.UP * 30
	print("30 px up:   ", pos)
	print("UP is ", Vector2.UP, " and DOWN is ", Vector2.DOWN)

Going up the screen made y smaller. Vector2.UP is (0, -1) so that you never have to remember the sign yourself. Change UP to RIGHT, then to DOWN, and read the second line each time.

Parents, and local space

Here is the idea the rest of the chapter leans on. A node's position is not where it is on the screen. It is where it is measured from its parent. A hat that is a child of a character has a position like (0, -24): twenty-four pixels above the character, wherever the character happens to be. That private set of axes, with the parent at (0, 0), is the child's local space.

Where the hat ends up in the world is its global_position. For a parent that is neither turned nor stretched, that is one addition:

extends Node

func _ready() -> void:
	var character := Vector2(200, 120)   # the parent's position
	var hat := Vector2(0, -24)           # the child's position: local
	print("hat in the world: ", character + hat)

	character.x += 50                    # move ONLY the parent
	print("hat in the world: ", character + hat)
	print("hat's own position is still ", hat)

This is why the tree in Chapter C matters so much. You move one node – the character – and the hat, the shadow, the name tag and the camera under it all come along, because none of their own numbers changed. Make the hat sit lower by changing its -24 to -10, and notice that you did not have to know where the character was.

In Godot both numbers are properties, and you may read or set either one. Setting global_position makes Godot work out the local position that would put the node there:

func _ready() -> void:
	print($Hat.position)          # (0.0, -24.0)   measured from the parent
	print($Hat.global_position)   # (200.0, 96.0)  measured from the world's corner

	$Hat.global_position = Vector2(10, 10)   # "be HERE in the world, whoever my parent is"

	# The same conversion for any point, not only the node's own:
	var p := to_local(Vector2(200, 96))      # a world point, seen from this node
	var q := to_global(Vector2(0, -24))      # one of this node's points, in the world

The trap: position when you meant global_position

Two nodes with different parents cannot compare positions – the numbers are measured from different places. The classic bug is a bullet: it is added to the level, not to the gun, so bullet.position = $Muzzle.position puts it a few pixels from the level's corner. The line you want is bullet.global_position = $Muzzle.global_position. Whenever two things that are not siblings need to meet, use the global one.

Turning and stretching

The other two parts of the transform. Both are short to say and both have one surprise in them.

rotation is in radians

rotation is an angle, and code measures angles in radians: a full turn is TAU (about 6.283), a half turn is PI, a quarter turn is PI / 2. The Inspector shows degrees because people prefer them, and there is a second property, rotation_degrees, that is the same angle read through a converter. Set either and the other follows.

The surprise is the direction. Zero points along +x, to the right, and because y is down, a positive rotation turns clockwise.

extends Node

func _ready() -> void:
	print(deg_to_rad(90.0))                    # a quarter turn, in radians
	print(rad_to_deg(PI))                      # a half turn, in degrees
	print(rad_to_deg(Vector2.RIGHT.angle()))   # the angle of "pointing right"
	print(rad_to_deg(Vector2.DOWN.angle()))    # ...and of "pointing down"
	print(rad_to_deg(Vector2.UP.angle()))

Down is +90° and up is −90°: a quarter turn clockwise from "right" lands on "down". angle() gives the angle of any vector, so (target - position).angle() is the rotation that faces a target. Try Vector2(1, 1).angle() in the third line before you run it – which way is that, on a screen?

In a script you will mostly do one of three things with it:

func _process(delta: float) -> void:
	rotation += TAU / 4 * delta                # <1>
	rotation_degrees = 45                      # <2>
	look_at(get_global_mouse_position())       # <3>
  1. Spin steadily: a quarter turn every second, whatever the frame rate, because of delta (Chapter I).
  2. Set an angle outright, in whichever unit reads better at that spot.
  3. look_at() turns the node so that its own +x axis points at a place in the world. This is why sprites meant to be aimed are drawn facing right.

scale is a multiplier

scale is a Vector2 too: (1, 1) is the size things were drawn at, (2, 2) is twice as big, (0.5, 0.5) half. The two numbers are separate, so (2, 1) stretches sideways, and a negative one mirrors: scale.x = -1 is the oldest way to make a character face left. (Sprite2D also has flip_h, which mirrors the picture without touching the node's children.)

Like position, both of these are inherited. Turn a parent and its children swing round it; scale a parent by 2 and its children are twice as big and twice as far from it. Try it – the blue square is the parent, the pink one its child:

Slide the parent's rotation and watch the readout: the child's position never changes, only its global_position. That one sentence is local space. Godot applies the parent's transform in a fixed order – scale, then turn, then move – and you can do the same sum by hand:

extends Node

## Where a child ends up, given its parent's transform.
func global_of(parent_pos: Vector2, parent_rot: float, parent_scale: float, local: Vector2) -> Vector2:
	return parent_pos + (local * parent_scale).rotated(parent_rot)

func _ready() -> void:
	var hat := Vector2(50, 0)
	print(global_of(Vector2(110, 100), 0.0, 1.0, hat))
	print(global_of(Vector2(110, 100), 0.0, 2.0, hat))                   # parent twice the size
	print(global_of(Vector2(110, 100), deg_to_rad(90), 1.0, hat).round()) # parent a quarter turn round

The last line ends in .round() because sines and cosines leave crumbs like 0.000001 behind. Set the demo's sliders to the same numbers – parent at (110, 100), child at (50, 0) – and check each line against its readout.

Put the scale on the picture, not on the body

Because scale is inherited, scaling the node everything hangs from scales everything: the collision shape, the camera, the distance to the hat. Scale the Sprite2D at the end of the branch instead and leave its parents at (1, 1). For pixel art, keep the scale a whole number, or the pixels come out in uneven sizes – Chapter P is about exactly that.

Arithmetic with Vector2

A Vector2 is two numbers that travel together, and it is used for two different things: a place, and an arrow from one place to another. Almost all movement code is a handful of operations on arrows.

Subtracting two places gives the arrow between them: to - from. Everything else is a question you ask that arrow – how long is it, which way does it point?

extends Node

func _ready() -> void:
	var you := Vector2(40, 60)
	var door := Vector2(100, 140)

	var arrow := door - you
	print("the arrow:      ", arrow)
	print("its length:     ", arrow.length())
	print("distance_to:    ", you.distance_to(door))
	print("normalized:     ", arrow.normalized())
	print("direction_to:   ", you.direction_to(door))

distance_to() is "subtract, then take the length" in one call, and direction_to() is "subtract, then normalise". Move the door to (40, 160), straight below you, and predict all five lines before they appear.

normalized: a direction with the distance taken out

normalized() keeps where an arrow points and makes it exactly 1 long. That is what you multiply a speed by: direction * speed is a velocity, in pixels a second, and position += velocity * delta is a frame of movement.

It matters most with the arrow keys. Hold right and down together and the obvious code builds the vector (1, 1) – which is not 1 long:

extends Node

const SPEED := 100.0

func _ready() -> void:
	var straight := Vector2(1, 0)
	var diagonal := Vector2(1, 1)
	print("straight: ", (straight * SPEED).length(), " px a second")
	print("diagonal: ", (diagonal * SPEED).length(), " px a second")
	print("fixed:    ", (diagonal.normalized() * SPEED).length(), " px a second")

Forty-one per cent faster on the diagonal: every top-down game has had this bug once. Input.get_vector() (Chapter K) hands you a vector that is already no longer than 1, which is one reason to prefer it. And Vector2.ZERO.normalized() is Vector2.ZERO, so normalising "no keys held" is safe.

lerp: part of the way there

a.lerp(b, t) is the point a share t of the way from a to b: 0 gives a, 1 gives b, 0.5 the midpoint. Used once it places something between two others. Used every frame, on its own result, it makes a thing glide: each frame it closes the same share of whatever gap is left, so it starts fast and settles gently.

extends Node

func _ready() -> void:
	var a := Vector2(0, 0)
	var b := Vector2(200, 100)
	print(a.lerp(b, 0.25), " ", a.lerp(b, 0.5), " ", a.lerp(b, 1.0))

	# Gliding: a fifth of the remaining gap, eight frames running.
	var cam := Vector2(0, 0)
	for frame in 8:
		cam = cam.lerp(b, 0.2)
		print("frame ", frame + 1, ": ", cam.round())

Look at the steps: 40 pixels, then 32, then 26. Change 0.2 to 0.5 for a snappier glide, or to 1.0 for no glide at all. You will build a camera out of this line in a few minutes.

Who is drawn in front

Two sprites overlap. One of them has to be painted second, and whichever that is looks nearer. Godot decides with three rules, each one overriding the one before.

1. Tree order

With nothing else said, nodes are painted in the order they appear in the Scene dock, top to bottom: a parent first, then its children, then the next sibling. Later paint covers earlier paint, so the node at the bottom of the dock ends up in front. To put a background behind everything, make it the first child.

2. z_index

Every 2D node has a z_index (in the Inspector under Ordering), a whole number that starts at 0. Higher numbers are painted later, and that beats tree order. It is the tool for "always on top": rain at z_index = 100, a rug at -1. By default a child's value is added to its parent's, and the total has to stay between −4096 and 4096.

3. y-sorting

Neither rule is enough for a world seen from above and a little to the front, like most farm and village games. There, who is in front changes: walk above the tree and you should be behind it; walk below it and you should cover its trunk. The rule you want is "lower on the screen is nearer", and Godot has it as a switch: turn on y_sort_enabled on a parent, and its children are painted in order of their y, smallest first, every frame.

Drag "you" above the tree's base and below it. Then untick the box and do it again: that is plain tree order, and you are standing on top of a tree.

There is nothing magic inside the switch. It is a sort, on one number per thing:

extends Node

func _ready() -> void:
	var things := [
		{"name": "bench", "feet": Vector2(60, 150)},
		{"name": "you",   "feet": Vector2(90, 118)},
		{"name": "tree",  "feet": Vector2(80, 120)},
	]
	things.sort_custom(func(a, b): return a["feet"].y < b["feet"].y)
	for thing in things:
		print("paint ", thing["name"])

You are painted first, so the tree covers you: you are behind it, two pixels further up the screen. Change your 118 to 122 and you step in front.

The trap: sort by the feet, not the middle

The number that gets sorted is the node's own y – its origin. A Sprite2D is centred on its origin by default, so a tall tree and a short person are compared by their middles, and the person pops in front while still standing behind the trunk. Give every y-sorted thing an origin where it touches the ground: either turn off the sprite's Centered and set its Offset so the picture sits above the origin, or make the sprite a child of a plain Node2D and slide it up. The key in the example above is called feet for a reason.

In Little Hours

Little Hours never turns on y_sort_enabled. It does the same thing with rule 2: every piece of furniture and every character sets z_index to the y of its feet. A z_index is compared across the whole scene, so the furniture (children of the room) and the resident (a child of Main) sort against each other without sharing a parent. The code is in the last part of this chapter.

The camera, and what does not move with it

Without a camera the window shows the world from (0, 0) to wherever the window ends, and stays there. A Camera2D is a node whose position says which point of the world is at the centre of the screen.

The quickest way to use one is to add it as a child of the player. Its local position stays (0, 0), so by everything in the first section it is always where the player is, and the view follows with no code. Then three groups of settings make it behave:

extends Camera2D

func _ready() -> void:
	zoom = Vector2(2, 2)                 # <1>

	limit_left = 0                       # <2>
	limit_top = 0
	limit_right = 1280
	limit_bottom = 720

	position_smoothing_enabled = true    # <3>
	position_smoothing_speed = 5.0
  1. Zoom. Bigger means closer: (2, 2) draws the world at twice the size, so you see half as much of it. (Godot 3 had this the other way up; old tutorials will tell you 0.5.) Keep both numbers the same, and whole for pixel art.
  2. Limits. The edges of the world, in pixels. The camera will not show anything beyond them: walk into a corner and the view stops while the player carries on to the wall.
  3. Smoothing. Instead of being nailed to its target, the camera closes part of the gap each frame – the lerp glide from the last section. A higher speed is a tighter follow. After a teleport, call reset_smoothing() or the camera will visibly fly across the level.

All of these are in the Inspector too, under Zoom, Limit and Position Smoothing; most people set them there.

A limit is a clamp. The camera's centre has to stay half a screen away from each edge, or the view would hang over it:

extends Node

const VIEW := Vector2(320, 180)    # what the screen shows
const WORLD := Vector2(640, 360)   # limit_right and limit_bottom

func camera_x(player_x: float) -> float:
	return clampf(player_x, VIEW.x / 2, WORLD.x - VIEW.x / 2)

func _ready() -> void:
	for player_x in [20.0, 160.0, 300.0, 480.0, 630.0]:
		var cam := camera_x(player_x)
		print("player at ", player_x, "  camera at ", cam, "  view shows ", cam - VIEW.x / 2, " to ", cam + VIEW.x / 2)

At both ends the camera stops at 160 and 480 while the player goes on to the walls, and the view never shows less than 0 or more than 640. Make the world 400 wide and read the last two lines again.

CanvasLayer: the part that stays put

A camera moves everything. That is wrong for the score, the clock and the pause menu, which belong to the glass rather than the world. They go under a CanvasLayer: a node whose children are drawn in screen pixels, ignoring the camera completely – its position, its zoom, all of it.

Main (Node2D)
├─ World (Node2D)
│   ├─ Player (CharacterBody2D)
│   │   └─ Camera2D
│   └─ Tree (Sprite2D)
└─ HUD (CanvasLayer)
    └─ Clock (Label)

Each CanvasLayer has a layer number. The world is on layer 0; a higher layer is drawn in front of a lower one, whatever the z_index of the things inside. So a game usually has a few: the HUD on one, pop-up cards above it, a fade-to-black above everything.

Two answers to "where is the mouse?"

Once a camera has moved, the screen and the world disagree about every point. get_global_mouse_position(), called on a node in the world, answers in world pixels – what you want for "walk to where I clicked". get_viewport().get_mouse_position() answers in screen pixels – what a HUD wants. Mixing them up works perfectly until the first time the camera moves.

In Little Hours

A house you walk around in, seen from the front and a little above, drawn in pixel art: every idea in this chapter is load-bearing in Little Hours, and each one is a few lines.

A world measured in tiles

The world's units are set once, at the top of the Game autoload (Game.gd):

Game.gd · lines 20–23

# ── The world grid (identical to the web build, so layouts port 1:1) ──
const TILE := 96
const STAGE_W := 768    # 8 tiles
const STAGE_H := 1344   # 14 tiles

A tile is 96 pixels, and the room everything was first laid out in is 8 tiles by 14. Writing the size as "8 tiles" in a comment beside the number is a small habit worth copying: positions in a room make sense as tiles, and the constants turn them into pixels. Rooms are different sizes now, so the size of the one you are standing in is a variable, Game.ROOM, worked out again each time you go through a door (Map, rooms and doors).

One rule for depth

RoomView.gd builds a Sprite2D for each piece of furniture. Two lines of that loop are this chapter:

RoomView.gd · lines 347–359

# Snap to whole pixels: a sprite centred on a half-pixel re-introduces
# the uneven-edge look the integer scale exists to prevent.
s.position = centre.round()
# Flat coverings sit *on* the floor, so they're pulled out of the
# y-sort entirely and pinned below every character. Sorting them by
# their bottom edge like a tall piece made the rug draw over anyone
# standing north of it. FLAT_IDS already skips collision; depth has
# to skip it too.
# Depth is measured to the bottom of the ART, not of the texture. Many
# of these sprites carry transparent padding underneath — up to 78px
# once scaled — and sorting on the texture put a plant in front of
# anybody standing in that empty space.
s.z_index = FLOOR_Z if is_flat(oid) else int(centre.y + Assets.base_offset(oid)) + int(obj.get("z", 0))

The first is .round(). The room's layout is arithmetic and arithmetic produces halves; a sprite placed on half a pixel has its edges smeared across two. Rounding the position is the cheapest fix there is, and you will find it wherever this game places anything.

The second is the depth rule. These sprites are centred, so centre.y is the middle of the picture; Assets.base_offset(oid) is how far below the middle the drawn part ends. Their sum is the y of the piece's foot, in room pixels, and that number is its z_index. The comment records why it is the foot of the art and not of the image file: many of the pictures have empty rows underneath, and sorting on those put a plant in front of someone standing in the empty space. That is the "feet, not the middle" trap, one level subtler.

There are two honest exceptions. Rugs and mats are flat, so they are pinned at FLOOR_Z (which is 1) – on the floor, under every foot. And a piece can carry a small authored "z" nudge for the rare case the rule gets wrong.

The characters follow the same rule from the other side. Their node's origin is their feet, so there is nothing to add. These are the last lines of _process() in Player.gd:

Player.gd · lines 486–490

# Pixel-art bodies must land on whole pixels or the sprite shimmers as it
# walks. The node keeps its exact position for collision and depth; the art
# is nudged by the fraction so it draws on the grid.
_avatar.position = position.round() - position
z_index = int(position.y)

z_index = int(position.y): walk down the room and your number rises past the sofa's, and you are in front of it. No list is sorted and nothing checks who overlaps whom. The line above it is local space earning its keep. The node keeps its exact, fractional position, because movement needs it; the picture is a child, and its local position is set to the tiny difference between the exact place and the nearest whole pixel. Parent plus child lands on the grid.

Dragging furniture about has to keep the rule true, so the function that moves a piece works its z_index out again at every step of the drag (Decorating).

The camera

Main.gd makes one Camera2D in code, with position_smoothing_enabled = true and a position_smoothing_speed of 6. It is a child of Main, not of the resident; each frame Main copies the resident's position to it, rounded. Its limits and zoom are set by one function:

Main.gd · lines 607–618

## The camera's box and how far back it sits. Both are worked out from the room,
## so both are redone together every time the room changes — a zoom set once at
## startup would be wrong the first time you walked into a room of another size.
func _apply_camera_limits() -> void:
	if _camera == null:
		return
	_camera.limit_left = 0
	_camera.limit_top = 0
	_camera.limit_right = int(Game.ROOM.x)
	_camera.limit_bottom = int(Game.ROOM.y)
	var z := _world_zoom()
	_camera.zoom = Vector2(z, z)

The limits are the room: 0 to Game.ROOM. Because rooms differ in size, the comment insists the function runs again on every room change. The zoom comes from Game.camera_zoom(), which returns float(art + CAMERA_LEAN) / float(art), where art is the number of game pixels under one pixel of the drawings. Today that is 3 and the lean is 1, so the zoom is 4/3: each art pixel covers exactly one more screen pixel than before. It is not a whole number, but it is chosen so that the pixels still come out whole – the reasoning is in Chapter P and in Orientation and camera.

Everything that must not move with that camera is on a CanvasLayer, and the layer numbers give the stacking: the HUD is 10, the cards 20, the talk box 60, the opening sequence 90, and the black curtain that covers a change of room is 250, above them all. The world never has to know any of them exist.

What to remember

  • A Node2D's position is measured from its parent; global_position is where that puts it in the world. Compare and copy the global one whenever two nodes do not share a parent.
  • y points down, so up is negative and a positive rotation is clockwise. rotation is radians; rotation_degrees is the same angle in degrees.
  • b - a is the arrow between two places. length(), normalized(), distance_to(), direction_to() and lerp() answer nearly every question about it – and a direction should be normalised before it meets a speed.
  • Draw order is tree order, unless z_index says otherwise, unless the parent has y_sort_enabled. For a world seen from the front, sort by the feet.
  • A Camera2D chooses the point at the centre of the screen: limits clamp it, zoom scales it, smoothing lerps it. Interface goes on a CanvasLayer, which the camera does not move.
  • Round positions to whole pixels when the art is pixel art.
