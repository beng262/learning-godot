Saving and loading

user://, FileAccess, JSON, versions and a sanitiser – saves that still load after you change the game.

In this chapter

  • the one place a game is allowed to write – user:// – and where that folder is on each platform
  • writing and reading a text file with FileAccess
  • turning a Dictionary into JSON and back, and what comes back changed
  • loading a file you cannot trust: defaults, a sanitiser, versions and migrations
  • when to save, so that a phone closing the app loses nothing

Where a game may write

A game has two folders. One holds everything you made, and it is sealed when you export. The other belongs to the player, and it is the only place a save can go.

Every path so far has started with res://, the project folder (Chapter A). While you work in the editor that is an ordinary folder on your disk. When you export the game, Godot packs it into a single file that can be read and never changed. So a save written to res:// works on your computer, in the editor, and fails for every player.

The second root is user://. It is a folder for this game and this user, Godot makes it the first time it is needed, and it stays when the game is updated. Where it really is depends on the machine:

PlatformWhat user:// stands for
Windows%APPDATA%\Godot\app_userdata\Project Name\
macOS~/Library/Application Support/Godot/app_userdata/Project Name/
Linux~/.local/share/godot/app_userdata/Project Name/
Android and iOSThe app's own private storage. Other apps cannot see it, and it goes when the app is uninstalled.
WebThe browser's storage for the site the game is served from.

You never type those. "user://save.json" means the right thing on all of them, which is the point. When you want to look at the real folder – and while you are learning to save, you will, often – the editor opens it with Project › Open User Data Folder, and a script can ask for it:

func _ready() -> void:
	print(OS.get_user_data_dir())   # the real folder behind user://

A game with more than one save needs more than one file name, and the usual way is to build the path from a number. This runs, because it is only a String being put together:

extends Node

const SLOTS := 3

func slot_path(n: int) -> String:
	return "user://save_slot%d.json" % clampi(n, 1, SLOTS)

func _ready() -> void:
	print(slot_path(1))
	print(slot_path(2))
	print(slot_path(9))

Slot 9 does not exist, and clampi turns it into the nearest one that does. Press Edit and run, change SLOTS to 5 and ask for slot -2: a path built by a function is a path that cannot be wrong in a new way each time it is typed.

The folder is named after the project

On a desktop the last part of the path is the project's name, so renaming the game in Project Settings points user:// at a new, empty folder and leaves every player's save behind in the old one. Two settings under Application › Config fix the name for good: Use Custom User Dir and Custom User Dir Name. With them on, the folder is %APPDATA%\that name\ (and the matching place on macOS and Linux), whatever the game is called this year.

Writing and reading a file

One class does it: FileAccess. Open, write or read, close – and check that the open worked, because on a player's machine it sometimes does not.

const SAVE_PATH := "user://save.json"

func write_save(text: String) -> bool:
	var file := FileAccess.open(SAVE_PATH, FileAccess.WRITE)   # <1>
	if file == null:                                            # <2>
		push_warning("Could not open the save: error %d" % FileAccess.get_open_error())
		return false
	file.store_string(text)                                     # <3>
	file.close()                                                # <4>
	return true

func read_save() -> String:
	if not FileAccess.file_exists(SAVE_PATH):                   # <5>
		return ""
	var file := FileAccess.open(SAVE_PATH, FileAccess.READ)
	if file == null:
		return ""
	var text := file.get_as_text()                              # <6>
	file.close()
	return text
  1. FileAccess.open(path, mode) is called on the class, not on an object, and hands back a FileAccess for that file. FileAccess.WRITE makes the file if it is not there and empties it if it is.
  2. If the file could not be opened – a full disk, a folder the game may not touch, a path with a typing mistake – you get null, and FileAccess.get_open_error() says why. Calling store_string on null is a crash, so this check is not optional.
  3. store_string() writes the text.
  4. close() finishes the job: anything still waiting in memory goes to the disk.
  5. FileAccess.file_exists() answers without opening anything. On the first run there is no save, and that is not an error – it is a new player.
  6. get_as_text() reads the whole file as one String.
ModeWhat it does
FileAccess.READOpens a file that exists, for reading.
FileAccess.WRITECreates the file, or empties it, for writing.
FileAccess.READ_WRITEOpens a file that exists for both, leaving what is in it.
FileAccess.WRITE_READCreates the file, or empties it, for both.

Two of those say "empties it", and that is the trap in this section. WRITE throws the old save away the moment the file opens, before a single character of the new one is written. If the game is killed in between – a flat battery, a phone reclaiming memory – what is left on the disk is half a save. You cannot prevent that from inside the game. What you can do is write a loader that expects it, which is most of the rest of this chapter.

A disk you can run

The code in this page runs on the book's interpreter, which has no files. So for everything that follows, a save is a String – the text that would be in the file – and where a disk is needed, a Dictionary from paths to text stands in for one:

extends Node

var disk := {}     # path -> the text in that file

func write_text(path: String, text: String) -> bool:
	if not path.begins_with("user://"):
		print("refused: a game may not write to ", path)
		return false
	disk[path] = text
	return true

func read_text(path: String) -> String:
	if not disk.has(path):
		return ""              # no such file
	return disk[path]

func _ready() -> void:
	write_text("user://save.json", "coins: 12")
	write_text("res://save.json", "coins: 999")
	print(read_text("user://save.json"))
	print("[", read_text("user://nothing.json"), "]")

Write to user://save.json a second time with different text and read it back: the old text is gone, as it would be with FileAccess.WRITE. The shape of these two functions is the shape of the real ones above – a write that can fail and says so, a read that returns nothing when there is nothing – and the game around them need not know which pair it is calling. That is worth arranging on purpose: code that takes and returns text can be tested without touching a disk.

JSON: a Dictionary as text

A file holds text and a game holds variables. JSON is the most common way across: a plain-text format that looks almost exactly like a GDScript Dictionary.

Keep everything that should survive in one Dictionary (Chapter G), and saving is one call. JSON.stringify() takes a value and returns the text for it:

extends Node

var state := {"coins": 12, "day": 3, "name": "Wren"}

func _ready() -> void:
	print(JSON.stringify(state))
	print(JSON.stringify(state, "\t"))

The second argument is what to indent with. With none, the text is one tight line, which is what you want in a file. With a tab it is laid out for a person, which is what you want while you are finding out why a save will not load. Add a fourth key to state – a list, say, "bag": ["carrot", "carrot"] – and see both forms follow.

And back

JSON.parse_string() goes the other way: text in, value out. Something changes on the round trip, and it is the first surprise everyone meets:

extends Node

func _ready() -> void:
	var text := '{"coins": 12, "day": 3, "name": "Wren"}'
	var back: Variant = JSON.parse_string(text)
	print(back)
	print("Day ", back["day"])
	print("Day ", int(back["day"]))

The day went in as 3 and came back as 3.0. JSON has one kind of number and no idea of the difference between int and float, so Godot reads every number as a float. Nothing is lost – 3.0 == 3 is true – but a label will say "Day 3.0" unless you convert with int(), and a loader has to do that for every field that is meant to be whole.

Two details of that example. The text is in single quotes, which GDScript allows for any String and which saves writing \" eleven times. And back is typed Variant, meaning "any type at all": parse_string may return a Dictionary, an Array, a number, a String or nothing, depending on the text, so := has no single type to work out.

What survives the trip

extends Node

func _ready() -> void:
	var before := {"spot": Vector2(3, 4), 7: "seven", "bag": ["carrot", 2, true, null]}
	var text := JSON.stringify(before)
	print(text)
	var after: Variant = JSON.parse_string(text)
	print(after)
	print(after.has(7), " ", after.has("7"))
Goes in asComes back as
String, bool, nullThe same.
int, floatAlways float.
Array, DictionaryThe same shape, with each thing inside following these rules.
A Dictionary key that is not a StringA String: the key 7 becomes "7".
Vector2, Color and the other engine typesA String that only looks like one: "(3.0, 4.0)". It will not turn back by itself.

So keep the saved Dictionary to plain things. A position is saved as two numbers – {"x": 3, "y": 4} – and rebuilt with Vector2(d["x"], d["y"]); a colour as its hex String. Use String keys throughout.

Text that is not JSON

extends Node

func _ready() -> void:
	print(JSON.parse_string('{"day": 3'))        # cut off before the end
	print(JSON.parse_string(""))                 # an empty file
	print(JSON.parse_string("[1, 2, 3]"))        # fine JSON, but a list
	print(typeof(JSON.parse_string("[1, 2, 3]")) == TYPE_DICTIONARY)

Text that will not parse gives null, not an error. And text that parses is not promised to be a Dictionary. The one question to ask of the result, before anything else, is on the last line: typeof(x) == TYPE_DICTIONARY. Everything after that question can use [] and .get() safely; nothing before it can.

Two small differences on this page

Godot's JSON.stringify() writes a Dictionary's keys in alphabetical order, whatever order you added them in, and writes a whole float with its point: 1.0. The interpreter in this page keeps your order and writes 1. Neither matters to a save – parse_string reads both the same – but the text you see here may be ordered differently from the file Godot writes.

Never trust the file

The save was written by your game, so it is tempting to read it as if it must be right. It was written by an older version of your game, on a disk that may have been full, and has since sat in a folder anyone can open.

Things that are true of real save files: a field is missing, because the save is from before that field existed. A field has a value that is no longer allowed, because the room it names was cut. The file ends halfway. A player has opened it in a text editor and typed "coins": 999999, or "coins": "lots". A loader that writes state = parsed hands all of that to the rest of the game, which finds out much later, in a function that has nothing to do with saving, when it adds one to a String.

The cure is a function with one job, usually called a sanitiser. It does not repair the file's Dictionary. It starts from a fresh, known-good default and copies across only what passes a check:

extends Node

func default_state() -> Dictionary:
	return {"coins": 10, "day": 1, "volume": 0.8}

func is_number(v: Variant) -> bool:
	return typeof(v) in [TYPE_INT, TYPE_FLOAT]

func sanitize(s: Dictionary) -> Dictionary:
	var d := default_state()
	if is_number(s.get("coins")):
		d["coins"] = maxi(0, int(s["coins"]))
	if is_number(s.get("day")) and s["day"] >= 1:
		d["day"] = int(s["day"])
	if is_number(s.get("volume")):
		d["volume"] = clampf(s["volume"], 0.0, 1.0)
	return d

func _ready() -> void:
	print(sanitize({"coins": 55.0, "day": 4.0, "volume": 0.5}))
	print(sanitize({"coins": -300, "day": "tomorrow", "volume": 11}))
	print(sanitize({"cheat": true}))

Read the three results. A good save comes through, with its whole numbers whole again. A bad one comes through as far as it can: the coins are pulled up to zero, the day that is not a number is left at the default, the volume is pulled down to one. A file of nonsense gives a new game. In no case does anything reach the game that default_state() could not have produced.

Each line is the same three questions, and they are worth saying aloud for every field you add:

  • Is it there, and is it the right type? s.get("coins") gives null for a missing key instead of stopping the game, and typeof(…) in [TYPE_INT, TYPE_FLOAT] accepts a number of either kind – remember that every number from a file arrives as a float.
  • Is it in range? maxi, clampi and clampf (Chapter D) pull a number back inside its limits. For a value with no sensible nearest – a room name, a crop – the check is "is it one I know?", with .has().
  • Convert it to the type the game uses: int() for the whole numbers.

Try it: add a "room" to the defaults, "bedroom", and a line that accepts a saved room only if it is a String and one of ["bedroom", "kitchen", "garden"]. Then feed it "moon".

The field that never came back

This pattern has one failure of its own, and it is quiet. Add a field to the defaults, change it during play, save it – and forget its line in the sanitiser. Nothing errors. The field is written to the file every time and thrown away every load, because what is not copied across stays at the default. If something "resets itself" whenever the game restarts, look there first.

Versions, and when to save

A sanitiser protects the game from a bad file. A version number does a different job: it lets the game understand a good file from last year.

Defaults already cover the commonest change, a field that is new. What they cannot cover is a field that means something different now: it was renamed, or split in two, or its numbers are on a new scale. The file is not wrong; it is old. So write a number into every save that says which shape it has, and on loading, bring old shapes up to date one step at a time. Each step is a migration:

extends Node

const VERSION := 3

func migrate(s: Dictionary) -> Dictionary:
	var v := 1                        # a save from before versions is version 1
	if typeof(s.get("version")) in [TYPE_INT, TYPE_FLOAT]:
		v = int(s["version"])
	if v < 2:
		# 2 renamed "gold" to "coins"
		if s.has("gold"):
			s["coins"] = s["gold"]
			s.erase("gold")
		v = 2
	if v < 3:
		# 3 split one volume into two
		if s.has("volume"):
			s["music_vol"] = s["volume"]
			s["sfx_vol"] = s["volume"]
			s.erase("volume")
		v = 3
	s["version"] = v
	return s

func _ready() -> void:
	print(migrate({"gold": 40, "volume": 0.5}))
	print(migrate({"coins": 40, "version": 2, "volume": 0.5}))
	print(migrate({"coins": 40, "music_vol": 0.2, "sfx_vol": 0.9, "version": 3}))

The steps are a row of ifs, not elifs, on purpose: a version 1 save falls through both and arrives as version 3; a version 2 save skips the first. When version 4 comes you add one more block at the bottom and never touch the ones above, which have been tested by every load since they were written. The order on loading is then always the same: parse, check it is a Dictionary, migrate, sanitise.

A migration is also the most dangerous code in a game, because it runs once on every player's only copy and overwrites what was there. Keep each one narrow – change the thing that changed and nothing else – and you will see below what happened when Little Hours wrote one that was too broad.

When to save

Not every frame: that is sixty file writes a second for nothing. There are two good moments, and most games use both.

When something changes. If the whole state is a few kilobytes of JSON, write it whenever a value that matters is set. The save can never be more than one action out of date, and there is no "you forgot to save".

When the player leaves. Godot tells every node when the window is about to close or stops being the one in front, through _notification():

func _notification(what: int) -> void:
	if what == NOTIFICATION_WM_CLOSE_REQUEST \
			or what == NOTIFICATION_WM_WINDOW_FOCUS_OUT:
		save_now()

The second of those matters most on a phone. Nobody quits a phone game; they switch to something else, and some time later the system removes the game from memory without asking it. Losing focus is the last moment you are sure to be told about.

Build it live

A save system with the disk taken out: state to text, text to state, and every defence from this chapter in between. What you finish with is the part of saving that goes wrong, working.

In Little Hours

The whole of a life in Little Hours is one Dictionary in Game.gd, and the code that loads it is the longest function in the project. It is long for the reason this chapter gives: every field is checked on the way in.

Loading is two functions. The first deals with the disk and gives up, politely, at each of the three places a file can fail; the second never sees a file at all. This is where the second begins:

Game.gd · lines 636–668

## Load and *sanitise*. Every field is coerced back to its expected shape, so a
## corrupt or hand-edited save degrades to defaults instead of crashing — the
## same guarantee the web build's loadSave() gives.
func _load_save() -> Dictionary:
	var d := _default_state()
	if not FileAccess.file_exists(slot_path(slot)):
		return d
	var f := FileAccess.open(slot_path(slot), FileAccess.READ)
	if f == null:
		return d
	var raw := f.get_as_text()
	f.close()
	var parsed: Variant = JSON.parse_string(raw)
	if typeof(parsed) != TYPE_DICTIONARY:
		return d
	return _sanitize(parsed as Dictionary)

## Everything a save file claims, checked field by field against a fresh default.
##
## Split out from reading the file so the checks can be run on a dictionary — a
## test can hand this nonsense and prove it is refused, which is not possible
## when the validation is welded to FileAccess. Anything that fails validation is
## simply not copied across, so the default survives and the game still starts.
func _sanitize(s: Dictionary) -> Dictionary:
	var d := _default_state()

	# day: must be a finite integer >= 1, or the season index goes negative.
	if s.has("day") and typeof(s["day"]) in [TYPE_INT, TYPE_FLOAT] and float(s["day"]) >= 1.0:
		d["day"] = int(s["day"])
	if s.has("room") and typeof(s["room"]) == TYPE_STRING and RoomData.ROOM_IDS.has(s["room"]):
		d["room"] = s["room"]
	if s.has("coins") and typeof(s["coins"]) in [TYPE_INT, TYPE_FLOAT]:
		d["coins"] = maxi(0, int(s["coins"]))

No file, a file that will not open, text that is not a Dictionary: each returns the default state, so the game starts whatever is on the disk. Then _sanitize() does what the tutorial did, about five hundred lines of it. The first three fields show all three kinds of check: the day must be a number of at least 1 ("or the season index goes negative"), the room must be one that still exists on the map, and coins are clamped at zero. The comment above the function is the argument for splitting the job in two – with the checks apart from FileAccess, "a test can hand this nonsense and prove it is refused".

Little Hours has no version number in its save. It gets by on the sanitiser, with each change of shape handled where that field is read. One of those places records, in its comment, what a migration can cost:

Game.gd · lines 701–724

# A breed you PICKED is yours. A breed you were given is whatever the game
# currently comes with.
#
# There was a migration here once, moving every save off the pack dog onto
# the hand-drawn one. It was taken out because the drawn dog was "twice the
# scale of the world it stands in" — a measurement that predates the
# density dial and has been wrong ever since. It is 78x63 against a 72px
# person, which is a big dog.
#
# So it comes back, but narrower than before: only a save that never went
# to the pets menu and chose is moved. Otherwise changing the default would
# quietly overwrite somebody's actual choice, which is what a blanket
# migration does and why the last one was a mistake in both directions.
#
# This is the whole of "why are you using the old dog". The default has
# said "dreamland" since yesterday; a save written before that still said
# golden, and a default only ever applies to a life that has not started.
d["breed_chosen"] = bool(s.get("breed_chosen", false))
if typeof(s.get("dog_coat")) == TYPE_STRING \
		and str(Pet.coat(str(s["dog_coat"]))["id"]) == str(s["dog_coat"]):
	d["dog_coat"] = str(s["dog_coat"])
if typeof(s.get("dog_breed")) == TYPE_STRING and Pet.BREEDS.has(s["dog_breed"]):
	if bool(s.get("breed_chosen", false)):
		d["dog_breed"] = s["dog_breed"]

The default dog changed, and old saves still named the old one. The first fix moved every save to the new dog – and overwrote the choice of everyone who had picked theirs. So the save gained a flag, breed_chosen, and the rule became narrow: a saved breed is kept only if the player chose it, and otherwise the current default stands. That is a migration written as a condition instead of a version step, and the lesson holds for both kinds: change what changed, and nothing a player decided.

Saving is short by comparison:

Game.gd · lines 1220–1249

## Turned off by the test suite, which drives the game hard on purpose — buying
## things, doing every repair, walking into every room — and must never leave any
## of that in a real save file. Nothing else should ever set this.
var saving_enabled := true

func save_now() -> bool:
	if not saving_enabled:
		return false
	var f := FileAccess.open(slot_path(slot), FileAccess.WRITE)
	if f == null:
		push_warning("Tiny Home: could not open the save file for writing.")
		return false
	f.store_string(JSON.stringify(state))
	f.close()
	return true

func _notification(what: int) -> void:
	# Autosave when the game loses focus, is backgrounded, or quits — phones kill
	# backgrounded apps without warning, so this is the save that actually matters
	# on mobile. These four are all Node-level notifications; the
	# NOTIFICATION_APPLICATION_* family lives on MainLoop and is not in scope here.
	if what == NOTIFICATION_WM_CLOSE_REQUEST \
			or what == NOTIFICATION_WM_GO_BACK_REQUEST \
			or what == NOTIFICATION_WM_WINDOW_FOCUS_OUT \
			or what == NOTIFICATION_EXIT_TREE:
		save_now()

func _changed() -> void:
	state_changed.emit()
	save_now()

save_now() is the listing from the start of this chapter: open for writing, check for null, store_string(JSON.stringify(state)), close. Around it are the two moments to save. _changed() is what nearly every function that alters the state ends with – announce it, then write it – so nothing in the game has to remember to save. And _notification() writes once more when the window is closed, loses focus, gets Android's back gesture, or the node leaves the tree, for the reason its comment gives: a phone ends an app in the background without warning. saving_enabled is a switch for the test suite, which plays the real game hard and must leave no trace of it.

There are three lives, in three files. slot_path(), quoted earlier, gives each its name, and a fourth small file, user://tinyhome_slot.txt, holds the number of the one in use – read back at start-up with the same suspicion as everything else: not a whole number, or out of range, means slot 1. Changing slot is save_now(), change the number, load.

And one more way out of the device altogether, for a player whose phone may not last as long as their house:

Game.gd · lines 1561–1574

## The whole save as one line of text you can mail to yourself.
##
## Format: TINYHOME-1:<bytes>:<base64 of gzipped json>. The byte count is the
## length of the JSON before compressing, checked again after unpacking, which
## is what catches the failure that actually happens — a mail client wrapping
## or clipping a long line, leaving a code that decodes to most of a life. A
## hash would do the same job but would tie the format to one engine's hash.
const CODE_HEADER := "TINYHOME-1"

func backup_code() -> String:
	var json := JSON.stringify(state)
	var bytes := json.to_utf8_buffer()
	var packed := bytes.compress(FileAccess.COMPRESSION_GZIP)
	return "%s:%d:%s" % [CODE_HEADER, bytes.size(), Marshalls.raw_to_base64(packed)]

The same JSON, compressed, turned into letters that survive an email, and labelled: a header with the format's version (here, at last, is a version number), and the length of the JSON before packing. restore_code() refuses anything whose unpacked length differs, which is what catches the failure that really happens – a mail program cutting a long line short. What it accepts then goes through _sanitize() like any other save, and the life being replaced is first parked in a file of its own, so a code pasted into the wrong slot can be taken back. The last exercise below builds a small one.

Five exercises on text in and text out. None needs a disk; all of them are the part of saving that a disk cannot do for you.

What to remember

  • res:// is sealed in an exported game; saves go in user://, a per-player folder whose real place differs on every platform and is named after the project.
  • FileAccess.open() returns null when it fails – always check – and WRITE empties the file as it opens.
  • JSON.stringify() and JSON.parse_string() turn a Dictionary into text and back. Every number comes back a float, every key a String, and bad text comes back null.
  • Load by building: start from the defaults and copy across only what has the right type and a sensible value. Then a missing field, a wrong one and a new one are all the same, safe case.
  • A version number and a row of small migrations bring old saves forward; keep each migration to the one thing that changed.
  • Save when something changes and again when the window closes or loses focus. Keep the functions that make and read the text apart from the ones that touch the disk, so they can be tested.
