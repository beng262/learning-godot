What a tool is

A game is made of code and of a great deal that is not code: tables, pictures, stories, sounds. A tool is a small program whose audience is you. It reads those things and either tells you what is wrong with them or makes more of them.

Nearly every tool is one of three shapes.

ShapeReadsProducesFor example
A checkerYour dataA list of problems, and a yes or no"Three rooms have a door that leads nowhere"
A generatorSomething small you maintainSomething large you would not want to typeA catalogue of a thousand sprites from a folder listing
A converterA file as an artist saves itThe file as the game wants itOne sheet of hairstyles cut into parts and recoloured

None of them is clever. A checker is a loop with an if in it. Here is one that looks at a table of sprites and finds any whose size is not a whole number of 16-pixel tiles:

extends Node

const TILE := 16
var sprites := [
	{"file": "bed.png", "w": 48, "h": 32},
	{"file": "lamp.png", "w": 16, "h": 40},
	{"file": "rug.png", "w": 64, "h": 48},
]

func _ready() -> void:
	var bad := 0
	for sprite in sprites:
		if sprite["w"] % TILE != 0 or sprite["h"] % TILE != 0:
			print(sprite["file"], ": ", sprite["w"], "x", sprite["h"], " is not a whole number of tiles")
			bad += 1
	print(sprites.size(), " sprites checked, ", bad, " to fix")

Make the lamp 48 high and the report comes back clean. Now imagine the table has a thousand rows. You would not find the lamp by looking; the loop finds it in a blink, every time, including the day somebody adds a sprite at midnight.

When to write one

Write a tool the second or third time you do a job by hand, and straight away for any job where a slip is silent. Renaming forty files is tedious but shows its mistakes; a sprite one pixel too wide does not show until a player sees a seam. The questions to ask are "will I do this again?" and "would I notice if I got it wrong?".

Three habits make a tool trustworthy:

  • Say everything that is wrong, not only the first thing. Return a list of problems, as the release gate in Chapter X did.
  • Be safe to run twice. Running it again on its own output should change nothing.
  • Never touch what a person made. A tool reads the artist's file and writes a different one. The file a human edits and the file a tool writes are never the same file.

The rest of this chapter is about where such programs can live: inside the editor, on the command line, or outside Godot altogether.

Code that runs in the editor

Your scripts normally run only when the game does. Two small additions let GDScript run inside the editor itself, where it can see and change the scene you are working on.

@tool

Put @tool on the first line of a script and Godot runs that script in the editor as well as in the game. Its _ready() runs when the scene is opened, its _process() runs while you look at it, its _draw() paints into the editor's viewport. The classic use is a preview: a node that draws its own range, path or shape while you adjust it in the Inspector.

@tool
extends Node2D

@export var radius := 48.0:
	set(value):
		radius = value
		queue_redraw()                      # <1>

func _draw() -> void:
	draw_arc(Vector2.ZERO, radius, 0.0, TAU, 48, Color.YELLOW, 2.0)

func _process(delta: float) -> void:
	if Engine.is_editor_hint():             # <2>
		return
	rotation += delta
  1. Dragging Radius in the Inspector calls the setter, which asks for a redraw, so the circle follows the slider in the editor.
  2. Engine.is_editor_hint() is true only inside the editor. Everything below this line is game behaviour and stays out of it.

A tool script has the keys to your scene

In the editor, "the running game" is the scene file you have open. A @tool script that moves, renames or frees nodes does it to your work, and the next Ctrl+S makes it permanent. Guard game logic with Engine.is_editor_hint(), never call queue_free() from editor code you have not thought about twice, and commit before you try a new tool script. Only scripts marked @tool run in the editor, and after adding the line you usually have to close and reopen the scene for it to take effect.

Two more things @tool scripts are good for. A function called _get_configuration_warnings() that returns a list of messages puts the yellow warning triangle beside the node in the Scene dock – a checker that lives on the thing it checks. And @export_tool_button, in recent versions of Godot 4, puts a button in the Inspector that calls one of the script's functions.

EditorScript: run once

Often you do not want code that lives in a scene; you want to do one job now. That is an EditorScript: a script with a single function, _run(), which the script editor runs when you choose File › Run.

@tool
extends EditorScript

func _run() -> void:
	var root := get_scene()                 # the scene open in the editor
	if root == null:
		print("Open a scene first.")
		return
	var empty := 0
	for sprite: Sprite2D in root.find_children("*", "Sprite2D", true, false):
		if sprite.texture == null:
			print("No texture: ", root.get_path_to(sprite))
			empty += 1
	print(empty, " sprites without a texture")

This one is a checker: it walks every Sprite2D under the open scene and names the ones with no picture. The same shape will rename nodes, lay out a grid, or write a data file with FileAccess (Chapter S). An EditorScript that changes a scene does so without an undo step, so save and commit first.

The editor parts of such a script cannot run in this page, but the middle of most tools is plain logic that can. Here is the heart of a generator – the part that turns a list of file names into the text of a GDScript file:

extends Node

var files := ["Busk_Stand.png", "Bazaar_Kiosk.png", "Gift_Counter.png"]

func catalogue(names: Array) -> String:
	var sorted := names.duplicate()
	sorted.sort()
	var lines := [
		"## AUTO-GENERATED. Do not edit by hand: run the tool again.",
		"const PIECES := [",
	]
	for file in sorted:
		lines.append('\t{"k": "%s"},' % file)
	lines.append("]")
	return "\n".join(lines)

func _ready() -> void:
	print(catalogue(files))

Add "Apple_Crate.png" to the end of files and see where it lands in the output. Two details are worth copying. The list is sorted before it is written, so the same input always gives the same file and version control shows only real changes. And the first line the tool writes is a warning to people: this file is output, edit the source instead.

Editor plugins, in outline

A plugin is a tool script the editor loads at start-up and keeps. It is how you add a menu item, a dock or a new kind of node to Godot itself.

A plugin is a folder under addons/ with two files in it. The first, plugin.cfg, is a label:

[plugin]

name="Room Checker"
description="Adds a menu item that checks the rooms table."
author="You"
version="1.0"
script="plugin.gd"

The second is the script it names, which extends EditorPlugin:

@tool
extends EditorPlugin

func _enter_tree() -> void:                          # <1>
	add_tool_menu_item("Check rooms", _check_rooms)

func _exit_tree() -> void:                           # <2>
	remove_tool_menu_item("Check rooms")

func _check_rooms() -> void:
	print("Checking rooms…")
  1. Called when the plugin is switched on. Here it adds an entry under Project › Tools.
  2. Called when it is switched off. Everything _enter_tree() added, _exit_tree() removes.

You switch a plugin on in Project Settings › Plugins, which is also where the editor offers to create the two files for you. Beyond menu items, an EditorPlugin can add panels to the docks and the bottom of the editor, register custom node types, teach Godot to import a new kind of file, and add controls to the Inspector. The functions for docks in particular have been changing between 4.x versions, so look them up in the class reference for the version you have.

The rule that matters is the pairing in the listing above. A plugin can be switched off and on many times in one sitting, and anything it forgets to remove piles up. This small model of the Tools menu shows what that looks like:

extends Node

var tools_menu := []   # stands in for the editor's menu

func enter_tree() -> void:
	tools_menu.append("Check rooms")
	tools_menu.append("Bake sprites")

func exit_tree() -> void:
	tools_menu.erase("Check rooms")

func _ready() -> void:
	for i in 3:        # the plugin is switched on and off three times
		enter_tree()
		exit_tree()
	print(tools_menu)

Three stray "Bake sprites" entries. Add the missing erase to exit_tree() and the menu ends empty, as it should.

Start smaller than a plugin

A plugin is the right home for a tool several people use every day. For a job you do once a week, an EditorScript or a command-line script is less to build and less to break. Most of Little Hours' tools, as you will see, are not plugins.

Godot from the command line

The Godot you double-click is also a command-line program. Run from a terminal, it can import, test, export and run your own scripts with no window and nobody watching – which is what lets a release be one command.

The program is the same file you already have. On Windows and Linux it is the executable itself; on a Mac it is inside the app, at Godot.app/Contents/MacOS/Godot. These are the options worth knowing:

OptionWhat it does
--path folderUse the project in that folder. Without anything else, runs the game.
--editorOpen the editor on the project rather than running it.
--headlessNo window and no drawing. For jobs on a machine with no screen, or where a window would be in the way.
--quit-after NStop after N frames: a safety net so that a stuck run ends.
--importImport any new or changed files, then stop. Run it after adding pictures from outside the editor.
--script file.gdRun one script instead of the game. The script must extend SceneTree or MainLoop.
--export-release "Preset" pathExport with the named preset from Chapter X. --export-debug makes a debug build the same way.
--Everything after this is for your game, not for Godot.

godot --help prints the full list for your version, and it is the authority: options are added from release to release.

A script with no game

--script runs a script that is its own main loop. It has no scene; _initialize() is called once, and quit() ends it. This is where a checker can live so that other programs can run it:

extends SceneTree

func _initialize() -> void:
	var text := FileAccess.get_file_as_string("res://data/rooms.json")
	var rooms = JSON.parse_string(text)
	if rooms == null:
		print("rooms.json is not valid JSON")
		quit(1)
		return
	print(rooms.size(), " rooms read")
	quit(0)

The number given to quit() is the exit code: 0 means "all well", anything else means "something is wrong". It is how one program tells another the result without anyone reading the output. A release script runs the checker and stops if the code is not 0.

Your own flags

Words after -- are handed to your game untouched, and OS.get_cmdline_user_args() returns them as a list of strings. That gives a game private modes: godot --path . -- --sizes can print a report and leave rather than open the title screen. Reading the list is ordinary array work, and it is worth doing in one place:

extends Node

# Turns ["--zoom", "2", "--sizes"] into {"zoom": "2", "sizes": true}.
func parse_args(args: Array) -> Dictionary:
	var out := {}
	var i := 0
	while i < args.size():
		var word: String = args[i]
		if word.begins_with("--"):
			var key := word.trim_prefix("--")
			if i + 1 < args.size() and not str(args[i + 1]).begins_with("--"):
				out[key] = args[i + 1]     # a flag followed by a value
				i += 1
			else:
				out[key] = true            # a flag by itself
		i += 1
	return out

func _ready() -> void:
	# In a game: parse_args(OS.get_cmdline_user_args())
	print(parse_args(["--sizes"]))
	print(parse_args(["--zoom", "2", "--room", "living"]))
	print(parse_args(["--zoom", "--sizes"]))

Look at the third line: --zoom with nothing after it comes out as true, not as "--sizes", because the function looks at what follows before taking it as a value. Try ["--zoom", "2", "extra"] and decide what you think should happen to a stray word; at the moment it is quietly dropped.

A tool that fails must say so

A command-line run nobody watches needs two things to be trusted: an exit code that is not 0 when it failed, and a line of output that only appears when it truly finished. The second matters more than it sounds. A script that could not even start – a typing mistake in the code, say – may end without an error code, and "no complaints" then looks exactly like "all passed".

Art pipelines

A picture rarely goes from the artist's hand to the screen unchanged. The road it takes is a pipeline, and the more of it that is a script, the less of it can go wrong quietly.

What importing is

When you put bed.png in a project, Godot does not use that file as it is. It imports it: reads the PNG, applies the settings in the Import dock – filtering, compression, how a sheet is sliced – and stores the result in the .godot/ cache. The settings are written to bed.png.import beside the picture. So there are three things: your source file, which you edit; the .import file, which is settings and belongs in version control; and the imported copy, which is rebuilt whenever it is missing and never committed (Chapter A).

Importing normally happens when the editor notices a new file. A script that adds pictures has no editor watching, which is what --headless --import is for: add the files, run the import, and the game can load them.

Batch work outside the editor

Anything you would do to forty sprites in a paint program, a script can do to four hundred. People write these in whatever is handy: Python with an image library, or the scripting built into the art program itself. Aseprite, the pixel-art editor, can be run from a terminal in batch mode to export sheets or run a script of its own with no window. And Godot can do it too: the Image class loads a picture, reads and writes pixels, resizes and saves a PNG, so a --script tool in GDScript can cut, recolour and scale.

Whatever the language, the rules of a good art pipeline are the same:

  • One source, many outputs. The artist keeps one file. Every size, colour variant and atlas is made from it by the script, so they cannot drift apart.
  • Pixel art is scaled by whole numbers with nearest-neighbour only (Chapter P). A pipeline that smooths once has ruined every sprite it touched.
  • Derived files say that they are derived, and nobody edits them. Fix the source or fix the script.
  • Check the result: sizes, names, that every picture the data mentions exists. That is the checker from the start of this chapter.

A pipeline also needs to know what to redo. Rebuilding everything each time is fine for forty sprites and slow for four thousand, so tools compare when the source and the output were last changed:

extends Node

# When each file last changed, in seconds. A bigger number is later.
var sources := {"hair.png": 500, "body.png": 320, "eyes.png": 100}
var baked := {"hair.png": 400, "body.png": 350}

func needs_baking() -> Array:
	var out := []
	for file in sources:
		if not baked.has(file) or baked[file] < sources[file]:
			out.append(file)
	return out

func _ready() -> void:
	print("To bake: ", needs_baking())

The hair was repainted after it was last baked, and the eyes have never been baked at all. Change the hair's baked time to 600 and it drops off the list. In real Godot the numbers come from FileAccess.get_modified_time(path).

When GDExtension is worth it

GDScript is not the only language Godot can run. GDExtension loads code written in C, C++, Rust and others as a library, and makes its classes appear in the engine as if they had always been there. It is powerful, and for most games it is the wrong first move.

An extension is a compiled library plus a small text file ending in .gdextension that tells Godot which library to load on which platform. Once loaded, its classes can be created and called from GDScript like any built-in node. Nothing about the engine is rebuilt.

Reach for it when…Not when…
The thing you need already exists as a native library: a physics engine, a codec, a language model.You could write it in GDScript in an afternoon.
You have measured one piece of your game and it is too slow, and a better algorithm did not fix it.You suspect GDScript is slow but have not looked at the profiler (Chapter W).
You must talk to a platform's own software kit.A plugin somebody already maintains does it.

The costs are real. You must build the library separately for every platform and processor you ship on, and the web is harder still. A mistake in native code does not print a red error with a line number; it closes the game. And everybody who works on the project now needs a compiler.

Before paying that, exhaust the cheap fixes: do the work less often, do less of it, and above all pick a better method. A different algorithm usually beats a faster language. Count the steps in two ways of asking "are there any duplicate names in this list?":

extends Node

func _ready() -> void:
	var names := []
	for i in 300:
		names.append("sprite_%d.png" % i)

	# One way: compare every name with every other name.
	var pair_steps := 0
	for a in names.size():
		for b in range(a + 1, names.size()):
			pair_steps += 1

	# Another: remember each name in a dictionary as you pass it.
	var seen := {}
	var dict_steps := 0
	for file in names:
		dict_steps += 1
		seen[file] = true

	print("every pair: ", pair_steps, " steps")
	print("dictionary: ", dict_steps, " steps")

Change 300 to 600. The dictionary's count doubles; the pairs' count quadruples. No change of language closes a gap that grows like that, and a dictionary is one line of GDScript.

Build it live

You will write the tool most games need first: a checker for the map. Rooms are data (Chapter V), doors are entries in that data, and a typing slip in one of them is a door that leads nowhere. The checker reads the whole table and says everything that is wrong with it.

In Little Hours

Little Hours has more tools than most games its size, because its author draws and writes rather than programs. Almost none are editor plugins. They are flags on the game itself, scripts beside it, and a set of editors that run in a browser.

The game is its own tool

The most used tools in the project are the game, started with a word after --. Main.gd reads the user arguments at the top of _ready() and, for most flags, does one job and quits before any play begins. This is the smallest:

There are a couple of dozen flags like it. --test runs the suite of Chapter W; --rooms photographs rooms into a folder; --dump writes every line of the game's writing out as JSON:

A --script tool: the icons

The interface icons are made by a GDScript tool, godot/tools/PixelIcons.gd, run with --headless and --script. It extends SceneTree and does everything in _initialize():

../tools/PixelIcons.gd · lines 38–71

func _initialize() -> void:
	DirAccess.make_dir_recursive_absolute(ProjectSettings.globalize_path(OUT))
	var made := 0
	for file in DirAccess.get_files_at(SRC):
		if not file.ends_with(".svg"):
			continue
		var out := ProjectSettings.globalize_path("%s/%s.png" % [OUT, file.get_basename()])
		if KEEP.has(file.get_basename()):
			_double_if_small(out)
			continue
		var svg := FileAccess.get_file_as_string("%s/%s" % [SRC, file])
		var best: Image = null
		if _on_grid(svg):
			best = _render(svg, SIZE, Vector2.ZERO)
		else:
			var best_score := -1.0
			for off in OFFSETS:
				var img := _render(svg, CUT, off)
				if img == null:
					continue
				var score := _crispness(img)
				if score > best_score:
					best_score = score
					best = img
		if best == null or best.get_width() != best.get_height():
			push_error("could not render %s" % file)
			continue
		_threshold(best)
		if best.get_width() != SIZE:
			best.resize(SIZE, SIZE, Image.INTERPOLATE_NEAREST)
		best.save_png(out)
		made += 1
	print("%d icons written to %s" % [made, ProjectSettings.globalize_path(OUT)])
	quit()

Read it as a pipeline. For each .svg in the source folder: skip the ones drawn by hand (KEEP), render the drawing small – trying four half-pixel nudges and keeping the crispest – force every pixel fully on or off, scale up with INTERPOLATE_NEAREST, and save a PNG. Then report a count and quit(). The SVGs stay as the source; the PNGs are output. Every rule from the art section is here, in GDScript, using the Image class (UI).

The other is CharParts.gd, the table of where each piece of the drawn character sits on its sheet, which explains why its data is a script at all:

## Baked from the artist's own sheets rather than read from them at runtime: the

## bad way to find that out on a phone.

The last paragraph of that comment is Chapter X's warning turned into a design decision. A loose .json can be left out of an export; a constant in a script cannot. Generating GDScript rather than a data file is one way to make sure the data ships.

The character baker says why converters exist at all:

../../tools/bake-char.py · lines 18–21

Why bake at all: the sheets need cutting up by their dots, the dots need
removing (they are registration marks, not art), and every hairstyle needs
rendering in fourteen colours. None of that is work a game should be doing
while somebody waits to press Start.

The artist draws eleven hairstyles once, in one colour, with two dots where the eyes go. The script cuts them apart, lines each up with the body by those dots, removes the dots, and renders every style in every hair colour. That is work done once on a developer's machine so that it is not done every time a player starts the game.

The round trip to Aseprite has a bug story worth a line of your memory. Each layer of the exported file carries a note of which game file it came from, and the script that writes that note says:

../../tools/sprites-to-aseprite.lua · lines 11–14

-- Where it came from and where it sits, for sprites-from-aseprite.lua.
-- %d, not .. : the numbers arrive from JSON as floats and concatenate as
-- "102.0", which the reader's whole-number pattern then never matches.
layer.data = string.format("%s|%d|%d|%d|%d", l.rel, l.x, l.y, l.w, l.h)

This is Lua, but the trap is the one from Chapter S: numbers read from JSON arrive as floats. Joined into text they became 102.0, and the script reading them back, expecting whole numbers, matched nothing and wrote nothing. Tools pass data to each other as text, and text is where an int and a float stop looking alike.

Little Hours Studio

The folder editors/ is the largest tool: Little Hours Studio, a set of editors that run in a web browser. A small Python program serves them from the developer's own machine, and they save straight into the game's data and art folders. There is a tab for the map of the town and the furniture in each room, one for branching conversations, one for writing the townspeople's stories in Twine and one for checking what the game will make of them, and others for the art, the sprites and a catalogue of every picture (Talk). Every editor saves by itself a few seconds after the last change and keeps dated backups, because its user is a writer, not someone who should have to think about version control.

The studio is not written in GDScript, and that is the point: a tool should be built from whatever makes it easiest to use. But it has to agree with the game about what a room looks like, and it does that the generator's way. The file it reads begins:

../../editors/rooms.js · lines 1–2

// Made by `Godot --path godot -- --editor-reference` (godot/tests/EditorRef.gd)
// from the game itself. Do not edit by hand: run that again instead.

The game writes the studio's picture of itself. -- --editor-reference runs the real room-building code and writes every room, every piece of art and every size into this file; the release script of Chapter X runs it each time, so the editor can never start a room from a layout the game has stopped building. Where two programs must share a rule that cannot be generated – how a Twine story is read, which exists once in GDScript (TwineBook) and once in JavaScript – each side has tests running the same cases.

func _exit_tree() -> void:
	for d: Control in [_studio_dock, _ai_dock]:
		if d != null:
			remove_control_from_docks(d)
			d.queue_free()
	if runner != null:
		runner.queue_free()

_enter_tree() reads the project's studio settings, then creates two panels and adds them to a dock on the right of the editor: one with buttons that open the browser editors and run the project's named commands, one for a coding assistant. _exit_tree() removes and frees exactly what was added. The description in the label makes a point worth copying: the scripts the game needs from this add-on work without the plugin being switched on, so a broken editor panel can never stop the game running.

One GDExtension

Little Hours uses native code in exactly one place: the small language model behind the neighbours' small talk (the small-talk AI). Running a language model is the textbook case for GDExtension – the work is already done in a native library, and no amount of GDScript would replace it. The extension's own file lists what is shipped:

../addons/nobodywho/nobodywho.gdextension · lines 7–13

[libraries]

One library per platform and processor, and only for the platforms the game ships on: two kinds of Mac, and 64-bit Android phones. There is no web entry, which is why the Web preset in Chapter X has extensions switched off. The libraries are too large to keep in version control, so a script in tools/ fetches them. And because a library might be missing, TownMind.gd never assumes it is there:

TownMind.gd · lines 80–81

static func plugin_present() -> bool:
	return ClassDB.class_exists("NobodyWhoChat") and ClassDB.class_exists("NobodyWhoModel")

ClassDB.class_exists() asks the engine whether a class by that name was registered. If the extension did not load, the answer is no, and every neighbour keeps the small talk that was written for them. That is the cost of native code handled properly: the game has a version of itself that works without it.

Your turn

Five small tools: two that read a command line, a checker to mend, a generator, and an audit of an art folder.

What to remember

  • A tool is a program for you: a checker that reports problems, a generator that writes what you would not type, or a converter that turns an artist's file into the game's. Write one when a job repeats or when its mistakes are silent.
  • @tool runs a script in the editor and EditorScript runs one once; both can change your scene for good, so guard them and commit first. A plugin is plugin.cfg plus an EditorPlugin that removes in _exit_tree() everything it added in _enter_tree().
  • Godot is a command-line program too: --headless, --script, --import, --export-release, and your own flags after --, read with OS.get_cmdline_user_args(). A tool reports failure with its exit code, and proves success with a line it only prints at the end.
  • In an art pipeline there is one source a person edits and outputs a script makes. Outputs say they are generated, are made the same way every time, and are never edited by hand.
  • GDExtension is for native libraries that already exist and for slowness you have measured. Try a better algorithm first, and keep the game working when the library is missing.
  • A tool that touches the real game needs a sandbox, so that checking the game can never damage somebody's save.
