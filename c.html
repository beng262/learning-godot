Children and the scene tree

Parents, children, node paths, $Name, scenes inside scenes, groups, and why the tree is the game.

In this chapter

  • what a parent does for its children: place, visibility, life and order
  • reaching another node – paths, $Name, %UniqueName, get_node and get_node_or_null
  • adding, removing and freeing nodes while the game runs, and putting scenes inside scenes
  • groups, and the order in which the tree draws and wakes up

One parent, many children

Every node has exactly one parent – except the one at the very top – and any number of children. That one rule is what turns a pile of nodes into a game.

Chapter A said a character is not one big object: it is a node with a picture node and a sound node underneath it. "Underneath" is the word to look at. Putting node B under node A makes B a child of A and A the parent of B, and a parent does four things for its children without being asked:

A parent gives its childrenWhich means
A placeA child's position, rotation and scale are measured from its parent, not from the corner of the screen. Move the player and the sprite, the shadow and the camera under it all come too.
VisibilityHide a parent and everything under it is hidden. One line closes a whole menu.
A lifetimeFree a parent and everything under it is freed. Nothing is left behind to clean up.
A turnThings are drawn, and woken up, in the order they sit in the tree. Where a node is in the list decides when its turn comes.

The first of those is the one you feel straight away. Slide the parent about, then rotate it: the child's own position never changes, because it is still the same distance from its parent.

A tree you can run

The page has no engine in it, so it cannot make real nodes. It can do something more useful for learning: build a model of a node out of plain GDScript, small enough to see all of. A model node needs three things – a name, a parent and a list of children:

extends Node

class MiniNode:
	var name := ""
	var parent: MiniNode = null
	var children: Array = []

	func _init(n: String) -> void:
		name = n

	func add_child(child: MiniNode) -> void:
		child.parent = self
		children.append(child)

func _ready() -> void:
	var main := MiniNode.new("Main")
	var player := MiniNode.new("Player")
	var sprite := MiniNode.new("Sprite")
	var hud := MiniNode.new("HUD")
	main.add_child(player)
	main.add_child(hud)
	player.add_child(sprite)

	print(sprite.name, "'s parent is ", sprite.parent.name)
	print(main.name, " has ", main.children.size(), " children")
	print(main.name, "'s parent is ", main.parent)

class MiniNode: describes a kind of object, and MiniNode.new("Main") makes one; Chapter H is about classes, and for now it is enough to read the indented part as "every MiniNode has these variables and can do these things". The interesting line is in add_child: it writes the link in both directions. The parent adds the child to its list, and the child is told who its parent is. Godot's own add_child() does the same two things.

Press Edit and run and change player.add_child(sprite) to hud.add_child(sprite). The first line follows. The last line prints <null>: the top of this tree has nobody above it.

One parent, and Godot means it

The model above would let you add sprite to two parents and leave the tree in a muddle. Godot will not. Adding a node that already has a parent prints an error like Can't add child 'Sprite' to 'HUD', already has a parent 'Player'. and does nothing. To move a node you take it out of one parent first – or call reparent(), which does both halves for you.

The real thing

On a real node the same links are read with these. None of them searches: each one looks only at the node's own parent or its own children.

extends Node2D

func _ready() -> void:
	print(get_parent().name)        # <1>
	print(get_child_count())        # <2>
	for child in get_children():    # <3>
		print(child.name)
	print(get_child(0).name)        # <4>
	print(get_index())              # <5>
  1. The node above this one.
  2. How many children this node has – grandchildren are not counted.
  3. The children as an Array, in the order they appear in the Scene dock.
  4. One child by its place in that order. 0 is the first.
  5. This node's own place among its brothers and sisters.

A place: positions add up

Here is the first of the four gifts, in the model. Each node keeps a position measured from its parent, and where it ends up on the screen is every position on the way up, added together:

extends Node

class MiniNode:
	var name := ""
	var parent: MiniNode = null
	var children: Array = []
	var position := Vector2.ZERO

	func _init(n: String, at: Vector2) -> void:
		name = n
		position = at

	func add_child(child: MiniNode) -> void:
		child.parent = self
		children.append(child)

	func global_position() -> Vector2:
		if parent == null:
			return position
		return parent.global_position() + position

func _ready() -> void:
	var room := MiniNode.new("Room", Vector2(100, 40))
	var player := MiniNode.new("Player", Vector2(30, 60))
	var hat := MiniNode.new("Hat", Vector2(0, -12))
	room.add_child(player)
	player.add_child(hat)

	print("Hat, from its parent: ", hat.position)
	print("Hat, on the screen:   ", hat.global_position())
	player.position.x += 50
	print("After the player walks 50 to the right:")
	print("Hat, from its parent: ", hat.position)
	print("Hat, on the screen:   ", hat.global_position())

Nobody moved the hat. Its position is still twelve pixels above the player's head, and it is fifty pixels further right on the screen all the same. Change the room's Vector2(100, 40) and everything in the room shifts. Real nodes have exactly these two: position, from the parent, and global_position, on the screen. (The real one also folds in each parent's rotation and scale, which a sum cannot do. Chapter L does it properly.)

Parent is not owner

A node has a second link upwards, owner, and the two are easy to mix up. The parent is the node directly above. The owner is the root of the scene the node was saved as part of – for every node you place in the editor, that is the node at the top of the Scene dock, however deep the node sits. Godot uses the owner to decide which nodes belong in a .tscn file when it saves one. A node you create in code has no owner unless you give it one, and most games never need to.

Finding a node: paths, $ and %

A script lives on one node and nearly always needs to talk to another. A node path is the set of directions from here to there.

A node path is a list of names with / between them, read from left to right: "go to my child called Player, then to its child called Sprite". It starts from the node the script is on, so the same path means different things in different scripts. Click the nodes in this tree and read the path to each from Main:

Add a Sprite2D under Room and its path appears. Delete Player and three paths stop existing at once. Paths are not stored anywhere – they are worked out from the names in the tree, every time, which is why renaming a node breaks the code that looked for the old name.

Ways to write one

extends Node2D   # this script is on Main

func _ready() -> void:
	var a = get_node("Player")            # <1>
	var b = get_node("Player/Sprite")     # <2>
	var c = $Player/Sprite                # <3>
	var d = $"Day Label"                  # <4>
	var e = b.get_node("../Camera2D")     # <5>
	var f = get_node("/root/Main/HUD")    # <6>
  1. A child, by name. get_node() takes the path as text.
  2. A grandchild: one name per step down.
  3. $ is shorthand for get_node() with the path written straight after it. It is the same call, and it is the form you will see most.
  4. A name with a space in it needs quotes after the $.
  5. .. means "my parent". Asked from Sprite, this goes up to Player and down again to its other child.
  6. A path that begins with / is absolute: it starts from the top of the running game, which is always called root, whichever node asks.

A path is a value of its own type, NodePath. You rarely write the type: text is turned into a NodePath wherever one is expected. You meet it by name in the Inspector, where a property of that type shows an Assign… button instead of a text box.

Going up a tree is easy, because each node has one parent. This model asks every node for its absolute path by walking up until there is nobody left:

extends Node

class MiniNode:
	var name := ""
	var parent: MiniNode = null
	var children: Array = []

	func _init(n: String) -> void:
		name = n

	func add_child(child: MiniNode) -> void:
		child.parent = self
		children.append(child)

	func get_path() -> String:
		if parent == null:
			return "/root/" + name
		return parent.get_path() + "/" + name

func _ready() -> void:
	var main := MiniNode.new("Main")
	var player := MiniNode.new("Player")
	var sprite := MiniNode.new("Sprite")
	main.add_child(player)
	player.add_child(sprite)

	print(sprite.get_path())
	print("The steps down to it: ", "Player/Sprite".split("/"))

Rename the player – change "Player" to "Wren" – and the path changes with it, without anything being updated. Real nodes have get_path() too. Going down is the harder direction, because a node has many children and you have to pick the right one at each step. The last line shows how a path splits into those steps, and writing the lookup yourself is this chapter's live tutorial.

When the node is not there

get_node() and $ expect to succeed. If no node is at the end of the path, Godot reports Node not found: "Plyer" (relative to "/root/Main")., hands back null, and the next line – the one that tries to use it – fails with an error about a null instance. Read the first error, not the second: it has the misspelt name in it.

When a node might honestly not exist – the player may have been freed, a room may have no lamp – ask with the version that treats "not there" as an ordinary answer:

func switch_off_the_lamp() -> void:
	var lamp := get_node_or_null("Room/Lamp")
	if lamp == null:
		return              # this room has no lamp: nothing to do
	lamp.visible = false

func has_a_lamp() -> bool:
	return has_node("Room/Lamp")

The trap: asking too early

A script's variables are set up when its node is created, and at that moment the node is not in the tree and has no children. A path asked for then finds nothing. Paths work from _ready() onwards, and @onready exists to say "set this variable at that moment":

extends Node2D

var too_early = $Sprite                  # runs before there is a tree: an error, and null
@onready var sprite: Sprite2D = $Sprite  # runs just before _ready(): works

func _ready() -> void:
	sprite.flip_h = true

Keeping the node in a variable has a second benefit. The path is walked once, and the name is written in one place, so a rename is one edit and not a hunt.

% – a name that survives rearranging

A path spells out every step, so moving a node deeper breaks it: $HUD/DayLabel stops working the day you tidy the label into $HUD/TopBar/Row/DayLabel. For nodes you reach for often, Godot has scene-unique names. Right-click the node in the Scene dock and choose Access as Unique Name; a % appears beside it. From then on any script in that scene finds it by name alone, wherever it sits:

@onready var day_label: Label = %DayLabel     # the same as get_node("%DayLabel")

func _on_day_changed(day: int) -> void:
	day_label.text = "Day %d" % day

Two limits keep it honest: the name must be unique within its scene, and % only sees nodes of the scene the script's node belongs to – this is one of the jobs of the owner link. Interface scenes, which are deep and get rearranged constantly, are where it earns its keep.

Reach down, not up

A path to your own children – $Sprite – is safe: the scene you are in decides whether it is right. A path that climbs – get_node("../../HUD/Score") – assumes things about wherever this scene has been placed, and breaks when it is placed somewhere else. The habit that keeps scenes reusable is: call down, signal up. A parent calls methods on its children; a child that needs something from above announces it with a signal (Chapter J) and lets whoever is up there decide.

Growing and pruning the tree

The tree in the Scene dock is only where a game starts. Coins appear, enemies are removed, menus are built and thrown away – all by changing the tree while it runs.

Adding

Any node type can be made in code with .new(). A new node is not part of the game until it has a parent: it is not drawn, it does not run, and its _ready() has not been called. add_child() is the moment it joins.

func spawn_label(words: String) -> void:
	var label := Label.new()       # <1>
	label.text = words             # <2>
	label.position = Vector2(8, 8)
	add_child(label)               # <3>
  1. A node that exists but is nowhere. Nothing shows yet.
  2. Set it up while it is still outside the tree.
  3. Now it is a child of this node, at the end of the list of children – and its _ready() runs during this call, seeing the values set above.

Removing is not freeing

There are two ways to take a node out, and they are not the same thing:

CallWhat happensUse it when
parent.remove_child(node)The node leaves the tree at once, with everything under it, but still exists. It can be added back, here or somewhere else.You will put it back: a card set aside, an item moved from the floor to a bag.
node.queue_free()The node, and everything under it, is deleted for good at the end of the current frame.It is finished with: a collected coin, a closed menu.

queue_free() waits for the end of the frame on purpose. A node is often freed from inside its own code, or while a signal it sent is still being handled, and deleting it in the middle of that would pull the floor from under whatever is still running. So until the frame ends the node is still there, still a child, and still counted by get_children(). There is also a plain free() that deletes immediately; leave it alone until you know why you need it.

A node that was removed and never freed or re-added is the one way to leak memory with nodes: it belongs to nobody, so nobody frees it. And a variable that pointed at a freed node does not become null – check it with is_instance_valid(node) before you use it.

The model shows the difference between "out of the tree" and "gone". Removing a branch takes its children with it, and the branch is still whole afterwards:

extends Node

class MiniNode:
	var name := ""
	var parent: MiniNode = null
	var children: Array = []

	func _init(n: String) -> void:
		name = n

	func add_child(child: MiniNode) -> void:
		child.parent = self
		children.append(child)

	func remove_child(child: MiniNode) -> void:
		children.erase(child)
		child.parent = null

	func count() -> int:
		var total := 1
		for child in children:
			total += child.count()
		return total

func _ready() -> void:
	var main := MiniNode.new("Main")
	var world := MiniNode.new("World")
	var player := MiniNode.new("Player")
	main.add_child(world)
	main.add_child(MiniNode.new("HUD"))
	world.add_child(player)
	player.add_child(MiniNode.new("Sprite"))
	player.add_child(MiniNode.new("Shadow"))
	print("Nodes in the tree: ", main.count())

	world.remove_child(player)
	print("After removing Player: ", main.count())
	print("Player still exists, with ", player.children.size(), " children of its own")

	main.add_child(player)
	print("Added back under Main: ", main.count())

count() is worth a second look: a node counts itself, then asks each child to count itself the same way. A function that calls itself on each child is how nearly everything is done to a tree, and you will write one in the tutorial. Try removing world from main instead and predict the three numbers first.

Scenes inside scenes

Building a coin from .new() calls every time you want one would be tedious, and it is what scenes are for. A scene is a saved branch; placing a copy of that branch into a tree is called instancing it.

In the editor: build the coin as its own scene and save it as coin.tscn. Open the level, select the node the coin should go under, and press the chain-link button beside + in the Scene dock – Instantiate Child Scene – or drag coin.tscn from the FileSystem dock into the viewport. The coin appears as a single line in the level's tree, with its insides folded away. Edit coin.tscn later and every coin in every level changes. To go the other way – you built something inside a level and want it as a scene of its own – right-click its top node and choose Save Branch as Scene….

In code it is two steps, load the scene and make a copy of its branch:

extends Node2D

const COIN := preload("res://coin.tscn")   # <1>

func drop_coin(at: Vector2) -> void:
	var coin := COIN.instantiate()         # <2>
	coin.position = at                     # <3>
	add_child(coin)                        # <4>
  1. preload() reads the file once, when this script is loaded, and gives back a PackedScene: the recipe, not a coin.
  2. instantiate() follows the recipe and returns the root node of a brand-new copy, with all its children already under it.
  3. Still outside the tree, so set it up first.
  4. In it goes. Call drop_coin() ten times and there are ten separate coins.

The idea in the model: a function that builds a fresh branch each time it is called stands in for the packed scene.

extends Node

class MiniNode:
	var name := ""
	var parent: MiniNode = null
	var children: Array = []
	var value := 1

	func _init(n: String) -> void:
		name = n

	func add_child(child: MiniNode) -> void:
		child.parent = self
		children.append(child)

# The "packed scene": a recipe for one coin branch.
func instantiate_coin() -> MiniNode:
	var coin := MiniNode.new("Coin")
	coin.add_child(MiniNode.new("Sprite"))
	coin.add_child(MiniNode.new("Area"))
	return coin

func _ready() -> void:
	var level := MiniNode.new("Level")
	for i in 3:
		level.add_child(instantiate_coin())

	level.children[0].value = 50
	for coin in level.children:
		print(coin.name, " is worth ", coin.value, " and has ", coin.children.size(), " children")

Three coins from one recipe, and changing one leaves the others alone: each is its own branch. Add a third child to the recipe – a "Sparkle" – and all three coins have it, which is what editing coin.tscn does to a real game. (Three siblings all called Coin is something only the model allows. Godot renames a newcomer whose name is taken, to something like Coin2, so that every path still leads to one node.)

Tree order: whose turn it is

A tree has an order – top of the Scene dock to the bottom, each node followed by everything under it. Godot uses that order for nearly everything, and in one important case uses it backwards.

Read the Scene dock like an indented list, top to bottom, and you have tree order: a node, then its first child and everything under that, then its second child, and so on. Two things follow it:

  • Drawing. Nodes are drawn in tree order, each on top of what came before. So a node lower in the dock is in front, and a child is drawn over its parent. (z_index and y-sorting can overrule this; Chapter L.)
  • Entering. When a branch joins the game, each node's _enter_tree() runs in tree order: parents before their children.

And one goes the other way. _ready() is called on a node only when all of its children are ready – so it runs children first, and the root of a scene is the last to hear it. That is deliberate: by the time a node's _ready() runs, everything under it is set up and safe to use.

extends Node

class MiniNode:
	var name := ""
	var children: Array = []

	func _init(n: String, kids: Array) -> void:
		name = n
		children = kids

func tree_order(node: MiniNode, out: Array) -> void:
	out.append(node.name)             # me first...
	for child in node.children:
		tree_order(child, out)        # ...then each child, top to bottom

func ready_order(node: MiniNode, out: Array) -> void:
	for child in node.children:
		ready_order(child, out)       # every child first...
	out.append(node.name)             # ...then me

func _ready() -> void:
	var main := MiniNode.new("Main", [
		MiniNode.new("Room", [MiniNode.new("Bed", []), MiniNode.new("Lamp", [])]),
		MiniNode.new("Player", [MiniNode.new("Sprite", [])]),
		MiniNode.new("HUD", []),
	])
	var drawn: Array = []
	tree_order(main, drawn)
	print("drawn, back to front: ", ", ".join(drawn))
	var woken: Array = []
	ready_order(main, woken)
	print("_ready() is called:   ", ", ".join(woken))

The two functions differ by one thing: whether the node adds itself before its children or after. Swap Room and Player in the list and run it again – the player is now drawn first, so the bed would be painted over her. In the editor you make that change by dragging a node up or down in the Scene dock; in code, with move_child(node, index).

What you can rely on in _ready()

Your children, always: they went first. Your parent, no: its _ready() has not run yet. Your brothers and sisters, only the ones above you in the dock. This is the second reason to reach down rather than up or sideways – it is the only direction that is guaranteed to be ready. Chapter I follows these calls frame by frame.

Groups: finding nodes by what they are

A path finds a node by where it is. A group finds nodes by what they are, wherever they have ended up.

"Every enemy", "everything that can be watered", "all the lamps": these are scattered across the tree, they come and go, and no path describes them. A group is a label you put on nodes. A node can carry several, and the tree keeps a list for each label.

In the editor, select a node, open the Node dock beside the Inspector and switch it from Signals to Groups. In code:

# on each lamp
func _ready() -> void:
	add_to_group("lamps")

# anywhere else
func night_falls() -> void:
	for lamp in get_tree().get_nodes_in_group("lamps"):   # <1>
		lamp.visible = true
	get_tree().call_group("lamps", "flicker", 0.5)        # <2>

func _on_body_entered(body: Node) -> void:
	if body.is_in_group("enemies"):                       # <3>
		take_damage()
  1. get_tree() is the running tree itself. It hands back every node carrying the label, in tree order; an unknown label gives an empty Array, not an error.
  2. Calls flicker(0.5) on every lamp, in one line.
  3. The commonest use of all: "is the thing I touched one of those?"

Nothing about a group is magic. It is a lookup from a label to a list of nodes, which you already have the tools to build:

extends Node

class MiniNode:
	var name := ""
	var lit := true

	func _init(n: String) -> void:
		name = n

	func switch_off() -> void:
		lit = false
		print(name, " goes dark")

class MiniTree:
	var groups := {}    # label -> Array of nodes

	func add_to_group(node: MiniNode, label: String) -> void:
		if not groups.has(label):
			groups[label] = []
		if not groups[label].has(node):
			groups[label].append(node)

	func get_nodes_in_group(label: String) -> Array:
		return groups.get(label, [])

	func call_group(label: String, method: String) -> void:
		for node in get_nodes_in_group(label):
			Callable(node, method).call()

func _ready() -> void:
	var tree := MiniTree.new()
	var lamp := MiniNode.new("Lamp")
	var candle := MiniNode.new("Candle")
	var kettle := MiniNode.new("Kettle")
	tree.add_to_group(lamp, "lights")
	tree.add_to_group(candle, "lights")
	tree.add_to_group(candle, "can_burn")

	print("lights: ", tree.get_nodes_in_group("lights").size())
	print("ghosts: ", tree.get_nodes_in_group("ghosts").size())
	tree.call_group("lights", "switch_off")
	print("Is the kettle still on? ", kettle.lit)

A dictionary whose keys are labels and whose values are lists: that is a group. Put the kettle in "lights" and it goes dark with the rest. Callable(node, method) is "that method on that node, as a value you can call" – Chapter F explains Callables. One thing the real tree does for you that this model does not: a freed node is taken out of its groups automatically.

Group or signal?

Use a group when the caller knows what kind of thing it wants and does not care how many there are: "all lamps, switch off". Use a signal when the sender should not know who is listening at all: "night has fallen", and lamps, shops and owls each decide what that means. Many games use both.

Build it live

You have called get_node() in listings. Now write it. Five steps turn a bare model node into a tree that can find any node from any other by a path, including ...

In Little Hours

Little Hours has one scene with one node in it, so its whole tree is grown by add_child() at the moment the game starts. That makes it an unusually clear place to watch a tree being built.

Chapter A showed the game's only .tscn: a Node2D called Main with a script. Everything else is added in that script's _ready(). This is the start of it – the world, before the interface:

Main.gd · lines 163–184

_room_view = RoomView.new()
add_child(_room_view)

_decor = DecorLayer.new()
add_child(_decor)

_partner = Player.new()
_partner.who = "partner"
_partner.bounds = Game.BOUNDS
add_child(_partner)

_player = Player.new()
_player.bounds = Game.BOUNDS
add_child(_player)
_player.arrived.connect(_on_player_arrived)

_dog = Pet.new()
add_child(_dog)
_dog.bounds = Game.BOUNDS
_dog.setup("dog", str(Game.state["dog_breed"]), Game.dog_coat())
_dog.follow_target = _player
_dog.mode = "follow"

Three of this chapter's ideas are in those lines.

The order of the add_child() calls is the tree order. The room goes in first, then the furniture the player has placed, then the partner, the resident and the dog. Each lands at the end of Main's children, so that is the order they sit in and the order they would draw in: the room at the back, the people over it. (Within the room the game then sorts by z_index, so that someone standing behind a sofa is hidden by it – Chapter L.)

What is set before add_child() is seen by _ready(). The partner is told who = "partner" while still outside the tree, and one line later add_child(_partner) runs the new node's _ready(). Here is what that _ready() does, in Player.gd:

Player.gd · lines 100–109

func _rebuild_avatar() -> void:
	if _avatar != null and is_instance_valid(_avatar):
		remove_child(_avatar)
		_avatar.queue_free()
	if _drawn():
		_avatar = DRAWN.new()
	else:
		_avatar = Avatar.new()
	add_child(_avatar)
	refresh_look()

Player._ready() is one line, a call to this. It chooses which kind of body to build by asking _drawn(), which reads who – so who has to be right before the node joins the tree, and in Main it is. The function is also the swap you learnt in "Growing and pruning": if there is an old body, remove_child() takes it out of the tree now and queue_free() deletes it at the end of the frame; then a new one is made and added. The character is a parent whose only job is to carry a body and be moved around; the body is a child that can be replaced without the rest of the game noticing.

A class made twice is the game's version of instancing a scene. Further down the same _ready(), Pet.new() is called once for the dog and once for the cat, and each is then told what it is with setup("dog", …) or setup("cat"). One recipe, two separate branches – the same idea as preload("res://pet.tscn").instantiate(), written as a class because this game keeps everything in code. Animals is about what the two of them then do.

Emptying a parent

The bar of chips and buttons over the game is a child of the HUD, and when the colour palette changes the HUD does not repaint it: it throws the whole branch away and builds a new one. The rebuild starts like this:

HUD.gd · lines 66–70

# Detach before freeing: queue_free() is deferred, so leaving the old root as
# a child would draw two HUDs for a frame.
for c in get_children():
	remove_child(c)
	c.queue_free()

The loop is the idiom to remember, and the comment says why both lines are needed. queue_free() alone would leave the old interface as a child until the end of the frame – and the new one is added a few lines later, in this same frame, so for one frame there would be two. remove_child() takes each child out immediately; queue_free() then makes sure it is deleted and not left as an orphan. Freeing the one root node frees every chip and button under it: the lifetime a parent gives its children, doing real work. The same two lines clear the reply buttons before each new question in a conversation (Talk), and clear a room of its furniture each time you walk into another one (Map, rooms and doors).

Asking upwards, carefully

The HUD is a child of Main – a little further down that long _ready() are the lines _hud = HUD.new() and add_child(_hud). Once a second the HUD decides whether the telephone should ring, and there is one thing it needs to know that only its parent can tell it:

HUD.gd · lines 760–782

## Does the phone ring? Once a second, not every frame — what makes it ring is
## the clock, and Game.incoming_call() walks the town to decide.
func _tick_ring(delta: float) -> void:
	if _ringing != "":
		return
	_ring_check -= delta
	if _ring_check > 0.0:
		return
	_ring_check = 1.0
	# Not while somebody is talking to her: the ring covered the conversation,
	# and the next tap declined the call or answering replaced the scene.
	var main := get_parent()
	if main != null and main.has_method("_talking") and bool(main.call("_talking")):
		return
	var who := Game.incoming_call()
	if who == "":
		return
	_ringing = who
	Sfx.play("ring", -10.0)
	if _phone != null and is_instance_valid(_phone):
		_phone.visible = true
		_phone.buzz()
	_open_phone()

The phone must not ring over a conversation, and whether anybody is talking is Main's knowledge. So the HUD reaches up with get_parent() – the direction this chapter told you to be wary of – and look how warily it does it. Before it calls anything it checks that there is a parent and that the parent has_method("_talking"); only then does main.call("_talking") call that method by name. If the HUD were ever placed under some other node, the check would fail quietly and the phone would ring as usual, where a bare get_parent()._talking() would stop the game. When you do have to reach up, this is the shape to copy. The cleaner design, for a new game, is for the parent to tell the child what it needs to know. Phone covers what happens once it rings.

What the game does not use

Search the game's scripts for $ paths, get_node() or groups and you will find none. Because Main creates every node itself, it already holds each one in a variable – _player, _dog, _hud – the moment it is made, and a variable is a reference that no rename can break. Paths and groups earn their keep in projects built in the editor, where the nodes exist before any code runs and a script has to find them. Both ways are ordinary Godot. Inside the code has the rest of what Main assembles.

Your turn

Six exercises on the model tree. Each starts with a MiniNode class that already has what earlier exercises built, so you only write the new part.

What to remember

  • Every node has one parent. A parent gives its children a place, visibility, a lifetime and a turn: move, hide or free the parent and the children follow.
  • A path is directions from the node that asks: names joined by /, .. for up. $Name is get_node("Name"); %Name finds a scene-unique node wherever it sits; get_node_or_null() is for nodes that may not be there.
  • Paths work from _ready() on – use @onready. Reach down to your children; let children signal up.
  • add_child() is when a node joins the game and its _ready() runs. remove_child() takes it out but keeps it; queue_free() deletes it, and its branch, at the end of the frame.
  • A scene is a saved branch: preload("res://coin.tscn").instantiate() makes a fresh copy to add.
  • Tree order is drawing order, back to front. _ready() runs the other way: children before parents. Groups find nodes by what they are, not where.
