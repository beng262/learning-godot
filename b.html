Building in the editor

The docks, the viewport, the Inspector and the Output, learned by using them – with a working copy of the editor in the page.

In this chapter

The window, dock by dock

The editor looks like a cockpit the first time you open it. It is a centre with a handful of panels round it, each with one job, and you will spend nearly all your time in four of them.

Open a project and this is what is on the screen. The panels at the sides are called docks.

PartWhere it starts outIts job
Scene dockleft, upperThe tree of nodes in the scene you are editing. Nodes are added, renamed, reordered and deleted here.
FileSystem dockleft, lowerEvery file in the project folder, shown from res://. Scenes are opened from here; pictures and sounds are dragged out of here.
The main viewcentreWhatever you are working on, chosen by the buttons above it: 2D and 3D show the scene, Script shows code, Game shows the game while it runs.
Inspector dockrightEvery property of the selected node, ready to edit.
Node dockright, a tab beside the InspectorThe selected node's signals, and the groups it is in.
The bottom panelbelow the main viewOutput – what the game prints. Debugger – errors, and the state of the game when it is paused. A few specialist editors live here too.
The run buttonstop right cornerStart the game, pause it, stop it.

Docks can be dragged to other places, and their starting arrangement has shifted a little between versions of Godot. Learn them by name and by job, not by position – every tutorial and every answer online refers to them by name.

The thread through all of it: the selection

Nearly everything in the editor acts on the node that is selected in the Scene dock. The Inspector shows that node. Add Child Node adds under that node. Attach Script attaches to that node. When something lands in the wrong place, the first question is always "what was selected?"

Five moves: add, set, attach, connect, run

Building in Godot is the same five moves over and over: add a node, set its properties, attach a script, connect a signal, run it. Here is a working copy of the editor to make them in.

The layout below is Godot's own, at a small scale: Scene and FileSystem on the left, the view in the middle with 2D and Script above it, the Inspector and Node docks on the right, the Output underneath. On a phone the docks are behind the four tabs along its top. A small game is already loaded. It is the same editor as on the workshop page and shares what you build with it.

If you have already changed the scene, press Start over under the editor so that what you see matches what follows. Then make the moves in order. Each one says what you should see when it has worked.

  1. Look before you touch

    Click each node in the Scene dock in turn. Three things change together every time: the highlighted line in the dock, the orange box in the view, and the name at the top of the Inspector. Tick gets no box – a Timer has no place on the screen. Two small marks are worth learning now: 📜 beside a node means it has a script (Main and Player do), and ⇢ means one of its signals is connected (Tick).

  2. Add a node

    Select Main. Press ＋ Add, type lab in the search box and pick Label. You should see a new line, Label, at the bottom of the tree, one step in from Main and already selected – and the word Hello near the top left of the view. Double-click the new line and rename it Hint. The new node became a child of Main because Main was selected; had Player been selected, it would be the player's child.

  3. Set its properties

    With Hint selected, go to the Inspector. Change text to Walk to the coin, and position to x 100, y 150. You should see the words change as you type and the label jump to the bottom of the view. Now drag the label a little way in the view and let go: the Inspector's numbers have followed. The view and the Inspector are two handles on the same value. Open Scene file (.tscn) under the view and find [node name="Hint" type="Label" parent="."] – beneath it are position and text, the two things you changed, and nothing else.

  4. Attach a script

    With Hint still selected, press Script at the top of the Scene dock. You should see the middle switch to the Script tab with a new script in it – extends Label, an empty _ready() and an empty _process() – plus a 📜 beside Hint and a hint.gd in the FileSystem dock. Under _ready(), replace the line that starts pass with text = "Arrow keys to walk", keeping its one tab of indent. Switch back to the 2D tab. Nothing has changed there, and that is correct: a script does nothing until the game runs.

  5. Run

    Press ▶ Run. You should see the Output print --- Running main.tscn ---, then Hello from Player, then a tick line every second – and in the view, the hint now reads Arrow keys to walk. Click the view and walk about. Press ■ Stop: the hint says Walk to the coin again. That is the most important thing on this page. The Inspector sets how a node starts, and that is what is saved. Code changes the running game, and stopping throws the running game away.

  6. Connect a signal

    Select Main and add a Button. Rename it Hide and, in the Inspector, set its text to Hide hint. With the button selected, switch the right-hand dock from Inspector to Node: these are the signals a Button can send. Beside pressed(), press Connect…. You should see the editor jump to Main's script, with a new empty function at the bottom called _on_hide_pressed(). Replace its pass line with $Hint.visible = not $Hint.visible. Back in the Scene dock, Hide has gained a ⇢, and the last line of the scene file is now a [connection …] from Hide to that method.

  7. Run again

    Go to the 2D tab and press ▶ Run. Click Hide hint in the view. You should see the hint vanish, and come back on the next click. You never called _on_hide_pressed() yourself: the button announced that it was pressed, and the connection carried that to your function. Chapter J is about why this is such a good arrangement.

  8. Break it, and read the Output

    Stop the game. Select Main, open the Script tab and, in _ready(), change $Spin to $Spinn. Run. You should see a red line in the Output that names main.gd, gives a line number and says Node not found: "Spinn" – and no game. An error message is three facts: which script, which line, what went wrong. Put the spelling right and run once more.

The same five moves in the real editor

Nothing you did changes when you open Godot itself. The buttons are in the same docks; some of them open a dialog that asks a little more.

MoveIn Godot
Add a nodeSelect the parent and press + at the top of the Scene dock, or Ctrl+A. The Create New Node dialog lists every node type as a tree, with a search box and a description of whichever one is highlighted – read those descriptions, they are the quickest tour of the engine there is.
Set propertiesIn the Inspector, or by dragging in the viewport. Ctrl+S saves the scene; an asterisk on the scene's tab means it has unsaved changes.
Attach a scriptSelect the node and press the scroll-shaped button at the top of the Scene dock, Attach Script. A dialog proposes a file name and a template; Create opens the new script in the Script view.
Connect a signalSelect the node that sends it, open the Node dock and double-click the signal. A dialog asks which node should receive it – one with a script – and proposes a method name of the same shape you saw, _on_hide_pressed. Connect writes the empty function for you.
RunF5 runs the project, F6 runs only the scene you are editing, F8 stops. More on these at the end of the chapter.

What the copy leaves out

The simulator knows seven node types – Node, Node2D, Sprite2D, ColorRect, Label, Button and Timer – where Godot has hundreds, and its Inspector shows a handful of properties where Godot's shows dozens. It also places a new sprite in the middle of the view to be kind. In Godot a new 2D node starts at position (0, 0), which is the top left corner of the screen – so a new sprite appears three-quarters off it, and the first thing you do is drag it somewhere.

The Inspector: every property, and where it is kept

A node is mostly a bundle of named values – where it is, what it shows, whether it can be seen. The Inspector is the list of them for the selected node.

Select a Sprite2D in Godot and the Inspector is arranged in bands, each headed by a class name. At the top are the properties only a sprite has: Texture, and groups called Offset, Animation and Region. Below that comes Node2D, with a Transform group: Position, Rotation, Scale. Below that, CanvasItem, with Visibility (where Visible and Modulate live) and Ordering (Z Index). At the bottom, Node. Reading down the Inspector is reading the node's family tree: a Sprite2D is a Node2D, which is a CanvasItem, which is a Node, and it has everything each of them has. Chapter H explains that chain.

Each label is the property's code name, tidied up: Flip H is flip_h, Z Index is z_index. Hover over a label and Godot shows the description from its manual. There is a search box at the top of the Inspector for when you know the name and not the band.

Only what you change is written down

Every property has a default, and a scene file records only the ones that differ from it – you saw that in the simulator's .tscn tab. The Inspector shows the same fact another way: a small circular arrow appears beside any value you have changed, and clicking it puts the default back. Here is the whole rule as a few lines of GDScript:

extends Node

const DEFAULTS := {"position": Vector2(0, 0), "rotation": 0.0, "scale": Vector2(1, 1), "visible": true, "z_index": 0}

var coin := {"position": Vector2(250, 60), "rotation": 0.0, "scale": Vector2(2, 2), "visible": true, "z_index": 0}

func _ready() -> void:
	print("[node name=\"Coin\" type=\"Sprite2D\" parent=\".\"]")
	for property in coin:
		if coin[property] != DEFAULTS[property]:
			print(property, " = ", coin[property])

Five properties, two lines saved. Press Edit and run, change the coin's "visible": true to false and a third line appears; set its scale back to Vector2(1, 1) and one goes. (A real scene file writes Vector2(250, 60) where this prints (250.0, 60.0); the rule is the same.) This is why a .tscn is short enough to read, and why a default that changes in a new version of Godot reaches every node you never touched.

The same values, from code

Everything in the Inspector can also be set by a script, by the name you see when you hover. These six are the ones a 2D game sets most:

In the InspectorIn a scriptWhat it is
Transform ▸ Positionposition = Vector2(80, 120)Pixels from the parent's origin. x goes right, y goes down.
Transform ▸ Rotationrotation_degrees = 30The Inspector works in degrees. Positive turns clockwise.
Transform ▸ Scalescale = Vector2(2, 2)A multiplier for each axis. (1, 1) is natural size.
Visibility ▸ Visiblevisible = falseWhether it, and everything under it, is drawn.
Visibility ▸ Modulatemodulate = Color(1, 0.7, 0.7)A colour every pixel is multiplied by. White changes nothing.
Ordering ▸ Z Indexz_index = 5Higher numbers draw in front, whatever the tree order.

One of those hides a trap. The Inspector shows rotation in degrees, and there is a matching rotation_degrees in code. But the property called plain rotation is in radians, the unit the maths functions use, where a full turn is about 6.28 and not 360:

extends Node

func _ready() -> void:
	print("A quarter turn is 90 degrees, or ", deg_to_rad(90.0), " radians")
	print("PI radians is ", rad_to_deg(PI), " degrees")
	print("Writing rotation = 90 turns the node by %.1f degrees" % rad_to_deg(90.0))

That last line is the bug nearly everybody writes once: fourteen full turns and a bit, which looks like a random angle. Change the 90.0 in it to PI / 2 and it comes out as the quarter turn that was meant.

Your own values in the Inspector

The Inspector is not only for Godot's properties. Put @export in front of a variable in a script and it appears at the top of the Inspector for any node carrying that script, with an editor to suit its type – a number box, a tick box, a colour picker:

extends Node2D

## How fast she walks, in pixels per second.
@export var speed := 90.0
@export var lives := 3
@export var player_name := "Wren"

func _ready() -> void:
	print(player_name, " walks at ", speed, " with ", lives, " lives")

The value in the script is now only the default. Type 140 into Speed in the Inspector and that node's speed is 140 when the game starts – it is saved in the scene with the node, like any other changed property – while the script still says 90. Two nodes with the same script can have different speeds. Here there is no Inspector, so the defaults are what you get; change them and run it. The line starting ## is a documentation comment, and Godot shows it when you hover over Speed, as it does for its own properties.

The 2D viewport

The middle of the editor is a drawing board that goes on for ever in every direction, with one outlined rectangle on it: the part your game's window will show.

Two thin lines cross at the origin, the point (0, 0): a red one running across, which is the x axis, and a green one running down, the y axis. The outlined rectangle has its top left corner on the origin, and its size is the window size from Project Settings. Anything you put inside it is on screen when the game starts. Anything outside it exists but is out of shot until a camera moves – which is how levels bigger than the screen are laid out.

The thing to get into your hands early is which way the numbers go. Screens are counted from the top left, so y grows downwards:

extends Node

const SCREEN := Vector2(320, 180)

func _ready() -> void:
	var p := Vector2(160, 90)
	print("start, in the middle: ", p)
	p.y += 40
	print("y + 40 is DOWN:       ", p)
	p.x -= 100
	print("x - 100 is left:      ", p)
	print("the bottom right corner is ", SCREEN)
	print("snapped to a 16-pixel grid: ", Vector2(203, 77).snapped(Vector2(16, 16)))

If that feels upside down after school graphs, you are in good company. Make the first move p.y -= 40 and the point goes up the screen. The last line is what the viewport's grid snapping does to a drag: every position is rounded to the nearest grid point. Change 203 to 199 and watch it fall to the line on the other side.

The tools

Along the top of the viewport is a row of tool buttons. The first four decide what a drag on a node means:

ToolKeyA drag…
SelectQpicks a node up and moves it. A drag on empty space draws a box that selects everything in it. The everyday tool.
MoveWonly moves – it cannot select something else by accident.
RotateEturns the node about its origin.
ScaleSresizes it.

The rest you will pick up as you need them. The mouse wheel zooms, and dragging with the middle button (or holding Space and dragging) slides the board about. F centres the view on the selected node – the cure for "where has it gone?". The magnet-like buttons switch snapping on, so that things you drag land on a grid or line up with each other. The padlock locks the selected node so that it cannot be moved by a stray click – very welcome on a background that fills the screen and catches every click meant for something on top of it.

Files go straight in, too: drag a picture from the FileSystem dock into the viewport and Godot makes a Sprite2D for it where you let go.

Moving a parent moves its children

Drag a node that has children and they all come with it. That is the tree at work, and Chapter C is about it – but it changes what the Inspector's numbers mean, so meet it now. A child's Position is measured from its parent, not from the corner of the screen:

Move the parent's sliders: the child travels across the board and its own position does not change by a pixel. This is the usual explanation when a number in the Inspector seems not to match where a node is. Look up the tree.

The script editor, the Output and the Debugger

Godot has its own code editor, and it knows your project: which nodes exist, what every function takes, and where an error came from.

Press Script above the main view, or click the scroll icon beside a node in the Scene dock, and the viewport is replaced by code. Down the left side are the scripts you have open and, below them, the functions in the current one – click a name to jump to it. A few things in it are worth knowing from the first day:

  • It completes as you type. Type a node's name and a dot and it offers that node's properties and methods. It is better at this when variables have types (Chapter D).
  • The manual is inside it. Hold Ctrl and click any class or function name and its documentation opens in a tab – or your own function's definition, if it is yours. Search Help, at the top right, searches the whole reference. None of it needs the internet.
  • It checks before you run. A line Godot cannot make sense of is marked in red as you type, with the reason in a bar under the code. Fix those first: the game will not start with one in it.
  • Nodes can be dragged in. Drag a node from the Scene dock into the code and Godot types the path to it for you.

Output: what the game says

When the game runs, the bottom panel opens on Output. Everything print() writes arrives there, in order, and it is the simplest tool you have for finding out what your code is doing. Besides print there are two functions that mark a line as a problem without stopping the game:

extends Node2D

var coins := 3

func _ready() -> void:
	print("Ready.")
	print("Coins: ", coins)
	print("Several things: ", Vector2(8, 6), " ", true, " ", 2.5)
	push_warning("The coin texture is missing; using a placeholder.")
	push_error("Could not find the save file.")
	print("Still running.")

print() takes any number of values of any type and writes them one after another – add , " left" after coins. In Godot the warning shows in yellow and the error in red, and both are also collected in the Debugger panel's Errors tab, where a count beside the tab's name tells you they are there even when you were not watching the Output. Use them for things that should not happen but need not end the game.

Debugger: when it stops

Some mistakes cannot be carried on from. The game pauses, the editor comes to the front with the offending line highlighted, and the Debugger says what happened. This one is the commonest of all – using something that is not there:

extends Node2D

var lamp = null    # stands in for a node that was never found

func _ready() -> void:
	print("Starting up")
	lamp.hide()
	print("This line is never reached")

Read it as three facts. Where: line 7. What: a method was called on null – on nothing. Which: hide. So the question to ask is not "what is wrong with hide()?" but "why is lamp empty?" – and the answer is on some earlier line, the one that was supposed to fill it. Notice also what the Output shows: Starting up did print. Everything before the error happened; nothing after it did. Give lamp something that has no hide() – var lamp = 5 – and read how the message changes.

The Debugger does a good deal more – pausing on a line you choose, stepping through code, showing every variable's value at that moment – and Chapter W is about using it. One part is worth knowing today: while the game is running, the Scene dock gains two tabs, Local and Remote. Remote shows the tree of the running game, live, including every node created by code. Click a node there and the Inspector shows its values as they change.

Running it, and settings for the whole project

Two keys start the game, and knowing which one you want saves a lot of confusion. Behind them sits one file of settings that belongs to the project as a whole.

Button, top rightKeyWhat it runs
Run ProjectF5The whole game, starting from the project's main scene, exactly as a player would get it.
Run Current SceneF6Only the scene open in the editor. This is how you test an enemy or a menu on its own, without playing through to it.
StopF8Ends the game and returns you to the editor.

On a Mac the three are ⌘+B, ⌘+R and ⌘+. by default. The first time you press F5 in a new project Godot asks which scene is the main one; you can change the answer later by right-clicking a scene in the FileSystem dock and choosing Set as Main Scene. F5 and F8 work in the simulator above as well – try them from the keyboard.

The game runs as a program of its own, separate from the editor. It loads the scenes as they were saved and goes its own way from there, which is the reason behind what you saw in the simulator: whatever happens while it runs – nodes moved, hidden, freed – is gone when it stops, and the scene in the editor is exactly as you left it.

Project Settings are not Editor Settings

There are two settings windows and they are easy to confuse. Project Settings describe the game: they are saved in the project folder and travel with it. Editor Settings describe your editor – its font size, its colours, its shortcuts – and are saved on your computer for every project you open. If a tutorial tells you to change a setting and you cannot find it, check you are in the right one of the two.

Build it live

The Inspector and a script are two ways of setting the same values. To feel that properly, set each of the Inspector's main fields from code, one at a time, and watch the same thing happen that a typed-in number would cause.

In Little Hours

Little Hours is built almost entirely in code, so its editor looks nearly empty: one scene, one node. That makes it a good place to see what the docks you have just learnt are a front for.

Open the project in Godot and the Scene dock is one line long – a Node2D called Main, with a script. Press F5, switch the Scene dock to Remote, and the whole game is there: rooms, furniture, the resident, the dog, the interface, every node of it added by that script as the game starts. Chapter C looks at the order they are added in. What matters here is how each one is set up, because it is the Inspector with the window taken away. This is the camera being made, in Main.gd:

Main.gd · lines 234–243

# The room used to be framed like a dollhouse: the whole floor on screen at
# once, nothing ever moving. A camera that follows them makes it a place you
# walk around in. Zoom is a WHOLE number — 2x means one art pixel is two
# screen pixels, so nothing softens.
_camera = Camera2D.new()
_camera.position_smoothing_enabled = true
_camera.position_smoothing_speed = 6.0
add_child(_camera)
_camera.make_current()
_apply_camera_limits()

In an editor-built game you would add a Camera2D with Add Child Node, open Position Smoothing in the Inspector, tick Enabled and type 6 into Speed. Here Camera2D.new() is the add, the two lines under it are the tick and the number – the same property names, lower case with underscores – and add_child() puts it in the tree. The result is identical; what differs is where the decision is written down. In the editor it would be two lines in a .tscn file. Here it sits beside a comment that says why the camera exists at all. Orientation and camera follows what the camera does next.

The settings that are not on any node

The game still has Project Settings, like every project. This is the part of its project.godot that Display ▸ Window writes:

../project.godot · lines 64–69

[display]

window/size/viewport_width=768
window/size/viewport_height=1344
window/stretch/mode="canvas_items"
window/stretch/scale_mode="integer"

Read it back into the dialog: Viewport Width 768 and Viewport Height 1344 – taller than it is wide, because the game is made for a phone held upright – then two of the Stretch settings, which decide how those 768 by 1344 pixels are fitted to whatever screen the game finds itself on. Chapter P explains those two lines and why a pixel-art game cares about them so much. The file is plain text, so you can read every decision the project has made without opening the editor.

One tab the game does not use

The Input Map tab of Project Settings is where most games list their controls. Little Hours leaves it alone and registers its keys in code when it starts, and says why:

Main.gd · lines 135–146

## The keys, registered here rather than in project.godot for the same reason
## everything else in this game is built in code: one place to read, nothing to
## keep in sync with a file the editor rewrites.
##
## Physical keycodes, so WASD stays under the same fingers on an AZERTY board.
const KEYS := {
	"move_left":  [KEY_A, KEY_LEFT],
	"move_right": [KEY_D, KEY_RIGHT],
	"move_up":    [KEY_W, KEY_UP],
	"move_down":  [KEY_S, KEY_DOWN],
	"interact":   [KEY_E, KEY_SPACE],
}

Main.gd · lines 148–155

func _setup_input() -> void:
	for action in KEYS:
		if not InputMap.has_action(action):
			InputMap.add_action(action, 0.2)
		for code in KEYS[action]:
			var ev := InputEventKey.new()
			ev.physical_keycode = code
			InputMap.action_add_event(action, ev)

KEYS is the table you would otherwise fill in by clicking: an action name, and the keys that trigger it. _setup_input() walks the table and tells the engine's InputMap about each one, which is what the dialog's Add button does when you press it. Either way the game ends up with an action called move_left that A and the left arrow both trigger. Chapter K is about actions, and Reaching shows how the game uses these alongside taps.

Which way should you build?

The editor's way first. It shows you every property a node has, it lets you see the result as you change a number, and it is how nearly every tutorial and example is written. Building in code, as Little Hours does, suits a game whose 50 rooms are generated from tables of data – but you can only write camera.position_smoothing_enabled = true from memory after you have ticked that box a few times.

Your turn

Six exercises. Some have a game view in place of a console: your script is one Node2D on a 320 by 180 screen, and Check looks at its properties.

What to remember

  • Scene dock: the tree. FileSystem: the files. Inspector: the selected node's properties. Node dock: its signals and groups. Output and Debugger: what the running game says. Nearly everything acts on the selection.
  • Building is five moves: add a node, set its properties, attach a script, connect a signal, run.
  • The Inspector and code set the same values. The Inspector decides how a node starts, and only what differs from the default is saved; code changes the running game, and stopping discards that.
  • In 2D, (0, 0) is the top left and y grows downwards. The Inspector's rotation is in degrees – rotation_degrees – while rotation is in radians. A child's position is measured from its parent.
  • An error is three facts: which script, which line, what went wrong. Read the first one first.
  • F5 runs the project from its main scene, F6 the scene you are editing, F8 stops. Project Settings describe the game and live in project.godot; Editor Settings describe your editor.
