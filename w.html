Reading an error message

An error is the engine telling you, as exactly as it can, what it was doing when it could not go on. Most of debugging is reading that sentence slowly instead of glancing at the red and guessing.

Run this. It is meant to stop.

extends Node

const PRICES := {"carrot": 4, "tomato": 6}

func price_of(crop: String) -> int:
	return PRICES[crop]

func basket_value(basket: Array) -> int:
	var total := 0
	for crop in basket:
		total += price_of(crop)
	return total

func _ready() -> void:
	print("Selling...")
	print(basket_value(["carrot", "tomato", "pumpkin"]))
	print("Sold.")

There are three things to read, and they answer three different questions.

1. The line: where it stopped

Line 6, return PRICES[crop]. That is where the engine was, not necessarily where the mistake is. Hold on to that difference; it is the most useful idea in this chapter.

2. The sentence: why it stopped

Invalid access to property or key "pumpkin" on a base object of type "Dictionary". Error messages are written by programmers and read stiffly, but each one is a plain statement once you take it apart: "I looked for pumpkin in a Dictionary and it is not there." The value in quotes and the type at the end are the two facts. Always find them before doing anything else.

3. The stack: how it got there

A function is called by a function that was called by a function. The list of who is waiting on whom at the moment of the error is the call stack. In Godot, the Debugger panel at the bottom of the editor opens on its Stack Trace tab when the game stops, with something like this in it:

0 - res://shop.gd:6 - at function: price_of
1 - res://shop.gd:11 - at function: basket_value
2 - res://shop.gd:16 - at function: _ready

Read it from the top down as "this, called by this, called by this". Frame 0 is the line that stopped. Frame 1 is the loop that called it. Frame 2 is where the whole thing began, and here it is also where the mistake is: line 6 did nothing wrong, it was handed a crop that has no price. Click a frame in Godot and the editor jumps to that line and shows the variables as they were in that function.

The page you are reading shows the line and the sentence but not the stack, so here you work it out by reading who calls whom. The printed output helps as well: Selling... appeared and Sold. did not, which tells you how far the script got.

Now fix it two ways, and notice that they are different decisions. Add "pumpkin": 15 to the table: the data was incomplete. Or make price_of() return PRICES.get(crop, 0): an unknown crop is worth nothing. Chapter V is about choosing between those.

Errors before the game runs

Some mistakes Godot can find by reading the script, without running it: a missing colon, a wrong indent, a name that does not exist. The script editor marks the line in red as you type, and a script with such an error does not load at all.

extends Node

func _ready() -> void:
	var total := 4 + 6
	print("Total: ", totl)

Identifier "totl" not declared in the current scope: there is no variable, function or class of that name anywhere this line can see. It is nearly always a typo, or a variable that was made inside a different function. Godot's editor finds this one before the game starts; this page finds it when the line runs. Either way the cure is the same, and it is the cheapest kind of error there is, because nothing has to happen in the game for you to see it.

An error does not always stop the game

Run from the editor, a runtime error pauses the game on the line so that you can look around. Without the editor's debugger attached – an exported game, or a run from the command line – the error is written to the log, the function it happened in is abandoned where it stood, and the game carries on with whatever that function had half done. A player sees no red text. They see a button that does nothing. That is why the log, and tests, matter later in this chapter.

The usual suspects

A handful of messages account for most of the errors you will ever see in GDScript. Meet each one on purpose now, and it will be an old acquaintance when it turns up by accident.

Something is null

extends Node

var plots := [
	{"crop": "carrot", "watered": true},
	{"crop": "tomato", "watered": false},
]

func first_dry_plot():
	for plot in plots:
		if not plot["watered"]:
			return plot
	# falls off the end: a function that returns nothing returns null

func _ready() -> void:
	print("First: ", first_dry_plot().get("crop"))
	plots[1]["watered"] = true
	print("Then: ", first_dry_plot().get("crop"))

Cannot call method "get" on a null value. The first call worked. The second found no dry plot, fell out of the loop and returned nothing, and "nothing" is null. The error names the method (get) and says what it was called on. Whenever a message says null or Nil, the thing before the dot or the bracket is empty, and the question is never "why is get broken?" but "why is there nothing here?" The usual answers:

  • a function that returns a value on some paths and falls off the end on others, as here;
  • dictionary.get(key) for a key that is not there, with no fallback given;
  • a search that found nothing, or load() on a path with no file;
  • a variable that is declared but not filled yet, such as an @onready variable used before _ready() has run (Chapter I);
  • a node path that is misspelt or has not been added to the tree yet (Chapter C).

Fix the example: keep what first_dry_plot() returns in a variable, and print "Nothing to water" when it == null. A relative of this error mentions a "previously freed" object: the variable is not empty, but the node it pointed at has been deleted. is_instance_valid(thing) is the test for that.

The index is not there

You met the dictionary version at the top of the chapter. This is the array version:

extends Node

var seasons := ["Spring", "Summer", "Autumn", "Winter"]

func _ready() -> void:
	for day in [1, 6, 11, 16, 21]:
		print("Day ", day, ": ", seasons[day / 5])

Out of bounds get index '4' (on base: 'Array'). Both facts are in the message again: the index asked for, and what it was asked of. Four seasons have indices 0 to 3. Day 21 divides to 4. The four lines printed before the stop show the pattern working, which is the trap: an index error often needs a particular value before it appears. Fix it with seasons[(day / 5) % seasons.size()], so that the fifth season is the first again. When you see this message, look for an off-by-one, a loop that runs one step too far, or an array that is empty when you assumed it was not.

The types do not fit

extends Node

func _ready() -> void:
	var saved = JSON.parse_string('{"coins": "12", "day": 3}')
	var coins: int = saved["coins"]
	print("Coins tomorrow: ", coins + 1)

Somebody edited the save by hand and put the coins in quotes. The variable was declared int, the value arriving is a String, and the assignment is refused. Godot words it as Trying to assign value of type 'String' to a variable of type 'int'; the book's interpreter says the same thing in slightly different words. The type on the variable did its job: without : int the text "12" would have travelled on, and the error would have come out of coins + 1 or, worse, from somewhere three functions away. Convert at the door: int(saved["coins"]) accepts 12, 12.0 and "12" alike.

The other common form is an operator given two types it cannot combine: "Day " + 3 is Invalid operands "String" and "int" in operator "+". Text joins only to text; write "Day " + str(3) or "Day %d" % 3 (Chapter D).

It has no such function

extends Node

func _ready() -> void:
	var basket = {"carrot": 2}
	basket.append("tomato")
	print(basket)

Invalid call. Nonexistent function "append" in base "Dictionary". The function name may be a typo, but look at the base first: it tells you what the thing really is, which is often not what you thought. Here the code treats a dictionary as an array. In a game it is more often a node of a different class from the one you expected.

Looking inside: print, assert and the debugger

An error message tells you where the game stopped. Most bugs do not stop anything: the game runs and does the wrong thing. Then you have to look inside while it runs.

print, with labels

The oldest tool is still the one used most. The skill is in what you print. print("here") tells you a line ran. Printing the values, each with its name, tells you why the next line did what it did.

extends Node

const GROW := 15.0

# How long until a crop planted at `planted_at` is ripe, at clock time `now`.
func ripe_in(planted_at: float, now: float) -> float:
	var waited := now - planted_at
	print("planted_at=", planted_at, " now=", now, " waited=", waited)
	return GROW - waited

func _ready() -> void:
	print(ripe_in(100.0, 110.0))
	print(ripe_in(450.0, 10.0))

The first answer is 5 seconds, which is right. The second is 455. With the labelled line above it you can see why at a glance: waited is minus 440. The crop was planted at 450 in the evening, the clock started again from zero the next morning, and "now minus then" went negative. Without the print you would be staring at a crop that will not ripen. This exact bug was in Little Hours, and you will meet the fix further down.

print has relatives, each for a slightly different job:

CallWhat it does
print(a, b)Writes its arguments one after another with nothing between them.
prints(a, b)The same with a space between each: quicker for a row of values.
print_debug(a)Like print, and when run from the editor adds the script and line it was called from. Good for a print you might forget to remove.
push_warning(text)Reports a warning: a yellow entry on the Debugger's Errors tab, with the place it came from. The game carries on.
push_error(text)The same in red. It still does not stop the game: it is you saying "this should never happen" out loud.
print_stack()Prints the call stack at this point: how did we get here?
 
extends Node

func buy(coins: int, price: int) -> int:
	prints("buy:", coins, price)
	if price < 0:
		push_error("a price below zero: %d" % price)
		return coins
	if coins < price:
		push_warning("not enough coins for that")
		return coins
	return coins - price

func _ready() -> void:
	print(buy(10, 4))
	print(buy(3, 4))
	print(buy(3, -4))

Here the warning and the error come out as lines beginning WARNING: and ERROR:; in Godot they also collect on the Errors tab, where they are still waiting after the print lines have scrolled away. Use them for things the game survives but you want to hear about: a missing file, an id that is not in a table, a save that had to be repaired.

assert: stop at the cause

assert(condition, message) says "this must be true here". When it is not, the game stops on that line with your message.

extends Node

func sell(count: int, price: int) -> int:
	assert(count >= 0, "cannot sell a negative number of things")
	return count * price

func _ready() -> void:
	print(sell(3, 4))
	print(sell(-2, 4))

Without the assert, sell(-2, 4) returns minus 8 and the player quietly loses coins; the bug is found days later, far from here. With it, the game stops at the first moment something impossible happened, which is the best place to be stopped. One thing to know: asserts exist only in debug builds. An exported release build skips them, condition and all, so never put work inside one. assert(save_game()) would save while you are developing and not at all for players.

The debugger

A print shows you what you thought to ask for. A breakpoint stops the game and shows you everything.

  1. Set a breakpoint

    In the script editor, click in the margin to the left of a line number. A red dot appears. (Writing the keyword breakpoint on a line of its own does the same from code.)

  2. Run

    The game runs normally until it is about to execute that line, then freezes. The editor comes forward with the line marked.

  3. Look

    The Stack Trace tab of the Debugger panel lists the call stack, and beside it every variable the current function can see: its locals, and the script's members. Click a frame further down the stack to see the caller's variables.

  4. Step

    Step Over runs the one marked line and stops again. Step Into does the same, but if the line calls a function of yours it goes inside. Continue lets the game run until the next breakpoint. Watching the variables change one line at a time is often all it takes.

The other half of the debugger is in the Scene dock. While the game runs, two buttons appear above the tree: Local, the scene as you built it, and Remote, the tree as it is in the running game at this moment. Remote shows every node, including autoloads and everything made by code with new() and add_child(). Select one and the Inspector shows its live values; change a value there and the running game changes. For a game built in code, as Little Hours is, the Remote tree is the only place the scene can be seen at all. The Debug menu also has switches worth knowing, such as Visible Collision Shapes, which draws every collision shape over the running game (Chapter M).

In what order do things happen? How does this value change over a second?print, with labels
What is everything, at this one moment?A breakpoint

Stricter settings, and the command line

The best time to find a bug is before the game runs, and the second best is when nobody has to be watching. Godot has a setting for the first and a way of running for the second.

Warnings, and turning them into errors

As you type, GDScript notices things that are legal but suspicious: a variable that is never used, a local variable with the same name as a member, an integer division that throws away its remainder, code after a return. These are warnings. The script editor counts them at the bottom of the editor and lists them when you click the count. They do not stop anything, which is why they are easy to ignore, and why a list of forty of them hides the one that matters.

You decide how seriously each is taken. In Project Settings, under Debug and then GDScript (switch on Advanced Settings if the section is not shown), every kind of warning has its own level: Ignore, Warn or Error. At Error, the script will not run until the line is fixed. Several of the most useful checks are off until you turn them on, among them the ones that insist on types: an untyped declaration, or a call on something whose type Godot cannot work out.

Types are what make the difference. Compare where this stops with where it would stop if amount had no type:

extends Node

var coins := 10

func add_coins(amount: int) -> void:
	coins += amount

func _ready() -> void:
	var from_file = "5"        # text read from a file, not a number
	add_coins(from_file)
	print(coins)

The text is refused on the way into the function. Take the : int off the parameter and the same mistake gets one line further before failing, with a message about operands. In a real game "one line further" can be another file. And where Godot can see both types while reading the script, as it could if from_file were declared var from_file := "5", it reports the mismatch before the game starts. Each type you write moves a class of errors from "while playing" to "while typing".

When a warning is about something you meant, say so on that line and nowhere else: the annotation @warning_ignore("integer_division") on the line above silences that one warning for that one statement.

Running without the editor

Godot is an ordinary program that takes arguments, and anything you can do with the Run button you can do from a terminal:

godot --path path/to/project                 run the game in that folder
godot --path . --headless --quit-after 600   no window; stop after 600 frames
godot --path . -- --test --room kitchen      everything after -- is for your game

godot stands for wherever the program is on your machine; on a Mac it is inside the application, at Godot.app/Contents/MacOS/Godot.

FlagMeaning
--path dirWhich project to run: the folder that holds project.godot.
--headlessNo window and nothing drawn. For anything that only needs the game's logic, and for machines with no screen.
--quit-after NStop by itself after N frames. A safety net for a run nobody is watching.
--The divider. Arguments after it are not Godot's: they are handed to your game, which reads them with OS.get_cmdline_user_args().

That last one turns a game into a tool. The game looks at its own arguments when it starts and decides what kind of run this is:

func _ready() -> void:
	if OS.get_cmdline_user_args().has("--test"):
		run_the_tests()      # and then get_tree().quit(0), or quit(1) if any failed
		return
	start_the_game()

The number given to get_tree().quit() is the program's exit code. Zero means "all well" and anything else means "something failed", which is how a script, or a service that builds your game on every change, knows the result without reading a word of output.

The arguments arrive as an array of strings, and dealing with them is ordinary array work. The interpreter here has no command line, so this example keeps the array in a variable:

extends Node

# What OS.get_cmdline_user_args() would return for:
#   godot --path . -- --test --room kitchen
var args := ["--test", "--room", "kitchen"]

func value_after(flag: String, fallback: String) -> String:
	var at := args.find(flag)
	if at == -1 or at + 1 >= args.size():
		return fallback
	return args[at + 1]

func _ready() -> void:
	if args.has("--test"):
		print("This run is a test run")
	print("Room: ", value_after("--room", "bedroom"))

Remove "kitchen" from the array and run it again: the flag is there with nothing after it, and the check on at + 1 is what stops that being an out-of-bounds error.

Two cautions. Headless means nothing is rendered, so a headless run cannot check anything about what is on the screen. And a run with no editor attached has nowhere to show a red line, so turn on file logging in Project Settings: Godot then writes each run's output, errors included, to a log file under user://, where you can read it afterwards.

Tests: checking it again tomorrow

Every time you run the game to see whether something works, you are testing it by hand. A test is that same check, written down as code, so that it can be done again tomorrow, and after every change, without you.

The reason is not that you cannot check a thing yourself. It is that you will check it once. The bug that hurts is the one you put into something that used to work, six weeks later, while changing something else. Nobody re-plays the whole game after every edit. A test does.

Arrange, act, check

Every test has the same three parts, and it helps to write them in that order every time. Arrange: put things in a known state. Act: do the one thing being tested. Check: compare what happened with what should have.

extends Node

# The function under test: how far through the day, as a clock from 06:00 to 22:00.
func clock_text(fraction: float) -> String:
	var mins := int(lerpf(360.0, 1320.0, fraction))
	return "%02d:%02d" % [mins / 60, mins % 60]

func _ready() -> void:
	# Arrange: nothing. This function needs only its argument.
	# Act
	var got := clock_text(0.5)
	# Check
	if got == "14:00":
		print("ok    half way through the day reads 14:00")
	else:
		print("FAIL  half way through the day reads 14:00, but got ", got)

Now find out whether the test is any good: break the function. Change 360.0 to 300.0 and the line turns to FAIL, with the wrong answer in it. Put it back. A test you have never seen fail is a test you cannot trust, because a check that always passes looks exactly the same as one that works.

clock_text() is easy to test because it is a pure function: its answer depends on its arguments and nothing else, and it changes nothing. There is nothing to arrange and one thing to check. That is a reason to write rules as pure functions where you can. You cannot easily test "the label in the corner shows 14:00 at midday", but if the label gets its text from clock_text(fraction), you can test the part that could be wrong. Little Hours' own clock_text() is these two lines, reading the fraction from its clock (C: Clock).

Testing something with state

Most of a game is not pure. Buying something changes the coins and the bag. The three parts matter more here, because there is something to arrange and more than one thing to check:

extends Node

var state := {"coins": 10, "bag": {}}

func buy(item: String, price: int) -> bool:
	if state["coins"] < price:
		return false
	state["coins"] -= price
	state["bag"][item] = state["bag"].get(item, 0) + 1
	return true

func test_buying() -> void:
	# Arrange: a known start, not whatever the last test left behind.
	state = {"coins": 10, "bag": {}}
	# Act: one thing.
	var bought := buy("seeds", 4)
	# Check: what it returned, and everything it should have changed.
	print("returns true:     ", bought == true)
	print("takes the coins:  ", state["coins"] == 6)
	print("fills the bag:    ", state["bag"].get("seeds", 0) == 1)

func test_too_dear() -> void:
	state = {"coins": 3, "bag": {}}
	var bought := buy("lamp", 25)
	print("returns false:    ", bought == false)
	print("keeps the coins:  ", state["coins"] == 3)
	print("bag stays empty:  ", state["bag"].is_empty())

func _ready() -> void:
	test_buying()
	test_too_dear()

Six lines of true. Break buy() in small ways and see which line catches each: delete the line that takes the coins; change < to <= and then give the second test exactly 25 coins. Two habits are on show. Each test arranges its own start, so that tests can run in any order and one cannot spoil the next. And the test for the refusal checks what did not change, which is where the nastier bugs live.

Tests that drive the real game

Tests of single functions are called unit tests. They are fast and exact, and they miss a whole kind of bug: the kind that lives between the pieces. The data is right, the drawing code is right, and the card still comes out empty because of how the two met. To catch those you start the whole game and operate it from code – walk into every room, open every card, wait, and measure what is there. That is an integration test.

Testing one functionDriving the whole game
SpeedThousands a secondSeconds each; minutes for a suite
When it failsYou know which functionYou know something is wrong, and then you debug
CatchesWrong rules, wrong sums, edge casesPieces that do not fit: data, art, layout, timing
NeedsRules written as functionsA game that can be started and steered from code

Driving a real game brings rules of its own. It must not touch the player's save. It must wait in real time, not in frames, because a window nobody is looking at can run at any speed (Chapter T). And it must check what is actually on the screen, not that some node exists. Little Hours learned each of those the hard way, as you will see.

There are add-ons for Godot that give you a ready-made test framework with a panel in the editor; GUT and GdUnit4 are two that are widely used. You do not need one to begin. A test runner is about thirty lines, and you are about to write it.

Build it live

A test runner of your own: one function that checks, a count, a report. Then you use it for what tests are for – there is a bug planted in the starter, and your checks are going to corner it.

In Little Hours

The game is tested by starting it for real and playing it from code, and its source is full of comments that record a bug and what fixed it. Here is the runner, then three of those stories.

How the tests run

The tests live in godot/tests/, and the main file is Suite.gd. They are started from the command line with a flag of the game's own, after the -- divider:

Godot --path . --audio-driver Dummy --quit-after 26000 -- --test

Every part of that line was earned. --audio-driver Dummy keeps the speakers quiet while the suite plays the game. --quit-after is, in the words of the script that wraps this command, "a frame budget, not a timer": a backstop in case the suite hangs, because the suite quits by itself when it has finished. And there is no --headless, on purpose: some checks measure how tall a card was drawn, and a headless run draws nothing.

Inside the game, the end of Main._ready() looks for the flag with OS.get_cmdline_user_args().has("--test"). By then the whole game has been built exactly as it is for a player. If the flag is there, Main loads the suite with preload("res://tests/Suite.gd"), adds it to the tree, calls suite.call("run", self) and returns, handing the finished game to the tests instead of to you. Two short comments at that spot are bug reports in themselves. The suite is preloaded by path, not named by its class_name, because a script written outside the editor is not known by name until the project is re-imported, and then Main itself would not parse. And it is added to the tree, not only created, because the suite uses await, and an object nothing holds on to is freed at its first await: the header printed and nothing else ever happened.

The suite's opening comment explains the choice the section on tests ended with: "The game is BUILT first and then driven – these are not unit tests", because nearly every real bug in this game has been an interaction between the room data, the art and what actually got drawn. This is the whole of the function every check goes through:

../tests/Suite.gd · lines 147–152

func _ok(passed: bool, what: String, detail: String = "") -> void:
	_checks += 1
	if passed:
		return
	_fails += 1
	print("    FAIL  %s%s" % [what, ("  —  " + detail) if detail != "" else ""])

It is your check() with the comparison done by the caller: a condition, the claim in words, and an optional detail for the FAIL line. The claim is written as the thing that is true when the check passes, so a failure reads as a sentence that has stopped being true. Here it is in use, on the tables of Chapter V:

../tests/Suite.gd · lines 2684–2693

# Every art id a room asks for must exist and its file must be there.
for room in RoomData.ROOM_IDS:
	for obj in RoomData.objects(room):
		var oid := str((obj as Dictionary)["id"])
		_ok(not Assets.piece(oid).is_empty(), "%s/%s has art" % [room, oid])
for id in Assets.ART:
	var entry: Array = Assets.ART[id]
	_ok(ResourceLoader.exists(str(entry[0])), "art file for %s exists" % id, str(entry[0]))
	_ok(int(entry[1]) == roundi(float(entry[1])) and int(entry[1]) >= 1,
		"%s is drawn at a whole scale" % id, str(entry[1]))

Two loops and three claims: every piece of furniture in every room has art, every art file exists, every scale is a whole number. No one could check that by eye, and a missing picture would otherwise be found by a player standing in an oddly empty room. Other groups drive the game instead of reading its tables: _test_rooms() calls await _enter(room) for every room, which uses the game's own _go_to_room and then waits, and measures the furniture it finds there.

At the end, run() prints either "checks passed" or "checks FAILED" with the counts and calls get_tree().quit(1 if _fails > 0 else 0), so the exit code tells a script the result. Before any of it, the suite sets Game.saving_enabled = false, and any run with a test flag uses a save file of its own. The comment in Game.gd says why: a suite run used to land in the first save slot and quietly overwrite whatever was being played (S: Saving). A full run is several thousand checks and takes about four minutes; setting the environment variable SUITE_ONLY to the name of one group runs only that one.

Story one: the tap that landed somewhere else

The symptoms came as three bugs: the resident walked to a place you had not tapped, furniture did not respond, and in decorate mode a drag picked up nothing. They were one bug, and the function that fixed it carries the whole account:

Main.gd · lines 1095–1113

## Where a tap actually landed, in room coordinates.
##
## This must come from the *event*, not from `get_global_mouse_position()`.
## That call reports the pointer's own position, which
##   * is never updated by touch events at all (so on a phone every tap
##     resolved to a stale pointer spot), and
##   * carried the letterbox offset, so even with a mouse a click came out
##     a few hundred pixels off.
## The symptom was the player walking somewhere you didn't click, furniture
## never responding, and drags in Decorate mode grabbing nothing.
func _event_point(event: InputEvent) -> Vector2:
	var inv := get_viewport().get_canvas_transform().affine_inverse()
	if event is InputEventMouse:
		return inv * (event as InputEventMouse).position
	if event is InputEventScreenTouch:
		return inv * (event as InputEventScreenTouch).position
	if event is InputEventScreenDrag:
		return inv * (event as InputEventScreenDrag).position
	return inv * get_viewport().get_mouse_position()

The old code asked get_global_mouse_position() where the tap was. That function reports where the pointer is, and the comment gives the two ways that is wrong: a finger on a phone never moves the pointer, so every tap resolved to a stale spot, and even with a mouse the answer carried the offset of the black bars at the edge of the window. The fix takes the position from the event itself, whichever kind of event it is, and converts it into the room's coordinates with the inverse of the canvas transform (Chapters K and L).

The debugging lesson is in the first line of the story. Three symptoms that appear together are probably one cause, and the place to look is whatever all three share: here, the one line that turned a tap into a point. A labelled print of "where the tap was" against "where the event says it was" would have shown it at once. The mechanic it serves is R: Reaching.

Story two: the crop that waited all day

You have seen this one's numbers already, in the print example. A crop planted in the evening sat unripe through the whole of the next day.

Game.gd · lines 450–473

## A watered crop ripens on its own after its grow time, so the farm rewards you
## for coming back later in the same day — you don't have to sleep to see it.
## Only writes to disk on the frame a plot actually flips, never every frame.
func _tick_farm() -> void:
	var changed := false
	for plot in (state["farm"] as Array):
		if plot["state"] != "planted" or not plot["watered"] or plot["ready"]:
			continue
		var crop := str(plot["crop"])
		if not CROPS.has(crop):
			continue
		var grow := float((CROPS[crop] as Dictionary)["grow"])
		# The clock starts again every morning and whenever the game is opened,
		# and it is not saved: a time from before that is later than now, and
		# a crop planted in the evening would wait all of the next day for the
		# clock to catch up. It has been in the ground since before today.
		if float(plot["planted_at"]) > clock_t:
			plot["planted_at"] = 0.0
		if clock_t - float(plot["planted_at"]) >= grow:
			plot["ready"] = true
			changed = true
	if changed:
		farm_updated.emit()
		save_now()

A plot remembers the clock time at which it was planted, and ripeness is "now minus then, compared with the crop's grow time". The comment in the middle records what was missed: the clock starts again every morning and whenever the game is opened, and it is not saved. So a planted_at from yesterday evening is later than this morning's clock, the subtraction goes negative, and the crop waits for the clock to climb all the way back to where it was. The fix is the two lines under the comment. A planting time later than now can only be from before today, so it is treated as the start of today.

Nothing crashed, and no error was ever printed. Each line was correct by itself; the bug was an assumption that "now" is always later than "then". Bugs of this kind are found by a player's report or by a test that arranges the awkward case on purpose. The last exercise in this chapter has you write that test. Notice two smaller pieces of care in the same function: if not CROPS.has(crop): continue guards against a saved crop that is no longer in the table, and the save file is written only on the frame a plot actually changes, not sixty times a second (F: Farming).

Story three: the suite that passed by covering less

The third bug was in the tests themselves. Remember the callout at the start of the chapter: without the editor's debugger, a runtime error abandons the function it happened in and the game carries on. A group of tests is a function. One day a change to the game meant two calls inside the suite were to methods that no longer existed. Those groups stopped part way, the checks after that point never ran, and the suite printed "0 failed" – truthfully, since nothing had failed. Twenty checks had ceased to exist and the report was green. The suite now keeps two lists, of the groups that started and the groups that reached their last line, and compares them at the end:

../tests/Suite.gd · lines 180–186

## Called once at the end: did every group get to the end of itself?
func _check_groups_finished() -> void:
	for name in _opened:
		if not _closed.has(name):
			_ok(false, "the '%s' checks ran to the end" % name,
				"they stopped part way — look for a SCRIPT ERROR above, which "
				+ "aborts the rest of the group without failing anything")

A group that opened and never closed is counted as a failure in its own right, and the message tells whoever reads it where to look. The shell script that runs the suite has the same thought one level up: if the game fails to start at all, Godot exits cleanly and no checks run, which would read as a pass, so the script insists on finding the summary line in the output before it will report success.

The lesson is one to keep. "No failures" and "everything was checked" are different claims, and a test run should prove the second: count what ran, not only what failed. The suite has other scars of this kind. One failure that came and went, about one run in three, turned out to be the test measuring a card while it was still animating into place; it was cornered with a separate small harness that opened one card over a hundred times in a row, and fixed by waiting for the animation to finish instead of for a number of milliseconds (U: UI). Tests are code, and they get debugged like code.

Your turn

Three of these are scripts that stop with an error. Run each one first and read the message properly – the line, the name in quotes, the type – before you change anything.

What to remember

  • Read an error in three parts: the line where it stopped, the sentence (find the name in quotes and the type), and the stack of callers. The mistake is often in a caller, or upstream of the stack altogether.
  • Most errors are a few old friends: something is null, a key or index is not there, two types do not fit, the thing is not the type you thought.
  • Print values with labels; use push_warning and push_error for what the game survives; assert what must be true, and never put work inside it. A breakpoint shows everything at one moment, and the Remote tree shows the running scene.
  • Types and warnings-as-errors move bugs from "while playing" to "while typing". Arguments after -- and an exit code turn the game into something a script can run and judge.
  • A test arranges, acts and checks. Write rules as pure functions so they are easy to test, drive the whole game to catch what lives between the pieces, and see every test fail once.
  • Tests are code. Count what ran, not only what failed.
