Frames on a sheet

Most 2D animation is one old trick: show a slightly different picture several times a second. The pictures are called frames, and they nearly always arrive packed into one image.

That image is a sprite sheet: every frame of a character, laid out in a grid. One file is quicker to load than forty, and the graphics card can draw from one texture without switching. Your job is to say which cell of the grid to show right now.

A Sprite2D can do the cutting. Tell it how many columns and rows the sheet has, and then choose a frame by number:

extends Sprite2D

func _ready() -> void:
	hframes = 4      # four columns…
	vframes = 2      # …and two rows: eight frames, numbered 0 to 7
	frame = 5        # second row, second column

Frames are numbered the way you read: left to right, then down a row. frame_coords = Vector2i(1, 1) picks the same cell by column and row, which is handy when each row is a direction and each column a step. All three are in the Inspector too, under Animation.

There is a second way to show part of a texture: switch on region_enabled and give region_rect the rectangle of pixels you want. It is the same idea with the arithmetic left to you, and it does not need the cells to be equal. This is all the arithmetic there is:

extends Node

const HFRAMES := 4    # columns on the sheet
const FRAME_W := 16   # one frame, in pixels
const FRAME_H := 24

func region(frame: int) -> Rect2:
	var col := frame % HFRAMES
	var row := frame / HFRAMES
	return Rect2(col * FRAME_W, row * FRAME_H, FRAME_W, FRAME_H)

func _ready() -> void:
	for frame in [0, 1, 3, 4, 7]:
		print("frame ", frame, " is the pixels at ", region(frame))

Press Edit and run and change HFRAMES to 2: frame 3 moves from the end of the first row to the end of the second. % gives the column and whole-number division gives the row – the one place the integer division trap from Chapter D is exactly what you want.

Which frame, and when

Changing frame by one every time _process runs would play the animation at the speed of the screen: sixty frames a second on one phone, a hundred and twenty on another. Animation has its own speed, far slower, so the frame has to come from time. If t is the seconds an animation has been playing, one line turns it into a frame number:

extends Node

const FPS := 4.0      # animation frames per second
const FRAMES := 3     # how many frames the animation has

func _ready() -> void:
	for tick in 10:
		var t := tick * 0.125
		print("%.3f s  ->  frame %d" % [t, int(t * FPS) % FRAMES])

t * FPS is how many frames have gone by, int() throws away the part of a frame, and % FRAMES wraps back to the start so the animation loops. Change FPS to 8.0 and each frame lasts one line instead of two. That expression, int(t * fps) % frames, is worth knowing by heart: it needs no timer, no counter and no node.

Frames do not have to play in the order they sit on the sheet. A walk drawn as three pictures – left foot forward, standing, right foot forward – plays as four steps, and the order is a list:

extends Node

const WALK_CYCLE := [0, 1, 2, 1]   # step, stand, step, stand

func _ready() -> void:
	for step in 9:
		print("step ", step, " shows column ", WALK_CYCLE[step % WALK_CYCLE.size()])

In Little Hours

That list is the game's own. Each layer of the paper-doll character is a sheet of 3 columns by 4 rows of 48 × 96 frames: a row for each direction, and columns for step, stand, step. WALK_CYCLE = [0, 1, 2, 1] picks the column and the facing picks the row. You will see the code in In Little Hours below.

AnimatedSprite2D: the node that does the counting

Counting frames from time is so common that Godot has a node for it. An AnimatedSprite2D holds a SpriteFrames resource: a set of named animations – idle, walk, wave – each with its list of frames, its speed in frames per second and a switch for whether it loops.

  1. Add the node

    Add an AnimatedSprite2D. In the Inspector, click the empty Sprite Frames slot and choose New SpriteFrames, then click the new resource. The SpriteFrames panel opens at the bottom of the editor.

  2. Name an animation

    The panel starts with one animation called default. Rename it walk, or add more with the button above the list.

  3. Cut the sheet

    Press Add frames from sprite sheet (the grid icon), choose your image, set how many columns and rows it has, and click the frames you want in order.

  4. Set speed and looping

    Each animation has its own FPS box and a loop toggle. A walk loops; a wave does not.

From then on, code only says which animation it wants:

extends CharacterBody2D

@onready var sprite: AnimatedSprite2D = $AnimatedSprite2D

func _physics_process(_delta: float) -> void:
	var dir := Input.get_axis("ui_left", "ui_right")
	velocity.x = dir * 120.0
	move_and_slide()
	if dir != 0.0:
		sprite.play("walk")
		sprite.flip_h = dir < 0.0     # one set of frames, mirrored for the other way
	else:
		sprite.play("idle")

Calling play("walk") while the walk is already playing does not restart it, so asking every frame is fine. When a one-off animation should lead on to something, wait for its signal (Chapter J):

sprite.play("wave")
await sprite.animation_finished    # only animations that do not loop ever finish
sprite.play("idle")

Use AnimatedSprite2D when the animation is the frames and nothing else has to keep time with them. It is the quickest way to get a character moving, and for many games it is all the animation system they need.

AnimationPlayer: keys on a timeline

A flip-book changes one thing, the picture. AnimationPlayer changes anything: it is a timeline on which you pin values of any property of any node, and it fills in the time between.

Three words describe everything it does. An animation has a name and a length – open, 0.6 seconds. Inside it are tracks, one for each property being animated, such as the position of a lid or the modulate of a glow. On a track sit keys: "at 0.0 s the value is this, at 0.3 s it is that". While the animation plays, the player works out each track's value for the current moment from the keys either side of it and writes it to the property.

That working-out is small enough to write yourself, and doing so once makes the editor's timeline much less mysterious. Here is one track with three keys, the height of something that jumps:

extends Node

# One track. Each key is [time in seconds, value].
var keys := [[0.0, 0.0], [0.25, -40.0], [0.5, 0.0]]

func sample(t: float) -> float:
	if t <= keys[0][0]:
		return keys[0][1]
	for i in range(1, keys.size()):
		var a: Array = keys[i - 1]
		var b: Array = keys[i]
		if t <= b[0]:
			var share: float = (t - a[0]) / (b[0] - a[0])
			return lerpf(a[1], b[1], share)
	return keys[keys.size() - 1][1]

func _ready() -> void:
	for t in [0.0, 0.125, 0.25, 0.375, 0.5, 1.0]:
		print("at ", t, " s the track says ", sample(t))

Find the two keys the time falls between, work out how far along that gap it is as a share from 0 to 1, and lerpf between their values. Add a fourth key, [0.75, -10.0], and ask for the value at 0.625: a small second bounce appears without touching sample(). That is the appeal of keys – the movement is data.

Making one in the editor

  1. Add the player

    Add an AnimationPlayer as a child of the scene's root. The Animation panel opens at the bottom. Choose Animation → New and name it.

  2. Key a property

    Select the node to animate. While the Animation panel is open, every property in the Inspector has a small key icon beside it. Click the one next to Position: a track appears with a key at the timeline's cursor.

  3. Move time, change, key again

    Drag the cursor to 0.3 s, move the node in the viewport, and click the key icon again. Press play in the panel and it glides from one to the other.

  4. Add more tracks

    Key another property, or another node. Every track shares the one timeline, so they stay in step for ever.

A track does not have to hold a property that glides. Add Track offers several kinds:

TrackWhat its keys do
PropertySet a property of a node: position, scale, modulate, a sprite's frame, a shape's disabled.
Call MethodCall a function at that moment – spawn the dust, deal the damage.
Audio PlaybackStart a sound on an AudioStreamPlayer exactly on the footfall.
Animation PlaybackStart an animation on another AnimationPlayer.

A property that should jump instead of glide – frame, visible, texture – wants its track's update mode set to Discrete, so the value changes at each key and is not blended between them.

In code, an AnimationPlayer is used much like an AnimatedSprite2D:

@onready var anim: AnimationPlayer = $AnimationPlayer

func open_chest() -> void:
	anim.play("open")
	await anim.animation_finished
	give_reward()

Which tool for which job

Godot gives you four ways to animate, and choosing is easier than it looks: ask who knows where the movement ends.

UseWhenFor example
AnimatedSprite2DThe animation is frames of art and nothing else.A walk, a flickering torch, a coin turning.
AnimationPlayerYou designed the movement in advance and several things must keep time: frames, a hitbox, a sound, a flash.A sword swing, a door opening, a cutscene.
A tweenA one-off change from wherever a value is now to a place the code has only now decided.A card sliding in, a fade, a number counting up.
Code in _processThe movement never ends, or its target changes every frame.A bob, a camera following, feet that keep pace with speed.

The interpreter in this page has no AnimationPlayer and no tweens, so those two are shown as listings. The fourth way runs here in full, and it is what the rest of the chapter builds with.

Tweens: from here to there

A tween takes one property from the value it has now to the value you want, over a time you choose. It is the tool for everything that happens once: a fade, a slide, a pop.

The name is short for in-between. You do not add a tween in the editor. You make one in code at the moment you need it, describe its steps, and forget about it:

func collect() -> void:
	var tween := create_tween()                                  # <1>
	tween.tween_property(self, "position:y", position.y - 24.0, 0.3)   # <2>
	tween.tween_property(self, "modulate:a", 0.0, 0.2)           # <3>
	tween.tween_callback(queue_free)                             # <4>
  1. create_tween() is a method of every node. The tween it returns belongs to that node and starts by itself; there is nothing to add to the tree and nothing to call to set it going.
  2. tween_property(object, property, final value, seconds). The start is whatever the property holds when this step begins. "position:y" reaches inside the Vector2 to animate one part of it.
  3. A second step. Steps run one after another, so the coin rises and then fades. modulate:a is the alpha of the node's colour (Chapter L).
  4. tween_callback calls a function when the tween reaches it – here, the coin deletes itself once it is invisible.

A tween is used once. When it has finished it is gone; to play the movement again, make another. The steps you can give it:

StepWhat it does
tween_property(obj, "prop", to, secs)Move a property to a value.
tween_interval(secs)Wait.
tween_callback(callable)Call a function.
tween_method(callable, from, to, secs)Call a function every frame with a value going from from to to – for things that are not a plain property.

One after another, or together

Steps chain by default. To run steps side by side there are two switches:

# Every step at once: rise and fade together.
var tween := create_tween().set_parallel(true)
tween.tween_property(self, "position:y", position.y - 24.0, 0.3)
tween.tween_property(self, "modulate:a", 0.0, 0.3)

# Or only one step joined to the one before it.
var pop := create_tween()
pop.tween_property(self, "scale", Vector2(1.2, 1.2), 0.1)
pop.parallel().tween_property(self, "modulate", Color.YELLOW, 0.1)   # with the step above
pop.tween_property(self, "scale", Vector2.ONE, 0.2)                  # then this

Two more that earn their keep: tween.set_loops() repeats the whole sequence (give it a number, or nothing for "for ever"), and await tween.finished pauses a function until the last step is done.

Easing: how it gets there

Left alone, a tween moves at a constant speed, which is how machines move and nothing else does. Real things speed up and slow down. Two settings on a step describe that. The transition is the shape of the curve – Tween.TRANS_SINE is gentle, TRANS_BACK overshoots and returns, TRANS_BOUNCE bounces. The ease says which end of the movement the curve is applied to: Tween.EASE_IN starts slowly, EASE_OUT ends slowly, EASE_IN_OUT does both.

Choose a transition and an ease below and press Play. The curve is the value against time; the block on the right is something moved by it. The code under the picture is what you would write.

Try BACK with OUT – it arrives, goes a little too far and settles, which is what makes a pop-up feel alive. Then BOUNCE with OUT, a ball landing. As a rule of thumb, things arriving on screen want EASE_OUT (fast, then settling), things leaving want EASE_IN, and things moving from one place to another want EASE_IN_OUT.

An easing curve is not magic. It is a function that takes how far through the time you are, from 0 to 1, and returns how far through the movement you should be. The simplest ones are a line each:

extends Node

func ease_in(t: float) -> float:
	return t * t

func ease_out(t: float) -> float:
	return 1.0 - (1.0 - t) * (1.0 - t)

func _ready() -> void:
	print("time   linear  in    out")
	for i in 6:
		var t := i / 5.0
		print("%.1f    %.2f    %.2f  %.2f" % [t, t, ease_in(t), ease_out(t)])

Read the middle rows. At 0.4 of the time, ease_in has covered only 0.16 of the distance, and ease_out has already covered 0.64. Both start at 0 and end at 1; they differ in where they hurry. These two are what Godot calls TRANS_QUAD.

And with that, a tween itself can be written in four lines. Each frame it adds delta to a clock, turns the clock into a share, bends the share with an ease, and uses lerpf to turn it into a value:

extends Node

func ease_out(t: float) -> float:
	return 1.0 - (1.0 - t) * (1.0 - t)

func _ready() -> void:
	var from := 20.0
	var to := 120.0
	var duration := 0.5
	var elapsed := 0.0
	for frame in 8:
		elapsed += 0.0625
		var share := clampf(elapsed / duration, 0.0, 1.0)
		var x := lerpf(from, to, ease_out(share))
		print("frame %d   x = %.1f" % [frame + 1, x])

Look at the gaps between the lines: 23 pixels in the first frame, under 2 in the last. Swap ease_out(share) for plain share and every gap is 12.5. That is all a tween does; create_tween() saves you the bookkeeping.

The trap: two tweens, one property

Starting a new tween does not stop an old one. If a message is still fading out when the next one asks it to fade in, both tweens write to modulate:a every frame and the last writer wins, frame by frame. Keep the tween in a variable and kill() the old one before making the new:

var _fade: Tween

func show_message() -> void:
	if _fade != null and _fade.is_valid():
		_fade.kill()
	modulate.a = 0.0
	_fade = create_tween()
	_fade.tween_property(self, "modulate:a", 1.0, 0.2)
	_fade.tween_interval(2.0)
	_fade.tween_property(self, "modulate:a", 0.0, 0.5)

In Little Hours

That listing is, almost word for word, how the game shows its toasts – the small messages that fade in, wait 2.4 seconds and fade out. show_toast() in HUD.gd kills _toast_tween first, for the reason above. The same three lines of care appear wherever the game keeps a tween: the ghost's fade, the black curtain between rooms, the pop of a card.

Animation in code

A tween knows where it is going before it sets off. A dog following you does not, and a lantern swaying never arrives anywhere. For movement like that you write a line or two in _process, and four small tools cover nearly all of it.

Chasing a target: lerp and move_toward

Both move a value towards another, a step each frame, and they feel completely different. move_toward(from, to, step) goes a fixed distance and stops dead on the target. lerpf(from, to, share) covers a share of whatever distance is left, so it starts fast and slows as it closes in:

extends Node

func _ready() -> void:
	var a := 0.0
	var b := 0.0
	for frame in 8:
		a = move_toward(a, 100.0, 15.0)
		b = lerpf(b, 100.0, 0.25)
		print("frame %d   move_toward %5.1f   lerp %5.1f" % [frame + 1, a, b])

move_toward arrives on frame 7 and stays exactly on 100. The lerp is ahead for the first few frames and then creeps; after eight it is still ten short. Change the 0.25 to 0.5 to make it snappier. Use move_toward when arriving matters – a walker reaching a spot, a bar draining at a steady rate – and lerp when softness matters: a camera, a health bar catching up, a nose turning towards the mouse. Both exist on Vector2 as methods, position.move_toward(target, step) and position.lerp(target, share).

The trap: a share per frame is not a share per second

move_toward is easy to make fair: multiply the step by delta, as in move_toward(x, target, SPEED * delta), and it covers SPEED pixels a second at any frame rate (Chapter I). lerp with a fixed share is not fair: a quarter of the way sixty times a second is slower than a quarter of the way a hundred and twenty times a second. Writing lerp(x, target, 8.0 * delta) is the usual cure and close enough for most things. The exact one is lerp(x, target, 1.0 - exp(-8.0 * delta)).

A bob with sin

sin() turns a steadily growing number into one that swings smoothly between −1 and 1 for ever. Feed it time, multiply by how far the thing should move, and you have breathing, floating, swaying and hovering:

extends Node

const BOB := 5.0       # pixels up and down
const SPEED := 2.0     # how fast the swing is

func _ready() -> void:
	var base_y := 100.0
	for tick in 9:
		var t := tick * 0.5
		var y := roundf(base_y + sin(t * SPEED) * BOB)
		print("%.1f s   y = %d" % [t, int(y)])

Two details in that line matter. The bob is added to a stored base_y, never to the current position: position.y += sin(…) would pile each frame's offset on the last and the thing would drift away. And roundf keeps it on whole pixels, which pixel art needs (Chapter P). Make SPEED 6.0 for a hummingbird; make BOB 1.0 for somebody breathing.

Squash and stretch

The oldest trick in drawn animation: a thing that lands gets wider and shorter for a moment, a thing that leaps gets thinner and taller. In Godot that is the scale property (Chapter L), knocked out of shape in one line and brought back by a chase:

extends Node

func _ready() -> void:
	var scale := Vector2(1.3, 0.7)      # the moment of landing: wide and short
	for frame in 8:
		scale = scale.move_toward(Vector2.ONE, 0.0625)
		print("frame %d   %.2f wide, %.2f tall" % [frame + 1, scale.x, scale.y])

Wider by as much as it is shorter, so it seems to keep its volume. It only looks right if the node's origin is where the thing touches the ground: scaling happens around the origin, and a character whose origin is at their middle would lift their feet off the floor when squashed. Put the origin at the feet. You are about to.

A walk cycle on five layers at once

The paper-doll character in Avatar.gd is five Sprite2Ds stacked on each other – body, eyes, outfit, hair, accessory – each showing one frame of its own sheet through region_rect. All five sheets share one layout, so one rectangle moves the whole person:

Avatar.gd · lines 147–167

func _process(delta: float) -> void:
	if moving:
		_anim_t += delta
		if _anim_t >= STEP_TIME:
			var steps := int(_anim_t / STEP_TIME)
			_anim_t -= steps * STEP_TIME
			_cycle_i = (_cycle_i + steps) % WALK_CYCLE.size()
			_refresh_frame()
	elif _cycle_i != 1:
		_cycle_i = 1        # settle on the neutral stand
		_anim_t = 0.0
		_refresh_frame()

func _refresh_frame() -> void:
	var col: int = WALK_CYCLE[_cycle_i] if moving else 1
	var row: int = ROW.get(facing, 0)
	var region := Rect2(col * FRAME_W, row * FRAME_H, FRAME_W, FRAME_H)
	for s in _layers:
		s.region_rect = region
	_measure_shadow()
	queue_redraw()

_anim_t counts seconds while moving is true. Every STEP_TIME (0.16 s) the place in WALK_CYCLE moves on. Notice int(_anim_t / STEP_TIME): after one very long frame, several steps may be owed, and this takes them all at once so the walk never falls behind the clock. When the character stops, the elif puts them on column 1, the standing pose – once, not every frame.

_refresh_frame() is the arithmetic from the start of this chapter: the column from the cycle, the row from which way they face, and one Rect2 given to every layer. The hand-drawn character in DrawnAvatar.gd counts steps with the same STEP_TIME, and adds a second timer of its own for blinking, with an uneven gap of 2.4 to 6.5 seconds between blinks because, as its comment says, "a blink on a timer reads as a blinking light rather than a person".

One clock, two animations

The ghost (G in the game's A to Z) is four frames of a sheet and a slow float. Both come from one number:

Ghost.gd · lines 41–50

func _process(delta: float) -> void:
	if _sprite == null:
		return
	_t += delta
	var frames: int = maxi(1, int(_sprite.texture.get_width() / FRAME.x))
	var f := int(_t * FPS) % frames
	_sprite.region_rect = Rect2(f * FRAME.x, 0, FRAME.x, FRAME.y)
	# A slow rise and fall, on whole pixels so they stays crisp.
	position.y = roundf(_base_y + sin(_t * 1.6) * BOB)
	z_index = int(position.y)

There is int(_t * FPS) % frames, with the number of frames worked out from the width of the texture so that a longer sheet would need no change to the code. And there is the bob: a sine of the same _t, added to _base_y – the height she was placed at – and rounded to whole pixels. The dog and the cat in Pet.gd (A) turn their frames the same way, with one refinement: the walk's frame rate is multiplied by how fast the animal is really moving, so a dog hurrying to keep up takes quicker steps and does not slide.

Tweens for the one-off moments

Tap the dog and it bounces:

Pet.gd · lines 495–498

func _bounce() -> void:
	var tw := create_tween()
	tw.tween_property(_sprite, "position:y", _sprite.position.y - 18.0, 0.12)
	tw.tween_property(_sprite, "position:y", _sprite.position.y, 0.16).set_trans(Tween.TRANS_BOUNCE)

Two steps, so they chain: up 18 pixels in 0.12 s, then back down in 0.16 s. Only the way down has a transition, TRANS_BOUNCE, so the dog lands and patters to a stop. It is the sprite inside the pet that moves, not the pet node, so the shadow stays on the floor and the dog's real position – which the walking code depends on – is never touched.

The ghost fades in and out with tweens, and its fade-out shows both of this chapter's cautions in five lines:

Ghost.gd · lines 66–71

func fade_out() -> void:
	if _fade != null:
		_fade.kill()
	_fade = create_tween()
	_fade.tween_property(self, "modulate:a", 0.0, 0.9)
	_fade.tween_callback(func() -> void: visible = false)

The old tween is killed first; the comment where _fade is declared records what happened before that line existed: "a fade-out's last step hid a ghost that had just been asked to appear". And hiding is done with tween_callback as a step after the fade, so visible turns false only when the alpha has reached zero.

Elsewhere the same tools do the same jobs. The black curtain when you walk through a door (M) is one tween_property on color:a with TRANS_SINE and EASE_OUT in Main.gd. Cards pop in (U) with set_parallel(true): a fade and a rise of a few whole pixels together, the rise eased with TRANS_BACK. And the ring that spreads where you tap (R) is not a tween at all – Ripple.gd grows a radius and shrinks an alpha by delta each frame and frees itself when it has faded. Chapter O opens that one up.

What to remember

  • A sprite sheet is frames in a grid. hframes, vframes and frame on a Sprite2D pick a cell; region_rect picks any rectangle. The frame showing is int(t * fps) % frames.
  • AnimatedSprite2D plays named sets of frames. AnimationPlayer pins values of any property to a timeline, as keys on tracks, and keeps several things in time.
  • A tween comes from create_tween(), runs its steps in order unless told set_parallel or parallel(), and is used once. Keep it in a variable and kill() it before starting another on the same property.
  • Easing is a function from a share of the time to a share of the movement. EASE_OUT for arriving, EASE_IN for leaving.
  • In _process: move_toward arrives, lerp approaches, sin of time bobs around a stored base, and scale squashes around the origin – so put the origin at the feet.
  • Everything is driven by delta, never by counting frames.
