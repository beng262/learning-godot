Joining things up: signals

Announcing instead of reaching: signal, connect, emit, the built-in signals, and await.

In this chapter

  • why a node should announce what happened instead of reaching for whoever cares
  • the three verbs: declare a signal, connect a function to it, emit it
  • extra arguments with bind, one-shot connections, and disconnecting
  • the signals nodes already have – pressed, timeout, body_entered – and the rule "call down, signal up"
  • await: pausing a function until a signal arrives

Announce, do not reach

A coin is picked up. The score should go up, a chime should play, and perhaps an achievement unlocks. This chapter is about one question: who tells whom?

The obvious answer is that the coin tells everybody. It knows it was picked up, so it finds the score label, the sound player and the achievement tracker and calls each of them:

# coin.gd – the reaching way
extends Area2D

func pick_up() -> void:
	get_node("../../HUD/ScoreLabel").add_points(1)
	get_node("../../Sound/Chime").play()
	get_node("/root/Main/Achievements").count_coin()
	queue_free()

It works, and it has three problems that grow with the game.

  • The coin knows the shape of the tree. Those paths (Chapter C) are a description of where everything else lives. Move the score label into a different panel and every coin breaks.
  • The coin cannot be used alone. Open the coin scene by itself to test it, or drop it into a level with no HUD, and the first line stops with "Node not found".
  • Every new listener means editing the coin. Add a particle burst, a quest counter, a tutorial that notices the first coin – each one is another line in a script that should only be about being a coin.

A signal turns it round. The coin says one thing – "I was collected" – and says it to nobody in particular. Whoever cares has asked, beforehand, to be told. The coin does not know who they are or whether there are any. Try it: tick and untick the listeners, then pick up coins.

Notice what happens with every box unticked: nothing, and no error. An announcement to an empty room is fine. That is what makes the coin a thing you can drop anywhere.

Here is the same idea as a script you can run. The signal, the two listeners and the announcement are all in one file for now, so you can see the whole of it:

extends Node

signal collected

func _ready() -> void:
	collected.connect(_add_point)
	collected.connect(_play_chime)
	collected.emit()

func _add_point() -> void:
	print("Score goes up")

func _play_chime() -> void:
	print("♪ chime")

Press Edit and run. Write a third function that prints Unlocked! and connect it. Then delete all the connect lines and run again: no output, no error.

Declare, connect, emit

Three verbs, one line each. The node that announces declares and emits; the node that cares connects.

Declare

A signal is declared at the top of a script, beside its variables, with the keyword signal. It can carry values, written like a function's parameters:

signal collected                        # carries nothing
signal collected(value: int)            # carries what the coin was worth
signal health_changed(current: int, maximum: int)

Name a signal for what happened, in the past tense: collected, died, door_opened. A name like add_score is the reaching way in disguise – it is the emitter deciding what its listeners should do. The parameters are whatever a listener will want to know about the event.

Connect

A listener asks to be told with connect, giving the function to run. The shape is always emitter.signal_name.connect(function). What you hand over is a Callable – a function as a value, from Chapter F – so it is the function's name with no brackets after it.

Emit

The emitter announces with emit, passing a value for each parameter it declared. Here the coin is a small class of its own (Chapter H) so you can see the two sides apart: nothing inside Coin mentions a score.

extends Node

class Coin:
	signal collected(value: int)
	var value := 1

	func pick_up() -> void:
		print("coin: about to emit")
		collected.emit(value)
		print("coin: emit has finished")

var score := 0

func _ready() -> void:
	var coin := Coin.new()
	coin.value = 5
	coin.collected.connect(_on_coin_collected)
	coin.collected.connect(_on_coin_sparkle)
	coin.pick_up()

func _on_coin_collected(value: int) -> void:
	score += value
	print("score is now ", score)

func _on_coin_sparkle(value: int) -> void:
	print("sparkle x", value)

Read the order of the output. emit is not a message left for later: it calls every connected function there and then, in the order they were connected, and only when the last one has returned does the line after emit run. Swap the two connect lines and watch the middle two lines swap.

The name _on_coin_collected follows a convention worth keeping: _on_, then who announced, then the signal. When you meet that function six months from now, its name says it is called by a signal and which one.

The trap: brackets

This is the mistake everybody makes once. Run it and read both the output and the error:

extends Node

signal collected

func _ready() -> void:
	collected.connect(_add_point())
	collected.emit()

func _add_point() -> void:
	print("Score goes up")

_add_point() with brackets calls the function, now, once – that is the line of output – and hands connect whatever it returned, which is nothing. Godot refuses it too. Take the brackets off and it runs: _add_point is the function, _add_point() is the result of running it.

The arguments have to match

A listener must take what the signal sends. Emit one value to a function that expects one and all is well; forget the value and the call cannot be made:

extends Node

signal collected(value: int)

func _ready() -> void:
	collected.connect(_on_collected)
	collected.emit()

func _on_collected(value: int) -> void:
	print("worth ", value)

Put a number in the brackets of emit to fix it. In Godot the error names the signal and the function it was trying to call, and tells you how many arguments each side had.

A lambda as the listener

When the reaction is one line, it can be written in place as a lambda (Chapter F) instead of as a named function:

extends Node

signal door_opened(who: String)

func _ready() -> void:
	door_opened.connect(func(who: String) -> void: print("Hello, ", who))
	door_opened.emit("Wren")
	door_opened.emit("Bo")

Use a named function when the reaction is more than a line, or when you will want to disconnect it later – you will see why in the next section.

Extra arguments, once only, and letting go

Three refinements cover nearly everything else you will want from a connection: telling one emitter from another, hearing a signal a single time, and no longer listening.

bind: one function, many emitters

A menu has three buttons. A button's pressed signal carries nothing – it cannot say which button it was. You could write three nearly identical functions. Or you can connect all three to one function and bind a different value to each connection. FakeButton here stands in for Godot's Button, which this page does not have:

extends Node

class FakeButton:
	signal pressed

	func click() -> void:
		pressed.emit()

var play_button := FakeButton.new()
var shop_button := FakeButton.new()
var quit_button := FakeButton.new()

func _ready() -> void:
	play_button.pressed.connect(_on_menu.bind("play"))
	shop_button.pressed.connect(_on_menu.bind("shop"))
	quit_button.pressed.connect(_on_menu.bind("quit"))
	shop_button.click()
	play_button.click()

func _on_menu(which: String) -> void:
	print("Opening ", which)

_on_menu.bind("shop") makes a new Callable: _on_menu with "shop" already filled in. When a signal does carry values of its own, the bound ones arrive after them:

extends Node

signal collected(value: int)

func _ready() -> void:
	collected.connect(_on_collected.bind("the garden"))
	collected.emit(5)

func _on_collected(value: int, place: String) -> void:
	print(value, " coins found in ", place)

Swap the two parameters of _on_collected and run it: the 5 lands in place, which is a String, and the types catch the mistake.

CONNECT_ONE_SHOT: hear it once

Some reactions should happen the first time only: the tutorial tip on the first coin, the cutscene when a door first opens. connect takes a second argument, and CONNECT_ONE_SHOT makes a connection that removes itself after it has been called once.

extends Node

signal collected

func _ready() -> void:
	collected.connect(_count)
	collected.connect(_first_time, CONNECT_ONE_SHOT)
	collected.emit()
	collected.emit()
	collected.emit()

func _count() -> void:
	print("a coin")

func _first_time() -> void:
	print("  Tip: coins buy things at the shop.")

Delete , CONNECT_ONE_SHOT and the tip nags three times. The alternative is a var tip_shown := false that the function checks and sets – which works, and is one more variable to forget.

In Little Hours

The opening sequence plays once and then hands the game over. Whoever asked for it passes in a Callable, when_done, and it is connected to the opening's finished signal as a one-shot – so if the opening is ever played again, the first caller's function is not still hanging on:

Main.gd · lines 2470–2477

## Plays the opening over the town, then lets the game begin.
func play_opening(pages: Array, when_done: Callable) -> void:
	if _opening == null or pages.is_empty():
		when_done.call()
		return
	if not _opening.finished.is_connected(when_done):
		_opening.finished.connect(when_done, CONNECT_ONE_SHOT)
	_opening.play(self, pages)

Look at the line before the connect as well. It asks is_connected first, for the reason below.

disconnect, and asking first

disconnect takes the same Callable that was connected and removes that connection. is_connected answers whether it is there. You need the second more often than you would think, because connecting the same function to the same signal twice is an error:

extends Node

signal collected

func _ready() -> void:
	collected.connect(_play_chime)
	collected.emit()

	collected.disconnect(_play_chime)
	collected.emit()   # silence
	print("connected? ", collected.is_connected(_play_chime))

	if not collected.is_connected(_play_chime):
		collected.connect(_play_chime)
	collected.emit()

func _play_chime() -> void:
	print("♪ chime")

Remove the disconnect line and the if does its job: without the question, the second connect would be an error. In Godot it is reported in the Output and the second connection is not made; this page stops so that you cannot miss it.

To disconnect, you must be able to name what you connected. That is easy for _play_chime. A lambda written inside the brackets of connect has no name, so if you will want to remove it, keep it in a variable first and connect the variable.

You rarely disconnect by hand

When a node is freed, Godot removes the connections to its functions. A coin that is queue_free()d does not leave the score label listening to a ghost. Disconnect when a listener should stop caring while both sides are still alive – a muted sound, a paused tutorial.

The signals nodes already have

You will connect to far more signals than you declare. Every node type comes with its own, and they are how the engine tells you things.

They connect exactly like your own. These three listings need real nodes, so they are for reading, not running. A button:

extends Control

func _ready() -> void:
	$StartButton.pressed.connect(_on_start_button_pressed)

func _on_start_button_pressed() -> void:
	print("Let's go")

A timer that drops a coin every two seconds (Chapter T is about timers):

extends Node2D

func _ready() -> void:
	$SpawnTimer.wait_time = 2.0
	$SpawnTimer.timeout.connect(_spawn_coin)
	$SpawnTimer.start()

func _spawn_coin() -> void:
	print("a coin appears")

And the coin from the start of the chapter, done properly. Area2D (Chapter M) announces that something walked into it; the coin listens to its own built-in signal and turns an engine event, "a body entered", into a game event, "I was collected":

extends Area2D

signal collected(value: int)

func _ready() -> void:
	body_entered.connect(_on_body_entered)   # <1>

func _on_body_entered(body: Node2D) -> void:   # <2>
	if body.is_in_group("player"):
		collected.emit(1)                      # <3>
		queue_free()
  1. No node before the dot: body_entered is this node's own signal, inherited from Area2D.
  2. The parameter matches what the table says the signal carries.
  3. The coin does not know what a score is. It says what happened and removes itself.

Connecting in the editor

Signals can also be connected without writing connect. Select the emitting node, open the Node dock beside the Inspector, and choose its Signals tab: every signal the node has is listed, with its parameters. Double-click one, pick the node whose script should hear it, and press Connect. Godot writes an empty function with the conventional name into that script, and marks it with a green icon in the margin so you can see it is connected.

The two ways do the same thing. A connection made in the editor is saved in the scene file and shows in the Scene dock; one made in code is in the script, where you can read it and search for it. Pick one habit per project. The workshop lets you try the editor's way.

A signal you can run here

One built-in signal does work on this page: the timeout of a one-off timer made with get_tree().create_timer(). The page skips the waiting and fires the timers in order of time:

extends Node

func _ready() -> void:
	get_tree().create_timer(2.0).timeout.connect(_on_slow_timer)
	get_tree().create_timer(0.5).timeout.connect(_on_quick_timer)
	print("_ready() has finished")

func _on_slow_timer() -> void:
	print("2.0 seconds: the slow one")

func _on_quick_timer() -> void:
	print("0.5 seconds: the quick one")

The slow timer was made first and fires last. Connecting is not calling: _ready() finishes before either function runs. Change the 2.0 to 0.1 and the order flips.

Call down, signal up

Signals are not a replacement for calling functions. There is a rule of thumb for which to use, and it follows the shape of the tree.

A parent knows its children: it made them, or they are in its scene. So a parent talks to a child by calling its functions – $Door.open(), hud.add_points(5). That is safe, because the child is part of the parent and will always be there.

A child should not know its parent. The same door scene may sit in a house today and a dungeon tomorrow. So a child talks upwards by emitting a signal, and whoever placed it there connects.

Two siblings – a coin and a HUD – should not know each other either. Their shared parent knows both, so the parent does the introducing: it connects the one's signal to the other's function. Here Coin and Hud are separate classes that never mention each other, and the script that owns them joins them up:

extends Node

class Coin:
	signal collected(value: int)
	var value := 1

	func _init(v: int = 1) -> void:
		value = v

	func pick_up() -> void:
		collected.emit(value)

class Hud:
	var score := 0

	func add_points(n: int) -> void:
		score += n
		print("Score: ", score)

var hud := Hud.new()
var coins := [Coin.new(1), Coin.new(5), Coin.new(1)]

func _ready() -> void:
	for coin in coins:
		coin.collected.connect(hud.add_points)   # the parent introduces them
	for coin in coins:
		coin.pick_up()

hud.add_points is a Callable too: a function of that object. Add a fourth coin worth 10 to the list. Neither class changes.

When a signal is the wrong tool

  • When you need an answer. emit returns nothing. If the door must know whether the player has the key, it has to ask someone – call a function.
  • When exactly one known thing must happen. A parent telling its own child to open is a function call. Wrapping it in a signal only hides it.
  • When the chain gets long. A calls B is a line you can follow. A emits, B hears and emits, C hears and emits, is a puzzle: to find out what a signal causes you have to search for everyone who connected. Use signals at the joints between parts of a game, not inside every part.

Signals with no tree between them

Some news is for anyone, anywhere: "the day changed", "the save was loaded". No parent sits conveniently above both the clock and every screen that shows it. The usual answer is to declare such signals on an autoload – a node that exists for the whole game and that every script can reach by name (Chapter U). Little Hours does this, as you will see below.

await: wait here until it happens

connect says "run that function when it happens". await says "pause this function, right here, until it happens" – which lets a sequence of events be written top to bottom, in the order it occurs.

When a function reaches await some_signal it stops at that line and hands control back to whoever called it. The rest of the game carries on. When the signal is next emitted, the function wakes and continues from the line after.

extends Node

signal door_opened

func _ready() -> void:
	print("1  _ready() starts")
	wait_at_door()
	print("3  _ready() carries on")
	door_opened.emit()
	print("5  _ready() ends")

func wait_at_door() -> void:
	print("2  waiting at the door")
	await door_opened
	print("4  through the door")

The numbers are the order things happened in. Line 3 printed while wait_at_door() was paused in the middle. Delete the door_opened.emit() line: line 4 never prints, and there is no error. A function awaiting a signal that never comes waits for ever, silently – when a sequence stops halfway, look for the await it is stuck on.

What await gives back

await is an expression. If the signal carries one value, that is what await returns; if it carries several you get them in an Array; if none, null. And the most used signal to wait for is a timer's, which gives "wait a moment" in one line:

extends Node

signal answered(choice: String)

func _ready() -> void:
	get_tree().create_timer(2.0).timeout.connect(func() -> void: answered.emit("tea"))
	ask()

func ask() -> void:
	print("Tea or coffee?")
	var choice: String = await answered
	print("You chose ", choice, ".")
	await get_tree().create_timer(1.0).timeout
	print("One ", choice, ", coming up.")

Without await that conversation is three functions and two connections. With it, it reads as a script for a scene – which is why dialogue, cutscenes and tutorials are where you will use it most.

Waiting for a function that waits

A function with an await in it is a coroutine: it may return to its caller before it has finished. If you call it plainly, as _ready() called wait_at_door() above, you start it and carry on. If you want to wait for it to finish – or you want its return value – you await the call:

extends Node

func _ready() -> void:
	print("Putting the kettle on")
	var cups: int = await boil(3)
	print("Poured ", cups, " cups")

func boil(cups: int) -> int:
	await get_tree().create_timer(3.0).timeout
	print("  (the kettle clicks off)")
	return cups

Now _ready() is a coroutine as well: it pauses while boil() does. Waiting spreads upwards through every caller that wants the result.

The world moves while you wait

Between the await and the line after it, anything may have happened: the player left the room, the game was loaded from a save, the node you were about to use was freed. Code after an await should check that what it was doing still makes sense before it carries on. Main.gd in Little Hours does exactly this after it awaits a neighbour's small talk (X): the next line asks whether this is still the same conversation in the same saved life, and returns if not.

Build it live

One small event system, built in five steps: a player who announces each coin, a score that listens, a badge that unlocks once, and a level that waits for its goal.

In Little Hours

The game keeps everything that changes in one autoload, Game, and six signals at the top of that file are how the rest of the game finds out.

These are the first lines of Game.gd after its header comment:

Game.gd · lines 8–13

signal state_changed          ## anything in `state` changed (HUD listens)
signal day_changed(day: int)  ## a new morning began
signal toast(text: String)    ## a transient line of flavour text
signal farm_updated           ## a crop finished growing on its own
signal theme_changed          ## the UI palette was switched (More ▸ Look)
signal orientation_changed    ## portrait <-> landscape

Two of the six carry a value and four do not. Each has a comment saying what happened, not what should be done about it. Because Game is an autoload (Chapter U), any script can write Game.day_changed.connect(…) without a path to anything – these are the "signals with no tree between them" from earlier.

One function that every change ends with

The busiest of the six is state_changed, and almost nothing emits it directly. Dozens of functions in Game.gd change the state – earning coins, placing a decoration, walking into another room – and each ends by calling this:

Game.gd · lines 1247–1249

func _changed() -> void:
	state_changed.emit()
	save_now()

Two lines: tell whoever is listening, and write the save file (S). Here is one of the functions that uses it:

Game.gd · lines 2720–2724

## Coins in, for the hustles that aren't a straight item sale (a concert fee, a
## commission, a month of gallery takings).
func earn(amount: int) -> void:
	state["coins"] = int(state["coins"]) + maxi(0, amount)
	_changed()

earn() does not know there is a coin counter on the screen. It changes a number and says "something changed". That is the whole reason the coin counter is never out of date: no code that changes the coins has to remember to update it, and no new code that changes them ever will have to.

The HUD listens

On the other side, HUD.gd makes its three connections when it enters the tree:

HUD.gd · lines 50–59

func _ready() -> void:
	layer = 10
	_build()
	Game.state_changed.connect(_refresh)
	Game.toast.connect(show_toast)
	# The chips and bars carry per-node style overrides baked from the palette at
	# build time, so a palette switch can't just reassign the Theme — the whole
	# bar is rebuilt instead.
	Game.theme_changed.connect(_build)
	_refresh()

_refresh takes no parameters, matching state_changed, which sends none. show_toast(text: String) takes one String, matching toast(text: String). The comment explains the third: a palette switch cannot be patched in, so the HUD connects theme_changed to the very function that builds it and rebuilds the lot. The last line calls _refresh() once by hand – a connection only hears what is emitted after it is made, so the HUD draws itself the first time and lets the signal handle every time after.

The toast pair is worth a second look, because the emitting side is this:

Game.gd · lines 1443–1444

func say(text: String) -> void:
	toast.emit(text)

A one-line function wrapped round an emit, so callers write Game.say("Put down.") and read naturally. Scripts all over the game call it. None of them knows the interface exists; if the HUD were removed the lines would go unheard and nothing would break.

Main listens too

Main.gd builds the whole game in _ready(), and at the end of that wiring it connects the other three:

Main.gd · lines 305–307

Game.orientation_changed.connect(_apply_orientation)
Game.day_changed.connect(_on_new_day)
Game.farm_updated.connect(_on_farm_updated)

_on_new_day is declared as func _on_new_day(_d: int): the signal sends the day number, so the function must accept it, and the underscore says it does not use it. The lines above these in Main._ready() are "call down, signal up" from top to bottom. Main creates the HUD, the dialogue box and the cards as its children, calls their functions directly, and connects to their signals – request_room, closed, farm_changed and a dozen more. A button in the HUD announces that the player asked for a card; Main decides what that means.

Your turn

Six exercises, from a first connection to a function that waits. The fourth and fifth are the ones that catch people out.

What to remember

  • A signal says what happened, to whoever asked to be told. The emitter does not know who is listening, and nobody listening is fine.
  • signal name(params) declares, emitter.name.connect(function) listens – the function's name, no brackets – and name.emit(values) calls every listener at once, in connection order.
  • .bind(extra) adds arguments after the signal's own; CONNECT_ONE_SHOT hears it once; ask is_connected before connecting or disconnecting twice.
  • Nodes come with signals – pressed, timeout, body_entered – and they connect the same way as yours.
  • Call down, signal up: parents call their children's functions, children announce, and a shared parent introduces siblings.
  • await signal pauses a function until the signal arrives and returns what it carried. The caller carries on meanwhile, unless it awaits the call.
