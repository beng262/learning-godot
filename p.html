Pixel art done right

Filtering, integer scaling, stretch modes and snapping – the settings that decide whether pixels stay pixels.

In this chapter

  • what a texture filter is, why Godot's default blurs pixel art, and the one setting that stops it
  • why a sprite drawn at 3.5 times its size looks ragged, and how to work out the whole-number scale that fits a screen
  • stretch mode, aspect and integer scaling – how a small game fills a big window
  • snapping: keeping an exact position and still drawing on whole pixels
  • one pixel density for all your art, the rule Little Hours is built on

Who decides the colour between pixels

A texture is a grid of colours. As soon as it is drawn at any size but its own, something has to decide what colour each pixel of the screen gets. That something is the filter, and Godot's default is the wrong one for pixel art.

One square of a texture is called a texel, to keep it apart from a pixel of the screen. Draw a 12 × 12 sprite at three times its size and each texel has to cover nine screen pixels. There are two ways to fill them in:

  • Nearest – each screen pixel takes the colour of the texel it lands on. Hard edges, and only the colours the artist chose.
  • Linear – each screen pixel is a blend of the texels around it. Smooth, which is right for a photograph or a 3D wall and wrong for a face that is six texels wide.

Here is one small sprite at six sizes. Tick the box to switch to Linear, then untick it and look closely at the ones marked uneven – that is the second half of this chapter.

Linear filtering does more than soften edges. It invents colours. A pixel artist picks a palette of perhaps sixteen colours on purpose; a blend puts a new one wherever two of them meet. This prints what a screen pixel gets when it falls between a dark outline and a skin tone:

extends Node

func _ready() -> void:
	var outline := Color("#3a2b30")
	var skin := Color("#f1c39b")
	# t is how far across the gap the screen pixel sits.
	for t in [0.0, 0.25, 0.5, 0.75, 1.0]:
		var nearest: Color = outline if t < 0.5 else skin
		var linear: Color = outline.lerp(skin, t)
		print(t, "   nearest #", nearest.to_html(false), "   linear #", linear.to_html(false))

The nearest column only ever holds the two colours that were drawn. The linear column holds three that nobody drew. Press Edit and run and add 0.1 to the list: another new colour.

Setting it

The filter for the whole game is in Project Settings → Rendering → Textures → Canvas Textures → Default Texture Filter. Set it to Nearest. In project.godot that is one line, and it is the first thing to do in any pixel-art project:

[rendering]

textures/canvas_textures/default_texture_filter=0

0 is Nearest and 1, the default, is Linear. Every node that draws in 2D also has its own texture_filter property, under CanvasItem → Texture in the Inspector. It starts as Inherit: do what my parent does. The chain of parents ends at the project setting, so one setting covers everything, and a single node can still disagree:

# This node and its children, whatever the project says:
$Photo.texture_filter = CanvasItem.TEXTURE_FILTER_LINEAR

# Back to "do what my parent does", the default:
$Photo.texture_filter = CanvasItem.TEXTURE_FILTER_PARENT_NODE

If a tutorial tells you to untick Filter in the Import dock

It is about Godot 3, where the filter was part of how an image was imported. In Godot 4 it belongs to whatever draws the image, which is why it is a project setting and a node property and no longer an import option.

What the Import dock still decides

Select a PNG in the FileSystem dock and the Import dock (beside the Scene dock) shows how Godot will turn it into a texture. The choices are saved in the .import file next to the image. For pixel art the defaults are already right, and it is worth knowing which two matter so you never change them by accident:

SettingKeep it atWhy
Compress → ModeLosslessThe texture is stored exactly as drawn. Lossy and VRAM Compressed save memory by changing colours a little, which shows as speckles on flat pixel art.
Mipmaps → GenerateOffMipmaps are smaller, pre-blurred copies used when a texture is drawn tiny. Pixel art is never drawn smaller than it was made.

Every image in Little Hours has the same two lines in its .import file:

compress/mode=0
mipmaps/generate=false

Fonts have import settings too, and a pixel font needs three of them turned off: Antialiasing, Hinting and Subpixel Positioning. Each one is a way of smoothing the edge of a letter, and a pixel font has no edge to smooth. Chapter R comes back to text.

Whole numbers only

Nearest filtering keeps pixels sharp. It does not keep them the same size. That takes a second rule: pixel art is only ever scaled by a whole number.

With Nearest, each screen pixel looks back into the texture and takes the texel it lands on. This draws one row of eight texels at twice and three times its size, using letters for colours:

extends Node

const ROW := "A.B.C.D."   # eight texels in a row

## Which texel does screen pixel x show, at this scale?
func texel_under(x: int, scale: float) -> int:
	return int((x + 0.5) / scale)

func _ready() -> void:
	for scale in [2.0, 3.0]:
		var drawn := ""
		for x in range(int(ROW.length() * scale)):
			drawn += ROW[texel_under(x, scale)]
		print("x", scale, "  ", drawn)

Every texel became two screen pixels, then three. Now change the list to [2.0, 2.5]. Twenty screen pixels cannot be shared evenly among eight texels, so some get two and some get three. On a face, that is one eye wider than the other.

The + 0.5 asks about the middle of the screen pixel and not its left edge, which is what a renderer does. Counting makes the pattern plain:

extends Node

## How many screen pixels each of `count` texels gets at this scale.
func widths(count: int, scale: float) -> Array:
	var out := []
	for i in range(count):
		out.append(0)
	for x in range(int(count * scale)):
		out[int((x + 0.5) / scale)] += 1
	return out

func _ready() -> void:
	print("x3.0   ", widths(8, 3.0))
	print("x3.5   ", widths(8, 3.5))
	print("x2.25  ", widths(8, 2.25))
	print("x2.979 ", widths(8, 2.979))

Three and a half times gives threes and fours in turn. The last line is the nasty one: 2.979 is so close to 3 that almost every texel comes out three wide, and one in the row does not. Those three scales are not made up. They are what an earlier version of Little Hours drew its dog, its cat and one kitchen table at, and you will see how that happened below.

The largest whole scale that fits

So the question for a pixel game is never "how big is the window?" but "how many whole times does my game fit in it?". Dividing one int by another throws the remainder away (Chapter D), and for once that is exactly the sum wanted:

extends Node

const GAME := Vector2i(320, 180)

func whole_scale(view: Vector2i, screen: Vector2i) -> int:
	return mini(screen.x / view.x, screen.y / view.y)

func _ready() -> void:
	for screen in [Vector2i(1280, 720), Vector2i(1920, 1080), Vector2i(1366, 768), Vector2i(2560, 1600)]:
		var n := whole_scale(GAME, screen)
		print(screen, "  x", n, "  drawn ", GAME * n)

mini takes the smaller answer because the game has to fit both ways. 320 × 180 is a popular size for exactly this reason: it goes into 1280 × 720, 1920 × 1080 and 3840 × 2160 a whole number of times. A 1366 × 768 laptop is the awkward one, with pixels left over on every side. Change GAME to Vector2i(400, 225) and see which screens it suits.

In the real editor Godot marks screen.x / view.x with a warning, integer division, decimal part will be discarded, so that nobody does it by accident. Little Hours writes the same sum as int(float(screen.x) / float(view.x)) to say it is on purpose.

One density for all the art

There are three kinds of pixel in a pixel-art game, and mixing them up is where the trouble starts:

  • an art pixel – one square as the artist drew it;
  • a file pixel – one square of the PNG, which is not always the same thing: many packs are sold already enlarged, each art pixel saved as a 3 × 3 block;
  • a screen pixel – what the player's display has.

The density of a sprite is how many screen pixels one of its art pixels covers. If the sofa is at six and the dog is at four, the dog looks as if it came from a different game, however sharp both are. So choose one density and give every file the scale that reaches it:

extends Node

const DENSITY := 6   # screen pixels per art pixel, for everything

# file pixels per art pixel, as each pack was saved
const PACKS := {"old furniture": 1, "town pack": 3, "icons": 2, "odd one": 4}

func _ready() -> void:
	for pack in PACKS:
		var per: int = PACKS[pack]
		var scale := DENSITY / per
		var fits := DENSITY % per == 0
		print(pack, ": scale ", scale, "  ->  ", per * scale, " per art pixel", "" if fits else "   WRONG")

Three packs land on six. The fourth cannot: 6 / 4 is 1 in whole numbers, and a sprite saved four to one would need a scale of 1.5. The remainder operator % is the test. Art like that has to be redrawn or resized in an image editor, once, and not at run time.

Filling the window: stretch mode and aspect

Your game has one size and the player's screen has another. Three project settings say what happens to the difference, and for pixel art one combination of them does most of the work for you.

The game's own size is the base size: Project Settings → Display → Window → Size → Viewport Width and Viewport Height. Everything you place is measured in it. Under Display → Window → Stretch are the three settings that fit it to a real window.

Mode: what gets stretched

ModeWhat happensGood for
disabledNothing is stretched. A bigger window shows more of the world at the same size.Tools, and games that lay themselves out by hand.
canvas_itemsThe base size is stretched to cover the window, and everything is drawn at the window's real resolution.Pixel art with sharp text and a smooth camera on top – if you keep the rules in this chapter yourself.
viewportThe game is drawn at exactly the base size into an image, and that image is enlarged.Low-resolution games where nothing may ever sit between two art pixels.

The difference shows when something moves or turns. In viewport mode a sprite rotated by ten degrees is redrawn in big art pixels, as it would have been on an old console. In canvas_items mode it is rotated smoothly at the screen's resolution, which is sharper and no longer looks like pixel art. Neither is a mistake; they are two looks.

Aspect: what happens to the spare room

A 16:9 game on a 16:10 screen has room left over. Aspect says where it goes:

AspectThe spare room becomes
ignoreNothing: the picture is pulled out of shape to fill the window. Never for pixel art.
keepBlack bars. The whole base size is always visible and nothing else is.
keep_width / keep_heightMore game in the other direction: the width (or height) stays as designed and the other side grows.
expandMore game in whichever direction has room.

Scale mode: whole or not

The third setting, Scale Mode, is the one this chapter has been walking towards. fractional, the default, stretches by whatever number fills the window: 3.56, if that is what it takes. integer rounds that number down to a whole one, and never below one. It is the last section's sum, done by the engine every time the window changes size.

This models keep with each scale mode. The bars are what is left over, shared between the two sides:

extends Node

const BASE := Vector2i(320, 180)

func fit(window: Vector2i) -> void:
	var exact := minf(float(window.x) / BASE.x, float(window.y) / BASE.y)
	var whole := maxi(1, int(exact))
	var drawn := BASE * whole
	var bars := (window - drawn) / 2
	print(window, "  fractional x", snappedf(exact, 0.01), "  integer x", whole, "  drawn ", drawn, "  bars ", bars)

func _ready() -> void:
	fit(Vector2i(1920, 1080))
	fit(Vector2i(1366, 768))
	fit(Vector2i(1920, 1200))
	fit(Vector2i(800, 600))

On the 1366 × 768 laptop the fractional answer is 4.27, a ragged scale, and the integer answer is 4 with a border 43 pixels wide and 24 tall. A thin border is the price of even pixels, and most players never notice it; uneven pixels they notice at once. Add fit(Vector2i(300, 160)): the scale stays at one and the bars go negative, which means the edges of the game are cut off. A pixel game has a smallest window.

A starting point

For a game that is all pixel art at a low resolution: base size 320 × 180 or close to it, mode viewport, aspect keep, scale mode integer. For pixel art with crisp text over it and a camera that glides: mode canvas_items, scale mode integer, and aspect keep or expand. With expand there are no bars – the player sees a little more of the world instead – so the interface must be laid out to cope with a screen of any shape, which is Chapter R.

Snapping to whole pixels

A whole-number scale puts every texel on a clean block of screen pixels – as long as the sprite itself starts on one. Positions in Godot are floats, and a sprite at x = 100.4 starts four tenths of a pixel in.

A position between pixels shows in two ways. Standing still, the sprite's edges fall unevenly, the same fault as a fractional scale. Moving, it shimmers: each column of texels flicks between two widths as the fraction changes. The cure is round(), and the question is where to put it.

extends Node

func _ready() -> void:
	var at := Vector2(100.4, 60.5)
	print("exact        ", at)
	print("whole pixels ", at.round())

	# When one art pixel is 3 screen pixels, snap to the art's own grid:
	var art := 3.0
	print("art grid     ", (at / art).round() * art)

	# A centred sprite 15 wide starts half a pixel off even at a whole position:
	var size := Vector2(15, 16)
	print("top-left     ", Vector2(100, 60) - size / 2.0)

The third line is the general recipe for snapping to any grid: divide by the grid, round, multiply back. The last line is a trap that catches everybody once. A Sprite2D is centred on its position by default, so a texture with an odd width begins at a half pixel however carefully the node is placed. Either draw art with even sizes or turn Offset → Centered off for those sprites.

Round what you draw, not what you store

The tempting fix is to round the position as you move it. Do that and a slow character never moves at all: a third of a pixel a frame rounds back to where it started, sixty times a second. You will mend exactly that bug in the exercises. The exact position is the truth, used for movement and collision; the rounded one is only where the picture goes.

Godot can do the rounding for you. Project Settings → Rendering → 2D → Snap → Snap 2D Transforms to Pixel draws every node at a whole pixel while its position keeps its fraction:

[rendering]

2d/snap/snap_2d_transforms_to_pixel=true

Beside it is Snap 2D Vertices to Pixel, which does the same for the corners of whatever is drawn. Turn on the first for any pixel-art game. It costs a little smoothness, because things now move in steps of one pixel, and that step is the look you chose.

The camera has to agree

Snapping each thing by itself is not always enough. What reaches the screen is the sprite's position minus the camera's, and if the two are rounded separately they can round in different directions. Here both move right at the same speed, so the sprite ought to stay in one place on the screen:

extends Node

func _ready() -> void:
	var camera := 100.4
	var sprite := 200.7
	for frame in range(6):
		var apart := roundf(sprite) - roundf(camera)   # each snapped alone
		var together := roundf(sprite - camera)        # snapped as one
		print("frame ", frame, "  on screen at ", apart, "   should be ", together)
		camera += 0.2
		sprite += 0.2

The left column hops between 100 and 101 while the right one stays put. That hop is jitter, and it is why a character can tremble against a scrolling background. The fixes are all the same idea: put the camera on a whole pixel too (the snap setting does this), and if a Camera2D has position smoothing on, expect it to pass through fractions on its way.

In Little Hours

Little Hours moved to Godot for the subject of this chapter. Its own notes say the web version never fully solved "pixel sizes are not the same", and the cure was to stop working scales out and start writing them down.

The settings

Nearest filtering and pixel snapping are the two lines of project.godot you have already seen. The stretch settings come with the story of a mistake:

../project.godot · lines 64–77

[display]

window/size/viewport_width=768
window/size/viewport_height=1344
window/stretch/mode="canvas_items"
window/stretch/scale_mode="integer"
; "keep" letterboxes rather than crops, and that is now the right choice
; because the base size is no longer fixed at 768x1344: Main._fit_view_to_phone
; derives the view from the surface it has to fill, so the view already carries
; the screen's aspect ratio and "keep" produces no bars at all. This was briefly
; "expand", which filled the phone but CROPPED any window smaller than the
; authored size — shrink the window and the edges of the game were cut off.
; With an adaptive view, "keep" fills the same screen and clips nothing.
window/stretch/aspect="keep"

Mode canvas_items, scale mode integer, aspect keep. The game is pixel art with a lot of text over it, so it draws at the screen's resolution and holds itself to whole numbers. The comment records that expand was tried and cropped small windows, and why keep no longer means black bars here: the game changes its own base size to match the screen, which is the third quote below.

A whole scale for every sprite

Assets.gd is a table from a piece of furniture's name to a picture and a whole-number scale. Its files come from two families, one saved one to one and one saved three to one, so the stored scales are 6 and 2 and both reach the same density. A single dial, DENSITY_DIV := 2, then divides every stored scale by the same whole number – maxi(1, base / DENSITY_DIV) – so today one art pixel is three game pixels everywhere. This is where a scale is used, in RoomView.gd, as a room's furniture is built:

RoomView.gd · lines 342–349

var s := Sprite2D.new()
s.texture = tex
_animate(s)
s.centered = true
s.scale = Vector2(sc, sc)
# Snap to whole pixels: a sprite centred on a half-pixel re-introduces
# the uneven-edge look the integer scale exists to prevent.
s.position = centre.round()

sc is an int that came out of the table, used for both axes, so no sprite can be wider than it is tall by a fraction as the cook table once was. And the position is rounded as it is set, for the reason its comment gives: a sprite centred on a half pixel undoes everything the whole scale was for. Furniture never moves, so rounding once is enough. (Assets.gd and RoomView.gd in the tour.)

Choosing the view from the screen

On a desktop the game sizes its window to a whole multiple of its view, with a function that is the tutorial's first step almost word for word: _whole_scale(view, screen) returns mini(int(float(screen.x) / float(view.x)), int(float(screen.y) / float(view.y))). A phone cannot resize its window, and no whole multiple of a fixed view fills every phone. So on a phone the sum is turned round. The game picks the largest whole scale at which a smallest useful view still fits, then makes the view whatever the screen is, divided by that scale:

Main.gd · lines 2589–2605

var raw := DisplayServer.window_get_size()
if raw.x <= 0 or raw.y <= 0:
	return
var long_side: int = maxi(raw.x, raw.y)
var short_side: int = mini(raw.x, raw.y)
var screen := Vector2i(long_side, short_side) if Game.landscape \
	else Vector2i(short_side, long_side)
# Landscape-only, so no swapping: the minimum is written the way the game
# is held.
var min_w := Game.MIN_VIEW_LANDSCAPE.x
var min_h := Game.MIN_VIEW_LANDSCAPE.y
var n: int = maxi(1, mini(int(float(screen.x) / float(min_w)),
	int(float(screen.y) / float(min_h))))
var view := Vector2i(screen.x / n, screen.y / n)
get_window().content_scale_size = view
Game.view_scale = n
Game.set_view_override(view)

Game.MIN_VIEW_LANDSCAPE is 940 × 520. A 1920 × 1080 phone gives n = 2 and a view of 960 × 540; a 2856 × 1280 one also gives 2, and a view of 1428 × 640. The view times n is the screen again, to within a pixel or two lost to the division, so there are no bars and every art pixel is still a whole block. The price is that different phones see different amounts of the room, which is only acceptable because the camera follows the player. content_scale_size is the base size from Project Settings, set from code. The first lines are there because, just after asking Android to turn the screen, the two numbers can still arrive the wrong way round. The whole story is under Orientation and camera in the mechanics, and in Main.gd and Game.gd in the tour.

Snapping the picture, not the person

The resident walks at speeds that put her between pixels on most frames. The last lines of her movement code are the tutorial's fifth step:

Player.gd · lines 486–489

# Pixel-art bodies must land on whole pixels or the sprite shimmers as it
# walks. The node keeps its exact position for collision and depth; the art
# is nudged by the fraction so it draws on the grid.
_avatar.position = position.round() - position

position is the exact place, used for collision and for sorting her in front of or behind the furniture. _avatar is the child node that holds her picture, and a child's position is measured from its parent. Moving it by position.round() - position – the distance from the exact place to the nearest whole pixel – puts the picture on the grid and leaves the truth alone. The camera is rounded in the same way wherever Main.gd sets it: _camera.position = (_player.position + lead).round(). (Player.gd in the tour; walking itself is Reaching.)

Your turn

Five problems, each one a sum a pixel-art game has to get right somewhere.

What to remember

  • Set Default Texture Filter to Nearest before anything else. Linear blends texels and invents colours; it is a project setting and a node property in Godot 4, not an import option.
  • Scale pixel art by whole numbers only. At 3.5 times, some texels are three screen pixels wide and some four.
  • Choose one density – screen pixels per art pixel – and give every file the whole scale that reaches it. Art that cannot reach it is fixed in an image editor, not at run time.
  • Stretch Mode says what is enlarged, Aspect says where spare room goes, and Scale Mode integer keeps the enlargement whole. The largest whole scale is mini(screen.x / view.x, screen.y / view.y).
  • Keep positions exact and round only what is drawn. Half a pixel hides in odd-sized centred sprites and in anything centred in an odd space.
  • The camera must land on whole pixels too, or sprites jitter against the world.
