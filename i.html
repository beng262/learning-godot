In the loop: the node lifecycle

_init, _enter_tree, _ready, _process, _physics_process and delta – the order things happen in, frame by frame.

In this chapter

  • the life of a node, in order: _init, _enter_tree, _ready, then the frames, then _exit_tree
  • why children are ready before their parent, and what that lets you rely on
  • _process(delta) and why every movement is multiplied by delta
  • _physics_process: the other clock, which ticks at a steady rate
  • turning processing off with set_process, and answering the engine with _notification

The life of a node

A node is not just there. It is made, it joins the running game, it gets ready, it is asked to do something sixty times a second, and one day it leaves. Godot tells it about each of those moments by calling a function with a fixed name, if the script has written one.

You have used one of these since Chapter A: _ready(). The rest of the family works the same way. Godot looks for a function with the right name, and calls it at the right moment; you never call them yourself. They begin with an underscore as a signal that they are Godot's to call, and the whole set is called the callbacks or virtual functions of a node.

FunctionWhen Godot calls itWhat is safe to do there
_init()when the object is created, before it is in any sceneset up your own variables. The node has no parent, no children and no tree yet.
_enter_tree()when the node is added to the tree – before its children arethings that need a parent, but not its children
_ready()once, when the node and all its children are in the tree and readyfind children, connect signals, set the starting state
_process(delta)every frame, as often as the screen is drawnanything that changes smoothly or is checked continuously
_physics_process(delta)at a steady rate, 60 times a second by defaultmovement and collision
_exit_tree()when the node is about to leave the treelet go of what it started: a connection, a server resource

_init and _ready, side by side

The two you will most often confuse. _init runs when the object is made, so it is the place for things that depend on nothing: a number, an empty array. _ready runs when the node has joined the game, so it is the place for things that depend on the game: its children, its parent, its place on screen. Here is the order they and the variable lines come in:

extends Node

var created := say("1. a variable's starting value")
@onready var onready_value := say("3. an @onready variable")

func say(text: String) -> bool:
	print(text)
	return true

func _init() -> void:
	print("2. _init")

func _ready() -> void:
	print("4. _ready")

Variables with a starting value are filled in first; then _init runs; then, when the node enters the game, any @onready variables are worked out, and only then _ready. That is the real reason @onready exists. A line such as @onready var label := $Label has to wait until there is a tree to look in, and writing it as an @onready means that it is done at exactly the right moment with no _ready to write. The page can run _init and _ready but has no tree, so it cannot show _enter_tree: it sits between 2 and 3, and it is the one you will use least.

Children first

The rule that surprises people: when a scene is added to the tree, its children become ready before the node that owns them. The parent's _enter_tree comes first, going down; the _ready calls come back up from the leaves. That ordering is a promise, and it is why a parent can write $Label.text = "Hi" in its own _ready and be sure that the label exists and has had its own set-up done.

The page has no scene tree, but a tree is a nested structure, and the order can be written in a dozen lines: visit every child first, then the node itself. This is the recursion from Chapter F.

extends Node

var scene := {"name": "Main", "kids": [
	{"name": "Room", "kids": [
		{"name": "Chair", "kids": []},
		{"name": "Lamp", "kids": []}]},
	{"name": "Hud", "kids": []}]}

func ready_order(node: Dictionary, out: Array) -> void:
	for kid in node["kids"]:
		ready_order(kid, out)
	out.append(node["name"])

func _ready() -> void:
	var out := []
	ready_order(scene, out)
	print(out)

Chair and Lamp are ready first, then their parent Room, then Hud, and last of all Main, the root. Move the line out.append(...) above the loop and you get the order of _enter_tree instead: parents before children, top to bottom. It is the same tree walked the other way, which is why one runs "down" and the other "up".

The trap: asking a sibling too early

Children first does not mean that siblings are ready in a useful order for each other. Two nodes in the same parent are ready in the order they sit in the tree, so a node must not reach into a sibling that is further down and expect it to have run yet. If one thing depends on another, put the dependency in the parent, or have the second announce when it is ready with a signal (Chapter J).

_exit_tree: tidying up

When a node is removed from the game with queue_free() or the scene changes, Godot calls _exit_tree() on it, children first this time, and then frees it. Most nodes need nothing here, because Godot cleans up children and connections for you. The exception is anything you asked outside the tree to hold for you. A game that builds a navigation region on a server, for example, has to give it back, and that is a good use of _exit_tree; you will see the game doing exactly that below.

Every frame: _process and delta

A game is a loop that draws a picture over and over. _process(delta) is how a node gets a turn in that loop – and delta is how it tells how long the last turn took.

On a laptop the picture may be redrawn 144 times a second. On an old phone, 30. A frame is not a fixed amount of time. Godot hands every _process a single number to deal with that: delta, the seconds since the previous frame, as a float. At 60 frames a second it is about 0.0167; at 30, about 0.033. Try it: slide the frame rate, and watch how many times each function runs in a quarter of a second.

The ticks on the _process lane crowd together at a high frame rate and spread out at a low one, while the _physics_process lane does not move. Now let us see why delta matters, without Godot at all. A character should walk 60 pixels in a second. One way adds a fixed step each frame; the other multiplies by delta:

extends Node

const SPEED := 60.0   # pixels a second

func walk_per_frame(fps: int, seconds: int) -> float:
	var x := 0.0
	for i in fps * seconds:
		x += 1.0                  # a step per frame
	return x

func walk_with_delta(fps: int, seconds: int) -> float:
	var x := 0.0
	var delta := 1.0 / fps
	for i in fps * seconds:
		x += SPEED * delta        # a step per second
	return x

func _ready() -> void:
	for fps in [30, 60, 144]:
		print(fps, " fps: ", walk_per_frame(fps, 1), " by frame, ", walk_with_delta(fps, 1), " by delta")

The first way gives 30, 60 and 144 pixels in the same second: the game plays at a different speed on every machine. The second gives 60 every time (a little rounding off in the last digit is float arithmetic, as in Chapter D). Change seconds to 3, and the second is still the same for all three frame rates. The rule is easy to remember: anything that changes with time is multiplied by delta. Speeds, timers, fades and fills; a speed of 60 pixels a second is written 60.0 * delta inside _process.

Counting time

A timer is a variable that delta adds to. When it passes a number, something happens, and it starts again:

extends Node

var timer := 0.0
var blinks := 0

func tick(delta: float) -> void:
	timer += delta
	if timer >= 0.5:
		timer -= 0.5          # keep the remainder, do not reset to 0
		blinks += 1

func _ready() -> void:
	for i in 60:
		tick(1.0 / 60.0)
	print(blinks, " blinks in one second")

Here _ready stands in for Godot and calls tick sixty times with a 60 fps delta, a second of play. timer -= 0.5, rather than timer = 0.0, keeps the little bit that went over on this frame, so the blinks do not slowly lag behind. The same function is two blinks a second at any frame rate. In the game's _process below this is the day itself: clock_t += delta * ....

Keep _process light

It runs on every frame of every node that has one, so five milliseconds of work in it costs you the whole frame. Do not search a list in it when you could hold the answer, do not build a new array in it when you could reuse one, and do not call a function that touches the disk. If something only needs to happen when something changes, a signal is cheaper than checking every frame.

_physics_process: the steady clock

Physics does not tolerate a wobbling clock. Collision, gravity and anything that has to behave the same on every machine run on a second loop that ticks at a fixed rate.

Godot runs _physics_process(delta) at a steady 60 ticks a second by default, whatever the screen is doing. If the game draws 144 frames a second, there are still 60 physics ticks and several frames pass between two of them; if it draws 20, Godot runs more than one physics tick in a frame to catch up. In both cases delta inside it is the same number every time, 1/60. That sameness is the point. Two players with different computers get the same jump, the same bump.

The idea is called a fixed time step, and the loop in the engine is small enough to write out. Real frames arrive with whatever delta they have; the clock adds them up into an accumulator; and every time the accumulator holds a whole tick, a tick is run and paid for:

extends Node

const TICK := 0.0625          # a tick every sixteenth of a second

var acc := 0.0
var ticks := 0

func frame(delta: float) -> void:
	acc += delta
	while acc >= TICK:
		acc -= TICK
		ticks += 1            # _physics_process would run here

func _ready() -> void:
	for d in [0.0625, 0.03125, 0.125, 0.0625]:
		frame(d)
		print("frame of ", d, " s: ", ticks, " ticks so far")

A frame of 0.125 pays for two ticks in one go; one of 0.03125 sometimes pays for none, and its time is kept for the next. Change the list to eight frames of 0.03125 and the total is the same four ticks. This is why physics is stable and why _physics_process is where move_and_slide() belongs (Chapter K).

The rule of thumb that follows: if a body is moved by the physics engine or moves a CharacterBody2D, do it in _physics_process. Anything else – reading a timer, animating a bar, moving the camera, watching for a key – belongs in _process. Do not mix the two for the same thing: moving a body in both gives it two chances to move in a frame.

Sixty ticks are not sixty frames

One consequence needs a name. When a screen draws 144 times a second but physics ticks at 60, a body moved only in _physics_process jumps forward every 2.4 frames, and looks very slightly stuttery. Godot can smooth that over for you (physics interpolation, a project setting), and a game that cares reads about it; a game like Little Hours, which moves things by hand in _process, never meets the problem.

Turning it off, and being told things

A node that is not doing anything should not be asked every frame whether it is. And some events – a window closed, a phone's back gesture – arrive from outside the game and need an answer.

set_process

set_process(false) stops Godot calling a node's _process; set_process(true) starts it again. set_physics_process does the same for the physics tick, and is_processing() asks. Your own function can keep running, signals are still delivered, and the node is still drawn. It is only not asked for its frame. An idle button, a door nobody is near, a bar that is full: switch off and wake it up when something changes.

Here is the trap: a node that has switched its own processing off cannot switch it back on from _process, because _process is no longer being called. Something else has to do it – a signal, a timer or another node. You will use a timer in the tutorial below.

Pausing the whole game

get_tree().paused = true freezes every node whose process_mode is the default, which follows its parent. A node can opt out: set process_mode to Node.PROCESS_MODE_ALWAYS and it keeps running while everything else is held, which is how a pause menu keeps working. PROCESS_MODE_WHEN_PAUSED is the opposite, and PROCESS_MODE_DISABLED turns the node off entirely. The same setting is in the Inspector under Process > Mode.

_notification

Besides the named callbacks, Godot sends every node a stream of numbered notifications, and a single function _notification(what: int) receives them all. Constants say which: NOTIFICATION_READY and NOTIFICATION_EXIT_TREE are the lifecycle ones you have just met, from another door, and some are about the world outside, such as NOTIFICATION_WM_CLOSE_REQUEST (somebody closed the window), NOTIFICATION_WM_WINDOW_FOCUS_OUT (the player switched to another app) and, on Android, NOTIFICATION_WM_GO_BACK_REQUEST (the back gesture).

func _notification(what: int) -> void:
	if what == NOTIFICATION_WM_CLOSE_REQUEST:
		save_game()

Read it as a question and an answer: Godot asks "has something happened?" with a number, and you answer for the numbers you care about and ignore the others. Phones in particular can end a game without warning, which is why a notification about losing focus is the right moment to save. You will see that exact use in a moment.

Build it live

A square that walks across the screen at the same speed on any machine, tells you how long it has been walking, and can be told to stop and start by switching its processing off and on. Every step uses one idea from this chapter, in the order in which Godot meets them.

In Little Hours

Little Hours has a handful of nodes that matter every frame, and the whole of the game's behaviour is a fan of small functions that those few _process calls fire. Two of them hold the day; one hands the engine's questions an answer.

Time passes in Game

Game.gd · lines 440–448

func _process(delta: float) -> void:
	if night_held:
		return
	clock_t += delta * mode_day_scale()
	if clock_t >= DAY_LENGTH:
		clock_t = DAY_LENGTH
		night_held = true
	_tick_farm()
	_tick_texts(delta)

This is the first tutorial of the chapter, grown up. clock_t += delta * mode_day_scale() is the timer from the "Counting time" example: seconds added every frame, so the day takes the same real time on any phone. When it passes DAY_LENGTH it is pinned there and night_held is set, and the very first line of the function sees that and stops. Game is an autoload, a node added to the tree before the game's main scene, so this _process runs for the whole life of the program. How the clock fits together, and the way the night is held until the player goes to bed, is C: Clock; the autoload's place is in Game in the tour.

The same file's _ready is a lesson in order. Its comments say that orientation "has to be settled before Main builds a room", and that is true because autoloads are made, and made ready, before the main scene. Game loads the save and fixes the layout of the rooms; only then does Main's _ready start creating them.

Main: one _process, many small ticks

void:" data-to="_tick_hold(delta)">

Main is the scene that owns the room, the people and the camera, and its _process is a list. It does not do the work itself; each line calls a small function (_tick_events, _tick_creatures...) with the same delta, so that each one can be read, changed and tested on its own. Look at the early return: while the opening sequence plays, it "owns the camera, the cast and the clock", so the rest of the frame does nothing. The next block moves the camera to the player and rounds it with .round(), whole pixels, which is the subject of Chapter P. Two lines use Time.get_ticks_msec() rather than a counter: the opening question card is shown 1.4 seconds after start and a hint after 3.2, which is a cheap way to say "a little while after the game began". Leaving, and being told

Main.gd · lines 1018–1021

		_nav_region = RID()

Game.gd · lines 1236–1245

func _notification(what: int) -> void:
	# Autosave when the game loses focus, is backgrounded, or quits — phones kill
	# backgrounded apps without warning, so this is the save that actually matters
	# on mobile. These four are all Node-level notifications; the
	# NOTIFICATION_APPLICATION_* family lives on MainLoop and is not in scope here.
	if what == NOTIFICATION_WM_CLOSE_REQUEST \
			or what == NOTIFICATION_WM_GO_BACK_REQUEST \
			or what == NOTIFICATION_WM_WINDOW_FOCUS_OUT \
			or what == NOTIFICATION_EXIT_TREE:
		save_now()

The first is the tidy-up described under "_exit_tree". Main asked the navigation server for a region of its own, and servers live outside the scene tree, so when Main leaves the tree it frees the region by hand. Without it the server would keep a region for a room that no longer exists.

The second is the _notification from the chapter, answering four different questions with one answer. Closing the window, the back gesture, losing focus and leaving the tree all end in save_now(). The comment says why: "phones kill backgrounded apps without warning, so this is the save that actually matters on mobile". NOTIFICATION_EXIT_TREE is on the list because it is the notification form of _exit_tree, so a save also happens when the game shuts down in an ordinary way. How saving works is S: Saving. Main has its own _notification for the back gesture: it closes an open card first, and only asks to leave when there is nothing left to close.

What to remember

  • A node's callbacks run in a fixed order: _init when it is made, _enter_tree going down the tree, _ready coming back up (children first), then the frames, then _exit_tree.
  • @onready variables are filled in just before _ready. Use _ready for anything that needs the tree; use _init only for what needs nothing.
  • _process(delta) runs every frame and delta is the seconds since the last. Multiply every speed, timer and fade by it, and the game runs the same on any machine.
  • _physics_process runs at a steady 60 ticks a second with a constant delta: the place for bodies and collision. Do not move the same thing in both.
  • set_process(false) stops a node being called; something else has to wake it. get_tree().paused and process_mode hold or exempt a whole branch.
  • _notification(what) receives the engine's messages from outside the game: closing, losing focus, the back gesture. A phone game saves on those.
