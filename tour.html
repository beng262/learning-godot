Before the files

The shape of it

Most Godot projects are a tree of .tscn files put together in the editor. Little Hours is a tree of function calls: one scene, one node, and everything else built in code when the game starts.

This is the whole of scenes/Main.tscn – one Node2D called Main with one script:

[gd_scene load_steps=2 format=3]

[ext_resource type="Script" path="res://scripts/Main.gd" id="1"]

[node name="Main" type="Node2D"]
script = ExtResource("1")

When it enters the tree, Main.gd creates the room, the resident, the pets, the neighbours, the heads-up display and the cards with .new() and add_child(), and connects their signals itself. Nothing is wired up by hand in the editor, so there are no scene files to fall out of step with the code, and the project runs the moment it is opened. The cost is that you cannot see the game laid out in the editor's 2D view – you read it here instead.

Three things are always there

Three scripts are autoloads, listed under Project Settings › Globals. Godot creates each one before the main scene and keeps it alive for the whole run, reachable from any script by its name:

NameWhat it holds
GameAll the state that outlives a room: the day, the clock, what you own, who you know, and saving and loading it.
SfxEvery sound, synthesised in code rather than loaded from audio files.
TownMindThe on-device language model that gives the townsfolk small talk.

Data and the things that draw it

Many files come in pairs: one that is data and one that draws or acts on it. RoomData.gd describes the 50 rooms and RoomView.gd draws whichever one you are in; NeighborData.gd holds the townsfolk and Neighbor.gd walks one about. The data files extend RefCounted and are mostly constants and static functions – no node, nothing in the tree. Keeping them apart means a room or a person can be added by writing a table entry, without touching the code that draws them.

Inside the code

The core

Five files hold the game up. Main.gd is the one scene, which builds every other node and decides what each tap means. Game.gd is the state that outlives every room, the clock and the save file. Lang.gd, Today.gd and Ripple.gd are small helpers the other two lean on.

Main.gd

The whole game, assembled. Little Hours has a single .tscn file holding one Node2D, and this is its script: it creates the room, the people, the animals, the camera and the interface in code, then sends each tap, drag and key press to whoever should handle it.

The file opens by listing what it owns: the room renderer, the resident, the partner, the dog and the cat, tap routing, decorating, the day and night wash, the weather, the HUD and the overlay stack. Under that comes a long list of member variables, one per thing it builds (_room_view, _player, _dog, _hud, _overlays and so on). They are typed with the classes the other scripts declare with class_name, which is why Main can write RoomView.new() without loading anything. After that the file falls into sections, each with a ruled banner comment: rooms, decorate mode, tap routing, the keys, hover, talking, written conversations, farming, the per-frame tick, ambient events, the day and night wash, and the code that fits the window to the screen. An inner class, Weather, sits at the very bottom.

Startup

_ready() is long, and most of it reads like a list of parts being unpacked. It reads any --zoom argument, fits the window to the screen, registers the keys and builds the day and night gradients. Then it creates the nodes one by one and adds each with add_child(). The order matters, because nodes in a Node2D draw in tree order unless a z_index says otherwise. First comes the room, then your placed decor, the partner, you, the dog, the cat, the ghost and one neighbour, then the gulls and butterflies at z_index 2700 and the rain at 3000 – the comment notes that this is "inside Godot's -4096..4096 z range". The neighbour is one node that is re-dressed for each room, because "keeping nine avatars alive to show at most one of them is nine times the sprites".

The keys are added in code too, by _setup_input(), which takes a small KEYS dictionary and calls InputMap.add_action() and InputMap.action_add_event() for each entry. It uses physical_keycode, so that WASD stays under the same fingers on an AZERTY keyboard.

The middle of _ready() sets up the camera and the interface layers, and connects the signals that let the pieces talk without knowing much about each other:

After this excerpt the overlays get the same treatment, about a dozen signals in all (farm_changed, pets_changed, request_room, slot_switched and more). Main also listens to three signals from the Game autoload: orientation_changed, day_changed and farm_updated. Then it enters the saved room and puts you at the spawn point.

The rest of _ready() is something you rarely see in a game: a long chain of command-line checks. Godot --path . -- --test builds the game exactly as normal, then hands it to the test suite instead of to you. Other flags take screenshots, play a hundred days, or dump all the writing to JSON for a document generator. Most of them preload a script from tests/, add it as a child and call its run method. Two comments are worth knowing. The suite is preloaded "not the global class name", because a script written outside the editor is not in the class cache until the project is re-imported. And it is added to the tree "not just constructed", because "an object nothing holds a reference to is freed at its first await". If no flag is set, a brand new life gets the character-creation card after a 1.1-second create_timer, so the house can appear first and you know what you are being asked about.

_notification() catches NOTIFICATION_WM_GO_BACK_REQUEST, the Android back gesture. It closes whatever is open – a card, the talk box, decorating – and only asks whether to quit when nothing is left to close: "Losing an hour of a slow game to a thumb resting on the wrong edge is not a thing this game should be able to do."

Input routing

All world input arrives in _unhandled_input(), not _input(). That choice does a lot of work. Before an event reaches _unhandled_input(), Godot offers it to the interface, and a button or an open panel that uses it marks it handled – so anything that arrives here really was meant for the world:

Main.gd · lines 1115–1142

func _unhandled_input(event: InputEvent) -> void:
	# Taps on a button or an open panel are consumed by the UI before they reach
	# here, so anything arriving is meant for the world.
	if _overlays.is_open or _hud.drawer_open():
		_clear_hover()
		return

	# Somebody is mid-sentence: the next tap or key is for them.
	if _dialogue != null and _dialogue.is_open:
		# A finger arrives twice on a phone, as a touch and as a pretend click made
		# from it. Counting both finished the line and skipped it in one tap.
		if UI.is_touch_copy(event):
			return
		if event.is_action_pressed("interact") and not event.is_echo():
			_dialogue.advance()
			return
		if event is InputEventMouseButton and (event as InputEventMouseButton).pressed:
			_dialogue.advance()
			return
		if event is InputEventScreenTouch and (event as InputEventScreenTouch).pressed:
			_dialogue.advance()
			return

	if event.is_action_pressed("interact") and not event.is_echo():
		_interact_nearby()
		return

	var p := _event_point(event)

It is a ladder of early returns. With a card or the HUD drawer open, the world ignores the pointer. With someone mid-sentence, any tap, click or press of the interact key moves the dialogue on – note not event.is_echo(), which ignores the repeats a held key sends. Otherwise the interact key (E or Space) acts on whatever is within reach. Only then is the event turned into a point in the room by _event_point(). That function multiplies the event's screen position by get_viewport().get_canvas_transform().affine_inverse(), and its comment explains why it does not use get_global_mouse_position(): touch events never update the pointer, so on a phone "every tap resolved to a stale pointer spot".

The rest of the function is a small state machine for pressing. A press records where and when (_press_at, _press_t). Holding still for HOLD_TIME (0.32 seconds) picks a piece of furniture up – _tick_hold() checks this every frame. Moving more than DRAG_START pixels from a piece picks it up at once. Moving more than HOLD_SLOP from empty floor cancels the hold. Letting go without any of that is a tap, and it goes to _handle_tap().

_handle_tap() works out what you touched, in order: the ghost, a way out, anything alive, something lying on the floor, a farm plot, water, your own decor, then fixed furniture, and finally bare floor, which means "walk there". For the living it once used a priority list. That went wrong, and the comment tells the story. Every body's tap box is 68×176, and walking up to a person put you inside their box and them inside yours, so the tap "found YOU and opened your own card. Fourteen of the fifteen people in town could not be said hello to at all." _living_at() now picks whoever's centre is nearest the tap.

Most taps do not act straight away. _queue() stores the action in _pending_action and _pending_ctx and sends the player walking. When the Player's arrived signal fires, _on_player_arrived() runs it through _run(), a match on the action name. "Furniture interactions firing on arrival rather than on tap is what makes the room feel physical instead of like a menu." _drop_pending() clears the errand whenever you start something new, or an old walk could arrive and open a conversation behind the card you had just opened.

The keyboard is polled rather than event-driven: "a held key is a state, not an event". Every frame, _tick_keys() reads Input.get_vector("move_left", "move_right", "move_up", "move_down") and passes it to _player.drive(). Hovering gets the same care. _update_hover() finds what the pointer is over, lifts it, shows its name in a tag and switches the cursor to CURSOR_POINTING_HAND. The tag lives on its own CanvasLayer, and _place_tag() snaps it to whole interface pixels each frame. It used to be a Label in the world, and the camera's zoom drew its font at 2.67 screen pixels per font pixel.

Talking, and waiting for an answer

_talk_to_neighbor() decides what a person says when you reach them. A conversation written in the dialogue editor comes first. Then the next beat of their story, if Game says one is open. Then small talk – and if the on-device AI (TownMind) is switched on, the line comes from await TownMind.small_talk(id). That await is a real lesson. While the model thinks, you can walk away, start another conversation or load a different life. So before the function uses the answer, it checks that nothing has moved on:

if n != _talk_n or not is_same(life, Game.state) or not _dialogue.is_waiting():
	return

_talk_n is a counter that goes up with every conversation, and is_same() asks whether Game.state is still the very same dictionary it was before the wait. Any code that resumes after an await needs a check like this. The written conversations show one more trick: _on_talk_closed() runs inside the dialogue box's own closed signal, so it reopens the box with _book_show.call_deferred(next). Reopening it straight away "would be undone by the rest of close()".

Rooms

There are two ways into a room. _go_to_room() answers a request from the map or a card: it plays the door sound, tells Game.set_room(), rebuilds the room and pulls the curtain. _go_through() is for walking. Each frame _tick_edges() checks whether you are standing in one of the room's thresholds, which are patches of walkable floor, and you arrive at the matching opening on the far side, so "leaving by the west puts you at the new room's east wall". Standing in a threshold is not enough on its own. Testers said "she sometimes goes through doors on her own", so _leaving_by() also asks for a walk aimed at that opening, or a heading within 60 degrees of straight through. That is a dot product: v.normalized().dot(out) >= 0.5.

Both routes call _enter_room(), which does the real work. It asks Game to work out the new room's size and walkable bounds, resets the camera limits and every mover's bounds, then builds the room view, the collision boxes, the decor, the weather, the cast and the neighbour. _refresh_solids() gives the same rectangles to everyone who walks, and rebuilds the navigation mesh from them in _rebuild_navmesh(). That uses NavigationServer2D directly: a region RID, a NavigationPolygon with agent_radius = 22.0, the floor as a traversable outline and every piece of furniture as an obstruction, baked with bake_from_source_geometry_data(). Because the route and the collision come from the same rectangles, "what the route avoids and what actually blocks you can never disagree". _exit_tree() frees the RID, since server resources are not freed with the node.

## old room dim, which nobody looks at anyway: you are already through the door.

func _curtain() -> void:
	if _wipe == null or not is_instance_valid(_wipe):
		return
	if _wipe_tw != null and _wipe_tw.is_valid():
		_wipe_tw.kill()
	_wipe.color.a = 1.0
	_wipe_tw = create_tween()
	_wipe_tw.tween_property(_wipe, "color:a", 0.0, CURTAIN) \
		.set_trans(Tween.TRANS_SINE).set_ease(Tween.EASE_OUT)

The curtain is set fully black and a Tween fades it to clear in a fifth of a second. create_tween() makes a tween bound to this node. tween_property(_wipe, "color:a", 0.0, CURTAIN) animates one property – the colon reaches inside the colour to its alpha – and set_trans() and set_ease() shape the curve. A tween still running from the last door is killed first, so two never fight over the same property. The comment explains why it only fades from black: the swap stays synchronous, so nothing that changes rooms has to wait, and the test suite, which changes rooms several hundred times, does not get half a second slower each time.

Indoors it is lerped a third of the way towards white, so rooms darken less than the street.

After that, the lamps come up as the light goes down. Their brightness is worked out from a second, darker gradient, so a hearth still glows at midnight in a room that is kept bright. The partner trails a step behind, and late at night the dog may doze off. The gradients themselves are built in _build_daynight(), with a comment for each stop: sunrise, bright morning, midday with no tint at all, golden evening, a rose dusk, a lavender blue hour and a soft indigo night.

The weather is the inner class Weather extends Node2D. It is drawn rather than made with particles, "so it costs almost nothing on a phone". configure() scatters drops over the whole room (more for bigger rooms), _process() moves them and calls queue_redraw(), and _draw() paints each one as a draw_rect() snapped to three-pixel steps, because a slanted line would be "the one soft thing in a pixel downpour".

One art pixel, one screen pixel

The last big section keeps the pixel art crisp. project.godot uses the canvas_items stretch mode with integer scaling, so Godot only ever magnifies the game by a whole number. On a desktop, _fit_window_to_screen() finds the largest whole multiple of the view that fits the screen the window is on, using DisplayServer.window_get_current_screen() and screen_get_usable_rect(). It does not trust the answer. It sets the window size and reads it back, because on a Mac with two displays the screen query "reported a 3840x1938 desktop while the window sat on a 1080-tall monitor". If nothing fits one way round, it tries the other orientation, because "being sideways is a smaller loss than being soft".

On a phone the window is the screen, so _fit_view_to_phone() works the other way round. It picks the largest whole scale at which the minimum interface still fits, and then makes the view exactly screen / scale, so the picture fills the glass with no bars and no half pixels. It reconnects itself to the window's size_changed signal, because a rotation or a fold arrives after start-up. _world_zoom() lets the camera lean in a little on top of that, by the smallest step that keeps each art pixel whole; the number lives in Game.gd, as CAMERA_LEAN.

A last group of public methods – set_cinematic_camera(), show_cast(), place_cast() and play_opening() – is what the opening sequence calls to point the camera and hide or show the cast. play_opening() connects its callback with CONNECT_ONE_SHOT, so it fires once and disconnects itself.

Game.gd

The game's memory and its rules. Registered as the Game autoload, it holds everything that changes while you play in one dictionary, runs the clock, loads and saves the file, and answers questions like "can I hear more of this person's story today?" for every other script.

An autoload is a node Godot creates before the main scene and keeps for the whole run, reachable by name from any script. project.godot lists three – Sfx, Game and TownMind – and Game is the one everything reads. When Main.gd rebuilds a room, the room goes, but Game.state stays. That is why the file is so big: it is the single place where the rules live, and the rest of the game asks rather than keeps its own copy.

It starts with six signals: state_changed (the HUD listens and redraws), day_changed, toast for the short lines of text that float up, farm_updated, theme_changed and orientation_changed. Any script can call Game.say("…") without knowing who will show it. say() only emits toast, and the HUD's show_toast() is connected to it.

Geometry: how big a room is, and how much of it you see

The first few hundred lines are about size, and they carry the most history in the file. Rooms are authored on a 768×1344 portrait grid of 96-pixel tiles, and the game is now always played sideways. VIEW is what the window shows, ROOM is how big the current floor is, and BOUNDS and SPAWN are the walkable rectangle and where you appear. They are var, not const, because they change with every room. apply_room() works them out from the room's size multiplier, keeping fixed margins from the walls. apply_orientation() resets the whole set, and it also sets get_window().content_scale_size itself. That used to happen in Main in response to a signal, so any code that called apply_orientation() directly "moved VIEW without moving the surface underneath it" and every card came out off-centre.

The comment on MIN_VIEW_LANDSCAPE is a lesson in testing on real hardware. It is "the dial that decides how big everything looks", and both ends were tried on a handset: 1140×640 made "the ui so so small", 780×360 zoomed the house right in. 940×520 puts every common phone on a scale of 2. camera_zoom() then returns (art + CAMERA_LEAN) / art, where art is how many game pixels one source-art pixel takes up. At half density art is 3, and the only zooms that keep a pixel whole are 3/3, 4/3 and 5/3, and the game uses 4/3.

##

_load_save() returns the default state if there is no file, if it cannot be opened, or if JSON.parse_string() gives back anything but a dictionary. Most of the remaining two thousand lines are the game's rules, each written as a short function that reads or changes state and ends with _changed(). The grouping comments are clear, and the reasoning is in the comments:

  • Money and things. add_item(), sell_one() (which removes the item before paying, so "a rapid double-tap can never mint free money"), buy_crop(), record_best() and log_memory(), which drops a repeat of the same memory on the same day and keeps the newest 40.
  • Neighbours. beat_gate() says what the next chapter of someone's story is waiting for: enough days passed and enough days on which you spoke to them. note_met() counts at most once a day, "so standing in the gelato shop tapping Marisol is worth exactly one day of knowing her". can_hear(), hear_blocked_by() and hear_neighbor() build on those.
  • The phone. The section opens with the rule it is written to: "Nothing here unlocks anything." Texts are free and worth nothing mechanically, and calls are limited to two a day.   • Today's list and the first steps. tick_today() and first_step() are "safe to call from anywhere and as often as you like", because they only write the first time. Today.gd reads these.
  • Hearts, the ghost, supplies, the house. Romance moves through five stages, with warmth added at most once a day. Repairs come one at a time, in order, and each can turn up a keepsake.
  • Who you are. Pronouns, the three modes and the four manners are constant dictionaries. Each mode "moves a real number" – mode_price_mult(), mode_event_gap(), mode_day_scale() – because "a mode that only changes a label is a lie".

Inside the code

The world

Forty-eight rooms, and not one of them is a scene file. Each room is a list of dictionaries in RoomData.gd, and one node, RoomView, reads that list and turns it into tiles, sprites, shadows and lamps every time you walk through a door. These six files are the world: the data, the drawing, the furniture you place yourself, the tables of art and light, and the birds.

RoomData.gd

Every room in the town as data: where it sits on the map, what it is called, how big it is, what furniture stands in it and what that furniture does when you tap it. It also works out the doorways, the paths and the scenery, so that nobody has to list them by hand.

RoomData is a class_name on RefCounted with nothing but static functions, constants and static vars. It is never instanced and never added to the tree: any script can call RoomData.objects("kitchen") the way it would call a function in a library. That is a good fit for data that every part of the game reads – Main.gd asks it which room is next door, RoomView.gd asks it what to draw, Player.gd and Neighbor.gd walk round what it places, Widgets.gd draws its plan as the map – but none of them owns.

The file falls into five parts, in this order:

  1. The town plan, read from data/town.json – which rooms exist, which grid cells each covers, their names, which are outdoors, which have the sea along them, and the boat crossings.
  2. Rooms laid out by hand in the project's own map editor, which writes pieces and props into the same JSON file.
  3. The built-in tables – BUILT_ROOM_IDS, BUILT_MAP_CELLS, ROOM_MULT and friends – the same town written into the code.
  4. Doorways and geometry: exits(), the water, the pool and farm rects, and the arithmetic that turns the phone-shaped layout sideways.
  5. The furniture and the dressing: _build(), one long dictionary of every room's pieces, then the code that generates scenery, shopfronts and parked cars round them.

A file first, the code as a safety net

The town is designed in an HTML editor that saves data/town.json. The game reads it once, as the script loads: static var _town: Dictionary = _read_town(), and then static var ROOM_IDS: Array = _town["ids"] and a dozen more lines like it. Static variables are initialised in the order they are written, so by the time anything asks for ROOM_IDS the file has already been read. What happens when the file is missing or broken is the interesting part:

## The neighbours along one wall, grouped into runs of consecutive cells. Walking
## the wall cell by cell and grouping equal neighbours is what gives a wide room
## two openings where it backs onto two rooms, instead of one arbitrary winner.
static func _edge_runs(room: String, cells: Rect2i, dir: String) -> Array:
	var step: Vector2i = DIR_STEP[dir]
	var horizontal: bool = step.y != 0        # a north or south wall runs along x
	var count: int = cells.size.x if horizontal else cells.size.y
	var names: Array = []
	for i in range(count):
		var cell: Vector2i = cells.position + (Vector2i(i, 0) if horizontal else Vector2i(0, i))
		# Step clear of this room's own footprint, however deep it is.
		var probe: Vector2i = cell + step
		while cells.has_point(probe):
			probe += step
		var other := map_room_at(probe, floor_of(room))
		names.append("" if other == room else other)
	var runs: Array = []
	var i := 0
	while i < count:
		var who := str(names[i])
		var j := i
		while j + 1 < count and str(names[j + 1]) == who:
			j += 1
		if who != "" and not _sea_between(room, dir, who):
			runs.append({
				"dir": dir,
				"room": who,
				"from": float(i) / float(count),
				"to": float(j + 1) / float(count),
			})
		i = j + 1
	return runs

For one wall, it steps along the room's cells, looks one cell beyond (past the room's own footprint, however deep the room is), and asks map_room_at() who owns that cell. Then it groups equal neighbours into runs. A room three cells wide that backs onto two rooms gets two openings, each at the right fraction of the wall (from and to, 0 to 1), which is what makes walking reversible: out of the left half of the living room's south wall is the farm, and the farm's north wall leads back. _sea_between() removes openings that would cross water. The two boat crossings to the islands cannot be derived this way – nothing on the water touches the mainland – so they are declared in LINKS and added in _build_exits() to both rooms, so a boat is a two-way trip like a door. The answer never changes while the game runs, so it is cached in _exits.

RoomView.gd

The node that draws the room you are in: the wall and floor tiles, the water, the road and paths, every piece of furniture at the right depth with a shadow under it, the lamps, the doors, and the farm plots. It also answers questions about what it drew – what you tapped, what blocks walking, which piece you are dragging.

There is one RoomView for the whole game. Main.gd creates it in _ready() and calls build(room) on every room change; build() frees all its children and starts again. It is a Node2D that does two kinds of drawing at once, and the split between them is the first thing to learn from it:

  • Immediate drawing in _draw() for everything flat and static: tiles, sky, water, road, paths, doormats, shadows, the decorate-mode outlines. Godot calls _draw() once and keeps the result until queue_redraw() is called, so a room's background costs nothing per frame.
  • Child Sprite2D nodes for everything that stands up: furniture, props, traces, doors, building fronts. These need to sort in depth against the characters, and draw calls made in _draw() all share their node's single depth – the comment above _add_building_front() says exactly that.

Depth: one number per sprite

The file's opening comment calls depth sorting "the whole trick". Each furniture sprite gets z_index equal to the bottom of its art in room pixels, and each character gets the height of its feet. Higher z_index draws in front, so whoever is lower on the screen is nearer the camera – the characters walk behind the couch and in front of it with no special code. Godot 4's y_sort_enabled property does a similar job by node position; doing it by hand here lets the game sort by the bottom of the painted pixels rather than the node's position. Shadows measured from the art

## night; `t` is a clock for the flicker.
func tick_lights(darkness: float, t: float) -> void:
	for entry in _lights:
		var light: PointLight2D = entry["node"]
		if not is_instance_valid(light):
			continue
		var energy := float(entry["base"]) * darkness
		if bool(entry["flicker"]):
			# Two sines at unrelated speeds: one slow breath, one quick tremor.
			# A single sine reads as a pulse, which looks like a machine.
			var ph := float(entry["phase"])
			energy *= 0.82 + 0.11 * sin(t * 2.7 + ph) + 0.07 * sin(t * 11.3 + ph * 2.1)
		light.energy = maxf(0.0, energy)

Energy is the light's full-night strength times darkness, so lamps are off at noon and rise on their own through the evening. Fires and televisions flicker with two sine waves at unrelated speeds plus a random phase per light, set when it was made – one sine reads as a machine pulsing, and without the phase every flame in the game would breathe in step. is_instance_valid() guards against a light freed by a room rebuild.

Inside the code

People and pets

Everybody who stands on a floor in Little Hours: the resident you steer, the dog and the cat who keep you company, the townsfolk in their shops, Margaery the ghost – and the files that turn a handful of small drawings into a character, layer by layer.

Three ideas run through every file in this part, and once you have seen them they are everywhere. Every character's node origin is at their feet, so z_index = int(position.y) is all the depth sorting the game needs: whoever is lower on the screen draws in front. Nobody uses physics bodies – each walker treats itself as a small disc and checks it by hand against a list of blocking Rect2s that Main.gd hands over on every room change. And the art always lands on whole pixels, because a pixel-art sprite at a fractional position shimmers as it moves.

Player.gd

The resident. Tap the floor and they walk there; tap a piece of furniture and they walk to it first and only then does the interaction fire. Hold a key and you drive them directly.

Player is a plain Node2D, not a CharacterBody2D. The body you see is a child node, _avatar, and it is deliberately typed loosely as Node2D: it is either the paper doll from Avatar.gd or the hand-drawn character from DrawnAvatar.gd, and the two share the small interface this file uses – apply(), moving, face_along() and hit_size(). UI.gd

The one place that decides what Little Hours looks like: the palette, the font, a single generated Theme, and a set of small functions that build every label, button, pill and panel in the game.

UI.gd is not a node. It starts class_name UI and extends RefCounted, and almost everything in it is static, so any script can call UI.button("Stay here", true) or read UI.ACCENT without making or finding an instance. Over a dozen of the game's scripts do. Its opening comment says why it exists: an earlier version styled each overlay by hand and the interface "drifted" – different paddings, different corner radii, different greys. With one file building everything, changing a colour here changes it everywhere.

The file runs top to bottom in layers. First the palette: CREAM, PANEL, INK, ACCENT and friends. They are static var rather than const because the player can pick one of three themes (pink, sand or blue, kept in the THEMES dictionary), and apply_theme() reassigns every colour and throws the cached Theme away so it is rebuilt. That has a knock-on the file handles carefully: a default parameter value cannot depend on a static var, so functions that want "the current panel colour" take a marker, NO_COLOR (a colour with negative components, which nobody can pass by accident), and swap it for the real colour inside the body with _or_default().

Then the measurements, each with its reason written next to it. The font, Lower Pixel, is drawn on a 10-pixel em, so text sizes are 20, 30 and 40 – whole multiples, so no glyph lands on half a pixel. Icons are 24-pixel drawings shown at 24 or 48 for the same reason. BUTTON_H is 64 because it has to be a comfortable thumb target on a phone held sideways. This is the pixel-art rule the whole game follows: never scale pixel art by a fraction.

The heart of the file is pixel_box(). Godot's usual way to style a panel is a StyleBoxFlat: a fill, a border, rounded corners and an optional soft shadow. The comment above it explains why the game stopped using it – smooth corners and a blurred shadow are "a web page's idea of a card", sitting badly next to a crisp pixel font. So the box is drawn into an Image, one interface pixel (PX, two screen pixels) at a time, and handed to Godot as a StyleBoxTexture.

A Label with wrapping turned on reports a minimum width of about one character, because in theory it could wrap after every letter. Put it in a container that sizes things to their minimum and it will do exactly that – the HUD's clock once grew twenty lines tall. So label() never wraps, and para(), which does, is kept for paragraphs inside a panel that gives them a real width. clip() is the opposite trap: a clipped label reports a minimum width of zero, so it is only used where the parent fixes the width.

Other builders show the same care. icon() sets texture_filter to TEXTURE_FILTER_NEAREST and stretch_mode to STRETCH_KEEP_CENTERED, so the icon is drawn at its own size and never resampled. icon_button() puts the icon in a CenterContainer anchored to the full rect, because the icon has no size yet when the button is built, and connects button_down and button_up to move that container two pixels down and back. sprite_tile() picks the largest whole-number scale at which a furniture sprite fits its tile, and _scaled() does the enlarging with Image.INTERPOLATE_NEAREST and caches it. Every button goes through clicky(), which connects a quiet click from Sfx.gd once, so no call site has to remember.

##
## Godot gives a touch to the control under the finger, and a Button keeps it
## (mouse_filter STOP), so a ScrollContainer only ever scrolled when the drag
## began on the bare gaps between buttons – on the character card, which is
## all rows of arrows, almost never. Testers: "scrolling down is a struggle".
## A control that PASSES the touch on still gets its tap, and the scroll gets
## the drag; once the drag is past SCROLL_DEADZONE the scroll tells the button
## and the press is cancelled, so scrolling never presses what was under the
## finger. Measured on 4.7.1 with finger events: with no deadzone a 2-pixel
## wobble scrolled and lost the tap; at 16 a 6-pixel wobble still taps and a
## 30-pixel drag scrolls.
##
## Not for anything that wants the drag for itself: sliders, text fields, a
## scroll inside the scroll, or a widget with its own _gui_input (the drawing
## pad, the minigames).
static func let_drags_scroll(root: Node) -> void:
	for c in root.get_children():
		var ctl := c as Control
		if ctl != null:
			if ctl is Range or ctl is LineEdit or ctl is TextEdit or ctl is ScrollContainer \
					or ctl is ItemList or ctl is Tree or _own_input(ctl):

It visits every Control under root and turns STOP into MOUSE_FILTER_PASS: the button still gets its tap, but the event carries on up to the scroll container too. Some controls are skipped because they want the drag for themselves – sliders (Range), text fields, a scroll inside the scroll – and so is anything whose script has its own _gui_input(). _own_input() finds those by asking the script for its method list and walking up through get_base_script(), which is how the minigames in Widgets.gd keep their fingers.

Next to it is is_touch_copy(), which every touch widget in the game uses. Cards and things

Almost everything you do in Little Hours happens on a card that rises over the room: the bag, the stove, the bed, the mailbox, the arcade. This part is the one file that builds all of them, and the two small tables that tell those cards which strawberry to draw and which letter came today.

Overlays.gd

Every modal panel in the game, in one file. Tap a thing in the room and Main.gd calls open("cook") or open("bag"); this file builds the card in code, fades it in, and tears it down again when you are done.

The opening comment gives the reason for the shape: one host panel is built and torn down per opening, and open() dispatches on a kind string. The web version of the game had grown twenty separate overlay components; here there is one shell and one visual language, and each card is a function called _build_something() that fills the shell's body. There are no scene files involved – every Control on every card is made with .new() and add_child().

Overlays extends CanvasLayer and sets layer = 20 in _ready(), so its cards draw above the room and the HUD whatever the camera is doing. Main.gd creates it with Overlays.new() and then connects to its signals. That list of signals is how a card talks back to the world without knowing anything about it: farm_changed (redraw the beds), avatar_changed, place_decor(k), request_room(room) for fast travel, reset_done, speak(who, lines, voice_id) when somebody should say a line out loud in the dialogue box, and plain closed. The card never reaches into the room; it emits, and Main decides what that means.

The shell

Every card is built inside the same stack of nodes, made fresh by open() each time:

  1. _root – a full-screen Control

    Given the game's theme with UI.theme() (see UI.gd), so every label and button inside picks up the same fonts and boxes. Freeing this one node later frees the whole card.

  2. _scrim – a ColorRect over the room

    Dims the room, swallows clicks, and closes the card when you tap beside it.

  3. A MarginContainer

    Its margins centre the card: card_side() works out the side margin so a card is at most 600 px wide (760 in landscape) and sits in the middle of what is left.

  4. _panel, then a ScrollContainer, then _body

    The pixel-bordered panel from UI.panel(), a scroll box so a tall card still fits, a small gutter on each side for the scroll bar, and finally a VBoxContainer that the builder fills from top to bottom.

Then a long match kind: calls the right builder – "bag": _build_bag(), "fish": _build_fishing() and around fifty more – and the last branch, _:, hands anything unknown to _build_moment(). Last of all comes _fit_card(), which sizes the card to its content.

Sizing to the content

_fit_card() exists because of a trap worth knowing: a ScrollContainer's own minimum height is zero, by design, since it expects its parent to give it a size. Dialogue.gd

The talk box along the bottom of the screen. It types each line out a letter at a time, makes the speaker's noise while it does, rests on full stops, and offers up to four replies once you have read to the end.

It is a CanvasLayer on layer 60, so it draws above the room and the HUD whatever the camera is doing. Main.gd creates it once and keeps it; everyone who wants to talk calls one of three methods on it: say(speaker, lines) for talk with no answer, ask(speaker, lines, replies) for talk that ends in buttons, and wait(speaker), which opens the box on a name and a thinking "…" while TownMind.gd makes the line. It reports back with three signals: opened (the player should stop walking), closed, and chose(reply_id).

The opening comment explains why there is a box at all: talking used to open a full card, which hid the one thing you wanted to see – the person in front of you. A box at the bottom keeps the room and the speaker visible above it. The whole layout is built in _ready() from code – a PanelContainer anchored bottom-wide, a VBoxContainer inside, an HBoxContainer with the name and the prompt sharing one row, and a two-column GridContainer for replies. Two decisions there are worth stealing. grow_vertical = Control.GROW_DIRECTION_BEGIN makes the panel grow upwards when a long line needs more room, because growing down from the bottom of the screen means growing off it. And because the box is built once at startup, it connects to Game.theme_changed and re-colours itself in _restyle(), or it would stay in the old palette while the rest of the interface changed.

DialogueBook.gd

Every written conversation in the game, gathered from three places, checked, and handed out one at a time: "who says what, when, and what can I answer?"

A conversation here is a small map. ScriptBook.gd

## One blip: a short tone with a fast attack and a fast decay.
##
## The attack is not instant. A waveform that starts at full amplitude on sample
## zero clicks, and forty clicks a sentence is a fault rather than a voice.
func _blip_samples(f: float, dur: float, wave: String, soft: float) -> PackedFloat32Array:
	var n := _len(dur)
	var out := PackedFloat32Array()
	out.resize(n)
	var phase := 0.0
	# A one-pole lowpass takes the edge off the square and saw voices. Without
	# it the harsher timbres alias into a fizz at this sample rate, which sounds
	# like a broken speaker rather than like a person with a sharp voice.
	var k: float = clampf(1.0 - soft * 0.72, 0.12, 1.0)
	var last := 0.0
	# Fifteen per cent of a forty-millisecond blip is six milliseconds, which is
	# short enough to still read as a consonant and long enough not to click.
	const ATTACK := 0.15
	for i in range(n):
		var t := float(i) / float(n)
		phase = fmod(phase + TAU * f / float(RATE), TAU)
		var s := 0.0
		match wave:
			"sine":
				s = sin(phase)
			"tri":
				s = asin(sin(phase)) * (2.0 / PI)
			"square":
				s = 1.0 if phase < PI else -1.0
			"pulse":
				# A narrow duty cycle: thinner and more nasal than a square.
				s = 1.0 if phase < TAU * 0.18 else -1.0
			"saw":
				s = phase / PI - 1.0
			"breath":
				# Noise with a tone under it — a voice with air in it.
				s = sin(phase) * 0.55 + (randf() * 2.0 - 1.0) * 0.45
			_:
				s = sin(phase)
		last = last + k * (s - last)
		var env: float = minf(1.0, t / ATTACK) * pow(1.0 - t, 2.2)
		out[i] = last * env * 0.9
	return out

phase advances by TAU * f / RATE each sample and fmod keeps it in one cycle; the match turns phase into a waveform (a square is "high for the first half", a saw is a straight ramp). last = last + k * (s - last) is the one-pole low-pass filter – each sample moves only part of the way towards the new value, which rounds off the harsh edges. The envelope rises over the first 15% (an instant start clicks) and falls away with pow(1.0 - t, 2.2). _blip_stream() bakes four pitch variants per voice and picks one at random each blip, because one sample repeated forty times a sentence "is a machine and four of them is a voice".

Playing is a round robin: play() looks for the next player that is not busy so a burst of taps never cuts itself off, and if all eight are playing it takes the oldest. Blips use their own three players for the same reason in reverse – at thirty a second they would otherwise cut off every chime and bark while somebody was talking. Volume sliders are converted with linear_to_db() and added to each effect's own level, so the mix between sounds stays the same; silence is -80 dB rather than minus infinity, which some platforms dislike. The music pad, _make_pad(), is four chords of two seconds each, every chord faded in and out with sin(t * PI) so the eight-second loop has no clicks at the seams.

Afters.gd

What people say once their written story has all been told – which is forever. Instead of running dry, the talk turns round and is about you: a question built from your own save.

The header makes the case. Fifteen people with twelve beats each run out in about a hundred days, and writing more beats only postpones that. An after is made of two pieces: a fact, a clause about your life filled in from the save ("how the pumpkins did in the end"), and a frame, that person asking it in their voice with one %s for the fact. ## true, or a fresh one – something not asked about lately, when there is one.
static func _pick(id: String, facts: Array) -> Array:

			if str((f as Array)[0]) == said:
				return f

		if not recent.has(str((f as Array)[0])):

## The stage a trace is at. `n` is days for one that ages and times-happened for
## one that grows; a trace with no stages has exactly one, which is itself.
static func stage(id: String, n: int = 0) -> Dictionary:
	var k := kind(id)
	if k.is_empty():
		return {}
	var list: Array = k.get("stages", [])
	if list.is_empty():
		return k
	var out: Dictionary = list[0]
	for entry in list:
		if n >= int((entry as Dictionary)["at"]):
			out = entry
	return out

Either way the number goes into stage(), which walks the list and keeps the last stage whose at has been reached. A kind with no stages returns itself, so every caller can treat every trace the same. The label changes with the stage, and "the flowers, going over" is a different sentence from "the flowers I picked", which, says the comment, is most of what the staging is for.
