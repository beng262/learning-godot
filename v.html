Facts in data, rules in code

A game is full of facts: a carrot ripens in fifteen seconds, a lamp glows warm, the kitchen is next to the hall. Where those facts live decides how hard the fiftieth one is to add.

The first way anybody writes it is with the facts inside the code, one if at a time:

func grow_time(crop: String) -> float:
	if crop == "carrot":
		return 15.0
	elif crop == "tomato":
		return 20.0
	elif crop == "pumpkin":
		return 40.0
	return 0.0

func display_name(crop: String) -> String:
	if crop == "carrot":
		return "Carrot"
	elif crop == "tomato":
		return "Tomato"
	elif crop == "pumpkin":
		return "Pumpkin"
	return "?"

It works for three crops. Adding a fourth means finding every function that has a chain like this and adding a branch to each, and the one you miss does not complain – it returns 0.0 or "?" and the bug turns up later, somewhere else. The fix is to notice that these functions are not really code. They are a list of facts written out as code. Write the list as a list:

extends Node

const CROPS := {
	"carrot":  {"name": "Carrot",  "grow": 15.0},
	"tomato":  {"name": "Tomato",  "grow": 20.0},
	"pumpkin": {"name": "Pumpkin", "grow": 40.0},
}

func _ready() -> void:
	for id in CROPS:
		var crop: Dictionary = CROPS[id]
		print(crop["name"], " ripens in ", crop["grow"], " s")

Press Edit and run and add a line to the table: "strawberry": {"name": "Strawberry", "grow": 25.0},. The loop prints it. No function changed, because there is no function that knows the name of any crop – only one that knows what to do with a crop.

That is data-driven design: the facts sit in one place, in a shape a loop can walk, and the code holds only the rules. It buys you four things.

  • Adding a thing is adding a line. A new crop, room or neighbour should not need a programmer to hunt through functions.
  • Everything about one thing is together. The carrot's name, time and price are on one line, not spread over three functions.
  • The data can be checked. A loop can ask "does every crop have a name?" – you cannot ask that of an if chain.
  • The data can be used twice. The same table fills the shop, the planting menu and the save file's list of what is allowed.

Godot gives you three places to keep such data, and this chapter takes them in turn: resources, which are files the editor understands; tables in code, like the one above; and data files such as JSON that the game reads when it starts.

Resources: data the engine understands

A node is something that is in the game. A resource is something nodes use. You have been using resources since Chapter A without making one.

A Sprite2D is a node; the picture it shows is a Texture2D, which is a resource. So is the sound an AudioStreamPlayer plays, the font a Label writes in, a Theme, a StyleBox, and a scene file once it is loaded (a PackedScene). A resource has no place in the tree, no _process() and no position. It is a bundle of values with a type, which Godot knows how to save to a file, load back, show in the Inspector and share between everything that uses it.

Resource extends RefCounted (Chapter H): nobody frees one by hand. It is kept while something holds it and goes when nothing does.

A resource type of your own

You make your own kind the way you make any class: a script, this time extending Resource. This is a whole file, crop_data.gd:

class_name CropData
extends Resource

@export var name := ""
@export var grow := 20.0        # seconds from watering to ripe
@export var price := 5
@export var icon: Texture2D     # <1>
  1. A resource can hold other resources. This one carries its own picture.

class_name gives the type a name the whole project can use, and makes it appear in the editor's lists. @export does two jobs at once: the field shows in the Inspector, and it is written to the file when the resource is saved. A plain var without @export exists while the game runs and is not saved.

  1. Make a file of that type

    In the FileSystem dock, right-click a folder, choose Create New and then Resource…, and pick CropData from the list. Save it as carrot.tres.

  2. Fill it in

    Double-click carrot.tres. The Inspector shows Name, Grow, Price and Icon as fields, with the defaults from the script. Type the carrot's values and save.

  3. Give it to a node

    A script with @export var crop: CropData gets a slot in the Inspector that accepts only that type. Drag carrot.tres onto it.

A .tres file is text, and worth opening once so that it is not a mystery. Leaving out the ids Godot adds, the carrot is roughly this:

[gd_resource type="Resource" script_class="CropData" format=3]

[ext_resource type="Script" path="res://crop_data.gd" id="1"]

[resource]
script = ExtResource("1")
name = "Carrot"
grow = 15.0
price = 4

The type, a pointer to the script that defines it, and the values. It sits happily in version control and you can read a change to it in a diff. There is a binary twin, .res, which loads faster and cannot be read; use .tres for anything you write by hand.

And the node that uses it:

extends Node2D

@export var crop: CropData       # carrot.tres, dropped on the slot in the Inspector

func _ready() -> void:
	print(crop.name, " ripens in ", crop.grow, " s")

What the type buys you

The book's interpreter has no files, so the example below makes its resources with new() instead of loading them. The type and its fields behave the same way.

extends Node

class CropData extends Resource:
	@export var name := ""
	@export var grow := 20.0
	@export var price := 5

func make(label: String, grow: float, price: int) -> CropData:
	var crop := CropData.new()
	crop.name = label
	crop.grow = grow
	crop.price = price
	return crop

func _ready() -> void:
	var crops: Array[CropData] = [make("Carrot", 15.0, 4), make("Pumpkin", 40.0, 15)]
	for crop in crops:
		print(crop.name, ": ", crop.grow, " s, ", crop.price, " coins")
	print("Is a carrot a Resource? ", crops[0] is Resource)

Compare crop.grow with the dictionary's crop["grow"]. A field is checked; a key is not. Here is the same typo made both ways:

extends Node

class CropData extends Resource:
	@export var name := ""
	@export var grow := 20.0

func _ready() -> void:
	var as_table := {"name": "Carrot", "grow": 15.0}
	as_table["grwo"] = 12.0          # a typo: quietly makes a new key
	print(as_table)

	var as_resource := CropData.new()
	as_resource.grwo = 12.0          # the same typo: stopped

The dictionary now has a grow and a grwo and nothing said a word. The resource refused. In Godot it is better than that: because as_resource has a known type, the editor underlines the misspelt field before the game runs at all. That check, and the Inspector, are what you pay for with the extra file.

Resources are for the game's data, not the player's

It is tempting to save the player's progress as a resource too, since Godot will write one to disk for you. Be careful: a resource file can carry a script inside it, so loading one that came from somewhere else can run code. That is why Chapter S saves with JSON, which can only ever be data.

load, preload, and the sharing trap

There are two ways to get a resource from a file into a variable. They differ in when the file is read, and both hand you something that is shared with everybody else who asked.

const CARROT := preload("res://crops/carrot.tres")    # read when this script is loaded

func crop_for(id: String) -> CropData:
	return load("res://crops/%s.tres" % id)             # read when this line runs
preload("…")load(path)
WhenAlong with the script that contains it, before any of its code runs.At the moment the line runs.
The pathMust be written out as a constant string: Godot has to know it without running anything.Any string, including one you build: "res://crops/%s.tres" % id.
If the file is missingThe script does not compile. You find out at once.You get null and an error in the log. Ask ResourceLoader.exists(path) first if it might not be there.
Use it forThings this script always needs.Things chosen while the game runs, or big things you want to put off loading.

Both also work on scripts and scenes, not only data: preload("res://enemy.tscn") gives you a PackedScene to instance, and preload("res://scripts/Util.gd") gives you a script whose constants and static functions you can call.

One file, one object

Godot keeps a cache of what it has loaded. Ask for the same path twice and you get the same object, not a second copy. That is what you want for a texture – two hundred carrots share one picture in memory – and it is a trap for data you intend to change:

extends Node

class CropData extends Resource:
	@export var name := "Carrot"
	@export var grow := 15.0

func _ready() -> void:
	var carrot := CropData.new()        # stands in for load("res://crops/carrot.tres")
	var plot_a := {"crop": carrot}
	var plot_b := {"crop": carrot}      # the same object, as a second load() would give

	# Fertiliser on plot A: its carrot should grow in half the time.
	plot_a["crop"].grow = plot_a["crop"].grow / 2.0

	print("A ripens in ", plot_a["crop"].grow)
	print("B ripens in ", plot_b["crop"].grow)

Plot B was never fertilised and its carrot is quicker too, because there is only one carrot. It is the shared-reference behaviour of arrays and dictionaries from Chapter G, with a file in the middle to make it harder to see. In a real project it shows up as "I changed one enemy's speed and they all sped up".

When you do want a private copy, ask for one:

var mine: CropData = load("res://crops/carrot.tres").duplicate()
mine.grow /= 2.0        # this copy only

duplicate() copies the resource itself. Resources inside it, such as the icon, are still shared unless you pass true for a deep copy, which is usually what you want for a texture anyway. For resources set on a scene's nodes there is also a Local to Scene checkbox in the Inspector, which gives every instance of the scene its own copy.

The better habit: definitions never change

Most of the time, needing duplicate() is a sign that two different things are sitting in one object: what a carrot is, which is the same for every carrot for ever, and what has happened to this carrot. Keep the first as data nobody writes to, and the second somewhere of its own that points at it by id.

extends Node

# What a crop is. Read, never written.
const CROPS := {
	"carrot": {"name": "Carrot", "grow": 15.0},
	"tomato": {"name": "Tomato", "grow": 20.0},
}

# What has happened on each plot. This is the part that changes, and is saved.
var plots := [
	{"crop": "carrot", "speed": 2.0},
	{"crop": "carrot", "speed": 1.0},
	{"crop": "tomato", "speed": 1.0},
]

func ripens_in(plot: Dictionary) -> float:
	return CROPS[plot["crop"]]["grow"] / plot["speed"]

func _ready() -> void:
	for plot in plots:
		print(CROPS[plot["crop"]]["name"], " ripens in ", ripens_in(plot), " s")

Change the first plot's speed to 3.0: only that plot changes. The state is small, it is plain data, and it is exactly what a save file needs to hold – ids and numbers, not whole definitions.

In Little Hours

A farm plot is a small dictionary in the save: its state, the crop as an id such as "carrot", whether it is watered, and planted_at. How long a carrot takes is not in the plot. It is looked up in Game.CROPS when it is needed, so changing the table changes every carrot, in old saves too.

The other road: tables in code

Little Hours does not have a single .tres file. All of its data is written as tables in GDScript, and it is worth understanding why somebody would choose that.

A table in code is one text file. You can search it, read a change to it in a diff, write a comment beside any entry, and generate it with a script from a spreadsheet or another program. A test can loop over it. Nothing has to be opened in the editor, and nothing can drift out of step with a file somewhere else. The price is the two things resources gave you: there is no Inspector, and nobody checks a key for you. You check it yourself, and this section ends with how.

A class that is only data

The usual shape is a script with a class_name, constants for the tables and static functions to read them (Chapter F). It extends RefCounted and is never instanced or added to the tree. Any script in the project can call Furniture.of("lamp"), as it would a function in a library (Chapter U compares this with autoloads).

The example below uses an inner class so that it fits in one runnable script; in a project, Furniture would be a file of its own that starts class_name Furniture and extends RefCounted.

extends Node

class Furniture:
	# What every piece is, unless its own entry says otherwise.
	const DEFAULT := {"price": 10, "solid": true, "light": false}

	# One entry per piece. An entry lists only what differs from DEFAULT.
	const PIECES := {
		"chair": {"name": "Chair"},
		"rug":   {"name": "Rug", "solid": false},
		"lamp":  {"name": "Lamp", "price": 25, "light": true},
	}

	static func of(id: String) -> Dictionary:
		var piece: Dictionary = DEFAULT.duplicate()     # <1>
		var own: Dictionary = PIECES.get(id, {})        # <2>
		for key in own:
			piece[key] = own[key]                       # <3>
		return piece

func _ready() -> void:
	print(Furniture.of("chair"))
	print(Furniture.of("rug"))
	print(Furniture.of("lamp"))
	print(Furniture.of("piano"))
  1. Start from a copy of the defaults. A const dictionary is read-only in Godot, and you would not want one lookup to change the defaults for the next even if it were not.
  2. get(id, {}) is the lookup with a fallback: an id that is not in the table gives an empty entry, not an error.
  3. Lay the piece's own values over the copy. Whatever it did not mention keeps the default.

This pattern is worth having in your hands. The chair's entry is one word long and it still has a price, because defaults sit under every entry. Add "tv": {"name": "TV", "price": 60, "light": true}, and print it. Then add a new key to DEFAULT – "flat": false – and watch every piece gain it without one entry being edited. A new property costs one line, not one line per piece. (Dictionaries also have a merge() method that does the loop's job in one call; the loop is written out here so that you can see it.)

Deciding what "not found" means

The piano is not in the table, and of("piano") returned a nameless thing that costs 10. Whether that is right depends on the table. For a voice or a colour, a quiet default is exactly what you want: the game carries on and nobody notices. For something with a price, a quiet default hides a bug – a misspelt id becomes a free piano. Decide for each table, and when unknown means "somebody made a mistake", say so loudly:

extends Node

const PRICES := {"chair": 10, "lamp": 25}

func price_of(id: String) -> int:
	if not PRICES.has(id):
		push_warning("no price for '%s'" % id)
		return 0
	return PRICES[id]

func _ready() -> void:
	print(price_of("lamp"))
	print(price_of("lmap"))

push_warning() writes a yellow line into Godot's Debugger without stopping the game; Chapter W is about it and its relatives.

Checking a table

Nobody checks a table's keys for you, so write the check. It is a loop that returns everything it finds wrong, as sentences a person can act on:

extends Node

const DEFAULT := {"price": 10, "solid": true, "light": false}

const PIECES := {
	"chair": {"name": "Chair"},
	"rug":   {"name": "Rug", "solid": false},
	"lamp":  {"name": "Lamp", "price": 25, "light": true},
}

func problems() -> Array:
	var found: Array = []
	for id in PIECES:
		var piece: Dictionary = PIECES[id]
		if not piece.has("name"):
			found.append("%s has no name" % id)
		for key in piece:
			if key != "name" and not DEFAULT.has(key):
				found.append("%s has a key nobody reads: %s" % [id, key])
		if piece.get("price", DEFAULT["price"]) < 0:
			found.append("%s has a price below zero" % id)
	return found

func _ready() -> void:
	var found := problems()
	if found.is_empty():
		print("The table is fine: ", PIECES.size(), " pieces")
	for line in found:
		print("PROBLEM  ", line)

Now break the table on purpose. Change the rug's "solid" to "soild", the commonest mistake there is: without the check the rug would silently become solid, because the misspelt key is ignored and the default takes over. Delete the lamp's name. Give the chair a price of -5. Each gets its own line. Return a list, not the first problem: when a table has three mistakes you want to fix three, not run it three times.

Where does the check run? At start in a debug build, or better, in a test that runs before every release – which is Chapter W.

Data files, read at start

When the data is made by a tool, or by somebody who does not write code, it lives in a file of its own and the game reads it when it starts.

A map editor saves a map. A writer keeps dialogue in a spreadsheet. A translator sends back a file of strings. None of them should have to touch a .gd file, and you should not be copying their work into one by hand. The usual format is JSON, which Chapter S introduced for saves: text, readable, and understood by every other tool there is.

const FILE := "res://data/crops.json"

static func read_crops() -> Dictionary:
	if not FileAccess.file_exists(FILE):
		return BUILT_IN.duplicate(true)
	var raw: Variant = JSON.parse_string(FileAccess.get_file_as_string(FILE))
	var table := parse_crops(raw)
	if table.has("problem"):
		push_warning("%s was not used: %s" % [FILE, table["problem"]])
		return BUILT_IN.duplicate(true)
	return table

The reading is two calls. Everything else is there because a file can be wrong in ways code cannot: missing, half written, edited by hand, saved by an older version of the tool. So the rules for a data file are stricter than for a table you typed yourself.

  • Never use what you read directly. JSON.parse_string() returns null for text that is not JSON, and for anything else it returns whatever the file said, which may be a list where you expected an object. Build your own table out of it, checking each value as you take it.
  • Numbers arrive as floats. JSON has one kind of number. A price of 4 comes back as 4.0; wrap it in int().
  • Decide what a mistake costs. Sometimes one bad entry can be skipped and the rest used. Sometimes the entries depend on each other and it is all or nothing.
  • Have something to fall back on. A game that will not open because of a comma in a data file is a worse game than one that opens with yesterday's data and says why in the log.

Here is the checking half, which is pure logic and so runs here. It returns either a good table or a dictionary with one key, "problem", saying why not:

extends Node

const TEXT := """
{"format": "crops", "crops": [
	{"id": "carrot", "name": "Carrot", "grow": 15, "price": 4},
	{"id": "pumpkin", "name": "Pumpkin", "grow": 40, "price": 15}
]}
"""

func parse_crops(raw: Variant) -> Dictionary:
	if not raw is Dictionary:
		return {"problem": "it is not a JSON object"}
	if str(raw.get("format", "")) != "crops":
		return {"problem": "it is not a crops file"}
	if not raw.get("crops") is Array:
		return {"problem": "it has no list of crops"}
	var table := {}
	for entry in raw["crops"]:
		if not entry is Dictionary:
			return {"problem": "a crop is not an object"}
		var id := str(entry.get("id", ""))
		if id == "":
			return {"problem": "a crop has no id"}
		if table.has(id):
			return {"problem": "there are two crops called %s" % id}
		var grow := float(entry.get("grow", 0))
		if grow <= 0.0:
			return {"problem": "%s has no grow time" % id}
		table[id] = {
			"name": str(entry.get("name", id.capitalize())),
			"grow": grow,
			"price": int(entry.get("price", 5)),
		}
	return table

func _ready() -> void:
	var table := parse_crops(JSON.parse_string(TEXT))
	if table.has("problem"):
		print("Not used: ", table["problem"])
	else:
		for id in table:
			print(id, " -> ", table[id])

Be the careless editor. Rename the pumpkin's id to carrot. Delete a grow. Remove the closing ]} so that the text is not JSON at all. Each time you are told what is wrong in a sentence, and each time the function returns something the caller can test for. Notice also what the good table contains: only the three keys the game reads, each of the type it expects. Whatever else was in the file was left behind.

A data file has to be in the exported game

When Godot exports a project it packs the files it recognises as resources. For other files under res:// – your JSON, your text – check the export preset's filter for non-resource files, or the game that worked on your machine will open on a phone with no data. Chapter X covers presets.

In Little Hours

The game took the second road all the way: no .tres files, tables in code for nearly everything, and one JSON file written by a map editor. Here are four of its tables and what reads them.

The crops: the smallest table

Game.gd · lines 257–263

const CROPS := {
	"carrot":     {"name": "Carrot",     "grow": 15.0},
	"tomato":     {"name": "Tomato",     "grow": 20.0},
	"strawberry": {"name": "Strawberry", "grow": 25.0},
	"sunflower":  {"name": "Sunflower",  "grow": 30.0},
	"pumpkin":    {"name": "Pumpkin",    "grow": 40.0},
}

An id, a name to show and a number of seconds. That is the whole of what a crop is, and three unrelated parts of the game read it. The planting card builds its rows with for key in Game.CROPS.keys():, one button per entry, so a new crop appears on the card by being in the table. The farm reads grow to decide when a watered plot is ripe (F: Farming). And when a save is loaded, the list of crops a save is allowed to mention is CROPS.keys(): a crop that has since been removed from the table is dropped from an old save, and nothing downstream ever looks up an id that is not there. One table is the menu, the rule and the validator. Game.gd has the rest.

The voices: defaults under every entry

Nobody in Little Hours has a recorded line. Each person has a short tone that plays as their words type out, described by seven numbers and words. Voices.gd is a RefCounted class of constants and static functions, never instanced, and it begins with the profile for anybody who has none:

Voices.gd · lines 29–31

## Used for anybody without an entry, and as the base every entry is merged over.
const DEFAULT := {"f": 330.0, "wave": "tri", "dur": 0.045, "step": 2,
	"wob": 0.05, "soft": 0.5, "db": -22.0}

Below it is BY_ID, one entry per person, each with a comment saying who they are and why they sound like that. Most entries leave something out – Marisol's has no "soft" – because this function fills it in:

Voices.gd · lines 98–104

## The profile for a speaker id, filled in from DEFAULT.
static func of(id: String) -> Dictionary:
	var v: Dictionary = DEFAULT.duplicate()
	var found: Dictionary = BY_ID.get(id, {})
	for k in found:
		v[k] = found[k]
	return v

It is the function you wrote in the tutorial, line for line: duplicate the default, look the id up with get(id, {}) so that a stranger is not an error, lay the entry over the copy. Here a quiet default is the right answer to "not found": a person with no entry should still make a sound. The file goes one step further for people who are not in the table at all, with from_name(), which works a voice out from the letters of a name, so that the same stranger sounds the same each time you meet them. That is a fallback that is computed, not stored. See V: Voices and sound and Voices.gd.

The town: a data file that is not trusted

The plan of the town – which rooms exist, where each sits on the grid, what it is called, which are outdoors – is drawn in a map editor that runs in a browser and saves godot/data/town.json. RoomData.gd reads it once, into static var tables such as ROOM_IDS and MAP_CELLS, which are filled when the script is loaded. The reading is done by parse_town(), and this is how it starts:

RoomData.gd · lines 100–118

## A town file read into the tables above, or {"problem": why not}.
##
## All or nothing. A plan with two rooms on one cell, or a room hanging off the
## grid, cannot be half used: the doorways are worked out from who touches whom,
## so one bad room changes everybody's neighbours.
static func parse_town(raw: Variant) -> Dictionary:
	if not raw is Dictionary:
		return {"problem": "it is not a JSON object"}
	var d: Dictionary = raw
	if str(d.get("format", "")) != "little-hours-town":
		return {"problem": "it is not a town file (format)"}
	var grid: Dictionary = d["grid"] if d.get("grid") is Dictionary else {}
	var cols := int(grid.get("cols", 0))
	var rows := int(grid.get("rows", 0))
	var sub := clampi(int(grid.get("sub", 1)), 1, 8)
	if cols < 1 or rows < 1 or cols > 64 * sub or rows > 64 * sub:
		return {"problem": "the grid is %d x %d" % [cols, rows]}
	if not d.get("rooms") is Array or (d["rooms"] as Array).is_empty():
		return {"problem": "it has no rooms"}

Read it as a list of refusals. Not a dictionary: refused. Not marked as a town file: refused. A grid of nothing, or an absurd size: refused, with the numbers in the sentence. Every value is taken with get() and a default and then forced to the type wanted with int() or str(), because JSON numbers arrive as floats and a hand-edited file can hold anything. The function goes on like that for every room: an id with anything in it but lower-case letters, digits and underscores, two rooms with one id, a room hanging off the grid, two rooms on one square. Each returns a one-key dictionary saying why.

The comment explains why this file is all or nothing: doorways are worked out from which rooms touch, so one bad room would change everybody's neighbours. Smaller mistakes are treated differently. A floor size that is not two sensible numbers, or a tile that is not a picture, is left out and noted in a list called layout_skipped, and the rest of the room is used. Two levels of strictness in one parser, chosen by what a mistake would cost.

The caller, _read_town(), is the fallback. If the file is missing or parse_town() returned a problem, it records the reason in town_problem (and, for a file that was there but wrong, says so with push_warning()), and returns the town as it is written into the code in the BUILT_ tables. A broken file means the game opens as the town it was, not that it does not open. The map itself is M: Map, rooms and doors; the file is RoomData.gd. And the game's export presets do list data/*.json among the extra files to include, which is the callout above learned in practice.

The art: a lookup that can say no

Assets.gd maps every piece of furniture to its picture. The table, ART, is id -> [path, scale]: a path, not a loaded texture, and a whole number, because the game's one rule about pixel art is that nothing is drawn at a fractional scale (Chapter P). The function that reads it is where this chapter's load lesson lives:

Assets.gd · lines 562–573

static func piece(id: String) -> Dictionary:
	var entry: Array = ART[id] if ART.has(id) else EXTRA_ART.get(id, [])
	if entry.size() < 2:
		return {}
	var path: String = entry[0]
	if not ResourceLoader.exists(path):
		push_warning("Tiny Home: missing art for '%s' at %s" % [id, path])
		return {}
	var tex: Texture2D = tex(path)
	if tex == null:
		return {}
	return {"tex": tex, "scale": scaled(int(entry[1]))}

Three ways to fail, none of them a crash. An id in neither table gives {}. A path with no file behind it is caught by ResourceLoader.exists() before loading, reported with push_warning() naming the id and the path, and gives {}. A file that would not load gives {}. Whoever asked draws nothing for that piece and carries on. And because the answer is built on each call – a new dictionary holding the shared texture and a scale – nobody can spoil the table by changing what they were given.

The game does not leave it at a warning, though. Its test suite walks ART and checks that every file exists and every scale is a whole number, which is the "check the table" step of the tutorial run before every release; Chapter W shows it.

Two more, briefly

DecorCatalog.gd is the list of pieces you can place in decorate mode (D: Decorating): an array of small dictionaries with one-letter keys, k for the file name, c for the category, w and h for the size. Its first comment says it is generated from another file and should be regenerated, not edited by hand. That is something a table in code can be and an Inspector cannot: the output of a script (Chapter Y). The tour has its opening lines.

NeighborData.gd holds the townspeople as an array of dictionaries, BUILT_PEOPLE, and reads optional keys the careful way throughout – p.get("work", "") for somebody who may not have a job. The list the game uses is static var PEOPLE: Array = ScriptBook.apply(BUILT_PEOPLE): the table in code, with each person's words from a writer's script file laid over it. A table and a data file, merged at start (N: Neighbours, NeighborData.gd).

Your turn

Five tables, each a little less trusting than the last.

What to remember

  • Facts go in data, rules go in code. When adding a thing means adding a line and no function changes, the design is right.
  • A Resource is typed data the engine can save, load and show in the Inspector: a script that extends Resource with @export fields, saved as .tres.
  • preload reads a constant path when the script loads; load reads any path when the line runs and can return null.
  • A loaded resource is shared by everyone who loaded it. Keep definitions read-only and put what changes somewhere else; use duplicate() when you truly need a private copy.
  • A table in code is a const dictionary read through static functions: defaults duplicated and the entry laid over them, get() with a fallback, and a check you write yourself because nobody checks keys for you.
  • A data file is untrusted. Parse it into a table of your own, say why when you refuse it, and have something to fall back on.
