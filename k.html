Keys, touch and the mouse

The Input Map, actions, polling versus events, and making one game work with a keyboard and a thumb.

In this chapter

  • the Input Map: naming what the player means ("jump") instead of which key they pressed
  • polling – asking Input every frame with is_action_pressed, is_action_just_pressed, get_axis and get_vector
  • events – being told, in _input and _unhandled_input, with an InputEvent for each key, click and finger
  • why the interface sees an event before your game does, and how to use that
  • one game for a keyboard and a thumb, including the tap that arrives twice

Actions, not keys

Your game does not care that the player pressed Space. It cares that they want to jump. Godot lets you write the second thing and decide the first somewhere else.

You could ask about keys directly – "is the space bar down?" – and the code would work on your keyboard. Then someone plays with a controller. Someone else is left-handed and wants the arrow keys. Someone has a French keyboard, where the key in the W position has a Z on it. Each of those is a hunt through every script that mentions a key.

An action is a name for something the player can mean: move_left, jump, interact. The Input Map is the table that says which keys, mouse buttons and controller buttons trigger each action. Scripts only ever mention actions. Changing the controls, or adding a second way to do the same thing, is an edit to the table and to nothing else.

Here is a small Input Map to try. Click inside it, then press the keys it lists, one at a time and several together:

Three things to notice. Two different keys can trigger the same action, and the right-hand column does not say which one you used. A key that is in no action changes nothing in the table. And the list underneath shows something the table does not – we will come back to it in the section on events.

Where the map lives

In the editor it is Project → Project Settings, the Input Map tab. Type a name into Add New Action and press Add; then press the + at the end of the new row, and Godot waits for you to press the key, click the mouse button or move the stick you want. Do that again to give the action a second trigger.

A new project already has a set of actions, hidden until you switch on Show Built-in Actions. Their names start with ui_: ui_accept (Enter and Space), ui_cancel (Esc), and ui_left, ui_right, ui_up, ui_down (the arrow keys), each with controller buttons as well. They exist so that menus work from the first minute: they are what moves the focus between buttons and presses one. They are handy for a prototype, and the game view on this page uses them. For a real game, add actions of your own – change what ui_accept means and you have changed how every menu behaves.

W is not always W

A key event in the map can be stored by the letter printed on the key or by the key's position on the keyboard – its physical keycode. For movement you want position: W, A, S and D are chosen for where they sit under the left hand, not for their letters. Position is what the editor records unless you choose otherwise.

The idea, as a dictionary

The real Input Map belongs to the engine, but the idea is small enough to hold in a Dictionary (Chapter G): each action, and the list of keys that trigger it.

extends Node

# A model of the Input Map: action -> the keys that trigger it.
var input_map := {
	"move_left": ["A", "Left"],
	"move_right": ["D", "Right"],
	"jump": ["Space", "W", "Up"],
	"interact": ["E"],
}

func actions_for(key: String) -> Array:
	var found: Array = []
	for action in input_map:
		if key in input_map[action]:
			found.append(action)
	return found

func _ready() -> void:
	print("Space -> ", actions_for("Space"))
	print("Left  -> ", actions_for("Left"))
	print("Q     -> ", actions_for("Q"))

Press Edit and run and add "Space" to the list for "interact". One key now triggers two actions. Godot allows that too, and both fire – which is sometimes what you want (Little Hours uses Space to act, and the same press moves a conversation on) and sometimes a bug you will spend an evening on.

The map can be made in code

The Input Map is also an object, InputMap, that scripts can change while the game runs. This is what a "rebind keys" screen calls, and it is how a game can set up its controls without the editor:

func _ready() -> void:
	InputMap.add_action("dash")             # <1>
	var event := InputEventKey.new()        # <2>
	event.physical_keycode = KEY_SHIFT
	InputMap.action_add_event("dash", event)   # <3>
  1. A new, empty action. It exists but nothing triggers it yet.
  2. An event object describing "the Shift key, by position". The same class describes a real key press when one arrives.
  3. Add it to the action's list. Call this again with another event for a second trigger.

Polling: asking every frame

The first way to read input is to ask. Every frame, in _process, your script asks the Input object how things stand right now and acts on the answer.

Input is always there, in every script, with no setup. Four of its questions cover most games:

QuestionAnswer
Input.is_action_pressed("jump")true on every frame the action is held down.
Input.is_action_just_pressed("jump")true only on the frame it went down.
Input.is_action_just_released("jump")true only on the frame it came up.
Input.get_axis("move_left", "move_right")A float from -1 to 1: the second action minus the first.
Input.get_vector("move_left", "move_right", "move_up", "move_down")A Vector2 for two axes at once, never longer than 1.

Held, or pressed this frame?

The difference between the first two rows is the most common input bug there is. A tap of a key that feels instant to a finger lasts several frames to a game. Here is a key over eight frames – down for three, up, then down for one – and what each question would answer:

extends Node

# Is the jump key down? One entry per frame.
var frames := [false, true, true, true, false, false, true, false]

func _ready() -> void:
	var was_down := false
	var jumps_wrong := 0
	var jumps_right := 0
	for i in frames.size():
		var pressed: bool = frames[i]
		var just_pressed := pressed and not was_down
		print("frame ", i, "  pressed=", pressed, "  just_pressed=", just_pressed)
		if pressed:
			jumps_wrong += 1
		if just_pressed:
			jumps_right += 1
		was_down = pressed
	print("jumping while pressed: ", jumps_wrong, " jumps")
	print("jumping on just_pressed: ", jumps_right, " jumps")

Two presses, and the wrong question counts four. That is all "just pressed" means: down now, and not down last frame – Godot keeps the was_down for you. Use is_action_pressed for things that last as long as the key is held (walking, charging, aiming) and is_action_just_pressed for things that happen once per press (jumping, firing, opening a door).

In a real script the two sit side by side:

extends Node2D

const SPEED := 120.0

func _process(delta: float) -> void:
	if Input.is_action_pressed("move_right"):
		position.x += SPEED * delta
	if Input.is_action_pressed("move_left"):
		position.x -= SPEED * delta
	if Input.is_action_just_pressed("jump"):
		print("boing")

get_axis: two actions, one number

Those two ifs for left and right are so common that Input does them for you. get_axis(negative, positive) gives -1 when only the first action is held, 1 when only the second is, and 0 when neither is – or both. This is the arithmetic inside it:

extends Node

func axis(negative_held: bool, positive_held: bool) -> float:
	return float(positive_held) - float(negative_held)

func _ready() -> void:
	print("nothing held: ", axis(false, false))
	print("left held:    ", axis(true, false))
	print("right held:   ", axis(false, true))
	print("both held:    ", axis(true, true))

With that, the walking code is one line: position.x += Input.get_axis("move_left", "move_right") * SPEED * delta. And because the answer is a float, not a bool, a controller stick pushed halfway gives 0.5 and the character walks at half speed, with no extra code.

get_vector, and the diagonal problem

For a top-down game you want two axes. The obvious thing is two get_axis calls put into a Vector2 – and it has a flaw you can measure:

extends Node

func _ready() -> void:
	var right := Vector2(1, 0)      # only "right" held
	var diagonal := Vector2(1, 1)   # "right" and "down" held together
	print("right:      length %.2f" % right.length())
	print("diagonal:   length %.2f" % diagonal.length())
	print("normalised: length %.2f" % diagonal.normalized().length())
	print("at 100 px/s the diagonal covers %d px each second" % int(diagonal.length() * 100))

A vector of one right and one down is 1.41 long, by Pythagoras, so a character moved by it walks 41% faster diagonally than straight. Players find this within minutes. The cure is to normalise the direction – keep where it points, make its length 1 – before multiplying by the speed.

Input.get_vector(left, right, up, down) does both jobs: it reads the four actions and never returns a vector longer than 1. Mind the order of its arguments – negative x, positive x, negative y, positive y – and that "up" is the negative y action, because in 2D y grows downwards (Chapter L).

func _process(delta: float) -> void:
	var direction := Input.get_vector("move_left", "move_right", "move_up", "move_down")
	position += direction * SPEED * delta

You will build exactly this, and feel the difference, in the live tutorial below.

Events: being told

The second way to read input is to be told. Every key going down, every click, every movement of a finger arrives at your script as an object, at the moment it happens.

Give a node a function called _input or _unhandled_input and Godot calls it once for each thing the player does, passing an InputEvent that describes it. Nothing is called on the frames when nothing happens.

func _unhandled_input(event: InputEvent) -> void:
	if event.is_action_pressed("pause"):                 # <1>
		toggle_pause()
	elif event is InputEventMouseButton:                 # <2>
		if event.pressed and event.button_index == MOUSE_BUTTON_LEFT:
			walk_to(event.position)                      # <3>
  1. Events know about actions too. On an event, is_action_pressed means "this event is that action going down".
  2. InputEvent is a family of classes (Chapter H). is asks which one this is, and after it you can use that class's properties.
  3. The event carries its own details – here, where the click was. This is what polling cannot give you.

The family

ClassArrives whenWorth reading
InputEventKeya key goes down or comes upkeycode, physical_keycode, pressed, echo
InputEventMouseButtona mouse button or the wheelbutton_index, pressed, position, double_click
InputEventMouseMotionthe mouse movesposition, relative (how far since the last one)
InputEventScreenToucha finger lands or liftsindex (which finger), position, pressed
InputEventScreenDraga finger moves while downindex, position, relative
InputEventJoypadButton, InputEventJoypadMotiona controller button; a stick or triggerbutton_index, pressed; axis, axis_value

Every press is two events: one with pressed true when it goes down, one with pressed false when it comes up. Forgetting to check pressed makes everything happen twice per click.

Echo: the key that repeats itself

Go back to the key tester at the top of the chapter, click in it, and hold E down for two seconds. The list fills with pressed=true echo=true. That is the keyboard's own repeat, the same one that types "eeeeee" in a text box: after a pause, a held key sends press events again and again, each marked as an echo. For typing that is right. For "advance the dialogue" it is this:

extends Node

# What arrives when E is held for a moment and let go.
var events := [
	{"key": "E", "pressed": true, "echo": false},
	{"key": "E", "pressed": true, "echo": true},
	{"key": "E", "pressed": true, "echo": true},
	{"key": "E", "pressed": false, "echo": false},
]

var lines_skipped := 0

func _ready() -> void:
	for event in events:
		handle(event)
	print("One press of E advanced the dialogue ", lines_skipped, " times")

func handle(event: Dictionary) -> void:
	if event["pressed"]:
		lines_skipped += 1

Fix handle() so it counts 1: the condition needs and not event["echo"]. On a real InputEventKey the property is event.echo, and every event answers event.is_echo(). Asking by action is safer still – event.is_action_pressed("interact") ignores echoes unless you ask it not to.

Which way for which job

The game needsUse
to know what is held now: walking, steering, holding to chargepolling, in _process
to react once to a press: jump, pause, confirmeither – is_action_just_pressed when you are polling anyway, an event otherwise
the details of what happened: where the click was, how far the finger movedevents – only the event has them
to stay out of the way when the press was meant for a buttonevents, in _unhandled_input – the next section

A held key is a state; a click is a happening. Most games use both ways, each for what it suits, and so does Little Hours.

Who gets the event first

There is a pause button in the corner and a world behind it. When the player taps the button, the character must not also walk to that corner. Godot solves this with a queue, and the interface is near the front of it.

Each event is offered round in a fixed order, and anyone it is offered to may consume it – mark it as handled – after which nobody further along hears of it:

  1. _input()

    Every node with an _input function sees the event first, whatever it is aimed at. For things that must work everywhere: a screenshot key, a debug toggle.

  2. The interface

    Next come the Control nodes (Chapter R): the button under the pointer, the text box with the keyboard focus. A control that uses the event consumes it. A click on a Button stops here.

  3. _unhandled_input()

    Only what nobody wanted arrives here. This is where the game world listens: by the time a click reaches _unhandled_input, it is known not to have been for a button.

(Two specialised stops, _shortcut_input() and _unhandled_key_input(), sit between the interface and _unhandled_input(). You can go a long way without them.)

The same thing as a model you can run. Two buttons are rectangles; a tap goes to the first one that contains it, and to the world only if none does:

extends Node

var buttons := {
	"Menu": Rect2(250, 4, 64, 24),
	"Bag": Rect2(4, 150, 48, 24),
}

func route(tap: Vector2) -> String:
	for button_name in buttons:
		if buttons[button_name].has_point(tap):
			return "the " + button_name + " button – consumed, the world never hears of it"
	return "the world – walk to " + str(tap)

func _ready() -> void:
	print(route(Vector2(260, 10)))
	print(route(Vector2(160, 90)))
	print(route(Vector2(20, 160)))

Add a third button that covers the whole 320 × 180 screen – "Shade": Rect2(0, 0, 320, 180) – as the first entry, and run it. Nothing reaches the world any more. Remember that result; you will meet it for real.

The rule this gives you

Put gameplay input in _unhandled_input, not _input. Then the interface wins without any code from you: buttons, sliders, open panels and text boxes all take what is theirs, and the world gets the rest. The classic bug – click a HUD button and the character walks to it as well – is what happens when the world listens in _input and hears everything first.

Polling does not pass through this queue at all. Input.is_action_pressed("jump") is true while Space is down, whether or not a menu also used that press. A game that polls has to check for itself that it should be listening, as you will see Little Hours do.

Consuming an event yourself

Your own code can stop an event travelling further. In _input or _unhandled_input:

func _unhandled_input(event: InputEvent) -> void:
	if event.is_action_pressed("interact") and near_a_door():
		open_door()
		get_viewport().set_input_as_handled()   # nobody after me sees this one

For controls, the switch is a property: Mouse → Filter in the Inspector, mouse_filter in code. Stop means "clicks on me are mine", Ignore means "I am not here, as far as the pointer is concerned".

The invisible wall

The commonest way to break _unhandled_input is the Shade button from the example above: a control that fills the screen – a container holding the HUD, a full-screen ColorRect used for fading – whose mouse filter is Stop. It can be completely transparent and it still consumes every click. If your world stops hearing clicks after you add some interface, look for a big control and set its filter to Ignore.

A keyboard and a thumb

A phone has no keys, no hover and no right button; a desktop has no fingers. A game for both has to decide what each player does with what they have – and to cope with one odd thing Godot does to be helpful.

What a finger sends

A touch arrives as events only – there is nothing to poll. A finger landing is an InputEventScreenTouch with pressed true; moving while down, a stream of InputEventScreenDrag; lifting, a ScreenTouch with pressed false. Each carries an index, so two fingers on the glass are two separate conversations.

Two project settings, under Input Devices → Pointing, decide how touch and mouse relate:

SettingNew projectEffect
Emulate Mouse From TouchonEvery touch also produces a mouse event – a pretend click made from the finger.
Emulate Touch From MouseoffEvery click also produces a touch event, so you can test touch code on a desktop.

The first being on is why a new Godot game works on a phone at all: every Button listens for mouse clicks, and the pretend click is what presses it. It is also a trap for your own code.

The tap that arrives twice

If your code listens for touches and clicks – the natural thing to write for a game that runs on both – then on a phone one tap is delivered to it twice: once as the touch, and once as the click made from it. For "walk to here" that hardly shows. For anything that toggles, it is a disaster:

extends Node

const DEVICE_ID_EMULATION := -1   # in Godot: InputEvent.DEVICE_ID_EMULATION

# One tap of one finger, as a phone delivers it.
var one_tap := [
	{"type": "touch", "pressed": true, "device": 0},
	{"type": "mouse", "pressed": true, "device": DEVICE_ID_EMULATION},
	{"type": "touch", "pressed": false, "device": 0},
	{"type": "mouse", "pressed": false, "device": DEVICE_ID_EMULATION},
]

var holding := false

func _ready() -> void:
	for event in one_tap:
		on_event(event)
	print("Tapped the box once. Holding it: ", holding)

func on_event(event: Dictionary) -> void:
	if event["pressed"]:
		holding = not holding   # pick up, or put down

Picked up and put straight back down, in one tap. There are three honest ways out:

  • Listen for the mouse only. With the emulation on, a finger is a mouse. The least code; one finger at a time.
  • Listen for touch only, and switch on Emulate Touch From Mouse so you can test at your desk.
  • Listen for both and drop the copies. Every event has a device, and a pretend click's is the constant InputEvent.DEVICE_ID_EMULATION. Add this as the first line of on_event() above and run it again:
    if event["type"] == "mouse" and event["device"] == DEVICE_ID_EMULATION: return

In Little Hours

The game takes the third way, and the comment on its helper records the day the bug in the example above was a real one, in one of the phone's small games (Q):

UI.gd · lines 579–587

## Whether a click is the copy of a finger that already arrived as a touch.
##
## A tap on a phone is delivered twice: once as InputEventScreenTouch and again
## as a pretend mouse click made from it. A widget that listens for both and
## TOGGLES on a press – pick up, put down – does both halves with one finger,
## which is how Sorting Boxes lifted every object and dropped it straight back
## ("the game doesn't work", 3 Nov). Widgets that read both should skip these.
static func is_touch_copy(e: InputEvent) -> bool:
	return e is InputEventMouse and e.device == InputEvent.DEVICE_ID_EMULATION

InputEventMouse is the parent class of both mouse events, so one is covers clicks and movement. Every widget that reads both kinds of event starts by asking this.

Where was that, in the world?

An event's position is measured on the screen, from the top-left corner of the view. If a camera has scrolled or zoomed (Chapter L), that is not where the click is in the world. The viewport knows the transform it is drawing the world with; applying it backwards turns a screen point into a world point:

func _unhandled_input(event: InputEvent) -> void:
	if event is InputEventMouseButton and event.pressed:
		var to_world := get_viewport().get_canvas_transform().affine_inverse()
		walk_to(to_world * event.position)

Take the position from the event. It is tempting to ignore the event and ask where the mouse is, and on a touch screen that asks about a pointer the player does not have – Little Hours has the scar, below.

Say the right thing to the right player

The last part is not code, it is manners. A phone player cannot hover, so nothing important may live in a tooltip. They have no E key, so a hint that says "press E" is about somebody else's device. Godot can tell you which you are on: DisplayServer.is_touchscreen_available() for the glass, and OS.has_feature("mobile") for a phone or tablet build. Little Hours asks both in one function, Game.touch_only(), and its first hint says "Tap the floor to walk" or "WASD or the arrows to walk" accordingly.

Build it live

A character you can walk in eight directions, who faces the way they last moved and dashes when you ask – polling for what is held, and for what was pressed this frame.

In Little Hours

The game is played with a thumb on a phone and with keys and a mouse on a desktop, and both go through one file. It polls for walking, listens for everything else, and has a comment for each lesson it learned on the way.

The Input Map, in code

Open the game's Project Settings and the Input Map is empty. The actions are made when the game starts, by Main.gd, from a table at the top of the file:

Main.gd · lines 135–155

## The keys, registered here rather than in project.godot for the same reason
## everything else in this game is built in code: one place to read, nothing to
## keep in sync with a file the editor rewrites.
##
## Physical keycodes, so WASD stays under the same fingers on an AZERTY board.
const KEYS := {
	"move_left":  [KEY_A, KEY_LEFT],
	"move_right": [KEY_D, KEY_RIGHT],
	"move_up":    [KEY_W, KEY_UP],
	"move_down":  [KEY_S, KEY_DOWN],
	"interact":   [KEY_E, KEY_SPACE],
}

func _setup_input() -> void:
	for action in KEYS:
		if not InputMap.has_action(action):
			InputMap.add_action(action, 0.2)
		for code in KEYS[action]:
			var ev := InputEventKey.new()
			ev.physical_keycode = code
			InputMap.action_add_event(action, ev)

KEYS is the dictionary model from the first section, for real: five actions, two keys each. _setup_input() walks it with two loops and makes the same calls you saw earlier – add_action, a new InputEventKey, action_add_event. It sets physical_keycode, and the comment says why: position, not letter. The second argument to add_action is the action's dead zone, which only matters for controller sticks. Main._ready() calls this before it builds anything else.

Walking is polled

Every frame, Main._process() calls this:

Main.gd · lines 1283–1295

func _tick_keys() -> void:
	if _overlays.is_open or _hud.drawer_open() or _editing or _hold_drag or _talking():
		if _player.driving():
			_player.drive(Vector2.ZERO)
		return
	var dir := Input.get_vector("move_left", "move_right", "move_up", "move_down")
	if dir != Vector2.ZERO:
		# Taking the wheel overrules whatever a tap had queued, and it is
		# walking: the first-day "WASD to walk" waited on a tap otherwise.
		_drop_pending()
		Game.first_step("step_walk")
	if dir != Vector2.ZERO or _player.driving():
		_player.drive(dir)

The middle line is the one from step three of the tutorial. The first four lines are the price of polling. Input does not go through the event queue, so nothing stops it reporting W as held while a card is open, a conversation is going on or a piece of furniture is being dragged. The function has to ask for itself whether the keys are the world's right now – and if they are not, and the character was being steered, it passes Vector2.ZERO to let go, so that opening a card with a key held does not leave them walking.

The last if has the same care in it: drive() is called while a direction is held and once more on the frame the keys are released, when dir is zero but driving() is still true. That one extra call is how the character stops. The two lines above it are about the other way of walking: taking the keys cancels whatever a tap had queued up (R).

Everything else arrives as events

Taps, clicks, drags and the interact key all come through one function. It is long; this is the top of it:

Main.gd · lines 1115–1142

func _unhandled_input(event: InputEvent) -> void:
	# Taps on a button or an open panel are consumed by the UI before they reach
	# here, so anything arriving is meant for the world.
	if _overlays.is_open or _hud.drawer_open():
		_clear_hover()
		return

	# Somebody is mid-sentence: the next tap or key is for them.
	if _dialogue != null and _dialogue.is_open:
		# A finger arrives twice on a phone, as a touch and as a pretend click made
		# from it. Counting both finished the line and skipped it in one tap.
		if UI.is_touch_copy(event):
			return
		if event.is_action_pressed("interact") and not event.is_echo():
			_dialogue.advance()
			return
		if event is InputEventMouseButton and (event as InputEventMouseButton).pressed:
			_dialogue.advance()
			return
		if event is InputEventScreenTouch and (event as InputEventScreenTouch).pressed:
			_dialogue.advance()
			return

	if event.is_action_pressed("interact") and not event.is_echo():
		_interact_nearby()
		return

	var p := _event_point(event)

It is _unhandled_input, not _input, and the first comment says what that buys: a tap on a button never gets here. Then it is a ladder of early returns, most important first.

  • A card or the map drawer is open: the world ignores everything. (Buttons consume their own taps, but a tap on the empty part of a card is "unhandled" too, and must still not walk the character.)
  • Somebody is talking (T): the next press of any kind moves the conversation on. Look at the three ways a press can arrive – the action, a mouse button, a finger – and at the first check, which throws away the pretend click so one tap does not count as two. The comment records exactly that bug: a tap finished the line and skipped it.
  • Otherwise, the interact key acts on whatever is in reach. is_action_pressed on an event already ignores echoes; the game says not event.is_echo() out loud as well.
  • Only then does it work out where the pointer is, for the tapping, hovering and dragging that fill the rest of the function.

Where the tap landed

That last line calls a small function with a long comment:

Main.gd · lines 1095–1113

## Where a tap actually landed, in room coordinates.
##
## This must come from the *event*, not from `get_global_mouse_position()`.
## That call reports the pointer's own position, which
##   * is never updated by touch events at all (so on a phone every tap
##     resolved to a stale pointer spot), and
##   * carried the letterbox offset, so even with a mouse a click came out
##     a few hundred pixels off.
## The symptom was the player walking somewhere you didn't click, furniture
## never responding, and drags in Decorate mode grabbing nothing.
func _event_point(event: InputEvent) -> Vector2:
	var inv := get_viewport().get_canvas_transform().affine_inverse()
	if event is InputEventMouse:
		return inv * (event as InputEventMouse).position
	if event is InputEventScreenTouch:
		return inv * (event as InputEventScreenTouch).position
	if event is InputEventScreenDrag:
		return inv * (event as InputEventScreenDrag).position
	return inv * get_viewport().get_mouse_position()

The code is the listing from "Where was that, in the world?" – the canvas transform, inverted, applied to the event's own position – once for each kind of event that has one. The comment is the reason this chapter told you to take the position from the event. An earlier version asked get_global_mouse_position() instead, and the comment lists what the game found: on a phone the answer was stale, because taps were not moving the pointer it asks about, and even with a mouse it was off by the width of the black bars at the sides of the view. The symptoms it names are worth remembering as a diagnosis: the character walks to somewhere you did not click, and nothing you tap responds.

From here the tap goes on to become a walk, a chat or a piece of furniture being moved: Reaching and Decorating on the mechanics page follow it the rest of the way, and Inside the code walks through the whole function.

Your turn

Three exercises run in the game view – click it and use the keys, or the buttons under it – and three work on models of the Input Map and the event queue.

What to remember

  • Scripts name actions, never keys. The Input Map – in Project Settings, or built with InputMap in code – says which keys and buttons mean what.
  • Poll Input in _process for what is held: is_action_pressed, get_axis, and get_vector, which keeps diagonals from being faster. is_action_just_pressed is true for one frame per press.
  • Events arrive when things happen and carry the details. Check pressed, beware echo, and take the position from the event.
  • Events are offered to _input, then the interface, then _unhandled_input. Put the game in the last and buttons win by themselves; watch for a full-screen control swallowing everything.
  • With the default settings a touch also arrives as a pretend mouse click. Listen for one kind, or drop events whose device is InputEvent.DEVICE_ID_EMULATION.
  • Tell players about the controls they have, not the ones you have.
