Unique things: autoloads

Singletons, global state, class_name statics, and keeping 'global' from meaning 'everywhere'.

In this chapter

  • what an autoload is: a node Godot makes before your main scene and keeps for the whole run, reachable by name
  • why global state is convenient, what it costs, and the rules that keep it fair
  • class_name with static functions, the alternative that needs no node at all
  • signals out of an autoload, so it announces and never reaches into the scene
  • load order, and how Little Hours chooses its three autoloads – and what it deliberately does not make one

A node above the main scene

Most nodes live in a scene and die with it. Some things have to outlive every scene: the score, the settings, the sound. An autoload is Godot's answer – one node, made first, kept always, and findable by name from any script.

When you change scenes in a game, the old scene is freed and a new one is built. Anything the old scene was keeping goes with it. That is usually what you want – a level should not leak into the next – and it is exactly what you do not want for the player's coins. Something has to hold what survives.

You add one in Project Settings, on the Globals tab, under Autoload. You give it the path of a script (or a scene) and a Node Name, and press Add. Godot then does three things every time the game starts, before it opens your main scene:

  1. Creates the node

    From the script or scene you named, with the name you chose. For a script, the node's type is whatever the script extends.

  2. Adds it to the tree

    As a child of the root, the Window the whole game lives in – a sibling of your main scene, not a part of it. It is not freed when you change scene.

  3. Makes the name a variable

    In every script, Game now means that node. No get_node(), no path, no preload.

The list is saved in project.godot, the plain-text settings file from Chapter A. This is the real one from Little Hours:

../project.godot · lines 52–56

[autoload]

Sfx="*res://scripts/Sfx.gd"
Game="*res://scripts/Game.gd"
TownMind="*res://scripts/TownMind.gd"

Each line is Name="path". The * before res:// is the Enable tick in the Autoload list: with it the name is a global variable, without it Godot still loads the node but you would have to find it by path. Leave it on. Three autoloads, three names – and notice the order, because it is the order they are made in (the last section of this chapter is about why that matters).

Picturing it

The running game's tree looks like this. Your scenes come and go on the right; the autoloads stay on the left:

root (Window)
├── Sfx          ← autoload, made first
├── Game         ← autoload, made second
├── TownMind     ← autoload, made third
└── Main         ← your main scene, added last
    └── …rooms, people, the HUD…

Because Game is already a child of the root, it is also reachable the long way – get_node("/root/Game") – and that is what the short name is. The short name is nicer to read and the editor can complete it. You can only get at an autoload by its name from code in the running game; a script run on its own, or in the editor, has no tree above it for the name to point into.

The same thing, in the page

The book's interpreter has no Project Settings and no root, so here is the idea as a model: a script with state, a method to change it, and two "scenes" that come and go while the store stays. Everything an autoload does comes from it simply not being freed.

extends Node

# This script plays the autoload: made once, never freed.
var coins := 0

# A "scene" is something made, used, and thrown away.
class Shop extends RefCounted:
	func visit(store) -> void:
		store.coins += 5
		print("shop: earned 5, store has ", store.coins)

class Garden extends RefCounted:
	func visit(store) -> void:
		print("garden: store has ", store.coins)
		store.coins -= 2

func _ready() -> void:
	Shop.new().visit(self)       # made, used, gone
	Garden.new().visit(self)     # a different scene, same store
	Shop.new().visit(self)
	print("end: ", coins)

Each Shop.new() is a brand new object that knows nothing of the last one, and yet the coins carry on: 5, then 3, then 8. In the game the scenes are rooms and the store is Game. Change the 5 in Shop to 10 and follow the numbers through.

Autoloads can be scenes too

The path can point at a .tscn instead of a .gd. Do that when the global thing needs children of its own – a CanvasLayer for a fade-to-black that covers every scene, say, or an AudioStreamPlayer that must be set up in the editor. Little Hours builds its players in code, so all three of its autoloads are plain scripts.

Global state: when it is fair

A global is a promise that anything can read this and anything can change it. That is a great convenience and the cause of the worst bugs in the book. The trick is to decide what earns it.

Good globals have two properties. They are things there is only ever one of – one player's save, one set of settings, one speaker for the sound. And they are things nearly every part of the game needs, so passing them around by hand would be a chore: if every function that touched the day count had to be given the day count, you would spend your life threading it through.

The bad side is quieter. When anything can change the coins, a bug where the coins are wrong could be in any script. You cannot test a function that reads Game without a Game. And two scripts that never mention each other can still affect each other through the global, which is exactly the kind of coupling nodes and signals were invented to avoid. Here is the smallest version of that – one function quietly depending on a global it never says it needs:

extends Node

var day := 1          # the "global"

# Looks innocent. What does it return?
func rent() -> int:
	return 20 + day * 5

func _ready() -> void:
	print("rent on day 1: ", rent())
	day = 3
	print("rent on day 3: ", rent())
	# Nothing about rent() changed, and its answer did.

Nothing in the call rent() says that it depends on the day. A reader has to open the function to learn it, and a test has to set day first. Compare rent_for(day), which takes what it needs as a parameter and gives the same answer to the same question forever. Prefer the second shape wherever you can, and keep the global for the state itself.

Four rules that keep a global fair

  1. Few of them. Little Hours has 34,000 lines of script and three autoloads. Each new one should have to argue for its place.
  2. State and services only. "What is true now" (the day, the coins, what is owned) and "do this for me" (play a sound). Not scene logic.
  3. One front door for changes. Anything can read freely, but writes go through a function, so there is one place that knows a change happened. The next section builds that door.
  4. Never reach into a scene. The autoload must not know that a HUD or a Room exists. If it needs to tell the scene something, it announces (the section on signals).

The trap: freed nodes and stale references

Scenes are freed; autoloads are not. If an autoload keeps a reference to a node from a scene – var current_room: Node – that node will one day be freed while the autoload still holds the name of it, and the next use is an error. Hold data in an autoload (a room's id, a string), never a scene's nodes, and when you must, check is_instance_valid() first (Chapter C).

The alternative: class_name and static functions

An autoload is a node, and a node costs something: it sits in the tree, it has a _process it can accidentally use, and it is created at startup whether it is needed or not. If all you want is a place for functions, there is a lighter tool.

A script with class_name is available everywhere by that name, as you saw in Chapter H. And a function marked static can be called on the class itself, with no object made at all:

extends Node

# In a real project this would be a file of its own, starting
#   class_name Money
# Here an inner class stands in for it.
class Money:
	const SYMBOL := "£"

	static func format(pence: int) -> String:
		return "%s%d.%02d" % [SYMBOL, pence / 100, pence % 100]

	static func add_vat(pence: int) -> int:
		return pence + pence / 5

func _ready() -> void:
	print(Money.format(1999))          # no Money.new() anywhere
	print(Money.format(Money.add_vat(1000)))

No object, no node, nothing in the tree, and it works from any script. A const on the class is shared too; a static var is shared state, but it is just a variable on the class, so it cannot emit signals or call get_tree(), and you can easily end up with a global that is harder to see than an autoload. Use statics for pure helpers: functions whose answer depends only on what you pass in.

You need…Reach for
Something that holds changing state and tells others when it changesAn autoload (it has signals, and _ready and _process)
Something that owns nodes: audio players, a timer, an HTTP requestAn autoload – it must be in the tree
Helper functions: formatting, maths, parsing, lookups in a tableclass_name with static func
Fixed data: a table of prices, a list of roomsclass_name with const and static functions – the next section's examples are this
Something only one scene usesA node inside that scene, passed to whatever needs it

That last row is the one people forget. Making something an autoload because it is easy to reach is the road to a project in which everything is global.

Signals out: announce, never reach in

A store in the tree above everything can see everything – and the rule is that it must act as though it cannot. It changes its own state and says so. What listens is not its business.

Suppose the coin total changes, and the heads-up display must show it. There are two ways to arrange that:

  • Reach in. The store finds the label and sets its text: get_node("/root/Main/HUD/Coins").text = …. Now the store depends on the exact shape of one scene. Rename a node, change scenes, run the store in a test where there is no HUD, and it breaks – and so does everything that tries to change the coins.
  • Announce. The store declares signal state_changed and emits it. The HUD, on its way in, connects to it. The store does not know the HUD exists; the HUD knows the store by its global name, which is the one thing the HUD is allowed to assume.

The dependency now points one way, towards the autoload, and that is the direction you want: the things that change often (scenes) depend on the thing that is stable (the store), and never the other way round. Chapter J is the full story of signals; this is the shape in miniature:

extends Node

# The store: it holds the coins and announces changes. It knows no HUD.
var coins := 0
signal coins_changed(total: int)

func earn(n: int) -> void:
	coins += n
	coins_changed.emit(coins)

# Two listeners, made later, each looking after itself.
class Hud extends RefCounted:
	func _init(store) -> void:
		store.coins_changed.connect(_show)
	func _show(total: int) -> void:
		print("HUD shows: ", total, " coins")

class Chime extends RefCounted:
	func _init(store) -> void:
		store.coins_changed.connect(_ring)
	func _ring(total: int) -> void:
		if total >= 10:
			print("Chime: ding, ten coins")

func _ready() -> void:
	var hud := Hud.new(self)
	var chime := Chime.new(self)
	earn(4)
	earn(7)

Add a third listener and the store does not change by a line. Delete the Chime and the store still works. Try moving the line var chime := Chime.new(self) below the two earn calls: the chime misses everything, because a signal only reaches whoever was connected when it was emitted. Anything that starts later has to read the store's current value once, as it arrives.

A single signal for "something changed"

Chapter J gave a signal per event. An autoload with a lot of state often adds one coarse signal as well – state_changed, with no arguments – and lets listeners re-read whatever they show. It is less precise, and much less to wire: the HUD has one connection and redraws its chips from the dictionary. That is how Little Hours does it, as you will see below.

Load order, and who may use whom

Autoloads are made in the order they are listed. That order is a rule you have to know, because an autoload's _ready() can use the ones above it and cannot count on the ones below.

Godot makes each autoload and adds it to the tree in list order; each node's _ready() runs when it enters the tree with its children ready (Chapter I). So the first autoload is entirely ready before the second is even created, and every autoload is ready before the main scene's _ready(). Two things follow:

  • Your main scene may use any autoload in its _ready(). They are all there.
  • An autoload may use earlier ones in its own _ready(). Using a later one is using something that has not been made.

You can drag the rows of the Autoload list to reorder them, and the order you leave them in is the order they are created in. This model creates three stores in the order listed. Read the output, then swap two names in ORDER and see who finds whom missing:

extends Node

const ORDER := ["Sfx", "Game", "TownMind"]
var ready_names: Array = []      # who has finished _ready so far

# What each one needs from the others when it starts.
const NEEDS := {"Sfx": [], "Game": ["Sfx"], "TownMind": ["Game"]}

func boot(autoload_name: String) -> void:
	for needed in NEEDS[autoload_name]:
		if needed in ready_names:
			print(autoload_name, " starts: found ", needed)
		else:
			print(autoload_name, " starts: ", needed, " is NOT THERE YET")
	ready_names.append(autoload_name)

func _ready() -> void:
	for n in ORDER:
		boot(n)
	print("main scene starts with: ", ready_names)

With the order as written every need is met. Put "Game" first and it looks for Sfx and does not find it. In Godot that is not a polite message: it is a null instance and an error at start-up, often one that only appears in an exported build where something else is a little slower.

Keep it simple, and do not make circles

Two autoloads that each need the other in _ready() cannot both go first. The remedy is rarely a clever order; it is to stop one from needing the other at start. Let it use the other lazily (on first use, inside a function), or let the other be told through a signal, or – most often – notice that one of them is really not a global and move it. A start-up that depends on a delicate order is a start-up that breaks the day somebody adds a fourth autoload.

An autoload can see the tree, but should not trust it

When an autoload's _ready() runs, the main scene does not exist. get_tree().current_scene is empty then, and anything you look up by path in it will not be found. Do work that needs the scene from the scene, or wait with await get_tree().process_frame – and ask first whether the thing that wanted the scene should have been listening for a signal instead.

Build it live

A small Game store, built the way Little Hours builds its own: a dictionary of state, one door for changes, a signal that announces them, listeners that react, and a snapshot you could save.

In Little Hours

Three autoloads, chosen with care: the state, the speaker and the storyteller. And two things that look as if they could be autoloads and deliberately are not.

The list, and why these three

The list at the top of this chapter is the game's own. Game.gd is the state, the clock and the save; Sfx.gd builds every sound; TownMind.gd is the on-device writer of small talk. Each passes the two tests for a global: there is exactly one of each, and nearly every other script needs it. Sound is needed from the UI, the rooms, the pets and the minigames; the state is needed by everything; the small-talk model is a single, large, loaded-once thing that must not be started twice. Sfx is also the case for needing the tree: it owns AudioStreamPlayer nodes, so it has to be a node. It is first because Game uses it at start-up, as you will see.

One dictionary, one door

Game.gd · lines 8–13

signal state_changed          ## anything in `state` changed (HUD listens)
signal day_changed(day: int)  ## a new morning began
signal toast(text: String)    ## a transient line of flavour text
signal farm_updated           ## a crop finished growing on its own
signal theme_changed          ## the UI palette was switched (More ▸ Look)
signal orientation_changed    ## portrait <-> landscape

These are the announcements. Six signals declare everything the game's memory can tell the rest of it: something in the state changed, a new morning, a line of flavour text, a crop ripened by itself, the palette switched, the screen turned. Each carries a one-line ## comment saying who listens. The state itself is a plain Dictionary, var state := {}, declared further down. Everything else in the game reads it freely (Game.state["day"] appears all over) and writes through functions, and the one every writer finishes with is this:

Game.gd · lines 1247–1249

func _changed() -> void:
	state_changed.emit()
	save_now()

Two lines. state_changed.emit() announces, and save_now() writes the file. That pairing is the whole reason for a front door: because every change that matters ends here, the game cannot change something and forget to save it, and no listener has to remember to ask for the state. Notice that the signal has no arguments – this is the coarse "something changed" signal from the signals section, and the HUD answers it by redrawing from the dictionary:

HUD.gd · lines 53–58

Game.state_changed.connect(_refresh)
Game.toast.connect(show_toast)
# The chips and bars carry per-node style overrides baked from the palette at
# build time, so a palette switch can't just reassign the Theme — the whole
# bar is rebuilt instead.
Game.theme_changed.connect(_build)

The HUD is the listener: it connects to three of Game's signals in its own _ready(), and Game never learns that a HUD exists. Look at the last line of its _ready(), _refresh() with no signal behind it: it reads the current state once on the way in, because a signal only reaches what was already connected (the late-listener trap from the signals section). More on how the two fit in Saving and Clock.

The order that matters

Sfx is listed before Game for a reason, and the reason is in what Game does with it when the settings are applied:

Game.gd · lines 2593–2597

Sfx.enabled = bool(st.get("sfx", true))
Sfx.set_sfx_volume(float(st.get("sfx_vol", 0.8)))
Sfx.set_music_volume(float(st.get("music_vol", 0.7)))
Sfx.set_music(bool(st.get("music", true)))
Sfx.voices_enabled = bool(st.get("voices", true))

This runs from Game._ready() (by way of apply_settings()), setting the volumes and switches on an Sfx that must already be there. List them the other way round and the first line of this block would be an error on a missing node. This is the dependency in one direction only – Game knows the sound; the sound knows nothing of Game – which is what makes the order possible at all. What it is for is under Voices and sound.

Services that guard themselves

TownMind is a service, not a store, and it does something worth copying: before it does anything, it checks whether it should.

TownMind.gd · lines 101–110

## Whether small talk comes from here right now.
##
## English only. The model is small and was taught in English; its Turkish
## would be the weakest writing in a game that is otherwise carefully written,
## so in any other language the townsfolk say their written lines – which are
## translated – and the download and the switch stay as they were.
func enabled() -> bool:
	return plugin_present() and _state != "failed" and downloaded() \
		and bool((Game.state.get("settings", {}) as Dictionary).get("ai_talk", false)) \
		and Lang.current() == "en"

The comment gives the reason for the last condition, and the shape is what matters here. Callers elsewhere – Main.gd does it when you walk up to a neighbour – write if TownMind.enabled(): and carry on, and when it is false the neighbours say their written lines instead. The global did not need to tell anyone about its internal state ("the plugin is present", "the download failed", "the setting is off"); it exposes one question and answers it. A global with a narrow face is a global that is cheap to live with. See the small-talk AI for what it writes.

What is deliberately not an autoload

Open RoomData.gd and NeighborData.gd and look at the first lines of each: class_name RoomData / extends RefCounted, and the same for NeighborData. They are the game's rooms and its townsfolk, read everywhere, and they are not autoloads. They are the "fixed data" row of the table in the statics section: constants and static funcs on a class that is never instantiated. They hold no changing state (that is Game's), emit nothing, need no tree, and so need no node – calling RoomData.room_name(id, id) from anywhere just works. NeighborData does read Game.state["day"] when a function is called and needs it, but never at start-up; and Game._ready() calls into RoomData (it sets the orientation first), not the other way about.

That is the whole policy in two lists. A node that holds what is true now, or owns something in the tree, is an autoload. A table of what is always so, or a bag of helpers, is a class_name script with statics. Everything else belongs to a scene.

Your turn

Six exercises on the shapes of this chapter, all pure logic: the book has no autoload settings, so each script plays the autoload itself.

What to remember

  • An autoload is a node made from a script or scene listed under Project Settings › Globals › Autoload: created before the main scene, kept through every scene change, and reachable from any script by its Node Name. The list lives in project.godot.
  • Global state is fair for things there is one of and nearly everything needs – the save, the settings, the sound. Keep them few, keep data and not scene nodes in them, and write through one front door.
  • For helpers and fixed tables, a class_name script with static func and const needs no node and no autoload. Reach for an autoload only when it must hold changing state, emit signals or own nodes.
  • An autoload announces with signals and never reaches into a scene. Listeners connect, and read the current state once as they arrive, since a signal only reaches what is already connected.
  • Autoloads are made in list order. One may use the ones above it in _ready(); the main scene may use all of them; two that need each other at start-up are one design problem, not an ordering one.
