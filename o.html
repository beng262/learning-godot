On-screen drawing with _draw

draw_rect, draw_line and friends, queue_redraw, and building a widget out of nothing but code.

In this chapter

  • _draw(): a node that paints itself with draw_rect, draw_circle, draw_line, draw_arc, polygons and text
  • local coordinates – why a drawing is made around its own node and follows it everywhere
  • why _draw() runs once, and what queue_redraw() really does
  • drawing order: later calls cover earlier ones
  • building widgets from nothing – a stamina bar and a stopwatch – and how Little Hours draws its rain

A node that draws itself

A sprite shows a picture somebody made. Sometimes there is no picture: the thing is a bar that is 62% full, a line from here to the mouse, ninety drops of rain. For those, a node can paint itself in code.

Everything you can see in a 2D game – every Node2D and every Control – is a CanvasItem, and every CanvasItem has a function called _draw(). Godot calls it when it needs to know what the node looks like. Inside it you call drawing functions, and what they draw is the node:

extends Node2D

func _draw() -> void:
	draw_rect(Rect2(-30, -20, 60, 40), Color("#d9644a"))   # a card
	draw_circle(Vector2.ZERO, 6.0, Color.WHITE)            # a dot in its middle

No texture, no child nodes, no scene: two lines and there is something on the screen. It is the right tool when the thing is a shape and not a piece of art, when what it looks like depends on numbers that change, when you want to see something while debugging (a path, a collision box), or when there are so many small things that a node for each would be wasteful.

Local coordinates

The numbers you give the drawing functions are measured from the node's own origin, not from the corner of the screen. Vector2.ZERO is wherever the node is. x grows to the right and y grows downwards, as everywhere in Godot's 2D (Chapter L). For a node that is not rotated or scaled, the place a point ends up is its position plus the point:

extends Node

func _ready() -> void:
	var node_position := Vector2(160, 90)
	var corners := [Vector2(-20, -20), Vector2(20, -20), Vector2(20, 20), Vector2(-20, 20)]
	for local in corners:
		print("drawn at ", local, "  appears at ", node_position + local)

Change node_position to Vector2(40, 40): the right-hand column moves and the left does not. That is the point. The drawing describes the thing; where the thing is stays the node's business. Move the node, rotate it, scale it, and the drawing goes along without one line of _draw() changing.

Your turn already, because this chapter is for the hands. The exercises inside the sections are small; the game view beside each one is your script running as one Node2D in a 320 × 180 window.

The calls

There are about thirty drawing functions. These seven do nearly everything:

CallDraws
draw_rect(rect, color, filled = true, width = -1.0)A rectangle. With filled false it is an outline, width pixels thick.
draw_circle(center, radius, color)A filled circle.
draw_line(from, to, color, width = -1.0)A straight line between two points.
draw_arc(center, radius, start_angle, end_angle, point_count, color, width = -1.0)Part of the outline of a circle, between two angles. It is made of point_count points joined by straight pieces, so more points is smoother.
draw_colored_polygon(points, color)A filled shape through a list of points: a triangle, an arrow, a hill.
draw_polygon(points, colors)The same with a list of colours – one for each point, blended across the shape, or a single one for all of it.
draw_string(font, position, text, alignment, width, font_size, color)One line of text. There is more on this one below.

A width of -1.0, the default, means the thinnest line there is. There are also calls for pictures (draw_texture), for a line through many points (draw_polyline) and for dashes (draw_dashed_line); once you know these seven, the rest read the same way.

Angles are in radians, as always in Godot. Zero points along +x, to the right, and because y grows downwards a growing angle turns clockwise on the screen. A full turn is TAU. To find the point at an angle on a circle – which every dial, clock and spinner needs – use cos for x and sin for y:

extends Node

func on_circle(angle: float, radius: float) -> Vector2:
	return Vector2(cos(angle), sin(angle)) * radius

func _ready() -> void:
	var names := ["3 o'clock", "6 o'clock", "9 o'clock", "12 o'clock"]
	var angles := [0.0, PI / 2, PI, -PI / 2]
	for i in 4:
		print(names[i], ": angle ", snappedf(angles[i], 0.01), ", point ", on_circle(angles[i], 50.0).round())

Six o'clock is at a positive y and twelve o'clock at a negative one: up is minus. Twelve o'clock is the angle -PI / 2, a quarter turn back from where angles start. Add PI / 4 to the list of angles (and a name for it) and see which way it went from three o'clock.

Drawn once, kept until asked

The most important fact about _draw() is how rarely it runs. Godot calls it once, keeps the result, and shows that result every frame until you say the picture is out of date.

It is tempting to think of _draw() as "what happens every frame", like _process. It is not. The drawing functions do not put pixels on the screen; they add commands to a list that belongs to the node. Godot keeps the list and replays it each frame, which costs almost nothing. A floor of four hundred tiles is drawn by your code once and then shown for as long as you stand on it.

The catch is the other side of the same coin. Change a variable that _draw() reads, and nothing on the screen changes: the list was made from the old value and nobody has asked for a new one. You ask with queue_redraw().

The word queue is exact. It does not draw anything now. It raises a flag, and before the next frame is shown Godot looks at the flag and calls _draw() once if it is up. Here is that mechanism as a few lines you can run:

extends Node

var needs_drawing := true     # a new node always needs its first drawing
var draws := 0

func ask_for_redraw() -> void:      # what queue_redraw() does
	needs_drawing = true

func end_of_frame() -> void:        # what Godot does before showing a frame
	if needs_drawing:
		draws += 1                  # here it would call _draw()
		needs_drawing = false

func _ready() -> void:
	for frame in 6:
		if frame == 3:
			ask_for_redraw()
			ask_for_redraw()
			ask_for_redraw()
		end_of_frame()
		print("frame ", frame, ": _draw() has run ", draws, " time(s)")

Once at the start, then silence, then once more on frame 3 although it was asked three times. Asking is free, so you never need to worry about asking twice. Move the three calls out of the if so they happen every frame, and draws climbs by one a frame: that is what "redrawing every frame" means.

Not every change needs a new drawing. The list is drawn through the node's transform and colour, so those can change freely:

You changeNew drawing needed?
position, rotation, scaleNo. The kept drawing is moved, turned or stretched.
modulate, visible, z_indexNo. It is tinted, hidden or re-ordered as it is.
Anything your _draw() reads – a value, a list of points, a colour of your ownYes: queue_redraw().

When to ask

There are two honest answers, and a real game uses both.

When something changed. A health bar changes a few times a minute. Ask at the moment the value changes, and the node costs nothing for the rest of the time. In a real Godot project the tidy place for that is a setter, a small function that runs whenever the variable is assigned (the interpreter in this page does not run setters, so this one is a listing):

var value := 0.0:
	set(v):
		value = v
		queue_redraw()     # whoever changes value, the bar follows

Every frame. Rain, a spinner, a stopwatch hand: these are never still, so _process ends with queue_redraw() and that is that. It is not wasteful when the picture really is different every frame.

Drawing calls only work inside _draw()

Call draw_rect() from _process() or _ready() and Godot reports an error and draws nothing: there is no list open to add to. The same is true in this page. The pattern is always the same two halves – change variables anywhere and call queue_redraw(); turn variables into shapes in _draw() and nowhere else.

Later covers earlier

Inside one _draw() there is no depth and no layers. There is only order: each call paints over whatever is already there, like paint on a wall.

So you draw from the back to the front. Background, then the things on it, then outlines, then text. An outline drawn before its fill is half hidden by it; a label drawn before its panel is never seen. A colour with an alpha below 1 lets what is underneath show through, which is how a highlight or a shadow is made – and one more reason order matters, because it blends with whatever was drawn before it.

When a _draw() grows past a dozen lines, split it into helper functions and let _draw() be the list of layers. Drawing calls work in any function, as long as that function is being called from _draw():

func _draw() -> void:
	_draw_sky()
	_draw_hills()
	_draw_house()
	_draw_rain()        # in front of everything

Now the order of the picture can be read, and changed, in one place. The next exercise is written that way.

Between nodes

Order inside _draw() is yours. Order between nodes is the scene tree's, and it is the subject of Chapter L: nodes lower in the tree draw later, a node's children draw over what the node itself drew, and z_index overrides both. What matters here is that everything one _draw() paints sits at that node's single depth. One node cannot paint a tree trunk that a character walks behind and a treetop the character walks under. That takes two nodes.

In Little Hours

The room is drawn in exactly these two ways at once. RoomView.gd paints everything flat – wall, floor, paths, water, the road – in its _draw(), once for each room you walk into. Everything that stands up, and so must sort in front of or behind the people walking about, is a Sprite2D child with its own z_index.

A widget from nothing

A progress bar, a dial, a chart, a minimap: none of them needs an image. Each is a few numbers and a rule for turning them into shapes, and they are all built to the same plan.

  1. State

    Decide the few variables that say what the widget shows: value and max_value; seconds; a list of numbers.

  2. Geometry

    Write small functions that turn state into shapes and return them: "the rectangle of the filled part", "the point where the hand ends", "the colour for this level". They draw nothing, so they are easy to test and to get right.

  3. Paint

    _draw() calls those functions and paints the results, back to front. It should contain almost no arithmetic.

  4. Ask

    Wherever the state changes, queue_redraw().

The geometry is where the thinking goes, and most of it is the same sum: a share of a length. A chart is a good example, because of the one thing about it that trips everyone – y grows downwards, so a bar that stands on a line starts above it:

extends Node

const DATA := [3, 7, 5, 12, 9]
const MAX_H := 80.0     # how tall the tallest bar is, in pixels
const BASE_Y := 40.0    # the y of the line the bars stand on

func _ready() -> void:
	var top: int = DATA.max()
	for i in DATA.size():
		var h: float = MAX_H * DATA[i] / top
		print("value ", DATA[i], ": ", snappedf(h, 0.1), " px tall, from y = ", snappedf(BASE_Y - h, 0.1), " down to y = ", BASE_Y)

Each height is the value's share of the largest value, times the room there is. The top of a bar is BASE_Y - h, and the Rect2 for it would start there and be h tall. Change the 12 to 24: every other bar halves, because the scale follows the data. You will turn this into a drawn chart in the exercises.

Text

draw_string has the longest list of arguments and the most surprises, so here it is slowly:

draw_string(
	ThemeDB.fallback_font,          # <1>
	Vector2(-60, 26),               # <2>
	"62 / 100",
	HORIZONTAL_ALIGNMENT_LEFT, -1,  # <3>
	12,                             # <4>
	Color.WHITE)
  1. Text needs a font. ThemeDB.fallback_font is the one Godot always has. A game uses its own, loaded once and kept (Chapter R).
  2. The position is the left end of the baseline – the line the letters sit on – not the top-left corner of the text. Text drawn at Vector2.ZERO appears above the origin. This is the surprise.
  3. Alignment and a width to align inside. With a width of -1 there is no box and the text starts at the position.
  4. The size, in pixels.

To centre or right-align text by hand you need to know how wide it will be, and the font can tell you: font.get_string_size(text, HORIZONTAL_ALIGNMENT_LEFT, -1, font_size) returns a Vector2. Draw at x - size.x / 2 and the text is centred on x.

Node2D or Control?

The game view in this page is a Node2D, so these widgets are drawn around the origin. In a real interface a hand-drawn widget should extend Control instead. A Control has a size, given to it by whatever container it sits in, so its _draw() paints from Vector2.ZERO to size and the same bar works at any width. Set custom_minimum_size so the layout knows how much room it needs. Everything else in this chapter is the same for both – they are both CanvasItems.

Build it live

Two widgets, each from an empty _draw(). The first is all rectangles and is about when to draw. The second is all angles.

In Little Hours

Little Hours draws a great deal by hand: the rain and snow, the ring where you tap, the shadow under every character, the farm plots, the floor of every room and the whole of each minigame are _draw() functions. Four of them show this chapter from start to finish.

Rain is ninety rectangles

The weather (W in the game's A to Z) is a small class inside Main.gd, class Weather extends Node2D. The heading above it says it is drawn and is not a particle system, "so it costs almost nothing on a phone". Its state is a list, _drops, of dictionaries with an x and a y. _process moves every drop down by its speed times delta, sends any that have left the bottom back to the top, and ends with queue_redraw(). Then:

Main.gd · lines 2826–2842

func _draw() -> void:
	if not active:
		return
	if kind == "Rainy":
		for d in _drops:
			var x := float(d["x"])
			var y := float(d["y"])
			# A streak of whole art pixels, falling straight: a slanted line
			# is a smooth polygon, the one soft thing in a pixel downpour.
			draw_rect(Rect2(roundf(x / 3.0) * 3.0, roundf(y / 3.0) * 3.0, 3.0, 24.0),
				Color(0.80, 0.88, 0.96, 0.42))
		draw_rect(Rect2(Vector2.ZERO, Vector2(Game.ROOM)), Color(0.42, 0.52, 0.68, 0.10))
	else:
		for d in _drops:
			draw_rect(Rect2(roundf(float(d["x"]) / 3.0) * 3.0, roundf(float(d["y"]) / 3.0) * 3.0,
				6.0, 6.0), Color(1, 1, 1, 0.72))
		draw_rect(Rect2(Vector2.ZERO, Vector2(Game.ROOM)), Color(0.80, 0.86, 0.98, 0.10))

One draw_rect for each drop: 3 wide and 24 tall for rain, 6 by 6 for snow. roundf(x / 3.0) * 3.0 snaps each to a grid of three game pixels, the size of one pixel of the game's art, so the rain is made of the same squares as everything it falls on. The comment explains why a drop is an upright rectangle and not a slanted draw_line: a slanted line is smooth, "the one soft thing in a pixel downpour". The last call in each branch paints one faint rectangle over the whole room, after the drops and so on top of them, to cool the light. And when the weather is clear the function returns at once and the node draws nothing at all.

The smallest file in the game

Tap the floor and a ring spreads from your finger (R). Ripple.gd is seventeen lines, and these are the ones that do anything:

Ripple.gd · lines 9–17

func _process(delta: float) -> void:
	_r += 300.0 * delta
	_a -= 1.9 * delta
	queue_redraw()
	if _a <= 0.0:
		queue_free()

func _draw() -> void:
	UI.draw_pixel_ring(self, Vector2.ZERO, _r, Color(1, 1, 1, _a), 3.0)

State: two numbers, a radius and an alpha. _process grows one and shrinks the other by delta, asks for a new drawing, and frees the node once it is invisible. _draw() is one call, at Vector2.ZERO. That is local coordinates at work: Main puts the ripple's position on the place you tapped, and the ripple draws round its own origin without knowing where that is.

A circle out of squares

The ripple does not call draw_arc, and nothing in the minigames calls draw_circle. They call helpers in UI.gd, and this is the plainest of them:

UI.gd · lines 273–286

## A filled circle drawn as pixel art, on a grid of `unit`-sized pixels, for the
## few things the game draws by hand (a ball, a dot on the map, a crop). Godot's
## draw_circle is a smooth polygon; this is rows of whole squares.
static func draw_pixel_disc(ci: CanvasItem, centre: Vector2, radius: float, col: Color,
		unit: float = PX) -> void:
	var rr := maxi(1, roundi(radius / unit))
	var c := (centre / unit).round() * unit
	for dy in range(-rr, rr):
		var y := float(dy) + 0.5
		var hw := int(sqrt(maxf(0.0, float(rr * rr) - y * y)) + 0.5)
		if hw <= 0:
			continue
		ci.draw_rect(Rect2(c.x - float(hw) * unit, c.y + float(dy) * unit,
			float(hw * 2) * unit, unit), col)

Two things to take from it. First, how a helper outside the node can draw at all: the drawing functions are methods of the CanvasItem, so the node hands itself over as ci, and the helper calls ci.draw_rect. It still only works while that node's _draw() is running. Second, what it draws: one rectangle for each row of the circle, the row's half-width worked out with a square root, everything a whole number of units. As the comment says, Godot's own circle is smooth, and a smooth circle next to pixel art looks like it came from another game.

The panels and buttons of the interface look as if they were drawn the same way, and they are not. UI.pixel_box() paints each kind of box once, pixel by pixel, into an Image, keeps it as a texture and hands it to the theme as a StyleBoxTexture (Chapter R). No _draw() of the game's runs for a button.

A widget from nothing

Fishing (Q) is a float that slides back and forth along a bar, and a button to press while it is in the green part. The bar is a class at the bottom of Overlays.gd. Its _process is two lines – add to a clock, queue_redraw() – and this is its picture:

Overlays.gd · lines 4681–4694

func _draw() -> void:
	var w := size.x
	var track := Rect2(0, 40, w, 40)
	draw_rect(track, Color("#dfe9ef"))
	draw_rect(track, Color("#b6c9d4"), false, 3.0)
	# the green "bite" window
	var zx := track.position.x + w * _zone_start
	var zw := w * _zone_size
	draw_rect(Rect2(zx, track.position.y, zw, track.size.y), Color(0.49, 0.71, 0.45, 0.55))
	# the float
	var mx := track.position.x + w * marker()
	var col := UI.GOOD if in_zone() else UI.ACCENT
	draw_rect(Rect2(mx - 5, track.position.y - 12, 10, track.size.y + 24), col)
	UI.draw_pixel_disc(self, Vector2(mx, track.position.y - 18), 9.0, col)

It is the stamina bar you built: a track, then its outline with false, 3.0, then a translucent green window, then the marker on top, in a colour that depends on the state. FishingBar extends Control, so it measures everything from size.x, the width the card gave it, and fits any phone. And the question the game asks when you press the button, in_zone(), is the same function the drawing uses to choose the marker's colour – the picture cannot disagree with the rule.

The larger minigames in Widgets.gd are built to the same plan, with their score and lives written by draw_string so that they need no labels beside them. The split between what is drawn once and what is drawn every frame is in RoomView.gd: the floor is one node that draws when you enter a room, the shimmer on the water is a second, tiny node that redraws every frame, and the farm plots (F) are a third that redraws only when you plant or water.

What to remember

  • Every 2D node is a CanvasItem and can paint itself in _draw() with draw_rect, draw_circle, draw_line, draw_arc, draw_colored_polygon and draw_string. The calls work nowhere else.

  • Coordinates are local: the origin is the node, y grows downwards, angles turn clockwise from the right. Moving, turning, scaling or tinting the node needs no new drawing.
  • _draw() runs once and the result is kept. queue_redraw() raises a flag; one new drawing is made before the next frame, however often you asked.
  • Ask when the state changes, or every frame for things that never rest – not every frame out of habit.
  • Inside _draw(), later calls cover earlier ones: paint back to front. Everything one node draws shares that node's depth.
  • A widget is state in variables, geometry in small functions that return shapes, and a _draw() that paints what they return.
