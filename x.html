eXporting and shipping

Export templates, presets, Android bundles and signing, desktop and web, and getting it to players.

In this chapter

  • what an export is: a template, a pack of your files, and a preset that says how to join them
  • debug and release builds, and the two version numbers every shipped game carries
  • Android properly: APK and AAB, the keystore, signing, and the Play Console's tracks
  • desktop, web and iOS in outline, and itch.io as the shortest road to a player
  • how Little Hours goes from a folder on a Mac to a tester's phone with one command

What an export is

Until now your game has run inside the editor, straight from the project folder. A player has neither. Exporting is how the folder becomes one thing somebody else can open.

An exported game is two parts joined together. The first is the engine, compiled for one platform with the editor taken out: the part that knows how to open a window on Windows or draw on an Android screen. The second is the pack, a single .pck file holding your project – the scenes, the scripts, the imported textures and sounds. The engine is the same for everybody's game; the pack is yours.

Export templates

The editor does not carry an engine for every platform inside it. Those come separately, as export templates, and you install them once per version of Godot from Editor › Manage Export Templates…. It is a large download because it holds a ready-built engine for each platform, in two flavours each.

Templates must match the editor exactly

Templates for 4.7.1 will not export from a 4.7.2 editor. When you update Godot, update the templates in the same sitting. Little Hours met this on a release day: the editor had been updated, the templates had not, and the Android export stopped with "Android build version mismatch" before anything was built.

Export presets

A preset is a saved answer to "export for what, and how?". You make one in Project › Export… with Add…, pick a platform, and fill in its options: the name of the app, its icon, which files go in the pack, where the result is written. One project can have many presets, and often has two for the same platform that differ in one option.

Godot saves them all in a text file beside project.godot called export_presets.cfg. It is the same kind of file as project.godot: sections in square brackets, key=value lines under them. A script cannot open a real one in this page, but the shape is easy to hold as data – an array with one dictionary per preset – and reading it is ordinary GDScript:

extends Node

var presets := [
	{"name": "Web", "platform": "Web", "path": "build/web/index.html"},
	{"name": "Android", "platform": "Android", "path": "build/game.aab"},
	{"name": "Android Phone", "platform": "Android", "path": "build/game.apk"},
	{"name": "macOS", "platform": "macOS", "path": ""},
]

func _ready() -> void:
	for preset in presets:
		var where: String = preset["path"]
		if where == "":
			where = "(no path yet)"
		print("%-14s %-8s %s" % [preset["name"], preset["platform"], where])

Give the macOS preset a path and run it again. A preset with no export path can still be used from the editor, where a file dialog asks, but not from a script, where nobody is there to answer. That matters once you automate a release (Chapter Y).

Which files go in the pack

By default a preset exports every resource in the project: everything Godot imported or knows how to load. The trap is the files it does not recognise. A .txt of dialogue, a story saved as .html, a data file your code opens with FileAccess (Chapter S) – these can be left out of the pack without a word, because to the exporter they are not resources. The game then works perfectly in the editor, which reads the real folder, and breaks on a phone, which only has the pack.

The cure is on the preset's Resources tab: a filter for extra files to include, written as patterns such as data/*.json. Whenever you add a new kind of file to a project, ask whether the export knows about it, and test an exported build rather than the editor.

Debug and release

Every platform's template comes in two flavours.

Debug buildRelease build
What it is forYou and your testers, while things still breakPlayers
ErrorsReported in full; the editor's debugger can attach to itChecks are stripped out for speed and size
assert()RunsSkipped entirely
OS.is_debug_build()truefalse

Pressing F5 in the editor counts as a debug build too. Two consequences follow. Never put work the game depends on inside an assert(), because in a release build the whole line is gone. And always play the release build before you ship it: it is the only one your players will ever run.

Code can ask what it is running in with feature tags. OS.has_feature("debug"), "release", "editor", "mobile", "pc", "web" and the platform names such as "android" each answer true or false. The book's interpreter has no OS, so here the tags of three builds are written out as arrays and the decisions are made the same way:

extends Node

# What OS.has_feature() would say yes to in three builds of one game.
const BUILDS := {
	"editor, F5": ["editor", "debug", "pc"],
	"debug APK": ["debug", "mobile", "android"],
	"release bundle": ["release", "mobile", "android"],
}

func cheats_allowed(features: Array) -> bool:
	return features.has("debug")

func save_hint(features: Array) -> String:
	return "Tap the disk to save" if features.has("mobile") else "Press S to save"

func _ready() -> void:
	for build in BUILDS:
		var features: Array = BUILDS[build]
		print(build, ": cheats ", cheats_allowed(features), ", ", save_hint(features))

Add a fourth build, "web demo": ["release", "web"], and see what it gets. In a real project the function bodies would read OS.has_feature("debug") and nothing else would change. Project settings can be tagged the same way: a setting followed by a full stop and a tag, such as renderer/rendering_method.mobile, applies only where that tag is true.

Two version numbers

A shipped game has two versions: a name for people and a number for machines. Mixing them up is the commonest way a release is refused.

The version name is what a player sees: 2.9.0. It is text, and you may write anything. Most projects use three numbers – major, minor, patch – and raise the last for a fix, the middle for something new, and the first for a change big enough to announce.

The version code (Android's word; Apple calls its equivalent the build number) is a whole number the store uses to tell builds apart: 39. Nobody sees it. It has one rule, and the rule is strict: every build you upload must carry a higher number than the last. Two uploads of version name 2.9.0 are fine; two uploads of code 39 are not.

Because the name is text, comparing two names needs care. This is the trap:

extends Node

func _ready() -> void:
	# Text is compared a character at a time, and "1" comes before "9".
	print("2.10.0" > "2.9.0")

	var parts := "2.10.0".split(".")
	print(parts)
	# The middle part as a number: ten is more than nine.
	print(int(parts[1]) > 9)

The first line prints false: as text, version 2.10 looks older than 2.9. Change "2.10.0" to "2.11.0" and it is still false. The only safe way is to split the name on its full stops, turn each piece into an int, and compare number by number – which is what you will build in the tutorial below.

Where the numbers live

Each preset has its own fields for them: on Android a version name and a version code, on iOS and macOS a short version and a build. Recent versions of Godot 4 also have one project-wide version under Project Settings › Application › Config, which code can read with ProjectSettings.get_setting("application/config/version") to show on a title screen. Which presets fall back to it when their own field is empty has changed between engine versions, so check an exported build rather than assuming.

Wherever they live, two habits save trouble. Show the version name somewhere in the game, so that a tester's "it crashed" comes with "on 2.9.0". And never raise the code by hand: let a script do it (Chapter Y), because a person forgets and a store does not.

Android: bundles, keys and tracks

Android is the platform with the most steps, and each of them exists for a reason. Take them one at a time and none is hard.

What you install first

Godot cannot build an Android app by itself. It needs a Java development kit and the Android SDK on your computer, and their locations entered in the editor's settings. The exact versions it wants move with every Godot release, so follow the "Exporting for Android" page of the official documentation for the version you have rather than a number printed here. The export dialog tells you in red what is still missing.

APK and AAB

APKAAB (Android App Bundle)
What it isAn app a phone can install as it isEverything needed to make APKs, in a publishing format
Who opens itA phone: copied over a cable, or downloaded from a page such as itch.ioGoogle Play, which builds a fitted APK for each kind of device
Use it forTrying a build on your own phone; shops outside PlayUploading to the Play Console, which asks for bundles from new apps

So most Android projects end up with two presets that differ in one option, the export format: an APK to try and a bundle to publish. At the time of writing, exporting a bundle needs Godot's Gradle build turned on in the preset, which in turn needs an Android build template installed into the project (the editor offers to do it and adds an android/ folder). Like the export templates, that folder belongs to one engine version and is remade when you update.

The keystore and signing

Android will not install an app unless it is signed: stamped with a private key that proves every update comes from whoever made the first version. The key lives in a file called a keystore, protected by a password.

  • A debug keystore is a throwaway that every developer has. It is enough for a debug build on your own phone.
  • A release keystore is yours alone. You make it once, with the keytool program that comes with Java, and you use it for every release for as long as the app lives.

The two rules of a release keystore

Do not lose it, and do not publish it. Keep the file and its password outside the project folder or in a folder version control ignores, with a backup somewhere safe. Depending on the engine version, Godot keeps signing details either in the preset or in a separate credentials file inside .godot/, and it can also take them from environment variables so they never touch a file at all. Before you commit export_presets.cfg to a public repository, open it and read it.

With Play's app signing, which new apps use, Google holds the final signing key and the key in your keystore becomes an upload key: proof that an upload is from you. That softens the first rule a little – a lost upload key can be replaced through Play's support – but treat it as though it could not be.

What Android does with the version code

The phone and the store both look at the code, and each refuses in its own way:

extends Node

var on_phone := 38                 # the code of the build installed now
var store_has_seen := [36, 37, 38] # every code ever uploaded

func phone_installs(code: int) -> bool:
	return code >= on_phone        # Android will not put an older build over a newer one

func store_accepts(code: int) -> bool:
	return not store_has_seen.has(code) and code > store_has_seen.max()

func _ready() -> void:
	for code in [37, 38, 39]:
		print(code, ": phone ", phone_installs(code), ", store ", store_accepts(code))

Only 39 gets past both. This is also why two presets for one app must carry the same code: if the bundle has gone to 39 while the APK preset still says 37, the phone that has the store's build refuses your test build, and the only way round is to uninstall – which deletes the save file with it.

The Play Console's tracks

A track is a group of people who receive a build. You do not upload "to the store"; you upload to a track, and promote a build from one to the next when you trust it.

TrackWho gets the buildUse it for
Internal testingA short list of people you name"Does it start on a real phone?"
Closed testingTesters you invite by email or by groupReal play, real feedback, before strangers see it
Open testingAnyone who opts in from the store pageA public beta
ProductionEverybodyThe release

On most tracks Google reviews a build before people receive it, which can take from hours to days, and its rules about who must test what before production change from year to year. Read what the Console asks of your account today. The tools around the Console use older names for two of the tracks: closed testing is alpha and open testing is beta.

  1. Once

    Install the Java kit and the Android SDK, make a release keystore, create the app in the Play Console with its package name (the reversed-domain id, like com.example.mygame, that can never be changed afterwards).

  2. Each release: raise the code

    Version code up by one in every Android preset; version name up if players should notice.

  3. Export a signed release bundle

    A release build, not a debug one, in AAB format, signed with the release keystore.

  4. Upload to a testing track

    With a line or two of release notes. Wait for review.

  5. Play it from the store

    Install the build the way a tester will, on a real phone, and play for ten minutes. Then promote it.

Desktop, web and iOS

The other platforms follow the same pattern – template, preset, export – with one thing each that catches people out.

Desktop

A Windows or Linux export is a program file with the .pck beside it (or folded into it, with the preset's option to embed the pack). A macOS export is an .app, usually delivered in a .zip or a .dmg. You can make all three from one computer.

The catch is trust. Windows and macOS both warn people away from programs that are not signed by a known developer, and macOS also wants apps notarised – checked by Apple – before it opens them without complaint. Signing costs money and takes setting up. For a first game shared with friends or on itch.io, an unsigned build with a sentence telling players how to open it is normal; for a commercial release, budget the time.

Web

A web export is your game as a web page: an .html file, a .wasm file that is the engine compiled for browsers, a .js file to start it, and the .pck. Name the page index.html and a host will serve it from the folder's address. Four things to know:

  • It must be served, not opened. Double-clicking the .html does nothing useful, because browsers do not let a page from your disk load the other files. It has to come from a web server – the editor starts a small one when you run the web preset from the toolbar.
  • Threads change where you can host it. A web build can be exported with or without thread support. With threads the browser demands that the page be cross-origin isolated, which means the server must send two particular headers with it; many simple hosts do not let you set headers. Without threads the build runs anywhere a static page does. Recent versions of Godot 4 export without threads unless you ask, which is the right default for a small 2D game.
  • It uses the Compatibility renderer, the one Chapter A suggested for 2D, and native extensions (Chapter Y) need extra care or do not work at all.
  • Browsers add rules of their own. No sound until the player has clicked or tapped once. user:// is kept in the browser's storage, which the player can clear. The first load is a download of several megabytes, so show something while it happens.

iOS, briefly

Shipping to an iPhone needs three things Godot cannot supply: a Mac, Xcode, and a paid Apple developer membership. Godot's iOS export produces an Xcode project; Xcode builds it, signs it and uploads it. Testers get it through TestFlight, and Apple reviews it before the App Store shows it. The version name and build number play the same parts as on Android, including the rule that the build number rises.

PlatformWhat comes outThe thing to watch

Getting it to players

A build nobody can reach is not shipped. The shortest road to a real player is a page on itch.io; the longest is a store. Both end the same way: a checklist you did not skip.

itch.io

itch.io is a shop and host for independent games with no review queue and no fee to start. You make a project page, upload one .zip per platform, tick which platform each is for, and it is live.

  • For a web build, zip the exported files with index.html at the top level and mark the upload as played in the browser. The page's settings include a switch for the cross-origin isolation that threaded builds need.
  • For desktop, zip each platform's export separately. For Android, the .apk itself.
  • itch.io has a command-line uploader, butler, which sends only what changed between builds. Once you release more than twice it is worth the ten minutes.

A web build on itch.io is the best way to get a first game played: one link, nothing to install, and it works on a phone.

A release is a checklist

Every release goes wrong in the same few places, so write the places down and have code read the list. A checklist is data (Chapter V): each line is a thing that must be true and whether it is.

extends Node

var checklist := [
	{"what": "tests pass", "done": true},
	{"what": "version code raised", "done": true},
	{"what": "played the release build", "done": false},
	{"what": "release notes written", "done": false},
]

func missing() -> Array:
	var out := []
	for item in checklist:
		if not item["done"]:
			out.append(item["what"])
	return out

func _ready() -> void:
	var left := missing()
	if left.is_empty():
		print("Ready to ship.")
	else:
		print("Not yet – ", left.size(), " to do:")
		for what in left:
			print("  [ ] ", what)

Set both falses to true and the message changes. Add a fifth line of your own – "icon is not the Godot robot" is a popular one – and notice that missing() did not have to change. The next step, which the tutorial takes, is to make the list able to refuse.

After it is out

Shipping is the start of hearing from players. Keep every build you release, named by its version, so you can run exactly what a bug report is about. Write one line per release saying what changed. And expect the first report within a day to be about something that never happened on your machine: a screen shape you did not try, a file the export left out, a back button you did not know phones had.

Build it live

Stores refuse bad releases after you have waited for an upload. A release gate refuses them first, in a second. You will write one: it understands version names, knows what was shipped last, reads a checklist, and says no with reasons.

In Little Hours

Little Hours ships to Android testers through Google Play's closed testing track, with one command. Everything that command does was added after something went wrong without it.

What the project file settles before any export

An export obeys project.godot, so the first shipping decisions are there. This is the display section:

../project.godot · lines 64–78

[display]

window/size/viewport_width=768
window/size/viewport_height=1344
window/stretch/mode="canvas_items"
window/stretch/scale_mode="integer"
; "keep" letterboxes rather than crops, and that is now the right choice
; because the base size is no longer fixed at 768x1344: Main._fit_view_to_phone
; derives the view from the surface it has to fill, so the view already carries
; the screen's aspect ratio and "keep" produces no bars at all. This was briefly
; "expand", which filled the phone but CROPPED any window smaller than the
; authored size — shrink the window and the edges of the game were cut off.
; With an adaptive view, "keep" fills the same screen and clips nothing.
window/stretch/aspect="keep"
window/handheld/orientation="portrait"

A portrait design size of 768 by 1344, stretched as canvas_items at whole-number scales only – the pixel-art settings of Chapter P – and keep for the aspect. The comment is the history of a shipping bug: expand looked right on the one phone it was tried on and cropped every smaller window. A setting like this cannot be judged in the editor; it has to be seen on the devices it will run on. How the game then fits itself to each screen is in Orientation and the camera.

Two more lines exist only because the game left the editor. The first is about a phone's back gesture:

../project.godot · lines 29–41

; The back gesture does NOT quit the app.
;
; Godot defaults this to true, and on a phone that is brutal: the back gesture
; is a swipe in from the left or right edge, this game is played sideways in
; immersive mode with the whole screen tappable, and the edges are exactly where
; a thumb rests. One stray swipe and the app is simply gone, instantly, with no
; dialogue and no crash — which is what "app crashed frequently" looks like from
; the outside, and why Android vitals has recorded no crash at all on any build
; since version code 3.
;
; Main._notification() takes the notification instead: back closes whatever card
; is open, and closes the game only after asking.
config/quit_on_go_back=false

Godot's default closes the app on "back". On a desk nobody notices; on a phone held sideways it meant the game vanished whenever a thumb brushed the edge, which players reported as crashes that no crash report ever showed. With the setting off, Main.gd receives the request as a notification and closes whatever card is open instead (Main). The second is about the save folder:

../project.godot · lines 17–24

config/name="Little Hours"
; The game was called Tiny Home until October 2026 (then Topia, for a day). On a desktop, Godot names
; the save folder after the game, so renaming it would have left the Mac's
; saves, logs and the 1.1 GB talking model behind in the old folder. This keeps
; the old folder. Phones ignore it: Android and iOS keep user:// in the app's
; own storage, which follows the package/bundle id and not the name.
config/use_custom_user_dir=true
config/custom_user_dir_name="Godot/app_userdata/Tiny Home"

On a desktop, Godot names the user:// folder after the project, so renaming a released game would strand every save in a folder under the old name. A custom user directory pins it. Phones keep user:// under the app's package id, which never changes, so they are untouched. If you ever rename a game after people have played it, this is the setting to reach for; the save file itself is the subject of Saving.

One thing the project file does not have is a version. Little Hours does not set the project-wide version setting at all: its version name and code live in the Android presets, and a script keeps them in step.

One command: tools-release.sh

A release is ./tools-release.sh "what changed", a shell script at the top of the repository. It is the tutorial's gate with a real export in the middle, and the order of its steps is the lesson:

  1. Fail early

    Before anything slow, it checks that the credential it will need for the upload exists, and fetches the small-talk plugin's libraries if they are not installed. Finding the first missing after four minutes of tests would mean doing it all again; a bundle built without the second would be a release with no small talk in it, which nobody meant.

  2. Presets must agree

    It reads the version code out of every Android preset and stops if they differ.

  3. Run the test suite

    First the game is asked to remake the map editor's picture of its rooms (Chapter Y). Then the whole suite of Chapter W runs against the real game. A failure stops the release; no version number has been touched yet.

  4. Raise the version code

    By one, in every preset, and set the version name if one was given. Only after the tests pass, so a failed run leaves no gap in the numbers.

  5. Export

    Godot, headless, exports the "Android" preset as a release bundle.

  6. Check the thing that was built

    It verifies the bundle is signed, then opens the bundle and reads its manifest back to confirm a setting made it in.

  7. Upload

    It hands the bundle to tools-publish.py, which sends it to a testing track with the release notes.

The second step, as written:

../../tools-release.sh · lines 59–68

# The two Android presets must agree before we start. If they have drifted, the
# APK on your phone is not the build that shipped, which is the whole point of
# having both.
DISTINCT=$(grep -E '^version/code=' "$CFG" | sort -u | wc -l | tr -d ' ')
if [ "$DISTINCT" != "1" ]; then
  echo "  The export presets disagree about the version code:"
  grep -nE '^version/(code|name)=' "$CFG" | sed 's/^/    /'
  echo "  They are bumped together now, so this is old drift — set them equal and re-run."
  exit 1
fi

This is shell rather than GDScript, but it reads the same: collect every version/code= line, count the distinct values, refuse unless there is exactly one. The comment gives the reason in a sentence – the APK on your phone should be the build that shipped. Exercise X.4 has you write the same check.

And the export itself is one line of the command-line Godot that Chapter Y explains:

../../tools-release.sh · lines 127–129

"$GODOT" --headless --path godot --export-release "Android" \
  "$PWD/build/TinyHome.aab" 2>&1 | grep -iE "^ERROR|error:" || true
[ -f build/TinyHome.aab ] || { echo "  export produced no bundle"; exit 1; }

--headless runs the editor without a window, --path names the project, and --export-release takes a preset's name and where to write the result. The line after it does not trust the export to have worked: it looks for the file.

That distrust is the script's best habit. One release reached Google with Android's backup of the save file switched off, although the preset plainly had it on: a comment line beginning with # rather than ; had made the exporter drop the setting. The preset was right and the file that shipped was wrong. So the script now refuses to run if the preset file contains a # comment, and after exporting it reads the value back out of the bundle with a small Python tool, because, as its comment says, "the answer comes from the artefact".

The uploader, tools-publish.py, talks to the Play Console's publishing service directly, so no browser is involved. It opens a draft change, uploads the bundle in pieces and carries on from where it stopped if the connection drops, attaches the build and its notes to a track – closed testing unless told otherwise – and commits. Its own description of the rule that matters:

../../tools-publish.py · lines 14–16

The edit is committed only if every step succeeds. A failure part-way leaves the
edit uncommitted and Play discards it, so a half-finished upload cannot become a
half-finished release.

All or nothing: the same rule your release() follows when it leaves shipped alone on a refusal.

Two real releases

The project's notes record how this went in practice. Release 2.8.15, version code 38, stopped on the first try: Godot had been updated to 4.7.2 and the export templates were still 4.7.1. With matching templates installed and the Android build folder remade, the script ran through and the bundle went to closed testing. The iOS half of that release was an Xcode project exported by Godot and archived, with the upload left to be done by hand in Xcode.

Release 2.9.0, version code 39, went through at the first attempt: the suite passed, a bundle of about 60 MB was signed and verified, the backup setting was read back as on, and Google's review began. Nothing about the second release was remembered by a person. That is what the script is for.

Your turn

Five pieces of release machinery, from a label to a checklist that knows what depends on what.

What to remember

  • An export is the engine for one platform plus a pack of your project. Templates supply the engine and must match the editor's version; presets in export_presets.cfg say how to join them.
  • Files Godot does not treat as resources are left out of the pack unless a preset's filter names them. Test the exported build, and the release flavour of it, not the editor.
  • The version name is text for people; the version code is a number for stores and must rise with every upload. Compare versions as numbers, never as text.
  • Android: an APK installs on a phone, an AAB goes to Google Play; both are signed with a keystore you must neither lose nor publish; builds reach people through tracks, testing first.
  • A web export has to be served and is simplest to host without threads; desktop builds want signing; iOS needs a Mac and Xcode; itch.io is the quickest way to hand anyone a link.
  • Make the release a script and a checklist. Check the file that was built, not the settings that were meant to build it.
