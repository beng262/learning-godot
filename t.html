Time and timers

The Timer node, create_timer, await, a day-night clock, and why counting frames is a bug.

In this chapter

  • why a wait is a number of seconds added up from delta, and never a number of frames
  • cooldowns, and things that happen every so often
  • the Timer node, and the timer you make in one line with create_timer and await
  • three clocks – real time, game time and a paused game – and which to use for what
  • a day and night clock, and how Little Hours times its texts, its visitors and its crops

Seconds, not frames

A game has no clock of its own. It has frames, and a frame is not a length of time. Everything in this chapter rests on one habit: add up delta.

_process(delta) runs once for every frame the game draws (Chapter I), and delta is how many seconds went by since the last one. On a 60 Hz monitor that is about 0.0167. On a 120 Hz phone it is half that. On a laptop having a bad moment it is whatever it is. Here is one second on three machines, with two ways of measuring it:

extends Node

var frames := 0        # one way: count the frames
var elapsed := 0.0     # the other: add up the seconds

func _process(delta: float) -> void:
	frames += 1
	elapsed += delta

# The page has no screen to refresh, so this plays the frames for us.
func play(seconds: float, fps: int) -> void:
	frames = 0
	elapsed = 0.0
	for i in int(seconds * fps):
		_process(1.0 / fps)
	print("%3d fps: %3d frames counted, %.2f seconds added up" % [fps, frames, elapsed])

func _ready() -> void:
	play(1.0, 30)
	play(1.0, 60)
	play(1.0, 120)

The frame counter gives three different answers to "how long was that?" and the sum of delta gives one. A door that opens if frames == 60 opens after two seconds on the first machine and after half a second on the third. A whole game written that way runs at double speed on a newer screen, and it is a bug you cannot see on your own computer, because yours is the one it was tuned on. Change one of the calls to play(1.0, 144) and look at the two columns again.

So: a wait is a number of seconds, kept in a float, and moved by delta.

Every so often

The first thing to build from that is an event that repeats. Keep a float, add delta to it every frame, and when it reaches the gap, do the thing and start again. This variable is often called an accumulator:

extends Node

const GAP := 2.0       # seconds between gulls
var wait := 0.0
var clock := 0.0       # only here so we can print when things happen
var gulls := 0

func _process(delta: float) -> void:
	clock += delta
	wait += delta
	if wait >= GAP:
		wait -= GAP        # start again, keeping what was left over
		gulls += 1
		print("%5.2f s: a gull flies past" % clock)

func _ready() -> void:
	for i in 16:           # twelve seconds of rather slow frames
		_process(0.75)
	print(gulls, " gulls in ", clock, " seconds")

Six gulls in twelve seconds, which is one every two. Look at the times, though: they are not 2, 4, 6. A frame never ends exactly on the gap, so the event fires a little late – and wait -= GAP carries that lateness into the next count, which then fires a little early. Change that line to wait = 0.0 and run it again: five gulls. Throwing the leftover away makes every gap slightly too long, and the error adds up for as long as the game runs.

Cooldowns and ready-at times

There are two ways to say "not yet". Count down what is left, or write down when it will be ready. They suit different jobs.

A cooldown is a wait that starts when the player does something and stops them doing it again until it has run out. Counted down, it is a float that falls to zero and stays there:

extends Node

const COOLDOWN := 1.5
var cooling := 0.0          # seconds until the can is full again

func _process(delta: float) -> void:
	cooling = maxf(0.0, cooling - delta)

func water() -> void:
	if cooling > 0.0:
		print("  not yet: %.2f s to go" % cooling)
		return
	cooling = COOLDOWN
	print("splash")

func _ready() -> void:
	water()
	water()                 # straight away: too soon
	for i in 4:
		_process(0.25)      # one second goes by
	water()
	for i in 2:
		_process(0.25)      # and half a second more
	water()

maxf(0.0, …) is the part people leave out. Without it the number sinks below zero and keeps going, and a bar drawn from cooling / COOLDOWN grows backwards across the screen. The number is also exactly what such a bar needs: 1.5 just after use, 0 when ready. Set COOLDOWN to 0.5 and the third water() succeeds.

Write down when

The other way keeps no countdown at all. When the thing starts, note the time at which it will be done, on some clock that keeps running; to ask whether it is done, compare.

extends Node

var clock := 0.0            # seconds since the day began
var ready_at := {}          # plot -> the clock time at which it ripens

func plant(plot: String, grow: float) -> void:
	ready_at[plot] = clock + grow

func is_ripe(plot: String) -> bool:
	return clock >= ready_at[plot]

func _ready() -> void:
	plant("carrot", 15.0)
	plant("pumpkin", 40.0)
	clock = 20.0
	print("at 20 s: carrot ", is_ripe("carrot"), ", pumpkin ", is_ripe("pumpkin"))
	clock = 45.0
	print("at 45 s: carrot ", is_ripe("carrot"), ", pumpkin ", is_ripe("pumpkin"))

Nothing runs each frame for a plot. A hundred plots cost a hundred numbers, not a hundred countdowns, and a number like that goes into a save file as it is (Chapter S). Plant a third crop at clock = 20.0 and check it at 45.

The price is that a time written down is only as good as the clock it was read from. If that clock is ever set back – a new day begins, the game is reopened – every note made before then is a time in a future that will not come. Little Hours met exactly this with its crops, and the fix is quoted further down.

When one frame is very long

Frames are not always short. A hitch while something loads, or a window dragged across the screen, can hand you a delta of a second or more. An if wait >= GAP then fires once and leaves the rest waiting. For something that must happen the right number of times – a coin every two seconds – use while in place of if, so a long frame pays for every gap it covered. For something that only needs to feel regular – a gull – once is right, and nobody wants four gulls in one frame. Exercise 4 is the first kind.

The Timer node

Godot has the accumulator built already, as a node. You tell it how long, and it tells you when: its timeout signal is the "do the thing".

On a TimerWhat it is
wait_timeThe gap, in seconds. 1.0 unless you change it.
one_shotfalse: fire, then count again, for ever. true: fire once and stop.
autostartStart counting as soon as the node joins the tree. Otherwise it waits for start().
start(), stop()Begin the count from the top; abandon it without firing.
is_stopped()Whether it is doing nothing at the moment.
time_leftSeconds still to go – the number a cooldown bar wants.
timeoutThe signal it emits each time the count reaches zero.

In the editor it is a node like any other: select the node that needs it, Add Child Node, choose Timer, set Wait Time, One Shot and Autostart in the Inspector, and connect timeout from the Node dock (Chapter J). The same thing in code:

extends Node2D

var gulls := 0

func _ready() -> void:
	var timer := Timer.new()
	timer.wait_time = 2.0                    # <1>
	timer.autostart = true                   # <2>
	timer.timeout.connect(_on_gull_timer)    # <3>
	add_child(timer)                         # <4>

func _on_gull_timer() -> void:
	gulls += 1
  1. Two seconds between gulls. one_shot is left at false, so it repeats.
  2. Set before the timer is added, so it starts the moment it is in the tree.
  3. timeout is an ordinary signal: connect any function to it.
  4. A Timer only counts while it is in the tree. Because it is a child of this node, it is freed with it – there is nothing to tidy up, and it cannot fire into a scene that has gone.

There is no mystery inside one. The interpreter in this page has no Timer, so here is the whole idea written out as a small class, with the engine's part – calling it every frame – done by hand:

extends Node

class MiniTimer:
	signal timeout
	var wait_time := 1.0
	var one_shot := false
	var time_left := 0.0

	func start() -> void:
		time_left = wait_time

	func is_stopped() -> bool:
		return time_left <= 0.0

	func tick(delta: float) -> void:
		if is_stopped():
			return
		time_left -= delta
		if time_left <= 0.0:
			if one_shot:
				time_left = 0.0
			else:
				time_left += wait_time     # keep the leftover, count again
			timeout.emit()

var kettle := MiniTimer.new()

func _ready() -> void:
	kettle.wait_time = 1.5
	kettle.one_shot = true
	kettle.timeout.connect(func(): print("the kettle whistles"))
	kettle.start()
	for i in 12:                  # three seconds, a quarter at a time
		kettle.tick(0.25)
	print("stopped: ", kettle.is_stopped())

It is the gull example with a signal where the print was. Set one_shot to false and it whistles twice in the three seconds and is still running at the end. Then move kettle.start() to after the loop: a timer that was never started never fires, which in a real project is the commonest reason for "my timer does nothing" – neither autostart nor start().

Starting again is a feature

Calling start() on a timer that is already counting puts it back to the top. That turns a one-shot timer into a way of saying "once this has stopped changing":

func _on_slider_value_changed(_value: float) -> void:
	_save_timer.start()       # every change pushes the moment back

func _on_save_timer_timeout() -> void:
	save_settings()           # runs once, a moment after the last change

Little Hours uses exactly this in its character maker. Dragging across a colour wheel reports a new colour many times a second, and each one would be written to the save file. A one-shot timer of 0.12 seconds is restarted on every change, so the colour is stored once, when the finger pauses.

A repeating Timer, made in code, on the settings card that shows a download's progress (Overlays.gd):

Four times a second it asks how far the download has got and rewrites one label. The comment gives the reason it is a timer and not a signal connection: the timer is a child of the card, so "it goes when the card goes". Where a timer lives decides when it stops, and that is often the whole reason to choose a node.

A timer in one line, and await

For a wait you need once, in the middle of doing something else, adding a node is a lot of ceremony. The scene tree will make you a throwaway timer, and await will wait for it right where you are.

extends Node

func _ready() -> void:
	print("The kettle goes on.")
	await get_tree().create_timer(3.0).timeout
	print("Three seconds later, it whistles.")
	await get_tree().create_timer(1.0).timeout
	print("One more, and there is tea.")

Read the second line of _ready() from the inside out. get_tree() is the scene tree every node belongs to. create_timer(3.0) asks it for a one-shot timer of three seconds, which is not a node, starts at once and removes itself when it has fired. .timeout is that timer's signal. And await (Chapter J) stops this function at this line until the signal arrives.

One thing is different in this page: you did not wait four seconds. When the interpreter has run everything that can run, it moves its clock straight to the next timer due, and then the next. The order things happen in is exactly what Godot would give you. Only the waiting is skipped.

What await does not do

It does not stop the game. It sets this one function aside and hands control back to whoever called it, and everything else carries on:

extends Node

func boil(what: String, seconds: float) -> void:
	print(what, " goes on")
	await get_tree().create_timer(seconds).timeout
	print(what, " is done, after ", seconds, " s")

func _ready() -> void:
	boil("the egg", 4.0)
	boil("the kettle", 3.0)
	boil("the toast", 1.5)
	print("_ready() has finished, and nothing is cooked")

Three calls, and each returns the moment it reaches its await, so all three "go on" lines print first and _ready() finishes before anything is done. Then they complete in order of time, not in the order they were called. A function with an await in it is called a coroutine: it can be part-way through while the rest of the game runs. Put await in front of the first call – await boil("the egg", 4.0) – and _ready() itself waits for the egg before it starts the kettle.

That makes a sequence easy to write top to bottom, which is what await is best at:

extends Node

func _ready() -> void:
	for n in [3, 2, 1]:
		print(n, "…")
		await get_tree().create_timer(1.0).timeout
	print("Go!")

Three ways it goes wrong

The world moved on while you waited. The line after an await runs later – seconds later – and whatever was true before it may not be. The player has left the room, the card has closed, the dog has been freed. Check again after every wait, and use is_instance_valid(node) before touching a node that might have gone.

It was started twice. Nothing stops a coroutine being called again while an earlier call is still waiting. Then there are two, and both finish. If that must not happen, keep a flag that says "already running" and return early. Exercise 6 is this.

It cannot be called off. The timer from create_timer has no stop(). For a wait you may need to cancel or restart, use a Timer node.

The same question is asked twice, once before the wait and once after it. In those 1.1 seconds a test, or a loaded save, may already have created the character – and a form asking again would be wrong. That second if is the first rule above, in five words of code.

Three clocks: real, game and paused

"How much time has passed?" has more than one answer in a game, and choosing the wrong one is how a cooldown keeps running behind a pause menu.

The real clock

Time.get_ticks_msec() is the number of milliseconds since the game started, as an int. It does not care about frames, pauses or anything your game does. Take one reading, take another later, subtract:

var _opened_at := 0

func open() -> void:
	visible = true
	_opened_at = Time.get_ticks_msec()

func _on_background_pressed() -> void:
	# A press in the first quarter of a second is the one that opened us.
	if Time.get_ticks_msec() - _opened_at >= 250:
		close()

Use it for things that are about the person and the device, not the world of the game: ignoring a press that comes too soon, measuring how long a piece of code took, giving up on something that has not answered. It is the wrong clock for a crop, because it runs while the game is paused and cannot be slowed down. (For the date and time on the wall there is Time.get_unix_time_from_system(), which is what a game needs to know how long it has been closed.)

In Little Hours

## A press that lands within this of the handset appearing is the same press
## that opened it, arriving a second time.
##
## Android delivers one tap twice — once as InputEventScreenTouch and again
## as an emulated InputEventMouseButton — so the copy arrives after the

The phone notes Time.get_ticks_msec() when it appears, and a tap beside it only closes it once ARM_MS has gone by. A quarter of a second of real time is the right measure here: the problem is two copies of one finger press, and no game clock knows anything about fingers.

The paused game

get_tree().paused = true stops the game: nodes no longer get _process or _physics_process, so every accumulator and cooldown in them stands still. Which nodes obey is set per node, by Process › Mode in the Inspector (process_mode in code). A pause menu has to be set to keep running, or it could never be un-paused:

# On the pause menu's own root node:
func _ready() -> void:
	process_mode = Node.PROCESS_MODE_WHEN_PAUSED

func _on_resume_pressed() -> void:
	get_tree().paused = false

The timers in this chapter do not all agree about pausing, and the odd one out is the convenient one:

Way of waitingWhile the tree is paused
Adding up delta in _processStops, with the node.
A Timer nodeStops, unless its process mode says otherwise.
get_tree().create_timer(2.0)Keeps counting.
get_tree().create_timer(2.0, false)Stops.
Time.get_ticks_msec()Keeps counting.

The second argument of create_timer is "process always", and it is true unless you say so. An await get_tree().create_timer(2.0).timeout in the middle of a boss's attack will finish behind your pause menu. If your game can pause, pass false for every wait that belongs to the world.

Not every game pauses the tree. Little Hours never does. Its clock stands still at night until you sleep, and its visitors do not call while a card is open – each because the function that would have counted returns early. A pause can be that small.

The game's own clock

The third clock is the one you make: a variable that holds the time in the game's world. You move it with delta, so you can also move it faster, slower or not at all. That is all a day and night cycle is:

extends Node

const DAY_LENGTH := 240.0     # real seconds for one day and night

var clock_t := 60.0           # seconds into the day: start at six in the morning
var speed := 1.0              # game seconds for each real second
var paused := false

func _process(delta: float) -> void:
	if paused:
		return
	clock_t = fmod(clock_t + delta * speed, DAY_LENGTH)

func hour() -> float:
	return clock_t / DAY_LENGTH * 24.0

func clock_text() -> String:
	var mins := int(hour() * 60.0)
	return "%02d:%02d" % [mins / 60, mins % 60]

func is_night() -> bool:
	return hour() < 6.0 or hour() >= 20.0

# Plays some real seconds, then says what the game's clock reads.
func play(seconds: float) -> void:
	for i in int(seconds * 4.0):
		_process(0.25)
	print(clock_text(), "  night" if is_night() else "  day")

func _ready() -> void:
	play(0.0)
	play(60.0)        # a real minute goes by
	speed = 4.0
	play(25.0)        # 25 seconds at four times the speed
	paused = true
	play(60.0)        # a minute of pause: nothing moves

Three ideas in the one line of _process. delta * speed is game time: with speed at 4 the day goes four times as fast, and nothing else in the game has to know. fmod is the remainder for floats, so the clock comes round to 0 at the end of the day instead of running on to hour 25. And the paused guard is a pause that touches only the clock. The hour, the text and the night are not stored anywhere – they are worked out from clock_t whenever somebody asks, so they cannot disagree with it. Try speed = 0.5, and try a DAY_LENGTH of 24.0, which makes every real second an hour.

Little Hours's clock is this one with two changes: its day does not come round by itself but stops at nightfall and waits for you to go to bed, and it shows only the hours from 06:00 to 22:00. That clock, its four phases and the colour of its sky are built step by step under Clock in Little Hours from A to Z, so this chapter will not build it again. What follows uses the same ideas for something else.

Build it live

A lighthouse. Its sun goes round on a game clock, its lamp flashes on a beat, its horn has a cooldown and an echo, and at the end you can wind the day forward without the lamp or the horn noticing.

In Little Hours

There is not one Timer node in the game's rules. A float counted in _process, and things compared with it, do nearly everything.

The float is clock_t, seconds into today, and it lives in Game.gd beside const DAY_LENGTH := 480.0 – a day is eight minutes of play. This is everything that happens to it in a frame:

Game.gd · lines 440–448

func _process(delta: float) -> void:
	if night_held:
		return
	clock_t += delta * mode_day_scale()
	if clock_t >= DAY_LENGTH:
		clock_t = DAY_LENGTH
		night_held = true
	_tick_farm()
	_tick_texts(delta)

delta * mode_day_scale() is game time, as in the last step of the tutorial. The scale is 0.8 if you chose a cosy game, 1.15 for a hustling one and 1.0 otherwise, so the same day is ten minutes long for one player and seven for another, and nothing that reads the clock needs to know. The first two lines are the game's only pause: once night has fallen the function returns before it counts anything, and stays that way until you sleep. How the clock becomes an hour, a phase and a sky is under Clock; what going to bed does to it, under sleeping and the new day. The last two lines are the two things that wait on it.

Crops ripen by the clock

Game.gd · lines 450–473

## A watered crop ripens on its own after its grow time, so the farm rewards you
## for coming back later in the same day — you don't have to sleep to see it.
## Only writes to disk on the frame a plot actually flips, never every frame.
func _tick_farm() -> void:
	var changed := false
	for plot in (state["farm"] as Array):
		if plot["state"] != "planted" or not plot["watered"] or plot["ready"]:
			continue
		var crop := str(plot["crop"])
		if not CROPS.has(crop):
			continue
		var grow := float((CROPS[crop] as Dictionary)["grow"])
		# The clock starts again every morning and whenever the game is opened,
		# and it is not saved: a time from before that is later than now, and
		# a crop planted in the evening would wait all of the next day for the
		# clock to catch up. It has been in the ground since before today.
		if float(plot["planted_at"]) > clock_t:
			plot["planted_at"] = 0.0
		if clock_t - float(plot["planted_at"]) >= grow:
			plot["ready"] = true
			changed = true
	if changed:
		farm_updated.emit()
		save_now()

This is "write down when". A plot remembers planted_at, the clock's reading when the seed went in, and is ripe once clock_t - planted_at reaches the crop's grow time – 15 seconds for a carrot, 40 for a pumpkin. No plot counts anything down. The comment in the middle is the price of that pattern, paid: clock_t starts again every morning and is not saved, so a time noted yesterday evening is later than any time this morning, and the crop "would wait all of the next day for the clock to catch up". A note from the future is treated as zero. And see the last three lines: the function runs every frame but writes the save only on the frame a plot changes. More in Farming.

Texts arrive on a schedule

Game.gd · lines 2036–2051

## Maybe deliver a text. Called on the clock; most ticks do nothing.
func _tick_texts(_delta: float) -> void:
	if not bool(state.get("created", false)):
		return
	var ph := phone()
	if int(ph.get("text_day", 0)) != int(state["day"]):
		ph["text_day"] = int(state["day"])
		ph["texts"] = 0
		# The first one of the day is never in the first minute: a text landing
		# as the morning starts reads as a notification rather than a person.
		ph["next_text"] = TEXT_GAP
	if int(ph.get("texts", 0)) >= TEXTS_A_DAY:
		return
	if clock_t < float(ph.get("next_text", TEXT_GAP)):
		return
	ph["next_text"] = clock_t + TEXT_GAP

The same pattern with a limit on top. next_text is the clock time at which the next message may arrive; when the clock passes it, one is sent and the note moves on by TEXT_GAP, 95 seconds. Two more rules are stacked in front as early returns: on a new day the count goes back to zero and the first text is pushed 95 seconds into the morning ("a text landing as the morning starts reads as a notification rather than a person"), and after TEXTS_A_DAY – two – nothing more is sent. The function takes _delta and never uses it; the underscore says so. It does not need to know how long the frame was, only what time it is. The phone's rules are under Phone.

Visitors come every so often

The small unprompted moments – the doorbell, the dog racing about, the cat bringing a present – are a countdown, the first pattern of this chapter. It lives in Main.gd, which declares var _event_t := 25.0 and then:

Main.gd · lines 2683–2689

func _tick_events(delta: float) -> void:
	if _overlays.is_open or _hud.drawer_open() or _editing or _talking():
		return
	_event_t -= delta
	if _event_t > 0.0:
		return
	_event_t = Game.mode_event_gap() + randf() * 45.0

Three things to notice. It counts down and is refilled when it runs out, so the gap can be different every time: mode_event_gap() is 16 seconds in a story game, 34 in a hustling one and 25 otherwise, and up to 45 random seconds are added so that nobody can feel the beat. It uses plain delta, not the scaled one – a visitor is paced for the person playing, not for the hour in the game. And its first line is a pause: while a card is open, the drawer is out, you are decorating or someone is talking, it returns before counting, because "an event firing behind an open overlay would spend its toast on nobody". What the visits are is under Evenings and events.

Your turn

Six exercises. Where a test needs time to pass it plays the frames itself, so you can see exactly which deltas your code was given.

What to remember

  • Time is seconds added up from delta. Counting frames makes the game's speed depend on the screen it is played on.
  • For "every so often", add delta to a float and subtract the gap when it is reached – subtract, so the leftover is kept. For "not yet", count a cooldown down to zero, or write down the time it will be ready and compare.
  • A Timer node is that accumulator with a timeout signal: wait_time, one_shot, autostart, start() and stop(). It stops when its node does.
  • await get_tree().create_timer(s).timeout waits in the middle of a function without stopping the game. Check the world again after it, and guard against starting twice.
  • There are three clocks: real time (Time.get_ticks_msec()), the frame's delta, and a game clock of your own that you can scale and stop. create_timer runs through a pause unless you pass false.
  • A day and night clock is one float that comes round, with the hour, the text and the darkness worked out from it when asked.
