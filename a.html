In this chapter

What an engine is for

A game is a loop. Sixty times a second it reads the controls, moves things, works out what bumped into what, and draws a picture. An engine is everything in that loop you would rather not write yourself.

Drawing thousands of sprites quickly, loading a PNG, playing a sound without a click at the start, telling a tap from a drag on a phone, packaging the whole thing for Android – none of that is your game, and all of it has to work before your game can. Godot does those jobs. What it leaves to you is the part that makes your game yours: what is on the screen, how it behaves, and what happens when somebody presses a button.

Godot is free and open source under the MIT licence: no fee, no royalty, no account, and what you make is entirely yours. It is a single program of around a hundred megabytes that contains the editor, the engine and the language. It is genuinely good at 2D – 2D is not a flattened 3D scene in Godot, it has its own renderer and its own units, which is one reason pixel-art games like it.

Which Godot this book is about

Godot 4 – specifically 4.7, which Little Hours is made with. Godot 3 is different enough that its tutorials will mislead you: KinematicBody2D became CharacterBody2D, yield became await, and signals connect differently. If an answer online uses yield or connect("signal", self, "method"), it is about Godot 3.

The four ideas

Everything in Godot is made of four ideas, and once they are how you picture a game, the engine gets much easier.

1. Nodes

A node is a small object that does one job. Sprite2D draws a picture. Camera2D decides what part of the world you see. Timer counts down. Label shows text. AudioStreamPlayer plays a sound. Godot has a few hundred kinds and you will use perhaps thirty.

You do not build one big object that can do everything. A character is not a class with a picture field and a sound field – it is a node with a picture node and a sound node underneath it, each doing its one job. That is composition, and Godot is designed around it.

2. The tree

Nodes live in exactly one tree, and the tree is the running game. A node's position is relative to its parent's, so moving a parent moves everything under it; deleting a parent deletes everything under it; and things draw in tree order unless you say otherwise. 3. Scenes

A scene is a branch of that tree, saved to a .tscn file. That is all it is. A player is a scene; so is a whole level, a single button, an enemy you will make two hundred of. There is no separate idea of a "prefab", a "level" and a "widget" – they are all scenes, and any scene can be placed inside any other. You will see this from the inside in Chapter C.

4. Signals

A signal is an announcement. A button says "I was pressed"; a timer says "time's up"; your coin says "I was collected". The node that announces does not know who is listening, and does not need to. That is how pieces of a game stay independent: the coin does not have to know the score label exists. Chapter J is all about them.

And holding it together: scripts. A script is attached to a node and gives it behaviour – in GDScript, Godot's own language, which reads a lot like Python and was designed for exactly this job.

Getting Godot and making a project

There is no installer and no account. You download one file and run it.

  1. Download

    From godotengine.org/download, the standard build for your computer. The ".NET" build is for writing in C#; for GDScript you want standard.

  2. Open it

    On a Mac, unzip and drag Godot into Applications; on Windows, unzip and run the .exe. The first thing you see is the Project Manager: a list of your projects, empty for now.

  3. New Project

    Give it a name and an empty folder. For the renderer, pick Compatibility if you are making a 2D game that should run on phones and older computers (Little Hours does); Forward+ is for desktop 3D with all the effects.

  4. The editor opens

    Chapter B walks round it. For now: the big middle area is the viewport, the left dock is the Scene tree, the right is the Inspector, and the bottom shows Output.

What is in the project folder

FileWhat it is
project.godotThe project's settings, as plain text: its name, its main scene, the window size, the input map, the autoloads. Godot writes it; you can read it.
.godot/Godot's cache – imported textures, compiled scripts. It is rebuilt whenever it is missing, so it never goes in version control.
*.tscnScenes, as text you could read and even edit by hand.
*.gdGDScript files.
*.importOne beside every image and sound: how Godot imports it (filtering, compression). Keep these – they are your import settings.
icon.svgThe Godot logo every new project starts with, handy as a placeholder sprite.

Every path inside Godot starts with res://, meaning "the project folder" – res://scenes/main.tscn – so a project works wherever it is copied. There is a second root, user://, for things the game writes while it runs, like saves (Chapter S).

A first scene and a first script

Five steps, and you have a window with something in it that is yours.

  1. In the Scene dock, choose 2D Scene. A Node2D called "Node2D" appears – the root of your scene. Double-click it and rename it Main.
  2. With Main selected, press Ctrl+A (⌘+A on a Mac) – Add Child Node – and choose Sprite2D.
  3. Drag icon.svg from the FileSystem dock onto the Inspector's Texture slot. The robot appears in the viewport.
  4. Ctrl+S saves the scene. Call it main.tscn.
  5. F5 runs the game. The first time, Godot asks which scene is the main one – pick this one. A window opens with the robot in it.

Now give it some behaviour. Select Main, click the scroll icon above the Scene dock (Attach Script), accept the defaults, and Godot opens a script that starts extends Node2D. Replace what is there with this, and run again:

extends Node2D

func _ready() -> void:
	print("Hello from my first scene")
	print("2 + 2 is ", 2 + 2)

The lines appear in the Output panel at the bottom of the editor. _ready() is a function Godot calls once, when the node has been added to the running game – the place for "when this starts, do this". The Run button above does the same thing here, in the page.

How the code in this book runs

Real Godot cannot run inside a web page, so the examples and exercises here run on a small GDScript interpreter written for the book. It follows Godot 4 where it matters for learning – integers and floats are different, "text" + 5 is an error, arrays are shared and Vector2s are copied, signals and await work – and it reports errors with line numbers, the way the editor does. What it does not have is the engine: no physics, no rendering beyond a small canvas, no scene files. Where a chapter needs those, it says so, and the workshop gives you a working model of the editor to try them in.

Press Edit and run on any example to change it: from then on it runs again each time you stop typing. Nothing you do can break anything.

extends Node

var greeting := "Hello"
var names := ["Ana", "Bo", "Wren"]

func _ready() -> void:
	for name in names:
		print(greeting, ", ", name, "!")
	print("That was ", names.size(), " hellos.")

In Little Hours

The game this book keeps opening up made one unusual choice on day one, and it is worth seeing before you learn the usual way.

Most Godot games have dozens of .tscn files – a player scene, an enemy scene, a scene per level. Little Hours has exactly one, and this is all of it:

[gd_scene load_steps=2 format=3]

[ext_resource type="Script" path="res://scripts/Main.gd" id="1"]

[node name="Main" type="Node2D"]
script = ExtResource("1")

One Node2D with one script. Everything else – the rooms, the furniture, the resident, the dog, the interface – is built from code when the game starts, with Node.new() and add_child(). Here is how Main.gd introduces itself:

Main.gd · lines 1–14

extends Node2D
## Tiny Home — the whole game, assembled.
##
## Everything is built in code rather than wired up in the editor, so the project
## runs the moment you open it and there are no .tscn files to keep in sync with
## the scripts. Main owns:
##   * the room renderer, the resident, the partner, the dog and the cat
##   * tap routing (floor -> walk, furniture -> walk then act, pets, farm, water)
##   * decorate mode
##   * the day/night wash and the weather
##   * the HUD and the overlay stack
##
## Ported from the React/web build. The room layouts, the grid, the clock and the
## save shape all match, so this is the same game rather than a lookalike.

That trades the editor's visual layout for code that can be read, searched and tested, and it suits a game whose rooms are generated from tables of data. It is a choice, not the norm – the next two chapters teach the editor-first way, which is how you should start. Inside the code shows what Main does with it.

The project file shows two more of this chapter's ideas. Autoloads are nodes Godot creates before anything else and keeps for the whole game (Chapter U), and Little Hours has three:

[autoload]

Sfx="*res://scripts/Sfx.gd"
Game="*res://scripts/Game.gd"
TownMind="*res://scripts/TownMind.gd"

Game holds everything that changes while you play, Sfx makes every sound, and TownMind runs the small on-device AI that gives the neighbours their small talk.

Your turn

Each exercise has an editor, a Run button to try your code and a Check button that tells you whether it does what was asked. Stuck? Hint gives you a nudge at a time.

What to remember

  • A game is a loop; the engine runs it and you decide what happens in it.
  • Nodes do one job each; the tree of them is the running game; a scene is a saved branch; signals let nodes announce without knowing who listens.
  • A project is a folder: project.godot, scenes, scripts, imported assets, and a .godot cache you never commit. res:// is the project, user:// is where the game may write.
  • _ready() runs once when a node joins the game; print() writes to Output.
