How a game hangs together

After twenty-five chapters of parts, here is the whole. It is smaller than you would think: five habits, and every game in this book, small or large, is made of them.

A first game is usually a heap. A player script that knows about the score label; a score label that knows about the enemy; an enemy that changes the level. It works, and then you want to add a second level, or save, or a pause, and every change touches six files. A finished game looks different. Not because the person was cleverer, but because they kept a few questions apart. These are the five.

1. State lives in one place

Everything that is true about the game right now – the day, the coins, what you own, what is planted – is in one structure that you could write to a file and read back. In a small game that is a handful of variables; in a big one it is a dictionary in an autoload (Chapter U). The point is not where, but that there is a single answer to "what is true now". If the score is also in a label's text, then the label is a copy, and copies drift.

2. What is always so goes in tables

The price of a carrot, how long a pumpkin takes, where the doors are, what a neighbour says on the third day: facts that do not change while you play are data, not code. A const dictionary, a list, a resource (Chapter V). The code asks the table; the table can grow without the code changing. A designer, or you in a month, can add a fifth crop without reading a line of logic.

3. Views draw; they do not decide

Something reads the state and the tables and makes a picture, a number on a bar, a sound. It never changes the state. That is what _draw was in Chapter O, what a HUD is, what a room's drawing code is. Because the view only reads, you can throw it away and rebuild it, change the theme, turn the screen sideways, and nothing about the game has moved.

4. Signals go upward

When something happens, the thing it happened to announces it, and does not know who is listening (Chapter J). Children talk to parents with signals; parents talk to children with function calls; the store tells the world "I changed". Everything depends on the stable thing above it and nothing on the shifting things below, which is why you can change a room without touching the clock.

5. One loop

The game is a loop (Chapter I): read the controls, change the state, draw. Rules that take time hang off one clock added up from delta (Chapter T), not off their own timers and counters. When something must stop – night, a menu, a pause – it stops in one place, at the top of the loop, and everything beneath it stops with it.

Here are all five in thirty lines, as a model: a table of crops, a state with a clock, a view that only reads, a signal for "ripe", and one loop that advances the clock. Run it, then add a pumpkin to the table and a plot for it.

extends Node

# 2. Data: what is always so
const CROPS := {"carrot": 15.0, "pumpkin": 40.0}

# 1. State: what is true now, in one place
var state := {"clock": 0.0, "plots": {"north": {"crop": "carrot", "at": 0.0, "ripe": false}}}

# 4. A signal, upward
signal ripened(plot: String)

# 3. A view: reads, never writes
func describe(plot: String) -> String:
	var p: Dictionary = state["plots"][plot]
	var age: float = state["clock"] - p["at"]
	if p["ripe"]:
		return plot + ": ripe"
	return plot + ": " + str(int(100.0 * age / CROPS[p["crop"]])) + " percent"

# 5. One loop: the clock moves, the rules follow it
func tick(delta: float) -> void:
	state["clock"] += delta
	for plot in state["plots"]:
		var p: Dictionary = state["plots"][plot]
		if not p["ripe"] and state["clock"] - p["at"] >= CROPS[p["crop"]]:
			p["ripe"] = true
			ripened.emit(plot)

func _ready() -> void:
	ripened.connect(func(plot): print(">> ", plot, " is ripe"))
	for i in 5:
		tick(4.0)
		print(describe("north"))

Nothing here knows about a screen, and so nothing here needs one. That is the useful side of the five habits: a game organised this way can be tested by calling tick in a loop, as the book's exercises have done all along, and the part that needs the engine – the drawing – is small.

Around that spine, the rest is chapters you have read. The game is built in code, from one empty scene (B and C); people and pets move by hand rather than by physics (M); animation is a few tweens and sheets (N); the pixels stay whole because of a few project settings (P); the sound is made from nothing (Q); it is a phone game exported as a bundle (X); and it is guarded by a test suite that plays the real game (W). The game's own tour follows the same files one by one, and the A to Z of the game's rules takes each rule – farming, the clock, the phone – on its own, with a model you can build.

If you want one lesson from reading a game this size, it is a dull one: almost none of it is clever. It is the same small ideas, applied every time, in the same places, so that a person who has read ten files can guess what the eleventh does.

Scope, and finishing

Most games are not finished because they got too big, not because they got too hard. Finishing is a skill, and mostly it is the skill of saying no early.

The pattern is familiar. The first day goes brilliantly: a walker, a room, a tree. The idea list grows faster than the game. Somewhere around the second month a feature turns out to need three others, nothing is quite playable, and the game quietly stops being opened. What the people who do finish have in common is not talent. It is a smaller first game, and a habit of keeping something playable at every step.

Rules that work

  • Make the whole loop first, badly. The capstone below is a complete game in sixty lines – input, rule, result, restart – with rectangles for art. Everything you add later goes into a game that already works.
  • Never break the game for long. If it has not run for an hour, you have gone too far from a working state. Make the next change smaller.
  • Cut by value over cost. A feature a player would notice and that costs a day beats one they might notice and costs a week. Write the list down, with a cost beside each.
  • Finish something small, then ship it. A game another person has played teaches you more than three that live in a folder. Chapter X is about that last mile, and it is longer than people expect.
  • Keep a record of what you decided and why. The comments in Little Hours' code mostly say why, and it is what makes the file usable a year on (Chapter W).

Here is the cut list as a tiny program: features in the order you want them, each with a cost in days, and a budget. Run it, then reorder the list so the thing you care about most is first, and see what survives.

extends Node

const BUDGET := 10

# [feature, cost in days] – the order is your priority.
const FEATURES := [
	["walk and collect", 2],
	["win and lose", 1],
	["a second level", 2],
	["sound", 2],
	["a shop", 5],
	["save the best score", 1],
]

func _ready() -> void:
	var spent := 0
	for f in FEATURES:
		if spent + f[1] <= BUDGET:
			spent += f[1]
			print("keep  ", f[0], " (", f[1], ")")
		else:
			print("CUT   ", f[0], " (", f[1], ")")
	print(spent, " of ", BUDGET, " days")

The shop is cut, and nobody had to be unkind about it – it did not fit, and the cheap things that finish a game (the second level, the best score) did. Move "a shop" to the top and see what you lose instead. That decision, made honestly and early, is most of what scope is.

What to learn next

You have the whole foundation. The way forward is not a longer list of features; it is a game of your own, and then reading other people's.

Make something small, now

Not after the next tutorial. The capstone below is a place to start; the exercises change it; then make a game of your own the same size – one screen, one rule, one way to win. Whatever you are stuck on will be the next thing you learn, and you will remember it, which is not true of anything read in advance.

Read the official documentation

The Godot manual and class reference at docs.godotengine.org are good, free and current for 4.x. In the editor, F1 opens the built-in reference; a class name in the script editor can be looked up in one step. The official demo projects are small, working games for you to run and change. Reading a working project is the best second teacher: this book's tour is that for Little Hours.

Ask well, and read errors

When you are stuck, the error message is the start, not the end (Chapter W). Say which Godot version you use, show the smallest script that fails, and say what you expected. Most questions answer themselves halfway through writing them down that way.

Build it live

The capstone. A complete game – a clock, input, falling things, a rule, a result and a restart – built in six steps, then yours to extend in the exercises below.

In Little Hours

The capstone has five habits in sixty lines. The real game has the same five in many thousands, and these three quotes are where they meet.

The one clock

Game.gd · lines 440–448

func _process(delta: float) -> void:
	if night_held:
		return
	clock_t += delta * mode_day_scale()
	if clock_t >= DAY_LENGTH:
		clock_t = DAY_LENGTH
		night_held = true
	_tick_farm()
	_tick_texts(delta)

It is the capstone's first step with more manners. clock_t is the one number everything waits on; night_held is the early return that stops the world, exactly like the capstone's phase != "playing"; and the two functions at the bottom read the clock to decide whether a crop is ripe and whether a text is due, with no clocks of their own. See Clock for what it becomes (hour, phase, sky) and the phone's texts for one of the things that wait on it.

A table the code reads

Game.gd · lines 257–263

const CROPS := {
	"carrot":     {"name": "Carrot",     "grow": 15.0},
	"tomato":     {"name": "Tomato",     "grow": 20.0},
	"strawberry": {"name": "Strawberry", "grow": 25.0},
	"sunflower":  {"name": "Sunflower",  "grow": 30.0},
	"pumpkin":    {"name": "Pumpkin",    "grow": 40.0},
}

This is the capstone's DROPS, grown up: a dictionary of crops, each a small dictionary of facts. Nothing in the code says "a carrot takes fifteen seconds"; it says CROPS[crop]["grow"]. A sixth crop is one more line here. The farm's rules are under Farming.

One loop, handed on

Main.gd · lines 2133–2137

_tick_hold(delta)
_tick_edges(delta)
_tick_reach()
_tick_ghost(delta)
_tick_neighbor(delta)

These are five lines from the middle of Main.gd's _process, the game's one frame-by-frame loop. The frame is handed on, delta and all, to one small function for each job: holding a finger down, walking to the screen's edge, reaching for something tapped, the ghost, a neighbour. None of them keeps a clock of its own. This is the shape that lets a game this size stay readable: the loop is a list, and each item on it is a name. See Reaching for how a tap becomes an action.

What to remember

  • A game hangs together on five habits: state in one place, what is always so in tables, views that draw and never decide, signals that go upward, and one loop with one clock.
  • Little Hours is those five at a larger size: Game.state, CROPS and RoomData, RoomView and the HUD, state_changed, and _process handing each frame on.
  • Finish by making the whole loop first, badly; keeping the game playable at every step; cutting by value over cost; and shipping something small.
  • Learn next by making a small game of your own, reading the manual and the demo projects, and reading working code. Each of the topics in the table has a chapter here to start from.
  • Anything that comes in from outside, including your own save, is untrusted until it has been checked.

You started with an empty project and a window. You can now read how a whole game is put together, and build one. Whatever you make next, make it small, make it playable, and show it to someone. Thank you for reading.
