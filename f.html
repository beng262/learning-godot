In this chapter

Writing a function

A function is a recipe with a name. You write the steps once, give them a name, and from then on you can ask for them by name as often as you like – with different ingredients each time.

You have been using functions since Chapter A: print(), int(), lerpf() and _ready() are all functions. Chapters D and E gave you variables and decisions to put inside them. This chapter is about writing your own, and it is where a script stops being a list of lines and starts being a set of tools.

extends Node

func shout(word: String) -> void:
	print(word.to_upper() + "!")

func _ready() -> void:
	shout("good morning")
	shout("time for the farm")

The pieces, left to right: func says "here is a function"; shout is its name; the brackets hold its parameters – the names it gives to the things you hand it; -> void says it hands nothing back; the colon opens the body, which is whatever is indented under it. Nothing in the body runs when the function is written. It runs when somebody calls it by writing its name and brackets, as _ready() does twice here. The values in the call – "good morning" – are the arguments, and each one lands in the parameter in the same place.

Add a third call with a word of your own. Then move the first call below the second: functions are looked up by name when they run, so the order they are written in does not matter, only the order they are called in.

return: sending something back

shout does something. Most functions are more useful when they answer: you give them a question and they hand back a value that you can store, compare or give to another function. return does that, and it also ends the function on the spot.

extends Node

func double(n: int) -> int:
	return n * 2

func _ready() -> void:
	print(double(4))
	var coins := double(10) + 3
	print(coins)
	print(double(double(3)))

A call is an expression (Chapter E): it is the value it returns, so it can sit anywhere a value can – after :=, inside +, even as the argument of another call. The innermost double(3) is worked out first and becomes 6, which is then the argument of the outer one. Change the last line to double(double(double(1))) and say the answer before you look.

Because return stops the function, anything after it never runs. That is not a trap, it is a tool, and you used it in Chapter E without being told: a ladder of one-line ifs that each return needs no elif, since reaching a rung means the ones above were false.

extends Node

func describe(coins: int) -> String:
	if coins <= 0:
		return "broke"
	if coins < 20:
		return "getting by"
	return "comfortable"

func _ready() -> void:
	for c in [0, 7, 20, 150]:
		print(c, " coins: ", describe(c))

print is not return

The most common beginner mistake with functions is thinking that showing a value and returning it are the same. They are not. print writes to the Output panel for a human to read; return gives the value to the code that called. A function that only prints has nothing to give back, and the caller is left holding null – the "no value" value from Chapter E.

extends Node

func triple(n):
	print(n * 3)

func _ready() -> void:
	var answer = triple(5)
	print("the answer is ", answer)

You saw 15 appear, so it looks as if it worked, but answer is null: the 15 went to the screen, not to the variable. Change print(n * 3) to return n * 3 and run it again. Now the number arrives in answer, and the only thing the function prints is the line in _ready(), which is where you wanted to print it.

A good habit

Let functions that work something out return it, and let one place near the top decide what to show. A function that prints its own answer can only ever be used by someone who wants it printed. One that returns it can be printed, stored, compared, tested and passed on.

Parameters: typed, defaulted, and not quite right

A parameter is a variable that the caller fills in. Everything you learnt about typed variables in Chapter D applies, and a parameter can also come with an answer ready, for the callers who do not care.

Types on parameters

n: int means "this must be a whole number". It is the same promise as var n: int, and Godot keeps it for you, in two ways. The editor underlines a call that is obviously wrong before you run anything, and the autocomplete knows what the function wants. The parameters of _ready() are the empty set; the parameters of _process(delta: float) you will meet in Chapter I. Types are optional, as with variables, but in a function they pay for themselves quickly, because a function is read by people who did not write it.

Here is a function with two parameters, called correctly and then not:

extends Node

func price(count: int, each: int) -> int:
	return count * each

func _ready() -> void:
	print(price(3, 18))

Now leave an argument out. This one stops, and the message is worth reading in full: it names the function and says how many arguments it wanted and how many it got.

extends Node

func price(count: int, each: int) -> int:
	return count * each

func _ready() -> void:
	print(price(3))

Too many fail in the same way. Every parameter without a default must be given, in order, and Godot has no "named arguments": there is no way to write price(each = 18, count = 3) and let the names do the matching. The position is the name.

The second mistake is the wrong kind of value. A String is not an int, even when it looks like one:

extends Node

func price(count: int, each: int) -> int:
	return count * each

func _ready() -> void:
	print(price("3", 18))

The fix is on the calling side: turn the text into a number first, with int("3") (Chapter D) or "3".to_int(). A whole number given where a float is wanted is fine – 3 becomes 3.0 without a murmur. The other way round loses a fraction, so Godot will warn you or refuse; do the rounding yourself, with int(), roundi() or floori(), so that the choice is yours.

Defaults

A parameter can say what it will be if the caller says nothing, by giving it a value with =. Parameters with defaults go last.

extends Node

func price(count: int, each: int = 18) -> int:
	return count * each

func greet(name: String, greeting := "Hello") -> String:
	return greeting + ", " + name

func _ready() -> void:
	print(price(3))
	print(price(3, 20))
	print(greet("Wren"))
	print(greet("Wren", "Good evening"))

The first call leaves each alone, so it is 18; the second overrides it. Look at greet: greeting := "Hello" gives the parameter both a default and, by inference, a type, exactly as := does for a variable. Try to move the default to the front, func price(each: int = 18, count: int). Godot refuses, and it is right to: with the defaults first, a call with one argument could not say which parameter it meant.

The caller's variable, or a copy?

When you pass a variable in, the function gets a copy of a number, a String, a bool or a Vector2, and changing it inside changes nothing outside. But an Array or a Dictionary is passed as the same one, the sharing you met in Chapter D, and a function that changes it changes the caller's.

extends Node

func add_one(n: int) -> int:
	n += 1
	return n

func add_nine(items: Array) -> void:
	items.append(9)

func _ready() -> void:
	var count := 1
	var list := [1]
	add_one(count)
	add_nine(list)
	print(count)
	print(list)

count is still 1 because add_one worked on its own copy – and the answer it returned was thrown away, which is the usual cause of "my function does nothing". list grew, because there was only ever one array. Neither is wrong; know which one you are holding. Write count = add_one(count) to keep the answer.

Return types, and promises

The arrow in -> int is a promise: "when I finish, I will have handed you a whole number". Godot reads it as a promise it can check.

A return type does three jobs. It tells a reader what comes back without their having to read the body. It lets the caller use := and get a typed variable. And it lets Godot find the mistakes in your side of the promise. There are three kinds, and you have already met two:

WrittenIt meansFor example
-> int, -> String, -> bool…always returns a value of that typeclock_text() -> String
-> voidreturns nothing; it is called for what it does_ready() -> void
nothing writtenmay return anything, or nothing, and Godot does not checkfunc triple(n):

The function below keeps its promise on one road and not on the other. In the editor this is a refusal before the game even starts: Godot sees that half(-4) would reach the end of the function without a return and says that not all code paths return a value. Here, without the type, you can watch the thing that the error is protecting you from:

extends Node

func half(n):
	if n > 0:
		return n / 2

func _ready() -> void:
	print(half(10))
	print(half(-4))

A function that falls off its end hands back null, so the second line prints <null>. With -> int written on the first line, Godot would never have let the script run. Make half keep its promise for every n: add a return 0 at the end, at the same indent as the if. That last line is the else of the ladder.

Guard clauses

The most readable functions deal with the unusual cases first, each with its own return, and leave the ordinary rule for the last line. They are called guard clauses, and the farm and the weather in Chapter E were full of them.

extends Node

func coins_back(paid: int, price: int) -> int:
	if paid < price:
		return -1       # not enough: nothing to give back
	return paid - price

func _ready() -> void:
	print(coins_back(20, 18))
	print(coins_back(18, 18))
	print(coins_back(10, 18))

A -1 that means "this did not work" is a code the caller has to remember to check; you will see better ways, such as returning a Dictionary with a reason, in Chapter G. But as a first tool for a function that can say no, it is the simplest.

One value, but a rich one

A function returns one value. When you need two answers – the quotient and the remainder, a success and a message – return one value that contains them: an Array or a Dictionary, or a Vector2 when the two things are numbers that belong together.

extends Node

func split_minutes(total: int) -> Dictionary:
	return {"hours": total / 60, "minutes": total % 60}

func _ready() -> void:
	var t := split_minutes(135)
	print(t["hours"], " h ", t["minutes"], " min")

The names inside the dictionary are the documentation: t["hours"] cannot be mistaken for t["minutes"] in the way that t[0] and t[1] can.

A function that calls itself

A function can call any function, including itself. That is recursion, and it works when each call is a smaller problem and one case is answered outright, so that it stops. Five factorial is 5 times four factorial, and one factorial is 1:

extends Node

func factorial(n: int) -> int:
	if n <= 1:
		return 1
	return n * factorial(n - 1)

func _ready() -> void:
	print(factorial(5))
	print(factorial(10))

The if is the guard that makes it stop. Without it the function would call itself for ever, and Godot gives up with a "stack overflow". Most of the time a loop is plainer; recursion earns its place when the problem is itself nested – a tree of nodes, a map of rooms.

static: a function that belongs to the script

An ordinary function works on an object: it can read and change that object's own variables. A static function belongs to the script itself, and needs no object at all.

Chapter H goes properly into scripts as classes and objects; here is all you need now. If a function only works from its arguments – double(n) uses nothing but n – then there is no reason to have an object around to call it on. Write static in front, and call it on the name of the script.

extends Node

class Maths:
	static func double(n: int) -> int:
		return n * 2

	static func clamp_day(day: int) -> int:
		return clampi(day, 1, 100)

func _ready() -> void:
	print(Maths.double(21))
	print(Maths.clamp_day(250))

Here Maths is a small class written inside the script, and nobody ever builds a Maths object: the functions are called on the class. In a game, a script with a class_name at the top is available everywhere under that name, so NeighborData.room_of(...) from any other file is an ordinary call of a static function. The built-ins you have been using are the same idea: Vector2.ZERO and Time.get_ticks_msec() belong to classes, not to objects.

The limit is the point: a static function cannot use the object's ordinary variables, because there is no object. It can use constants, its own arguments, and static var – a variable that belongs to the script and is shared by every use of it.

extends Node

class Counter:
	static var calls := 0

	static func next_id() -> int:
		calls += 1
		return calls

func _ready() -> void:
	print(Counter.next_id())
	print(Counter.next_id())
	print(Counter.next_id())

Static variables are global state in disguise and are hard to test, so use them sparingly – a counter or a cache, not the player's coins. Little Hours keeps its state in one place instead (S: Saving), and uses static for the other kind of function, which is the right one for a table: it looks something up, works something out, and changes nothing.

Functions as values: lambdas and Callables

A function is also a thing you can hold. You can keep it in a variable, put it in an array, and hand it to another function to use later. That is what makes buttons, sorting and signals work.

A lambda

A lambda is a function with no name, written where it is needed. On its own it is a value of type Callable, and you run it with .call().

extends Node

func _ready() -> void:
	var double := func(n): return n * 2
	print(double.call(8))

	var greet := func(name, greeting):
		var line = greeting + ", " + name
		return line + "!"
	print(greet.call("Wren", "Hello"))

A short lambda sits on one line, and its value is the expression after return. A longer one is a block under func(...):, indented as any other. Notice the brackets after .call, not after the variable: double(8) would look for a function called double and fail, since a variable holding a function is called with .call.

Passing a function to a function

The reason lambdas exist is to give a function a piece of behaviour as an argument. Arrays have several methods that work this way:

extends Node

func _ready() -> void:
	var prices := [18, 5, 40, 12]
	print(prices.map(func(p): return p * 2))
	print(prices.filter(func(p): return p > 10))
	prices.sort_custom(func(a, b): return a > b)
	print(prices)

map returns a new array with the lambda applied to each item; filter keeps those for which it answers true; sort_custom sorts using a lambda that says whether a should come before b. Make the sort cheapest-first by flipping the >. You could write each of those with a loop and an append, and it is worth doing once; the lambda is what you reach for when the loop is not the point.

You can write your own function that takes a Callable, with the type spelled out:

extends Node

func twice(action: Callable) -> void:
	action.call()
	action.call()

func _ready() -> void:
	twice(func(): print("ding"))

Method references

A function that you have already written is a value too. Use its name without brackets and you hold the function rather than its answer:

extends Node

func shout(word: String) -> String:
	return word.to_upper() + "!"

func _ready() -> void:
	var f := shout
	print(f.call("hello"))
	print(["a", "b"].map(shout))

This is the same trap as the brackets in Chapter J: shout("hello") is the answer, a String; shout is the thing that would give it. With brackets you are calling; without them you are holding.

bind: filling in an argument now

.bind() makes a new Callable with some of the arguments already supplied. When it is finally called, the bound values are added after the ones given then.

extends Node

func sell(item: String, price: int) -> String:
	return item + " for " + str(price) + "c"

func _ready() -> void:
	var sell_carrot := sell.bind(18)
	print(sell.call("carrot", 18))
	print(sell_carrot.call("carrot"))

Take care with that: bind(18) fills the last parameter, so sell_carrot.call("carrot") gives sell("carrot", 18). This is how one function serves many buttons (Chapter J uses it with signals): bind each button's own number, and every press arrives knowing which one it was.

What a lambda remembers

A lambda can use variables from the function that wrote it. It does not share them, though: it takes a copy of the value at the moment it is made. For a number, a String or a bool, later changes are invisible to it, in both directions.

extends Node

func _ready() -> void:
	var total := 0
	var add := func(n): total += n
	add.call(5)
	add.call(5)
	print(total)

	var shelf := []
	var stock := func(item): shelf.append(item)
	stock.call("jam")
	print(shelf)

The first prints 0: the lambda added to its own copy of total. The second works, because the copy of shelf is a copy of the reference, and there is still only one array. So a lambda that must record something should write into an array or dictionary, or call a function, never into a captured number. The same fact has a good side: a lambda made in a loop keeps the value from its lap, which is what you want when you are making one button per item.

When not to use one

A lambda is for a few lines that belong to the place they are written. When it grows past five or six lines, or the same one appears twice, give it a name and a place as an ordinary function, and pass that by name. A named function can be read on its own, and shows up with its name in an error message – which a lambda does not.

Build it live

Five small functions that turn the share of a day into the clock you read, the phase you feel and the season you are in – and a sixth idea to wire them together. They are the shape of the functions that Little Hours itself uses to tell the time.

In Little Hours

Most functions in the game are short. The long ones are mostly short ones joined up, and the habits you have just practised – a type on everything, one job, an early return – are how the file stays readable at 34,000 lines.

Three small typed functions

func clock_text() -> String:
	# 06:00 at sunrise through 22:00 at nightfall.
	var mins := int(lerpf(360.0, 1320.0, day_fraction()))
	return "%02d:%02d" % [(mins / 60) % 24, mins % 60]

func season_index() -> int:
	return int(floor(float(state["day"] - 1) / float(DAYS_PER_SEASON))) % SEASONS.size()

You have just written their cousins. These ones take no arguments, because the thing they ask about – how far through the day it is, which day it is – is state that lives in Game itself and can be read from inside. That is the usual trade: a function with parameters can be tested with any number, a function that reads the game's state is shorter to call. Each has a return type, each does one job, and none prints anything: the HUD, the clock and the sky all ask and show what comes back. clock_text and season_index use int() and float() to keep the types honest, and the float(...) inside season_index is there so that the division keeps its fraction before floor rounds it down. How the clock counts is in C: Clock, and the seasons are in W: Weather and seasons.

Static functions that look things up

NeighborData.gd · lines 759–771

## Where somebody is at a given point in the day.
##
## Four of these people have a job in a room they were never standing in:
## Marisol lives ABOVE the gelato shop, Tobias keeps the museum from a cottage
## behind it, Del walks other people's dogs, Nan swims. Every one of them stood
## in their own front room from dawn to dusk instead, which is most of why a town
## with nine people in it read as empty — the four rooms you would go looking for
## them in were the four they were never in.
static func room_of(p: Dictionary, day_f: float) -> String:
	var work := str(p.get("work", ""))
	if work != "" and day_f < WORK_ENDS:
		return work
	return str(p["room"])

NeighborData.gd · lines 806–814

## How many days late a person's chapters run.
##
## Without this everybody shares one pace, so every chapter in town opened on
## the same twelve days: a burst where six people all had news, then a week and
## a half where nobody in the world had anything. A town is people on their own
## clocks. Taken from the list position rather than a hash of the name, so it is
## stable across engine versions and a save cannot silently re-time itself.
static func stagger(id: String, pace: int) -> int:
	return index_of(id) % maxi(1, pace)

These live in NeighborData, a script with a class_name and no node: nobody ever builds one. room_of takes a person (a dictionary of their facts) and a time of day, and answers which room they are in: at work before WORK_ENDS, home after. stagger turns a name into a number of days late. Both are static because everything they need is in the arguments, so any file can call NeighborData.room_of(p, f) without first finding or making an object – and both return the same answer for the same arguments, every time, which is what makes them easy to trust. NeighborData in the tour shows the rest of the table; the people themselves are N: Neighbours.

A one-line lambda that gives every button a sound

UI.gd · lines 429–433

## A quiet click on every press, wired once at build time so no call site has to
## remember it.
static func clicky(b: Button) -> Button:
	b.button_down.connect(func() -> void: Sfx.play("click", -24.0))
	return b

clicky is a static function that takes a button and gives it back. It connects a one-line lambda to button_down: whenever the button is pressed, play the click sound quietly. The comment says why it exists, "wired once at build time so no call site has to remember it". Returning the button lets callers write return clicky(b) and keep building. A lambda is the right size for the job – one line, belonging to the place that connects it, with nothing to name. The sound itself is Chapter Q, and the buttons around it are in UI.

Your turn

Six exercises. The second hands you a bug, the third asks you to guess before you run.

What to remember

  • A function is a named recipe. Writing it does nothing; calling it runs the body, and a call is an expression with a value.
  • return hands a value back and ends the function. print only shows a value: a function that prints and does not return leaves the caller with null.
  • Parameters can have types and defaults, defaults go last, and every other argument must be given, in order – there are no named arguments. Numbers are copied in; arrays and dictionaries are shared.
  • -> int is a promise that every road through the function returns an int. -> void promises nothing comes back. Guard clauses put the unusual cases first.
  • static functions belong to the script and are called on its name: right for lookups and sums that need no object.
  • A lambda is a function with no name; a Callable holds any function; you run it with .call(), and .bind() fills arguments in early. A lambda takes a copy of the local variables it uses at the moment it is made.
